# 계획: search-ui — 브라우저로 검색하는 화면과 디자인 축 측정 수단

- slug: `search-ui`
- 브랜치: `loop/search-ui`
- **기점: `loop/crawl-throughput`** (미병합). `main` 이 없는 저장소다 —
  `serve.py`·`indexer.search()`·`store.py` 의 WAL 설정이 전부 그 브랜치에만 있어
  기본 브랜치가 없는 이상 앞 계획 위에서 딴다 (`rules/git.md` 1절의 "실제로 필요하면").
- 스텝: 2
- 설계: **필요** (아래 6절)

## 1. 문제

`concept.md` 의 네 축 중 **디자인 축만 아직 아무것도 없다.**

1. **화면이 없다.** `concept.md:5-6` 은 "누구나 브라우저로 접속해 검색어를 입력하면
   랭킹된 결과(제목·URL·스니펫)를 받는" 것을 제품으로 정의하는데, 지금 있는 것은
   `GET /search` 가 내는 **JSON 뿐**이다 (`src/websearch/serve.py:68-76`).
   브라우저로 열면 사람이 읽을 화면이 아니라 직렬화된 배열이 나온다.

2. **디자인 축을 잴 명령이 없다.** `docs/project.md` 는 지금 이렇게 서 있다:

   - "**번들 크기**: 없음 — search-ui 계획에서 JS 50KB(gzip) 측정 명령 추가 예정"
   - "**디자인 검사**: 없음 — search-ui 계획에서 추가 예정"

   `status.md` 는 이 두 줄을 "경량·디자인 축의 측정 명령이 없음"이라고 읽고
   `search-ui` 를 **사람 판단 대기**로 세워두었다. **그것은 오독이다.**
   저 두 줄은 승인을 기다린다고 적혀 있지 않다 — **"이 계획에서 만든다"고 적혀 있다.**
   승인 대기가 아니라 **아직 안 만든 것**이고, 만드는 것은 이 계획의 일이다
   (`rules/e2e.md` 4절: 측정 수단이 없으면 e2e phase 에서 만든다).

## 2. 목표

`concept.md:49-54` 의 디자인 4축을 **기계가 판정할 수 있게** 만들고, 그 판정을
통과하는 검색 화면을 낸다. (`concept.md:49` 는 화면이 **둘뿐**이라고 못 박는다 —
검색 홈과 결과 페이지. 세 번째 화면을 만들면 그것부터 컨셉 위반이다.)

| # | concept.md 의 문구 | 이 계획이 세우는 판정 |
|---|---|---|
| 1 | 결과 페이지 LCP 1.5s (`:50`) | 외부 서브리소스 0건 · 문서 gzip 크기 · 서버 왕복 실측 |
| 2 | JS 번들 50KB(gzip) 이하 | 페이지가 싣는 JS 를 gzip 해 51,200 바이트와 비교 |
| 3 | 텍스트 대비 4.5:1 · 키보드만으로 검색 | CSS 색 토큰 쌍의 WCAG 대비 계산 · 폼 GET 이라 키보드 기본 동작 |
| 4 | 모바일(360px)에서 (가로) 스크롤 없음 | viewport meta 존재 · CSS 에 360px 초과 고정폭 없음 |

## 3. 기대 결과

- 브라우저로 서버에 접속하면 검색창이 있는 홈이 나오고, 검색어를 넣으면
  제목·URL·스니펫이 있는 결과 화면이 나온다. **JS 0KB.**
- `GET /search` 의 JSON 응답은 **한 바이트도 바뀌지 않는다.** 기존
  `e2e/search_api_e2e.py`·`e2e/perf_search.py` 가 그대로 통과한다.
- `docs/project.md` 의 "번들 크기: 없음", "디자인 검사: 없음" 두 줄이
  **실제로 돌려본 명령**으로 바뀐다.

## 4. 무엇이 이미 참인가

- `src/websearch/serve.py:43` `make_server(db_path, port)` 가
  `ThreadingHTTPServer` 를 돌려주고, `Handler.do_GET` (`:51`) 이
  `parts.path != "/search"` 이면 404 를 낸다. **`/` 는 지금 404 다.**
- `src/websearch/serve.py:24` `_parse()` 가 `q`(1~200자)·`page`(1~100)를 검증한다.
  질의 문자열의 FTS5 문법·NUL·제어문자는 `indexer._fts_query()` 가 이미 막는다.
- `src/websearch/indexer.py` 의 `search(db, q, limit, offset)` 이
  `(url, title, snippet)` 튜플 리스트를 돌려준다.
- `tests/test_serve.py` 에 임시 DB 로 **서버를 실제로 띄워 HTTP 로 때리는**
  `ServeTestCase` 가 이미 있다 (`build_db()`·포트 0). 새 테스트는 이것을 상속한다.
- 전체 테스트 213/213 통과 (`crawl-throughput` DONE 시점).
- **시안이 이미 있다**: 스크래치패드의 `demo_ui.py` (151줄). 서버 렌더 HTML·JS 0KB·
  폼 GET·`html.escape()`·`prefers-color-scheme` 다크. 이 계획은 그 형태를
  저장소 안으로 들이되, **시안 코드를 그대로 복사하지 않는다** — 시안에는 저장소가
  쓰지 않는 것(자체 `build_db`, 하드코딩된 예시 링크, `real.db` 탐색)이 섞여 있다.

## 5. 스텝

### 작업 그래프

```
A. HTML 검색 화면 (serve.py)  ──▶  B. 디자인 4축 측정 (e2e/design_check.py)
                                        └─▶ (C) project.md 갱신  ※ B 스텝 안에 포함
```

엣지는 진짜 의존이다 — B 는 A 가 내는 **실제 응답 바이트**를 읽어서 잰다.
C 는 B 를 한 번 돌려 나온 출력을 적는 일이라 노드로 세우지 않는다.
임계경로는 A→B 이고 곁가지가 없다. 병렬로 돌릴 노드가 없으므로 순차 2스텝.

### 스텝 1 — 검색 화면을 낸다

- **건드릴 파일**: `src/websearch/serve.py`, `tests/test_serve.py`
- **하는 일**: HTML 을 내는 경로를 추가한다. 홈(질의 없음)과 결과(질의 있음)를
  같은 핸들러가 낸다. 렌더는 서버에서 하고 **JS 는 싣지 않는다.**
- **RED 먼저** (`rules/dev.md` 0절): 아래 단언이 **지금 코드에서 실패하는 것**을
  확인하고 시작한다. 지금은 `/` 가 404 라 전부 실패한다.
  - 홈에 `<input name="q">` 와 `<label>`/`aria-label` 이 있다
  - `q=김치` 로 요청하면 본문에 결과 제목이 있고 `Content-Type: text/html; charset=utf-8`
  - **`q=<script>alert(1)</script>` 를 넣으면 응답 본문에 `<script>` 가 문자
    그대로 나오지 않는다** — `&lt;script&gt;` 로 이스케이프된다.
    질의어·제목·URL·스니펫 **네 자리 전부** 확인한다 (넷 다 크롤한 남의 문서에서 온다)
  - `GET /search?q=김치` 는 **여전히 JSON** 이다 (회귀 방어)
- **변이 검사**: `html.escape()` 호출 하나를 지우면 XSS 단언이 실패해야 한다.
  `PYTHONDONTWRITEBYTECODE=1` 을 붙여 돌린다 (`project.md` 의 `.pyc` 함정).
- **완료 기준**: `PYTHONPATH=src python3 -m unittest discover tests` 전부 통과.

### 스텝 2 — 디자인 4축을 잰다

- **건드릴 파일**: `e2e/design_check.py`(신규), `docs/project.md`
  - e2e 파일은 계획 범위 밖이어도 만든다 (`rules/e2e.md` 4절 예외 3곳)
- **하는 일**: 스텝 1 의 서버를 포트 0 으로 띄워 실제 응답을 받아 2절 표의 넷을 잰다.
  하나라도 어기면 **종료 코드 1**, 잴 수 없으면 **2**(측정 불능 — `quality_eval.py` 관용구).
- **RED 먼저**: 각 축마다 "일부러 어긴 입력"으로 검사기가 실패하는지 확인한다.
  - JS 축: `<script>` 60KB 를 끼운 가짜 응답 → 1
  - 대비 축: 색 토큰 하나를 대비 3:1 값으로 바꾼 가짜 CSS → 1
  - 360px 축: `width:800px` 을 끼운 가짜 CSS → 1
  - 측정 불능: 색 토큰이 아예 없는 CSS → 2 (0 이 아니다. 0 이면 CSS 를 통째로
    지워도 "통과"가 된다)
- **완료 기준**: `PYTHONPATH=src python3 e2e/design_check.py` 종료 0.
  `project.md` 의 "번들 크기: 없음"·"디자인 검사: 없음" 두 줄이 이 명령과
  **그날 실측한 숫자**로 바뀐다.

## 6. 설계가 필요하다

`rules/design.md` 1절 트리거에 **넷** 걸린다:

| 트리거 | 이 계획에서 |
|---|---|
| 새 모듈·파일 생성 | `e2e/design_check.py` |
| 공개 인터페이스 추가 | HTML 을 내는 새 HTTP 경로 |
| 3개 이상 파일에 걸침 | `serve.py`·`test_serve.py`·`design_check.py`·`project.md` |
| **대안이 2개 이상 갈림** | 아래 |

설계 phase 가 고를 갈림길은 둘이다. **여기서 고르지 않는다** (계획은 무엇을·왜).

**갈림길 1 — HTML 을 어디로 내나**
(가) `/search` 에서 `Accept` 헤더로 협상 (나) `/` 를 HTML, `/search` 는 JSON 유지
(다) 정적 HTML 파일 + `fetch()` — 셋 다 동작하지만 결과가 다르다.
(다)는 `concept.md:50` 의 JS 50KB 를 형식상 지키면서도 첫 화면에 왕복을 하나 더
얹는다. 설계는 **되돌릴 수 있나 · 기존 계약을 깨나**로 판정한다
(`e2e/search_api_e2e.py`·`e2e/perf_search.py` 가 `/search` 의 JSON 을 이미 붙들고 있다).

**갈림길 2 — 대비 4.5:1 을 무엇에 대고 재나**
CSS 캐스케이드를 재현하지 않고 색 쌍을 얻는 방법이 갈린다. 검사기가 기대값을
따로 들고 있으면 CSS 와 **드리프트**한다 — 색을 고쳐도 검사기는 옛 값을 본다.
설계가 드리프트하지 않는 쪽을 고른다.

## 7. 범위 밖 (이 계획에서 하지 않는다)

- **랭킹·검색 품질 손대기.** `quality-eval`(007) 이 드러낸 fixture 한계는
  `digest.md` 후보로 남아 있다. 화면을 붙이는 일과 섞지 않는다.
- **페이지네이션 UI.** JSON 은 이미 `has_next` 를 낸다. 화면의 다음 페이지 링크는
  스텝 1 이 끝나고 4축이 통과한 뒤에 별도로 판단한다 (YAGNI — 색인이 아직 작다).
- **정적 파일 서빙(`/static/…`)·파비콘·검색 자동완성.** 전부 추측성이다.
- **실제 네트워크.** 측정은 전부 로컬 서버(`127.0.0.1`, 포트 0)로 한다.

## 8. 타협하지 않는 것

- **이스케이프.** 질의어·크롤한 제목·URL·스니펫이 전부 남이 쓴 문자열이고,
  화면은 그것이 HTML 로 다시 나가는 자리다. ponytail 사다리로 줄일 영역이 아니다.
- **접근성 기본.** 검색 입력에 접근 가능한 이름(라벨), 텍스트 대비 4.5:1,
  키보드만으로 검색 실행. `concept.md:53` 이 직접 요구한다.
- **JSON API 무손상.** 이미 나가 있는 계약이다. 회귀 테스트로 못 박는다.

## 9. 되돌리는 법

브랜치 `loop/search-ui` 를 버리면 끝난다. 스텝 1 은 기존 코드의 분기 하나를
추가하는 형태라 커밋 되돌리기로도 무른다. 스키마 변경·마이그레이션·의존성 추가
없음 — 야간 정지 조건에 걸리는 것이 하나도 없다.
