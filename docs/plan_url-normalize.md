# 계획 018 — url-normalize: 같은 문서는 한 URL 이다

브랜치 `loop/url-normalize` (기점 `e08bc8f`). 의존: 17(`domain-key`).
출처: `docs/digest.md ## 다음 계획 후보` `[5]` (2026-08-26 non-ascii-url 리뷰).

## 1. 문제 · 목표 · 기대 결과

**문제.** 017 `domain-key` 는 **어느 서버인가**를 한 칸으로 모았다 — 간격·in-flight·
`Crawl-delay` 는 이제 `http://a.test` · `http://A.test` · `http://a.test:80` 을 한
서버로 센다. 그러나 **URL 자체는 여전히 세 표기가 각각 살아 있다.**
`Frontier._seen` 도 `store.pages.url` 도 `docs` 색인도 문자열 그대로를 열쇠로 쓴다
(`src/websearch/frontier.py:56,61` · `src/websearch/store.py:26,34`).
그래서 **같은 문서를 표기 수만큼 받아 표기 수만큼 저장하고 표기 수만큼 색인한다.**
간격은 지켜지므로 윤리 위반은 아니지만, 크롤 예산과 색인 크기와 검색 결과가
같은 비율로 낭비된다 — 표기가 셋이면 100만 문서 단계에 세 배 늦게 닿는다.

`urls.to_ascii` 가 이것을 안 잡는 이유는 계약이 **"ASCII 만 든 URL 은 한 글자도
바꾸지 않는다"** 이기 때문이다(`src/websearch/urls.py:70`). 그 계약은 멱등성과
이중 인코딩(`%` → `%25`) 방지를 한 규칙으로 사는 좋은 거래라 **깨지 않는다.**

**목표.** URL 이 태어나는 세 경계에서 **의미를 바꾸지 않는 정규화**를 한 번 더 건다.
017 이 도메인 열쇠에 한 것을 URL 전체에 하는 것이고, 자는 같은 자를 쓴다.

**기대 결과.** 같은 문서를 가리키는 표기가 여럿이어도 **서버는 한 번만 받고**,
`pages` 에 한 행이 남고, 색인에 한 건이 남는다. 다른 문서는 여전히 다른 문서다.

## 2. 무엇을 정규화하나 — 의미가 안 바뀌는 것만

RFC 3986 6.2.2 가 **syntax-based normalization** 으로 인정하는 것만 건다.
"보통 같은 문서더라" 는 휴리스틱이지 동치가 아니라서 안 건다(§5).

| 거는 것 | 근거 | 예 |
|---|---|---|
| 스킴 소문자 | 스킴은 대소문자 무관 | `HTTP://h/p` → `http://h/p` |
| 호스트 소문자 | 호스트는 대소문자 무관 | `http://A.test/p` → `http://a.test/p` |
| 스킴별 기본 포트 제거 | `:80`/`:443` 은 생략과 동치 | `http://a.test:80/p` → `http://a.test/p` |
| 빈 경로 → `/` | 빈 경로와 `/` 는 동치 (6.2.3) | `http://a.test` → `http://a.test/` |
| 퍼센트 3연 hex 대문자 | 인코딩 표기만 다르다 | `/%ea%b0%80` → `/%EA%B0%80` |

앞의 셋은 `urls.domain_key` 가 **이미 하는 일**이다 — 새로 쓰지 않고 그것을 부른다.
다만 `domain_key` 는 `userinfo@` 를 떼므로(열쇠에는 필요 없다) URL 재조립에서는
`userinfo@` 를 도로 붙인다. **뗀 채로 재조립하면 요청 내용이 바뀐다.**

## 3. 스텝

### 스텝 1 — `urls.normalize(url)` (`src/websearch/urls.py`)

`to_ascii` 를 **고치지 않고** 그 위에 얹는다: `normalize = to_ascii` 결과에
§2 표의 다섯을 건다. 못 바꾸는 URL 은 `to_ascii` 와 같이 `None`.

- 착수 조건: 없음 (첫 스텝)
- 완료 기준: `PYTHONPATH=src python3 -m unittest tests.test_urls -v` 에서 새 클래스
  `TestNormalize` 전건 통과 + 기존 `TestAsciiUrlUntouched` 4건 **그대로** 통과
  (= `to_ascii` 계약을 안 건드렸다는 증거)
- RED 로 먼저 쓸 것 (`rules/dev.md` 0절):
  1. 호스트 대소문자만 다른 둘이 같은 문자열이 된다
  2. 스킴 대소문자만 다른 둘이 같은 문자열이 된다
  3. `:80`(http)·`:443`(https) 이 사라지고, `:443`(http)·`:8080` 은 **남는다**
  4. 빈 경로가 `/` 가 되고, `http://h/p` 의 끝에는 `/` 가 **안 붙는다**
  5. `%ea` 가 `%EA` 가 되고, `%zz`·홑 `%` 는 그대로 (부정 단언의 긍정 짝)
  6. 멱등: `normalize(normalize(u)) == normalize(u)`
  7. 비ASCII·경로 대소문자·질의 문자열은 `to_ascii` 결과 그대로 (대조군)
  8. `_split` 이 못 읽는 URL(`http://[::1/x`)에 **예외를 안 던진다**
     (digest `[7]` 마지막 항목 — 열쇠를 안전하게 만들어도 협력자가 다시 판다)
- 예상 규모: `urls.py` +20줄 내외 · `tests/test_urls.py` 새 클래스

### 스텝 2 — 호출부 셋을 `normalize` 로 배선

## 4. 하지 않을 것

- **끝 슬래시 일반화** (`http://h/p/` ↔ `http://h/p`) — 동치가 아니다. 서버가 다른
  문서를 낼 수 있다. 비어 있는 경로만 `/` 로 만든다(§2)
- **`index.html` 제거 · `www.` 제거 · 질의 파라미터 정렬/제거 · 기본 질의 제거** —
  전부 휴리스틱이다. 실물에서 중복이 실측되면 그때 별도 계획
- **`%7E` → `~` (unreserved 퍼센트 디코딩)** — 안전하지만 `%2F` 같은 예약 문자를
  골라내야 해서 한 줄이 아니다. 중복원으로 실측된 적이 없다
- **이미 저장된 옛 표기 행의 마이그레이션** — 데이터 변경이라 무인 모드가 안 한다.
  새 크롤부터 정규화된다. 옛 행은 recrawl 계획 소관
- **`store`·`frontier`·`indexer` 안에서의 정규화** — 열쇠를 만드는 자리를 늘리지
  않는다. 017 이 `domain_key` 한 곳으로 모은 것과 같은 이유다 (digest `[7]`)
- **`urls.to_ascii` 의 비ASCII·IDNA 로직** — 회귀 위험이 전부 거기 있다. 안 건드린다
- **`store.has` 재크롤 정책 · indexer 증분** — recrawl 계획 소관 (digest `[8]`·`[high]`)
- **리다이렉트 체인 자체** — `crawl.py:175` 가 최종 URL 을 정규화하는 것으로 끝낸다

## 5. e2e 시나리오

`e2e/domain_key_e2e.py` 와 같은 자세다 — **크롤러 내부 상태가 아니라 서버가 받은 것**
으로 잰다. 같은 서버를 가리키는 표기는 **한 실서버**에, 대조군만 **다른 실서버**에.

1. 한 서버에 `http://a.test/p` · `http://A.test/p` · `http://a.test:80/p` 세 링크
   → 그 서버가 `/p` 를 받은 횟수 **1회**, `pages` 1행
2. 빈 경로: `http://a.test` 와 `http://a.test/` 두 링크 → `/` 수신 **1회**
3. 퍼센트 표기: `/%ea%b0%80` 와 `/%EA%B0%80` 두 링크 → 수신 **1회**
4. 대조군 — **다른 실서버**(`http://a.test:8080/p`, 기본 아닌 포트)는 안 묶인다:
   자기 서버가 `/p` 를 **1회** 따로 받는다 (전체 문서 수 = 시나리오 1~3 + 1)
5. `--control`: 시드가 링크를 안 내면 잴 표본이 사라진다 → **종료 코드 2**

**변이 3종** (서로를 대신하지 않는지 확인한다):

| 변이 | 죽어야 하는 것 | 살아야 하는 것 |
|---|---|---|
| 호스트/포트 정규화 제거 | 시나리오 1 | 2·3·4 |
| 빈 경로 `/` 보정 제거 | 시나리오 2 | 1·3·4 |
| 퍼센트 hex 대문자화 제거 | 시나리오 3 | 1·2·4 |

## 6. 왜 이 방향인가

**대안 A — `store`/`frontier` 가 자기 열쇠를 정규화한다.** 기각. 열쇠를 만드는 자리가
둘로 늘고, 둘이 어긋나면 아무도 못 본다. 017 이 `domain_key` 를 한 곳으로 모은 이유가
그대로 적용된다(digest `[7]`: 가드는 파싱을 한 곳으로 모은 뒤 거기 하나만).

**대안 B — `to_ascii` 를 직접 고친다.** 기각. `to_ascii` 의 "ASCII 는 한 글자도 안
바꾼다" 는 멱등성과 이중 인코딩 방지를 **한 규칙으로** 사는 계약이고, 회귀 위험이
전부 거기 있다(007 `non-ascii-url` 이 그것으로 닫혔다). 얹는 쪽이 되돌리기도 싸다.

**채택 — `normalize = to_ascii + §2 다섯`, 호출부는 이름만 바꾼다.** 새 규칙은 전부
새 함수 안에 있고, 옛 계약을 재는 기존 테스트 4건이 **안 바뀐 채로** 회귀 탐지기로
남는다.
