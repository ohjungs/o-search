# 설계: search-api — 질의 JSON API 와 p95 기준선

- **계획**: `docs/plan_search-api.md`
- **작성**: 2026-08-25 (야간 반복 30)

## 결정 — 한 문장

`src/websearch/serve.py` 에 `ThreadingHTTPServer` 기반 `GET /search` 하나를 두고,
**요청마다 `indexer.search()` 를 그대로 호출한다**(연결도 요청마다 새로 연다).
페이지네이션은 `search()` 에 `offset` 을 **덧붙여** 넣고, 측정은 로컬 서버를 때리는
별도 스크립트가 한다.

## 대안 비교 — 연결 전략 (갈림이 여기 하나다)

`http.server` 의 `ThreadingHTTPServer` 는 **요청마다 새 스레드**를 만든다(풀이 아니다).
그리고 sqlite 연결은 만든 스레드 밖에서 쓸 수 없다. 그래서 "연결을 아낀다" 는 말이
세 가지 다른 구조를 뜻하게 된다.

| | A. 최소 — 요청마다 연결 | B. 정공법 — 연결 풀 + 락 | C. 되돌리기 우선 — 단일 스레드 1연결 |
|---|---|---|---|
| 되돌리기 | 해당 없음(추가만) | 어려움 — 수명 관리가 코드에 박힌다 | 쉬움 |
| 코드량 | **0줄** (`indexer.search()` 그대로) | 풀·락·수명 관리 | 적음 |
| 기존과 일치 | ○ — CLI 도 매번 연결한다 | △ | △ — 동시 요청이 직렬화 |
| 다음이 편한가 | ○ — 나중에 B 로 갈 길을 막지 않음 | ○ | △ — 서버를 바꿔야 함 |

**선택: A.** 탐침에서 연결 open+close 가 **0.04ms** 로 나왔다 — 질의 1.16ms 의 3%,
p95 예산 300ms 의 0.013%다. 아끼려던 것이 애초에 없었다. 사다리 2번(이미 있는 것을 쓴다)에서
멈춘다.
**버린 이유 B** — 없는 비용을 없애려고 스레드 수명·락을 코드에 들인다. 추측성 확장이라
비교 기준 4번에서 감점. 실측이 깨지면 그때 연다(컨셉 "예감은 근거가 아니다").
**버린 이유 C** — 동시 요청이 줄을 서서 p95 가 **부하에서만** 나빠진다. 측정이 목적인
계획에서 측정값을 왜곡하는 구조를 고를 이유가 없다.

## 계약 — 개발이 지킬 것

### `indexer.search(db_path, query, limit=10, offset=0)`
- **덧붙이기만** 한다. `offset` 은 기본값이 있어 기존 호출부(CLI·테스트 ~8곳)가 그대로 돈다.
- 반환은 지금과 같은 `[(url, title, snippet), ...]`.

### `GET /search?q=<질의>&page=<1부터>`

```json
{"query": "김치", "page": 1, "has_next": true,
 "results": [{"url": "...", "title": "...", "snippet": "..."}]}
```

- `Content-Type: application/json; charset=utf-8`, 본문은 `ensure_ascii=False`.
  (한국어가 `\uXXXX` 로 나가면 눈으로 검증할 수 없다 — 컨셉 기능 2가 한국어다)
- `has_next` 는 **개수 질의를 하지 않는다.** `limit=11` 로 받아 11번째가 있으면 참,
  응답에는 10건만 싣는다. FTS5 전체 개수는 두 번째 전수 질의라 p95 에 그대로 얹힌다.
- 오류는 `{"error": "<사람이 읽는 한 줄>"}` + 상태코드. **트레이스백을 본문에 싣지 않는다.**

### 진입점 방어를 한 자리에 모은다 <!-- digest "반복 실패" 2회 -->

핸들러 메서드마다 검사를 흩지 않는다. **두 함수만 둔다.**

- `_parse(params) -> (query, page)` — 검증 전부가 여기 있다. 위반이면 `ValueError(사유)`.
- `do_GET` 은 `try: _parse → search → 200 / except ValueError: 400 / except Exception: 500`
  **한 덩어리**. `do_POST` 등은 정의하지 않는다 — `BaseHTTPRequestHandler` 가 501 을 낸다.
  **계획서는 405 라고 썼지만 501 로 간다**: 메서드를 안 만들면 stdlib 이 이미 내주는
  응답이고, 405 를 내려면 메서드마다 스텁을 두는 — 방금 없앤 그 흩뿌림이 된다.
  둘 다 4xx/5xx 이고 "그 메서드는 안 받는다" 를 뜻한다. 스텁을 만들 값이 없다.

`_parse` 가 막는 것: `q` 없음·빈 문자열·공백뿐 → 400 / `page` 가 정수가 아니거나 1 미만 → 400
/ **`page` 상한 100** → 400 / `q` 길이 상한 200자 → 400.

- **`page` 상한은 성능이 아니라 방어다.** 탐침에서 `OFFSET` 은 선형으로 자랐다
  (offset 0 → 1.1ms, 90 → 2.4ms, 990 → 7.2ms). 100만 문서에서 `page=99999` 는
  한 요청으로 색인을 훑게 만든다. 상한이 없으면 이것이 무료 자원 고갈 경로다.
- 질의 문자열 자체의 FTS5 문법·NUL·제어문자는 **이미 `indexer._fts_query()` 가** 큰따옴표
  감싸기와 `_CONTROL` 제거로 막는다. 여기서 두 번 막지 않고, **도달 가능해졌으니 테스트로
  다시 고정**한다(스텝 3).

### 실행

```
python3 -m websearch.serve <db> [--port N]   # --port 0 이면 빈 포트, 실제 포트를 stdout 에 출력
```

포트를 출력하는 이유는 e2e 와 측정 스크립트가 **포트를 고정하지 않고** 띄우기 위해서다
(기존 e2e 3개가 로컬 서버에 쓰는 방식과 같다).

## 가정 — 틀리면 이 설계가 무너지는 것

1. **연결 비용이 무시할 수준이다** → 탐침으로 확인. 3000문서 색인에서 open+close 0.04ms,
   연결 재사용과의 p95 차이 0.05ms. **참.**
2. **`indexer.search()` 를 그대로 재사용할 수 있다** → 같은 탐침에서 200회 반복 호출로
   확인. p50 1.16ms. **참.**
3. (미검증, 감수) 3000문서 측정이 100만에서도 같은 비율일 것 — 확인할 색인이 없다.
   그래서 이 계획이 내는 숫자는 **합격 판정이 아니라 기준선**이다(계획서 가정 절).

## 되돌리기

전부 **덧붙이기**다. `serve.py` 는 새 파일이고, `offset` 은 기본값 있는 인자다.
계획 커밋들을 revert 하면 기존 CLI 경로는 손대지 않은 채 남는다.

## 범위 밖 — 눈에 띄었지만 안 하는 것

- **깊은 OFFSET 의 선형 증가** — 상한 100으로 막았다. 진짜로 필요해지면 키셋 페이지네이션
  (bm25 점수 커서)이지만 지금 화면이 없다. → digest 후보.
- **동시 요청 부하 측정** — 이번 측정은 순차 p50/p95 다. 부하 곡선은 서버 구조를 바꿀
  근거가 필요할 때.
- **gzip 응답·캐시 헤더** — 프런트가 생기는 `search-ui` 소관.
