# 계획 77 `page-store-compress` — 원본 HTML 을 압축해 컨셉 1·2단계를 저장 가능하게 만든다

## 1. 왜 지금인가

**출처가 digest 가 아니다.** 야간이 두 밤 연속 「근거 0」으로 멈췄는데, `discover.md`
8순위가 전부 «저장소가 자기에 대해 적어 둔 것»이라 **컨셉과 실물의 격차는 보지 못한다.**
`docs/specs/concept.md` 를 자로 대면 격차가 하나 있다:

| 컨셉 기준 | 오늘 |
|---|---|
| 색인 규모 1단계 **10만 문서** | **361 문서** (0.36%) |
| 경량 1 — 2단계(100만)까지 **단일 머신** | 환산 **250 GB** |

**구조가 규모를 못 받는다.** 실측(400문서 · `dbstat`): `pages` 가 DB 의 **78.6%**
(78.6MB), 문서당 평균 HTML **191KB**, 파일 전체로는 **250KB/문서**.
10만이면 25GB, 100만이면 250GB — 단일 머신 전제가 여기서 깨진다.

## 2. 먼저 의심할 것 — HTML 을 안 버리는 이유가 있다

**지우면 안 된다.** `pages.html` 은 두 곳에서 읽힌다:
`indexer.py:203`(색인할 본문 텍스트 — **전문**이 필요하다) · `indexer.py:222`
(근거 문단 — 앞 3,000태그만). 앞부분만 남기면 **색인 재현율을 판다.**
계획 74 가 「캡이 본문을 굶겼다」를 실측한 자리라 같은 실수를 반복하지 않는다.

그래서 **버리는 게 아니라 접는다.** stdlib `zlib` 이면 의존성이 0 이다
(컨셉 경량 3 — 신규 의존성 금지).

## 3. 실측이 먼저 나왔다 (착수 근거)

실물 400문서 전수:

| level | 크기 | 배수 | 압축 | 해제 |
|---|---|---|---|---|
| 1 | 15.4MB | 5.1배 | 0.7ms/건 | 0.13ms/건 |
| **6** | **12.6MB** | **6.2배** | **1.7ms/건** | **0.11ms/건** |
| 9 | 12.5MB | 6.3배 | 2.5ms/건 | 0.10ms/건 |

**6 을 고른다.** 9 는 0.1배 더 얻자고 압축을 1.5배 치른다. 1 은 1.1배를 잃는다.

- **질의 시점 비용은 없다시피 하다** — 해제 p95 **0.33ms** · `/passages` 가 읽는
  10건 최악 합이 **4.8ms**. 오늘 p95 138ms · 예산 500ms 이라 **1% 미만**이다.
- **크롤 시점 비용도 없다시피 하다** — 압축 1.7ms 인데 크롤은 3.67문서/초
  (272ms/문서) 네트워크 바운드라 **0.6%**다. 컨셉 성능 2(5문서/초)를 안 건드린다.

환산: 250KB/문서 → **85KB/문서**. 10만 = 25GB→**8.5GB**, 100만 = 250GB→**85GB**.

## 4. 스텝

| # | 산출물 | 완료 기준 |
|---|---|---|
| 1 | 읽기 경로가 **두 꼴을 다 받는다** | 옛 TEXT·새 BLOB 둘 다 같은 답 · 실패 테스트 먼저 |
| 2 | 쓰기 경로가 압축한다 | 새로 쓴 행이 BLOB · 전수 초록 |
| 3 | 실물 재측정 | 용량·`/passages` p95 를 계획 74 와 **같은 자**로 |

**스텝 1 을 먼저 하는 이유는 마이그레이션을 안 만들기 위해서다.** 읽기가 두 꼴을
받으면 기존 DB 는 **그대로 두고도 동작하고**, 재크롤이 자연히 갈아 끼운다.
`sqlite3` 는 TEXT 를 `str`, BLOB 를 `bytes` 로 주므로 판별에 열을 더할 필요도 없다.

## 4-a. 결과 — 예측이 맞았고, 스텝 1 이 함정 하나를 잡았다

| | 옛 | **새** |
|---|---|---|
| DB 파일 | 100.1 MB | **34.3 MB** (−65.7%) |
| 문서당 | 250,184 B | **85,852 B** |
| 10만 / 100만 환산 | 25.0 GB / 250 GB | **8.6 GB / 86 GB** |
| 근거 문단 | 96건 | **96건** (한 건도 안 변했다) |
| `/passages` p95 | 138.54ms | **141.41ms** (예산의 27.7 → 28.3%) |
| 색인 | 13.34초 | **13.43초** (+0.7%) |

**함정:** 「뒤늦게 noindex 를 선언한 문서를 뺀다」 경로가 `WHERE p.html LIKE '%robots%'`
로 후보를 골랐는데 **압축분은 BLOB 이라 매치가 0** 이다 — 초록불인 채로 크롤 윤리 축이
조용히 죽는 모양이었다. **기존 테스트가 잡았다**(픽스처를 `Store.upsert` 로 넣기 때문).
걷어낸 조건이 `is_noindex()` 첫 줄과 같은 검사라 **판정은 안 바뀐다.**

전문: `docs/e2e/page-store-compress/result.md`.

## 5. 하지 않을 것

- **마이그레이션 스크립트를 쓰지 않는다.** 4절의 이유다. 스키마 DDL 도 안 고친다
  (`pages.html` 은 선언이 `TEXT` 지만 SQLite 는 타입 친화라 BLOB 를 그대로 받는다).
- **HTML 을 잘라 버리지 않는다.** 2절의 이유 — 색인 재현율을 판다.
- **다른 열·다른 테이블은 안 건드린다.** FTS 색인(`docs_*` 21.3MB)은 이 계획 밖이다.
- **크롤·색인 알고리즘 0줄.** 저장 표현만 바꾼다.
