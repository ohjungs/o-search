`has_next`·`page` 는 **응답에 없다**(페이지네이션을 안 연다 — 계획 5절).
문단당 `MAX_PASSAGE = 2000`자에서 자른다 — `MAX_QUERY`·`MAX_PAGE` 와 같은 자리의
자원 상한이다. 자르면서 질의어가 잘려 나가면 **정확도가 떨어지는 것이 정직하다**(안 보정한다).

**상한이 하나 더 있다 — `indexer.MAX_PASSAGE_HTML = 35,000`자**(개발 4 가 10만으로
세웠고 리뷰 2 가 계수를 반려해 **개발 5 가 35,000 으로 내렸다**).
`MAX_PASSAGE` 는 **응답 바이트**를 자르지 재파싱 **CPU** 를 안 자른다. 문서당 앞
35,000자만 다시 파싱한다: 실측 최악(인라인 마크업이 촘촘한 위키·CMS 출력) 1,000자당
**0.352ms** 이고 `PASSAGE_LIMIT` 10건이면 **123ms — 예산 500ms 의 25%**.
단위는 문자다(`pages.html` 은 sqlite 에서 `str` 로 나온다). 자리는 `indexer` 다 —
`serve` → `indexer` 가 import 방향이라 반대는 순환이고, CLI 질의는 `serve` 를 안 지난다.
**천장: 잘린 뒤의 문단은 근거로 안 나온다**(그 문서는 검색에는 그대로 나온다).
자르는 **자리는 안 정한다 — 길이만 정한다**(개발 7 이 되감기를 지웠다, 아래 «되감기 줄은
지웠다»). 문자 슬라이스를 그대로 주면 파서가 미완성 태그를 데이터로 흘려 응답에 마크업이
섞이는데(테스트 3, 아래), 그것을 막는 자리가 `passages()` 의 문자열 규칙이 아니라
**`_BlockParser.close()`** 다 — 파서가 삼키지 못하고 남긴 꼬리를 버린다.

## 갈림길 1 — 문단을 어디서 얻나 → **A 원본 재파싱**

| 안 | 출발점 | 판정 |
|---|---|---|
| **A `pages.html` 재파싱** | 정공법 | **고른다.** 블록 경계가 원문에만 있고, 원문은 이미 DB 에 있다 |
| B 표식 색인 | 되돌리기 우선 | **접는다.** `body` 를 바꾸면 **전체 재색인**이다 — 계획 5절이 사람에게 올리라고 못박은 수술 |
| C 문자 창 | 최소 | **접는다.** 사양의 «문단» 을 «창» 으로 바꿔 읽는 것이다(계획 7절 위험 1번) |

**A 는 새 코드가 아니라 이미 있는 파서의 부산물이다.** `_TextParser._separate()` 가
블록 경계마다 이미 불리고 있고, 그 경계를 버리는 것은 `_normalize` 의 `split()` 뿐이다.
그래서 **`_TextParser` 를 한 줄도 안 고치고 하위 클래스로 끊는다** — `_separate()` 에서
지금까지 모은 것을 `_normalize` 해 블록으로 밀어내고 버퍼를 비운다.
색인 경로는 "같은 결과" 가 아니라 **안 지나간다**(회귀 위험 0).

**실측(2026-09-02 탐침, 스크래치패드)**

| 잰 것 | 값 |
|---|---|
| 불변식 `" ".join(blocks) == body` | 합성 13종 중 **12 참** · 코퍼스 64문서 **64/64 참** |
| 유일한 위반 | **블록 전체가 제어문자**일 때. 통짜 정규화가 겹공백을 남긴다(`'가  나'`) |
| 파싱 비용 (17.6KB) | `extract_text` 1.63ms → `extract_blocks` **1.83ms** (+12%) |
| 코퍼스 문서당 블록 | min 3 · avg 4.0 · max 4 |
| 검색+선택 (질의 40개, 인프로세스) | p50 **0.6ms** · p95 **0.7ms** — 예산 500ms 의 0.14% |
| 문단 채택률 | ko **199/200** · en **199/200** (각 99.5%) |
| 버린 둘 | `맛집`(한글 2-gram 이 블록을 가로질러 매치) · `tuples`(porter 가 `tuple` 로 매치) |

위반 한 줄은 `ponytail:` 주석으로 천장을 적고 **현 동작 그대로 테스트에 고정**한다 —
고치려면 `_normalize` 를 바꿔야 하고 그것이 색인을 바꾼다.

**`passages()` 는 `search()` 를 부른다 — 자체 질의를 짜지 않는다.** 그러면 503·500 판정과
옛 색인 검사를 **한 벌 더** 갖게 되고 계획 47 이 한곳에 모은 것이 다시 흩어진다.
대신 `pages.html` 을 읽으려 `_connect` 를 한 번 더 연다 — open+close **0.04ms**(설계 46 실측).

## 갈림길 2 — 파라미터 → **`_parse` 를 재사용하고 넓히지 않는다**

문단 수는 **서버 상수**(`PASSAGE_LIMIT = 10`)다. 사양 성능 5가 *"못 지키면 문단 수를
줄이지, 예산을 늘리지 않는다"* 라고 **서버 손잡이**로 못박았다 — 클라이언트가 돌리는
손잡이면 예산이 클라이언트 손에 있는 것이 된다.
`page` 는 `_parse` 가 이미 검증하므로 **받되 `1` 이 아니면 400** 이다. 조용히 무시하면
페이지를 넘기는 소비자가 같은 문단을 영원히 받는다.

## 갈림길 3 — 위치의 표기 → **블록 인덱스 하나**

문자 오프셋은 **거짓 정밀도**다. `docs.body` 는 응답에 없으므로 소비자가 오프셋을
맞춰 볼 원문이 없다. 순번은 *"이 문서의 N번째 문단"* 이라 문단 텍스트와 함께 뜻이 산다.
둘 다 내는 것은 쓰지도 않을 필드를 계약에 박는 것이다(계약은 지우기가 제일 비싸다).

## 갈림길 4 — 측정기 → **새 파일 `e2e/passage_eval.py`**

`quality_eval.py` 는 **한 글자도 안 고친다**(recall 숫자가 매달린 도구다).
코퍼스·질의 JSON 도 **동결 그대로 읽는다**. 새로 하는 것은 **HTML 포장**뿐이다 —
`quality_eval` 은 본문 전체를 `<p>` 하나로 감싸서 **문서당 블록이 1개**라 문단을 잴 수 없다.
`passage_eval` 은 같은 본문을 문장 단위 `<p>` 로 감싼다. **색인 본문은 64/64 바이트 동일**
(실측) — 마침표를 남기고 끊으면 정규화 뒤 같은 문자열이다. 같은 색인이라 채택률을
recall 옆에 놓고 읽을 수 있다.

**정확도 100% 는 기본값이다** — 고르는 규칙과 판정 규칙이 같은 술어라 그렇다.
그래서 숫자를 **둘** 찍는다: 사양 기능 8이 요구하는 **정확도**(≥90%, 미달 rc 1)와
실제로 움직이는 **채택률**(실측 99.5%, 기록만). 가드가 이 도구의 이빨이다 — 종료 **2**:
문단 총 0건 · 문서당 블록 < 2 · 반환 문단이 문서 본문과 통째로 같음 · 코퍼스/질의 수 미달.

**p95 는 HTTP 로 잰다**(사양 성능 5는 API 예산이다). `--port 0` 서버를 띄워 `perf_search`
와 같은 형태로 돈다. **주의 두 줄을 `project.md` 에 함께 적는다**: 코퍼스가 64문서라
FTS 축은 `perf_search`(3000문서 p95 8.90ms)가 재고 있고, 코퍼스 문서가 작아
**문서 크기 축은 이 숫자에 안 들어 있다**(18KB×10건 재파싱 = 탐침 실측 20.8ms).

## 안 고치는 것 (범위 밖)

`_TextParser`·`_normalize`·`search()`·`_send`·`_send_html`·화면 경로 · `/search` 스키마 ·
`quality_eval.py` · 코퍼스·질의 JSON · 스키마·`data/crawl.db` · 속도 제한 · 문서당 2문단 이상.

## 스텝 경계 — 계획의 3스텝 그대로

스텝 1이 `extract.py`+`indexer.py` 두 파일이지만 **산출물은 하나**(문단을 돌려주는 함수)라
노드 하나다. `extract_blocks` 만 있고 `passages` 가 없으면 검증할 것이 불변식뿐이고,
그 불변식은 «문단이 나온다» 를 안 보인다.

## 변이 표 — 여덟을 심는다

| # | 심는 변이 | 죽어야 하는 단언 |
|---|---|---|
| M1 | `_separate` 의 버퍼 비우기 삭제 | 불변식 `" ".join(blocks) == body`(블록이 누적된다) |
| M2 | `extract_blocks` 의 마지막 flush 삭제 | **깨진 HTML**(`<p>가<p>나<div>다`)의 마지막 블록 |
| M3 | 블록 마커를 `_normalize` 경로에 넣는 안으로 되돌림 | 기존 `test_extract.py` 본문 단언 — **대조군** |
| M4 | 매치 없는 문서에 첫 블록을 대신 낸다 | «매치 없는 문서는 안 낸다» 단위 **둘** (`passage_eval` 은 **안 죽인다** — 아래) |
| M5 | `position` 을 빈 블록 포함으로 센다 | 빈 `<p>` 가 낀 fixture 의 위치 값 |
| M6 | `page != 1` 거절 삭제 | `?page=2` 가 400 |
| M7 | `_send` 를 안 쓰고 직접 JSON 을 쓴다 | 모든 응답에 `version` — **대조군**(계약 물려받기) |
| M8 | `MAX_PASSAGE` 자르기 삭제 | 2,000자 넘는 블록의 응답 길이 |
| W1 | `MAX_PASSAGE_HTML` 자르기 삭제 | 캡 뒤에만 있는 문단이 안 나온다는 단언 |
| N1 | 캡을 한 글자 좁힘(`- 1`) | 캡 끝에 걸친 문단의 마지막 글자 |
| W2 | 캡 값 10만 → 100만 | **값 가드**(캡 × `PASSAGE_LIMIT` × 실측 계수 ≤ 예산 25%) |
| V1 | `MAX_QUERY` 200 → 20000 | 201자 질의가 400 — **이미 있었다**(리터럴 `"가" * 201`) |
| V2 | `MAX_PAGE` 100 → 10000 | `&page=101` 이 400 — **이미 있었다**(리터럴) |
| V3 | `MAX_PASSAGE` 2000 → 5000 | 8,000자 본문의 응답 길이가 **정확히 2000** |
| V5 | `MAX_PASSAGE` 2000 → 500 | 같은 단언(양방향) |
| V6 | `PASSAGE_LIMIT` 10 → 11 | W2 의 값 가드 — **손잡이 둘 중 나머지 하나** |
| V7 | `REQUEST_TIMEOUT` 10 → 600 | 핸들러 소켓 타임아웃이 **정확히 10** |
| X1 | 잘린 자리 되감기 삭제(`html[:cap]` 을 그대로 파서에 준다) | 캡이 태그 한가운데 떨어진 문서의 문단에 `<` 가 없다 |
| X2 | 되감기 조건을 옛 `len(raw) > CAP and "<" in cut` 으로 되돌린다 | ① `<p>`+긴 본문 하나가 **문단 1건을 낸다**(백지 아님) ② 캡 아래 깨진 속성값이 `<` 를 안 흘린다 |
| X3 | 되감기 비교를 `>` → `>=` | 태그 0개 문서의 문단이 **마지막 글자까지 온전**(둘 다 -1 이라 `html[:-1]`) |

**W2 는 처음에 살아남았다 (2026-09-02 개발 4 실측).** fixture 를 상수에서 만들면
(`"봄" * MAX_PASSAGE_HTML`) **상수와 함께 늘어나 값 변경이 안 보인다** — 기존 형제 상한
테스트도 같은 모양이라 같은 눈먼 자리를 갖는다. 값 가드를 세운 뒤에야 RED(1180ms >
125ms)가 났다. **메커니즘을 붙드는 단언은 값을 안 붙든다** — 손잡이는 따로 재야 한다.

**형제 상한 전수 (2026-09-02 테스트 2 실측 · `.mutation-lock` 아래 · 전부 원복 ·
`git diff -- src/` 0줄).** W2 의 교훈을 형제 넷에 적용하니 **직전 반복의 진단이 절반
틀렸다** — V1·V2 는 이미 RED 였다. `test_serve.py` 가 상수가 아니라 **리터럴**로 두드리기
때문이고, W2 가 지목한 «상수를 참조하는 fixture» 는 `MAX_PASSAGE` 한 곳뿐이었다.
살아남은 것은 **V3·V5(`MAX_PASSAGE` 양방향, 대략 [40, 5999] 무저항) · V7
(`REQUEST_TIMEOUT` 어떤 값이든)** 셋이고, V7 은 가드가 `is not None` 만 봤다 —
**`is not None` 은 값을 안 붙든다.** 둘 다 단언을 `assertEqual` 로 바꿔 닫았고
**새 가드는 공식이 아니라 리터럴로 적었다**(상수를 참조하면 W2·V3 와 같은 이유로 눈이 먼다).
V4(2000 → 20)가 RED 인 것은 실력이 아니라 픽스처가 30자쯤이라 걸린 것이고, 그래서
표에 안 넣었다 — **우연히 죽는 변이는 가드의 증거가 아니다.**

**계수 0.118 은 틀렸다 (2026-09-02 리뷰 2 실측 · 코퍼스 무관 · 10만자 합성 문서 ×5회).**
값 가드는 `MAX_PASSAGE_HTML / 1000 × 0.118 × PASSAGE_LIMIT ≤ 125ms` 라는 **순수 산수**라
초록불의 근거가 **계수 하나뿐**이다. 그 계수를 세 모양에서 다시 쟀다:

| HTML 모양 | ms/1,000자 | 캡 × 10건 | 예산 500ms 의 |
|---|---|---|---|
| 태그 성긴 영문 (긴 `<p>` 단락) | 0.026 | 26ms | 5% |
| 한글 · 태그 촘촘 (개발 4 가 잰 것) | 0.130 | 130ms | 26% |
| **인라인 촘촘** (낱말마다 `<b>`/`<i>`/`<em>` — 위키·CMS·에디터 출력) | **0.352** | **288ms** | **58%** |

개발 4 는 가운데 모양을 최악으로 보고 0.118 을 골랐는데 **평범한 인라인 마크업이 그것의
3배**다. 가드가 증명하는 `118ms ≤ 125ms`(여유 **6%**)는 실제로 **288ms** 라 2.3배 초과다.
**프로세스 밖 HTTP 로도 확인했다** — 10만자 문서 10건에서 `/passages` p95 **790ms**
(예산의 158%), 같은 코퍼스 `/search` p95 를 뺀 **문단 경로 몫 354ms(71%)**. 짧은 질의다.
`e2e/passage_eval.py` 의 p95 1.38ms(0.3%)는 동결 코퍼스 본문이 최대 305자라 이 축을
못 밟는다 — **리뷰 1 이 반려한 «초록불이 예산을 보증하지 않는다» 가 한 층 아래(가드)에서
되풀이됐다.** 산수 가드는 흔들리지 않는 대신, **계수가 틀리면 조용히 거짓말한다.**
처방: 계수 **0.352**, `MAX_PASSAGE_HTML` **100,000 → 35,000**(35 × 0.352 × 10 = 123ms).
**예산은 안 넓힌다** — 사양 성능 5 가 «못 지키면 문단 수를 줄이지, 예산을 늘리지 않는다».

**처방을 적용했고 예산이 닫혔다 (2026-09-02 개발 5 실측).** 계수를 세 모양에서 다시
재니 **0.070 · 0.285 · 0.327**(위 표와 같은 순서)로 리뷰의 0.352 보다 낮게 나왔고,
**낮은 쪽으로 안 내렸다** — 가드 계수는 최악이라야 거짓말을 안 한다. 캡을 35,000 으로
내린 뒤 프로세스 밖 HTTP 로 다시 재니 10만자 문서 10건에 `/passages` p95 **199.9ms
(예산의 40%)** · **문단 경로 몫 118.3ms** 로, 가드가 약속한 123ms 와 맞는다(반려 시점
790ms·158% → 40%). **사양 기능 8 은 안 움직인다** — 동결 코퍼스의 포장된 HTML 은 최대
409자로 캡의 1/85.6 이라 잘리는 문서가 **0건**이고 정확도 100.0% · 채택률 99.5% 가 그대로다.

**캡은 «몇 자» 만 정했지 «어디서» 를 안 정했다 (2026-09-02 테스트 3 실측 · 갭 8점).**
`row[0][:MAX_PASSAGE_HTML]` 은 **문자 슬라이스**라 컷이 태그 한가운데 떨어질 수 있고,
그때 `html.parser` 는 EOF 에 남은 미완성 태그를 **버리지 않고 데이터로 흘린다**
(`goahead(end=1)` 의 마지막 `handle_data`). 그래서 근거 문단이
`김치찌개 <a href="xxxxxxxxxxxxxxxx` 로 끝난다 — **소비자는 기계인데 출처가 붙은
텍스트 대신 마크업 조각을 받는다**(RED 실측 그대로). 도달 경로는 흔하다: 긴 `href`·
`data-*` 속성이 캡에 걸리기만 하면 되고, 그 블록이 질의어를 담고 있으면 **점수가 나서
실제로 뽑힌다**. 같은 컷이 엔티티 한가운데 떨어지면 `A&am` 이 된다(값 낮음).

처방은 **한 줄** — 자른 뒤 마지막 `<` 앞에서 다시 끊는다. 잃는 것은 많아야 온전한
태그 하나이고(닫는 태그면 `close()` 의 flush 가 대신 낸다 — M2 가 이미 고정한 동작).
**캡을 좁히지 않았다**(길이 예산은 그대로).

**그 처방은 절반만 맞았다 (2026-09-02 리뷰 3 → 개발 6).** 조건을 «`<` 가 있나» 로 물은
것이 둘을 낳았다: ① 문서 전체가 문단 하나면 캡 안 마지막 `<` 가 **인덱스 0** 이라
`html[:0]` — 문서가 통째로 `/passages` 에서 사라진다(잃는 원문 최대 캡 전부)
② 되감기의 원인은 «캡» 이 아니라 «미완성 마크업» 인데 조건이 캡에 걸려 있어, **캡보다
짧은 깨진 원문**(잘린 응답·손으로 쓴 HTML)은 되감기를 안 지나 그대로 `<` 를 흘렸다.
고친 조건은 **`cut.rfind("<") > cut.rfind(">")`** — 안 닫힌 마크업이 남았을 때만
되감는다. 엔티티(`A&am`)는 이 줄이 **안 건드린다**: 평문이라 마크업으로 안 새고,
안 닫힌 `<` 뒤에 있을 때만 함께 사라진다(위 문단이 무조건이라 적었던 것을 좁혔다).
변이 X2·X3 이 두 얼굴을 각각 붙든다.

**왜 아무도 안 밟았나 — 두 캡 테스트가 잘린 자리를 평문으로만 두었다.** 둘 다
fixture 가 `"봄" * cap` 이라 컷이 언제나 텍스트 한가운데다. HTML 모양 축을 다시 세어
보니(중첩 깊이·속성 폭탄·엔티티·주석·스크립트·블록 수) **나머지는 죽는 변이가 없다**:
중첩·주석·테이블·`<br>` 은 기존 블록 단언과 불변식이 덮고, `noscript` 는 `TestExtractText`
가 이미 문다(`_SKIP_TAGS` 에서 빼면 죽는다). **속성 폭탄만이 잘린 자리와 만나 새 변이를
낳았다** — 「입력이 하나뿐인 단언」의 다섯 번째 사례이고, 이번의 «하나» 는 값이 아니라
**입력의 모양**이었다(R1 절대 경로 · M2 깨진 HTML · W2 상수 파생 fixture · 계수 축).

**그 절반도 절반만 맞았다 — 여섯 번째 사례다 (2026-09-02 테스트 4 실측, RED 2건).**
`rfind("<") > rfind(">")` 는 **안 닫힌 구성물이 자기 안에 `>` 를 담을 수 있다**는 것을
못 본다. 주석(`<!-- TODO: <a href=x>`) · 선언 · 인용된 속성값(`title="a > b"`)이 전부
그 모양이라 비교가 뒤집혀 **되감기가 아예 안 걸리고**, `html.parser` 가 EOF 의 미완성
구성물을 데이터로 흘려 소비자가 다시 마크업 조각을 받는다. 주석 쪽은 **화면에 안 보이는
내용이 근거 문단이 된다** — 사양 기능 8 은 문단이 «원문에서 읽히는 텍스트» 라고 정한다.
개발 6 의 새 단언 3건이 쓰는 입력이 **안 닫힌 `<` 뒤에 `>` 가 없는** 모양 하나뿐이라
어떤 조건을 써도 다 걸렸다 — 「입력이 하나뿐인 단언」의 **여섯 번째** 사례이고, 이번의
«하나» 도 값이 아니라 입력의 모양이다.

**후보 수리 다섯을 얹어 재고 단언 둘만 넣었다** (`.mutation-lock` 아래 프로브 · `src/` 0줄):

| 입력 | C0 현행 | C1 `<!--` 만 아는 문자열 수리 | C2 조건만 넓히기 | C4 되감기 반복 | C5 파서에 묻기 |
|---|---|---|---|---|---|
| 주석 안에 `>` | 샌다 | 닫힘 | 샌다 | 샌다 | 닫힘 |
| 속성값 안에 `>` | 샌다 | **샌다** | 샌다 | 샌다 | 닫힘 |
| 앞선 주석이 열림 | 샌다 | 닫힘 | 샌다 | 샌다 | 닫힘 |
| 대조군(정상 · 태그 0개 · 평문 `5 > 3`) | 온전 | 온전 | 온전 | 온전 | 온전 |

가르는 것이 **C1 하나**뿐이라 주석·속성값 둘만 세웠다. «앞선 주석이 열린 채 되감기가
걸려도 새는» 모양과 `<![CDATA[` 도중은 다섯 후보에서 **판정이 한 칸도 안 갈려** 안 넣었다
(«죽는 변이가 없는 단언은 넣지 않는다»). C5 는 `feed()` 가 삼키지 못하고 남긴 꼬리
(`parser.rawdata`)를 `close()` 전에 버린다 — 문자열 규칙을 늘리는 대신 **파서에게 어디까지가
온전한지를 묻는다**.

**C5 에는 되갚을 것이 하나 있다 — 초록 가드로 못박았다.** `convert_charrefs` 때문에 잘린
엔티티로 끝나는 문서(`<p>김치찌개 &am`)는 꼬리가 통째로 남아, 그대로 버리면 문단이 **0개**가
된다 — 리뷰 3 의 «문서가 통째로 사라진다» 가 수리를 타고 돌아오는 문이다. 꼬리가 `<` 로
시작할 때만 버리면 통과한다.

**갈림길 — C5 를 어디에 두나 (개발 7 이 고른다).** ㉠ `extract.py` 안: 파싱이 한 번이라
비용 0 이지만 `extract_text` 를 타고 **색인 본문(`docs.body`)까지 바뀐다**(계획서의 «건드릴
파일» 밖 · 재색인 성격). ㉡ `passages()` 안: 범위 안이지만 문서마다 **파싱이 두 번**이라
예산(프로세스 밖 p95 123.5ms)을 다시 재야 한다. 계획이 성능 축에서 두 번 넘어진 자리라
산수가 아니라 실측으로 고른다.

**골랐다 — 둘 다 아니고 `_BlockParser.close()` 다 (2026-09-02 개발 7).** ㉠ 과 ㉡ 은
«`extract.py` 냐 `passages()` 냐» 로 물었는데, 그 물음이 **`extract.py` 안에 경로가 둘이라는
것**을 안 보고 있었다. 색인은 `_TextParser`(→`extract_text`)로 가고 문단은
`_BlockParser`(→`extract_blocks`)로 간다 — 계획 48 이 처음부터 갈라 둔 자리다. 꼬리를
`_BlockParser.close()` 에서 버리면 **㉠ 의 비용(파싱 한 번)과 ㉡ 의 범위(색인 무변경)를
동시에** 갖는다. 확인은 추론이 아니라 출력으로 했다 — 같은 입력에서 `extract_text` 는
수리 전과 **글자 그대로 같다**(`'김치찌개 <!-- TODO: <a href=x> 옛 링크'` 를 그대로 낸다.
색인은 통짜 본문이라 상관없다) 반면 `extract_blocks` 는 `['김치찌개']` 를 낸다.

| | ㉠ `_TextParser` | ㉡ `passages()` 두 번 파싱 | **㉢ `_BlockParser.close()` (고름)** |
|---|---|---|---|
| 색인 본문(`docs.body`) | **바뀐다** (재색인) | 무변경 | 무변경 |
| 파싱 횟수 | 1 | **2** | 1 |
| 계수 ms/1,000자 (위키 인라인) | — | **0.585** | 0.311 |
| 같은 계수 (`<p>가</p>` 반복) | — | **0.842** | 0.473 |
| 값 가드(`캡×계수×10 ≤ 125ms`) | — | **205ms — 깨진다** | 109ms 통과 |

**㉡ 을 죽인 것은 실측이다.** 파싱을 한 번 더 하면 계수가 **1.88배**가 된다(0.311→0.585).
**여기서 쓸 것은 절대값이 아니라 그 비율이다** — 내 위키 fixture 는 리뷰 2 의 것과 글자
그대로 같지 않아 0.311 과 0.352 를 나란히 놓을 수 없다. 비율만 값 가드
(`test_cap_and_passage_limit_together_stay_inside_the_budget`)에 태우면 0.352 → 0.66 이고
`35 × 0.66 × 10 = 231ms > 125ms`(내 계수로 직접 재도 205ms) — 가드를 되살리려면 캡을
깎아야 하고 그건 계획 밖의 손잡이다.

**프로세스 밖 재측 — 수리는 예산을 한 칸도 안 움직였다** (같은 탐침으로 수리 전/후,
임시 DB · `data/crawl.db` 안 열었다. 10만자 문서 10건 · `--port 0` · 20표본 p95):

| 모양 | 수리 전 `/passages` p95 | 수리 후 | `/search` 몫을 뺀 **문단 몫** |
|---|---|---|---|
| 위키 인라인 | 507.2ms | **507.1 · 509.2ms** | **123.2ms (예산의 25%)** |
| `<p>가</p>` 반복 | 2825.5ms | **2820.2 · 2845.9ms** | 213.6ms (43%) |

문단 몫 123.2ms 는 개발 6 이 적은 **123.5ms 와 오차 안에서 같다**. 총 p95 가 예산을
넘는 것(101%·569%)은 이 수리가 만든 것이 아니라 **`/search` 가 그 대부분**이라는
사실이고(386ms·2632ms), 질의어가 문서마다 수천 번 반복되는 **합성 코퍼스에서만** 나는
값이다 — 실물 64문서 코퍼스의 `e2e/passage_eval.py` p95 는 여전히 **1.39ms(0.3%)** 다.
갈림길 5(최악 입력을 누가 정하나)가 열어 둔 자리에 «/search 몫» 이라는 축이 하나 더 있다는
기록만 남기고 안 건드린다 — 캡·계수·`/search` 는 전부 이 스텝 밖이다.

**되감기 줄은 지웠다 — 남겨 두면 손해만 난다.** 파서가 꼬리를 버리므로
`html.rfind("<") > html.rfind(">")` 가 잡던 것은 전부 덮인다(변이 Y1 이 그 네 단언을
한꺼번에 물어 증명한다). 반대로 남겨 두면 **평문 `<` 를 계속 자른다** — `<p>a < b` 에서
`html.parser` 는 `<` 를 데이터로 내는데(뒤가 글자가 아니면 태그가 아니다 — 브라우저와
같은 판정) 되감기는 «a» 만 남긴다. 사양 기능 8 이 말하는 «원문에서 읽히는 텍스트» 는
`a < b` 쪽이다. 그래서 `passages()` 는 이제 **길이만** 정한다.

## 갈림길 5 — 최악 입력은 누가 정하나 (열린 채로 남긴다)

**0.352 도 최악이 아니다.** `<p>가</p>` 만 반복하는 합성 문서는 **0.489 ms/1,000자**
(35,000자 × 10건 = **171ms > 125ms**)다 — 비용을 끄는 것은 문자 수가 아니라 **블록 수**다.
그런데 그 모양은 «실물에서 이렇더라» 가 아니라 **내가 골라 만든 것**이라, 계수로 쓰면
가드가 다시 «누가 최악을 정했나» 를 코드 밖에 두게 된다(`digest` 의 성능 초록불 항목이
같은 실패를 두 번 적어 뒀다). 그래서 **셋 다 안 골랐다**:

| 안 | 판정 |
|---|---|
| 계수를 0.489 로 올리고 캡을 25,000 으로 | **접는다.** 합성 모양 하나가 품질 손잡이를 또 3분의 1 깎는다 |
| 가드를 타이밍 단언으로 | **접는다.** CI 기계마다 흔들려 거짓 RED 를 낸다(리뷰 2 가 산수를 고른 이유) |
| **모양을 주석에 적고 축을 열어 둔다** | **고른다.** 실물 크기 분포가 저장소에 없다 — `data/crawl.db` 는 2문서 × 66자다 |

**닫는 조건은 실물이다.** 크롤 코퍼스가 생겨 블록 밀도 분포를 재면 그때 계수가 아니라
**파서**(블록 단위 스트리밍)를 고친다 — 캡은 그 시점에 지운다(`indexer` 의 `ponytail:` 주석).

**축은 열어 두되 값은 쟀다 (2026-09-02 리뷰 3, 프로세스 밖 실측).** 계수 산수가 아니라
`GET /passages` **응답 p95** 를 잰다 — 서버를 `--port 0` 으로 띄우고 문서 12건 × 캡
35,000자를 색인한 뒤 30회 요청했다(`scratchpad/probe_http.py`, 임시 DB · `data/crawl.db`
는 열지 않는다).

| 문서 모양 | p95 | 예산 500ms 대비 |
|---|---|---|
| wiki(`<p>…<b>…<i>…</p>` 반복, 계수 0.352 를 낸 모양) | **121.0ms** | 24% |
| `<p>가</p>` 반복(계수 0.489, 블록 축의 최악) | **190.3ms** | 38% |

즉 **최악 모양에서도 예산의 38%** 다. 산수(171ms > 125ms)는 파싱만 센 것이라 응답
전체와 예산의 관계를 못 보여 줬고, 실측은 두 축 모두 예산 안임을 보인다. 그래서
**이 갈림길은 그대로 «열린 채로» 두되, 열려 있는 것이 위험이 아니라는 근거가 생겼다** —
계수를 올리거나 캡을 깎는 두 안은 여전히 접는다.

**개발 6 재측 (2026-09-02, 되감기를 고친 뒤 같은 탐침으로).** 조건이 바뀌면 파서에
들어가는 문자열 길이가 달라지므로 다시 쟀다: wiki **123.5ms(25%)** · `<p>가</p>` 반복
**196.3ms(39%)**. 리뷰 3 값(121.0 · 190.3)과 **오차 안에서 같다** — 한 줄이 길이 예산을
안 움직였다. 계획이 성능 축에서 두 번 넘어졌기에 산수로 넘기지 않고 실측으로 닫는다.

M2 는 정상 HTML 에서는 닫는 태그가 flush 를 대신해 **살아남는다** — 그래서 깨진 HTML
케이스를 테스트에 반드시 넣는다(탐침에서 `<p>가<p>나<div>다` 가 `['가','나','다']` 였다).

## 갈림길 6 — 「블록」이 「문단」인가 → **아직 열려 있다** (리뷰 4 가 열었다 · 개발 8·9 가 골랐고 리뷰 5·6 이 되돌렸다 · 개발 10 이 「길이」로 세워 두고 실물까지 연다)

**설계의 전제 한 줄이 절반만 참이다.** 갈림길 1 은 *"부모가 블록 태그마다 그 자리를 이미
안다"* 고 적었는데, `_separate()` 는 **블록 태그 전용이 아니다** — `extract.py:7` 이
`<br>` 을 *"줄바꿈이므로 일부러"* `_INLINE_TAGS` 에서 뺐기 때문에 `<br>` 도 그 자리를 부른다.
색인 경로에서 그것은 **공백 하나**지만 `_BlockParser` 는 그것을 **문단 경계**로 읽는다.
같은 태그가 두 경로에서 다른 뜻이 됐다.

**실측 (2026-09-02 리뷰 4).** 백지 패스가 둘을 냈고 재측에서 둘 다 재현했다:

| 입력 | 나오는 근거 | 왜 |
|---|---|---|
| `<nav><a>김치찌개</a></nav><article><p>김치찌개 만드는 순서를…</p></article>` | **`'김치찌개'`**(4자) | 동점이고 내비가 **항상 앞**이라 «먼저 나온 것» 이 이긴다 |
| `<p>오늘은<br>김치찌개<br>내일은 된장찌개를 끓인다</p>` | **`'김치찌개'`**(4자) | `<br>` 이 만든 4자 블록이 **질의어 밀도로 정직하게** 이긴다 |

둘째 것은 동점이 아니라 **점수로 이긴 것**이라 «동점이면 긴 쪽» 같은 손잡이로는 안 닫힌다.
가르는 것은 `<br>` 을 블록 경계로 볼 것인가다.

**이 결함은 준비된 측정기 어느 것도 못 잡는다 — 코퍼스가 마크업이 아니라 평문이라서다.**
`e2e/quality/corpus.json` 64건은 `url·lang·title·body` 뿐이고 `passage_eval.build_index`
가 **문장마다 `<p>` 하나**로 감싸 HTML 을 만든다. 그래서 코퍼스에는 `<br>` 0건 · `nav`/
`ul`/`li`/`h*` 0건이고, 블록 최소 길이가 **129자**(20자 미만 0개 · 근거 399건 중 20자 미만
**0건**)다. 정확도 100% 와 채택률 99.5% 는 **한 문장짜리 `<p>` 위에서만** 잰 값이다.
`data/crawl.db` 도 2문서 × 66자라 실물이 이 자리를 덮은 적이 없다.

| 안 | 판정 |
|---|---|
| 동점 키에 길이를 붙인다 | 첫째만 닫는다. 둘째는 동점이 아니다 |
| `_BlockParser` 에서 `br` 만 경계에서 뺀다 | 둘째를 뿌리에서 닫는다. `_separate()` 를 «블록 태그» 로 좁히는 것 |
| 블록 최소 길이 하한 | 증상만 막는다 — 짧아도 옳은 근거를 같이 버린다 |

**고르기 전에 코퍼스부터 정한다** — 세 안 중 무엇을 골라도 그것이 나은지 잴 자가 지금 없다.
캡·계수는 이 갈림길 밖이다(갈림길 5 와 섞지 않는다).

### 재개 (2026-09-02 리뷰 5) — **자가 한쪽으로만 눈금이 있었다. 갈림길 6 은 아직 안 닫혔다**

백지 패스가 둘을 냈고 둘 다 탐침으로 재현했다. **둘 다 갈림길 6 안이고 다른 축이 아니다** —
리뷰 4 가 연 것을 개발 8 이 절반만 닫았다.

**[R5-1] 안 2 는 «`_separate()` 를 블록 태그로 좁히는 것» 이 아니라 `<br>` 한 태그를 뺀 것이다.**
위 표가 안 2 를 그렇게 적었는데 구현은 `self._separate(tag != "br")` 이다. `_separate()` 를
부르면서 **문단 경계가 아닌** 태그는 `<br>` 말고도 있다 — `_INLINE_TAGS` 에서 빠진 phrasing
태그 전부와 `_SKIP_TAGS` 셋이다. 일곱 모양 중 **여섯이 여전히 한 문단을 조각낸다**:

| 입력 (`extract_blocks`) | 나오는 것 |
|---|---|
| `<p>…대표 음식이다<br>배추로 만든다</p>` | `['…대표 음식이다 배추로 만든다']` ← 개발 8 이 고친 하나 |
| `<p>…대표 음식이다<script>ad()</script>배추로 만든다</p>` | `['…대표 음식이다', '배추로 만든다']` |
| `<p>…대표 음식이다<style>.x{}</style>배추로 만든다</p>` | 둘로 쪼개진다 |
| `<p>…대표 음식이다<img src=k.jpg>배추로 만든다</p>` | 둘로 쪼개진다 |
| `<p>김치찌개는 <del>일본</del><ins>한국</ins>의 대표 음식이다</p>` | **넷**으로 쪼개진다 |
| `<p>김치찌개 <label>이름</label> 한국의 대표 음식이다</p>` | 셋으로 쪼개진다 |
| `<p>김치찌개는 <font color=red>매운</font> 한국 음식이다</p>` | 셋으로 쪼개진다 |

그래서 **개발 8 이 «고쳤다» 고 적은 실패가 `<br>` 을 `<script>` 로 바꾸면 그대로 재현된다.**
`<nav><a>김치찌개 레시피 모음 페이지 바로가기</a></nav><article><p>김치찌개는<script>ad()</script>배추로
만든다</p></article>` → 블록이 `['김치찌개 레시피 모음 페이지 바로가기', '김치찌개는', '배추로 만든다']`
로 갈리고 **내비 링크가 근거로 나온다**. 문단 안의 인라인 광고·트래킹 `<script>` 와 `<img>` 는
실물 HTML 에서 `<br>` 보다 흔하다.

**이 축은 재색인 없이 닫힌다.** 위 «닫지 않은 축» 문단이 `_SKIP_TAGS` 를 미룬 사유로 적은
*"색인 경로와 공유라 손대면 재색인"* 은 **`_INLINE_TAGS` 로 옮길 때만 참이고 `block` 인자로는
거짓이다** — `_TextParser._separate` 는 인자를 문법적으로 안 읽으므로(그것이 개발 8 이 4,128건으로
실측한 성질이다) 넘기는 집합을 넓혀도 `extract_text` 는 한 글자도 안 바뀐다. 위 일곱 모양 전부
불변식 `" ".join(extract_blocks(h)) == extract_text(h)[1]` 을 **7/7 유지**한다(리뷰 5 실측).
고칠 자리는 개발 8 이 이미 만든 기제 그대로다 — `br` 리터럴 자리에 «문단 경계가 아닌 태그» 집합.

### 재측 (2026-09-02 리뷰 6) — **갈림길 6 은 안 닫혔다. 같은 자가 이번엔 「이름표」 쪽으로 기울어 있었다**

**11/11 은 규칙의 실력이 아니라 자의 눈금이었다** — 리뷰 5 가 「길이」에서 잡아낸 것과

**뿌리는 이름표가 «최내곽 태그» 라는 것이다** (실측):


`<footer><p>`·`<aside><p>`·`<nav><li>` 는 실물에서 표준에 가까운 마크업인데 **이름표는
컨테이너를 아예 못 본다.** 그래서 보일러플레이트가 `<p>` 로 싸여 있으면 이름표 규칙은
그것을 **본문으로 승격시킨다** — 길이 규칙이 맞히던 자리다.

**`<p>` 대 `<p>` 동점은 계약으로 굳어 있다.** `tests/test_indexer.py` 의

그 자리가 곧 **본문 앞의 광고 문구·빵부스러기 `<p>`** 다(둘 다 새 8행에서 실패). 개발 8 의
