## 계획이 물은 것 — "예산이 다하면 새 요청이 안 나가는가"

계획 1절의 계약은 **`--deadline` 만료 뒤 새 요청 0건**이었고, 착수 탐침의 오늘 값은
**서버 수신 3건 · 70.08초**였다(`t=0.05 / 30.05 / 60.06` — 예산 2초의 35배).
**재는 자리는 크롤러의 내부 상태가 아니라 서버가 실제로 받은 요청 로그**(`REQUEST_LOG`)다.
"몇 건 안 보냈다" 는 밖에서만 확인되는 사실이라 시나리오 3 은 **CLI 서브프로세스**로 돈다.

값은 이 phase 가 정한 것이 아니라 **스텝 1·2 가 코드에 박아 둔 단언**이고, 여기서는
그것이 초록인지와 여유가 얼마인지를 적는다.

| `deadline_e2e.py` 시나리오 | 단언 | 이번 실측 | 여유 |
|---|---|---|---|
| [0] 대조군 — 예산 없음 | 16페이지 전부 | **16페이지 · 4.1s** | 잣대 |
| [1] CLI 배선 — `--deadline=2` 가 `crawl()` 까지 | < max 20 · 예산 소진 보고 | **8페이지 · 2.1s · `예산 2초 소진 — 8페이지에서 멈춘다`** | — |
| [1] 예절 — 그 요청들의 간격 | 1초 하한 | **최소 1.00s** | 0.00s |
| [2] 실시계 — 떠 있던 응답을 줍는다 | 버려진 응답 **0건** | **저장 8 / 응답 8 · 2.0s · 버려짐 0** | — |
| **[3] 예산 만료 뒤 새 요청 (계획 35)** | 서버 수신 **1건** · rc **0** · ≤ **12.0s** · `수집 0 페이지` · `예산 2초 소진` · DB **0행** | **1건 · rc 0 · 10.1s · 전부 일치** | 건수 0 · 시간 **1.9s** |
| [3] `--control` (페이지가 503 인 세계) | **rc 2** (측정 불능) | **rc 2** — `안 답하는 서버가 받은 페이지 요청 표본이 0개다(필요 1)` | — |

**70.08초 · 3건 → 10.1초 · 1건.** 요청 건수가 계약이고 시간은 파생값이다 — 두 발째는
`Crawl-delay` 만큼(30초) 뒤에 나가므로 건수가 늘면 시간도 같이 죽지만 반대는 아니다.
남은 10.1초는 소켓 읽기(`fetcher.TIMEOUT` 10초) **한 번**이고, 계획 5절이 "안 건드린다"로
명시한 자리다(계획 23 `deadline-patches` 가 일부러 정한 값).

**요청 1건은 예절 단언이기도 하다.** 예산 만료가 `Crawl-delay` 의 예외가 되는 순간
(간격을 깎아 빨리 털고 끝내기) 건수가 늘어 여기서 걸린다 — 계획 5절 "간격·robots·
`Crawl-delay`·1초 하한을 낮추지 않는다"를 이 한 줄이 지킨다.

**`--control` 이 초록의 뜻을 지킨다.** 시나리오 3 의 단언은 전부 "덜 보냈다" 꼴이라
**서버가 안 떠서 0건이어도 참**이다. 페이지를 503 으로 없애면 통과가 아니라 **불능 2**가
난다. 파일 전체에 `--control` 을 주면 시나리오 0 이 먼저 rc 2 로 죽어 이 가드가 실행조차
안 되므로, 시나리오 3 만 따로 세워 확인했다(테스트 phase 와 같은 수법).

**여유가 얇은 것은 이미 아는 항목이다**(`digest.md` `[4]` 의 셋째 자리). `HANG_LIMIT 12.0`
은 예산 2 + 소켓 10 **정확히 그 합**인데 **서브프로세스 기동부터** 재서 실측 10.1초의
여유가 1.9초다. 값을 올리지 않는 이유는 앞의 둘과 같다 — **12초가 곧 계약의 값**이다.
그리고 여기는 흔들려도 **오탐 RED** 다: 진짜 단언인 `len(hits) == 1` 은 시간과 무관하다.
깨지는 날의 답은 값을 올리는 것이 아니라 **시간 단언을 경고로 낮추는 것**이다.
