## 목표

`index_pages()` 의 워터마크 루프(`src/websearch/indexer.py:275-301`)는 재크롤된 문서마다
`DELETE FROM docs WHERE url = ?` 를 한 번 친다. `docs` 는 FTS5 가상 테이블이고 `url` 이
`UNINDEXED` 열이라 **URL 로 지우는 것은 색인 전수 스캔**이다. 값이 「재크롤 집합 ×
코퍼스 크기」로 곱해지므로 코퍼스가 커질수록 갱신 경로 전체가 2차식으로 붇는다.

워터마크 조인(`SELECT d.url, p.html, p.status FROM docs d JOIN pages p …`)은 **이미 그 행을
손에 들고 있다.** 조인에 `d.rowid` 를 얹고 세 `DELETE` 를 `WHERE rowid = ?` 로 바꾸면
전수 스캔이 rowid 조회가 된다(별도 세션 실측 4만 문서 3.35ms → **0.028ms**, 약 1000배).
스키마·마이그레이션 0줄이고, 지우는 대상 집합은 같다.

완료되면 갱신 경로의 문서당 삭제 값이 코퍼스 크기와 무관해진다 — 계획 78 이 「매 실행
17분」 고정비를 지운 것과 같은 모양의 항이 하나 더 사라진다.

## 하지 않을 것

- **신규 색인 질의의 전수 조인**(`indexer.py:224-227` 의 `url NOT IN (SELECT url FROM docs)`)
  — 같은 `ponytail:` 주석이 가리키지만 그쪽 처방은 `docs` 에 색인 상태 열이 필요해
  **스키마 변경**이다. 야간 범위 밖이고 별도 계획이다.
- **`search()` 의 `ORDER BY bm25(docs), rowid` 와 재크롤 문서의 동점 순위**
  (digest 후보 `[4]`) — 이 계획은 삭제의 **열쇠**만 바꾸고 `DELETE`+`INSERT` 관용구
  자체는 그대로 둔다. rowid 가 새로 잡히는 성질은 전과 같다.
- **`pages` 행 삭제** — 404·410 은 지금처럼 묘비로 남긴다(`indexer.py:283-285` 주석).
- **`_insert_doc` · 추출 경로 · 워터마크 판정(`>=`)** — 건드리지 않는다.
- 기존 테스트 리팩터링.

## 설계

- **생략** → 기존 함수의 질의 한 줄에 `d.rowid` 를 얹고 `WHERE` 절 열쇠를 바꾼다.
  새 파일·공개 인터페이스·스키마 변경이 없고 파일 1~2개다. 처방과 그 값은 후보 `[7]` 과
  `indexer.py:239` 주석이 **이미 실측으로 골라 뒀다**(대안이 갈리지 않는다).
  `design.md` 1절 트리거 해당 없음.

**짧은 경로로 가지 않는 이유**: 바꾸는 것이 **삭제의 열쇠**라 틀리면 엉뚱한 행이 지워지는
방향이고(`SKILL.md` 4-1절 「보안·데이터 …와 무관」에 걸린다), 실물 1.37GB DB 가 옆에서
돌고 있다. 형식을 줄이는 대신 **중복 URL 갈래**(아래 스텝 1)까지 테스트로 못박는다.

## 스텝

스텝이 2개인 이유: 고칠 자리가 한 함수의 네 줄이고, 나머지 절반의 일이 **그 변경이
실제로 값을 바꿨는지 재는 것**이라 「구현+단위」와 「규모에서 잰다」로 갈리는 것이 자연스럽다.
셋으로 쪼개면 개수를 채우려 쪼개는 것이다(`plan.md` 3절).

### 1. 워터마크 루프의 삭제 열쇠를 `rowid` 로 바꾼다

- **완료 기준**: 아래 넷이 전부 참.
  1. `src/websearch/indexer.py` 의 워터마크 질의가 `SELECT d.rowid, d.url, p.html, p.status`
     이고 루프 안의 `DELETE` 세 곳이 전부 `DELETE FROM docs WHERE rowid = ?` 다.
     `git grep -n "DELETE FROM docs WHERE url"` 가 **0건**.
  2. **먼저 빨간불을 본다**(TDD): 같은 URL 의 `pages.html` 을 갈고 재색인하면 새 본문이
     검색되고 옛 본문이 안 나온다 · 404 는 `docs` 에서 빠진다 · 뒤늦은 noindex 는 빠진다 —
     기존 `tests/test_indexer.py` 의 갱신·삭제 테스트가 **rowid 열쇠에서도 그대로 초록**이어야
     하므로, 이 스텝이 새로 쓰는 것은 **열쇠가 실제로 rowid 임을 무는 단언**이다:
     같은 `url` 을 가진 `docs` 행이 **둘**인 DB(재구축 경로가 아니면 안 생기지만 FTS5 에
     유일성 제약이 없어 만들 수 있다)에서 재크롤 갱신을 돌리면 **행이 하나씩 갱신되어
     둘 다 새 본문**이 된다. `url` 열쇠에서는 첫 행 처리가 **둘 다 지워** 결과가 1행이라
     이 단언이 빨갛다. (2026-09-11 실물 `docs` 에 중복 URL **0건** — 오늘 잠복이고,
     이 단언은 「열쇠가 무엇인가」를 재는 자다.)
  3. 전수 `PYTHONPATH=src python3 -m unittest discover -b tests` 가 **OK**
     (2026-09-11 기준선 **762**건).
  4. `indexer.py:239` 의 `ponytail:` 주석에서 **닫힌 쪽**(URL 당 `DELETE`)을 지우고
     남은 여는 조건(신규 색인 전수 조인)만 남긴다 — 주석이 이미 고친 것을 가리키면
     다음 사람이 같은 자리를 두 번 연다.
- **건드릴 파일**: `src/websearch/indexer.py` · `tests/test_indexer.py` ·
  `README.md`(계획에 없던 셋째 파일 — `ReadmeCommandsTest.test_verification_counts_match_reality`
  가 단위 건수 762→763 을 강제한다. 계획 76 `[R76-2]` 와 같은 자리라 여기에 적어 둔다)
- **의존**: 없음
- **상태**: 완료 (2026-09-11 · 전수 763 OK)

### 2. 규모에서 값을 잰다 — 1천·1만·4만 문서 before/after

- **완료 기준**: 임시 DB(실물을 건드리지 않는다)에 합성 문서 1천·1만·4만 건을 색인하고
  **재크롤 갱신 1건당 `DELETE` 값**을 옛 열쇠(`url`)와 새 열쇠(`rowid`)로 각각 재서
  `docs/e2e/docs-delete-rowid/result.md` 에 표로 남긴다. 판정은 둘:
  ① 새 열쇠의 문서당 값이 **코퍼스 크기에 따라 늘지 않는다**(4만 / 1천 비율 ≤ 2배).

  잰 명령을 그대로 적어 다음 사람이 재현할 수 있게 한다.
- **건드릴 파일**: `docs/e2e/docs-delete-rowid/result.md` (측정 스크립트는 `/tmp` 에서

## e2e 시나리오

1. 재크롤이 들어온 코퍼스에서 색인을 돌린다 — 사용자가 검색하면 **갱신된 본문**이 나오고
   404 가 된 페이지는 결과에서 사라진다(= 오늘의 동작 그대로). 실물 `data/crawl.db`
   사본에서 `python3 -m websearch.indexer` 를 한 번 돌려 `docs` 행 수와 `GET /search` 의
   응답이 변경 전과 같은지 본다 — **바꾼 것은 값이지 결과가 아니다**를 실물에서 확인한다.
2. 같은 실행의 갱신 경로 벽시계를 스텝 2 의 표와 대조한다.
