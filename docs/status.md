## 이번 반복이 한 것 (개발 4/4 — 리뷰 반려분)

`/passages` 가 요청마다 다시 파싱하는 **입력 크기에 상한을 뒀다.**
`indexer.passages` 가 `extract.extract_blocks(row[0][:MAX_PASSAGE_HTML])` 로 읽는다.
**사용자가 저장소에 승인을 위임했으므로** `rules/severity.md` 3·4절의 사람 게이트는
열린 것으로 보고 진행했다 — 값·자리·단위를 이 반복이 정했고 근거를 아래 남긴다.

### 값과 자리 — 셋을 리뷰 제안과 다르게 정했다

| 결정 | 리뷰 제안 | 이 반복 | 이유 |
|---|---|---|---|
| 값 | 200KB | **100,000** | 아래 실측이 리뷰 표보다 2배 비쌌다 |
| 단위 | 바이트 | **문자** | `pages.html` 은 sqlite 에서 `str` 로 나온다 |
| 자리 | `serve.py` | **`indexer.py`** | `serve` → `indexer` 는 순환이다 |

- **단위가 문자인 이유**: 바이트로 자르려면 `encode` 가 한 벌 더 드는데 그게 바로
  막으려던 그 비용이고, 코드포인트 중간에서 잘린다. 형제 `MAX_PASSAGE` 도 문자다.
- **자리가 `indexer` 인 이유**: `serve` 가 `indexer` 를 import 하므로 반대는 순환이고,
  `python3 -m websearch.indexer --query` 는 `serve` 를 안 지나 상한이 안 걸린다.
  **자르는 쪽이 상수를 갖는다** — `MAX_PASSAGE` 는 `serve` 가 잘라서 `serve` 에 산다.
- **천장**: «잘린 뒤의 문단은 근거로 안 나온다». 그 문서는 **검색에는 그대로 나온다**
  (색인은 통짜 본문을 본다). `ponytail:` 주석에 올릴 조건까지 적었다.

### 직접 잰 값 — 리뷰 표의 2배 비쌌다

`extract_blocks` 1회, 최소값 5회 중(스크래치패드 탐침, 2026-09-02):

| 입력 | 한글(태그 촘촘) | 영문(태그 성김) |
|---|---|---|
| 10만자 | **11.7 ms** (227KB) | 6.3 ms (100KB) |
| 20만자 | 23.6 ms (455KB) | 12.6 ms |
| 250만자 | 301.9 ms (5.7MB) | 156.2 ms |

**비용은 바이트가 아니라 문자와 태그 밀도에 붙는다.** 리뷰의 «257KB → 6.0ms» 는
성긴 마크업 쪽 숫자였고, 촘촘한 한글은 같은 바이트에서 2배다. 그래서 **최악값**
(1,000자당 **0.118ms**)으로 값을 골랐다 — 10만자 × 문서 10건 = **118ms, 예산 500ms 의 24%**.
20만자는 47%라 안 썼다. 이 축을 밟는 실물은 아직 없다(`data/crawl.db` 2행·66바이트).

**대안은 접었다** — `perf_search.py` 에 큰 문서를 얹어 회귀로만 잡는 쪽은 넘긴 **뒤에**
알려준다. 신뢰 경계의 자원 상한은 막는 쪽이 맞고, 코퍼스가 최대 305자라 e2e 로는
이 축이 안 밟힌다. **단위 테스트가 유일한 이빨이다.**

### 변이가 테스트 설계의 구멍을 하나 드러냈다

`.mutation-lock` 아래 셋을 심고 전부 원복(`git diff -- src/` 로 확인 · 커밋된 변이 0):

| 변이 | 결과 |
|---|---|
| W1 자르기 삭제 | **RED** — 캡 뒤 문단이 나온다(`[…] != []`) |
| N1 `- 1` 로 한 글자 좁힘 | **RED** — 경계 문단이 `김치찌` 로 잘린다 |
| W2 값 10만 → 100만 | **살았다 → 새 단언을 세워 RED(1180ms > 125ms)** |

**W2 가 산 이유가 요점이다.** fixture 를 상수에서 만들면(`"봄" * MAX_PASSAGE_HTML`)
**상수와 함께 늘어나 값 변경이 안 보인다.** 기존 형제 상한 테스트도 같은 모양이라
(`test_serve` 는 `serve.MAX_PASSAGE` 를 그대로 쓴다) 값이 예산 밖으로 나가도 초록이다.
그래서 **값 가드**를 하나 더 세웠다 — `MAX_PASSAGE_HTML × PASSAGE_LIMIT × 0.118ms/1,000자`
가 예산의 25% 이내인지 본다. **손잡이가 둘이고 다른 파일에 살아서** 캡을 그대로 두고
`PASSAGE_LIMIT` 만 올려도 예산이 깨지는데, 곱해서 보면 그쪽도 잡힌다.
