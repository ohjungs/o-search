## 2. 이 phase 가 실제로 잰 것 — **실서버 다섯 대를 띄워 상태 코드를 소켓에서 받았다**

본문이 아니라 **상태 코드**라 그 값은 밖에서 재야 참이다(계획 53 e2e 와 같은 논거).

DB 는 임시 디렉터리에서 `store.upsert` → `indexer.index_pages` 로 2문서씩 새로 만들고
사본 쪽만 손으로 부쉈다 — **저장소의 `data/crawl.db` 는 읽지도 않았다**(계획서 7절:
원본 무변경 · 재색인 0). 고장을 만드는 방법은 단위 테스트의 `setUp` 과 같다
(`DROP TABLE pages` 뒤 `html` 없는 스키마로 재생성 — `ALTER TABLE DROP COLUMN` 은
sqlite 판을 타서 안 쓴다).

### 2-1. 다섯 DB 상태 × 다섯 요청 — 판정이 질의 내용에 **안 달린다**

| DB 상태 | `/passages?q=김치찌개` | `?q=zzzznope` | `?q=%01` | `/search?q=김치찌개` | `/?q=…`(화면) |
|---|---|---|---|---|---|
| 정상 (대조군) | 200 · 문단 1건 | 200 `[]` | 200 `[]` | 200 · 1건 | 200 · 결과 그림 |
| **`html` 열 없음** | **500** | **500** | **500** | **200 · 1건** | **200** |
| `pages` 없음 | 503 | 503 | 503 | 200 · 1건 | 200 |
| 옛 색인 + `html` 열 없음 | 503 | 503 | 503 | 503 | 503 |
| `html` 열 없음 + 색인 전 | **500** | **500** | **500** | 200 · 0건 | 200 |

**둘째 행이 이 계획이다.** 착수 실측은 같은 자리에서 **500 / 200 `[]` / 200 `[]`** 였다 —
같은 고장난 DB 가 질의에 따라 «우리가 터졌다» 와 «근거가 없다» 로 갈려 나가던 것이
**세 질의 한 값**으로 모였다. 500 셋의 본문은 전부 고정 문구
`{"version": 1, "error": "검색 중 오류가 났다"}` 다.

**넷째 행이 우선순위를 실서버에서 붙든다.** 「옛 색인」과 「`html` 열 없음」이 겹치면
답은 **503**(색인을 다시 돌리면 낫는 상태)이지 500 이 아니다 — 테스트 phase 가 단위로
못박은 순서(없는 DB → 옛 색인 → 창고 없음 → 열 없음 500)가 HTTP 표면에서도 그대로다.

**셋째 행이 계획 53 의 답이 안 밀렸음을 보인다** — `pages` 가 통째로 없으면 여전히 503 이다.
새 판정이 위 칸을 안 먹었다.

### 2-2. 500 본문이 무엇을 안 흘리나 (완료 기준 3) · 로그에는 남나

경로에 공백과 `#` 을 일부러 넣은 DB(`부서진 창고#1.db`)로 띄워 세 응답 본문을 훑었다.
**11종 전부 안 샌다** — DB 절대경로 · 파일명 · 임시 디렉터리 · `html` · `pages` ·
`SELECT` · `LIMIT` · `OperationalError` · `no such column` · `Traceback` · `sqlite`.

같은 실행의 서버 stderr 에는 **3건 전부** 원인이 남는다:

```
127.0.0.1 - - [04/Sep/2026 23:33:24] /passages 실패: OperationalError('no such column: html')
```

설계 6절의 SRE 판정(«500 은 `serve` 가 이미 로그에 원인을 남기는 경로라 관측성 손실 0»)이
프로세스 밖에서 참이다. 응답에는 없고 로그에는 있다 — 신뢰 경계가 갈린 자리다.

### 2-3. 변이 둘을 **HTTP 표면에서** 다시 죽였다 (완료 기준 8)

개발·테스트·리뷰는 단위 실패 건수로 쟀다. 여기서는 같은 변이를 심고 **소비자가 받는
상태 코드가 어떻게 갈리는지**를 봤다. `src/` 사본을 스크래치패드에 두고 심었다
(`.git` 없는 트리 · `git checkout` **0회** · 저장소 무변).

| 변이 | `q=김치찌개` | `q=zzzznope` | `q=%01` | 「열 없음 + 색인 전」 | 정상 DB 대조군 |
|---|---|---|---|---|---|
| 없음(제품 그대로) | **500** | **500** | **500** | 500/500/500 | 200/200/200 |
| ① 판정 줄 삭제 | 500 | **200 `[]`** | **200 `[]`** | 200/200/200 | 200/200/200 |
| ② 판정 줄을 `hits` 루프 **안**으로 | 500 | **200 `[]`** | **200 `[]`** | 200/200/200 | 200/200/200 |

**착수 때의 갈림이 두 변이 모두에서 글자 그대로 돌아온다.** 계획서 1절이 «판정이 질의
내용에 달렸다» 고 적은 고장을 프로세스 밖에서 다시 본 것이다.

**새로 안 것 하나 — ①과 ②는 관측 표면에서 동치다.** 단위에서 둘 다 `failures=5` 였고
(개발·리뷰 실측), 여기 HTTP 표면에서도 **열다섯 칸이 한 칸도 안 다르다.** 줄을 루프
안에 두는 것은 루프 자신의 `SELECT html … WHERE url = ?` 이 이미 하던 일이라 **줄이
없는 것과 같기 때문**이다. 그래서 「루프 앞에 있다」를 붙드는 것은 ②를 ①과 **가르는**
단언이 아니라, **둘 다 RED 로 만드는** 단언 세 개(무매치·무토큰·색인 전)다. 둘을 가르는
단언은 없고, 있을 필요도 없다 — 어느 쪽이든 계약 위반이다.

「`html` 열 없는 DB 의 `/?q=…` 가 **200 · 결과를 그린다**」를 2-1절에서 실서버로 확인했다 —

RED 를 못 만드는 줄이 생긴다.
