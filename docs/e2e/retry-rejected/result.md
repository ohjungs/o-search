# 결과 — 계획 86 `retry-rejected`

## 1. 결과

```
전수 725 OK rc 0
실물 429 행 3,811개 · is_fresh 전부 False
→ 다음 크롤이 이 3,811개를 다시 받는다 (전에는 15일 대기)
```

## 2. 계획 84 가 남긴 부채였다

계획 84 가 429 를 **더 이상 저장하지 않게** 했다. 그런데 그 전에 박힌 행이 실물 DB 에
**3,811개** 있다(2026-09-09 1만 크롤 · 위키미디어 6도메인). 그 행들은 `status != 2xx` 라
`RETRY_DAYS`(15일) 동안 신선한 것으로 읽혀 재시도에서 빠졌다 —
**받은 적 없는 문서를 15일간 「받았다」로 취급**하는 것이다.

**앞을 막았으면 뒤도 치워야 한다.** 계획 84 는 새로 생기는 것을 막았고 이미 있는 것은
「별건」으로 미뤘는데, 미룬 값이 3,811문서다.

## 3. 지우지 않고 읽는 쪽을 고쳤다

행을 지우는 것은 데이터 삭제라 야간 금지이고, 계획 80 이 정한 「`pages` 는 묘비로
남긴다」와도 충돌한다. 대신 `is_fresh` 에 `status != 429` 한 조각을 넣었다.

**429 는 묘비가 아니다.** 404·410 은 「그 자리에 문서가 없다」는 **사실**이라 15일을
지킬 값이 있고, 429 는 「지금은 안 된다」는 **그 시각의 사정**이다.
사정을 사실처럼 붙들 이유가 없다.

## 4. 반대 방향의 문을 같이 닫았다

「실패는 전부 다시 받는다」로 넓히면 **없는 URL(404)을 매 실행 두드리게** 된다 —
고치려던 것과 **반대 방향의 윤리 문제**다. 그래서 429 만 열고, 404 가 여전히 묘비로
남는 것을 단언으로 못박았다(`test_a_404_row_is_still_a_tombstone`).

한 줄 고칠 때 **넓히는 쪽의 값도 같이 재는 것**이 이 저장소가 여러 번 배운 자리다.
