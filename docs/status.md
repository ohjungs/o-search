## 계획 phase 에서 실측한 것 (반복 82)

`perf_crawl.py` 하네스를 빌리되 **robots 가 페이지 11개 중 6개를 막는 사이트**로 바꿔 쟀다.

| | 처리량 | 요청 없이 태운 쿨다운 | 페이지 최소 간격 |
|---|---|---|---|
| **현재** | **4.48/s** | 팝 120회 중 **72회** | 1.003s |
| 팝 쓰기 제거 + **제출 시점** `mark_sent` | 4.49/s | 0회 | 1.005s |
| 팝 쓰기 제거 + **실제 발신 시각만** | **10.25/s** | 0회 | 1.007s |

**둘을 알아냈다.**

1. **현재 값이 컨셉 성능 2(초당 5문서)를 밑돈다** — 막는 것이 있는 사이트에서 4.48/s.
   `perf_crawl.py` 는 아무것도 막지 않는 사이트만 재서 8일 동안 이걸 못 봤다.
   기준선 10.25/s 는 **막는 것이 없는 세계의 숫자**였다 → 스텝 2가 이 눈을 만든다.
2. **digest 가 적어 둔 답이 아무것도 회수하지 못한다** — "제출 시점 `mark_sent`" 는
   4.48 → 4.49/s. 제출 시점에는 robots 판정이 아직 안 났다(`_fetch_one` 이 워커
   **안에서** 부른다). 회수는 **실제로 나간 요청에만** 시계를 걸어야 나온다.

## 설계가 먼저 닫을 구멍 (008 리뷰의 경고 — 유효하다)

팝 쓰기를 그냥 지우면 워커가 **예외로 끝날 때** `_store_result` 의 `except` 가지가

`mark_sent` 가 `max` 로 늦은 쪽으로만 움직인다.

## 넘지 않는 선 — 어기면 RED

**도메인당 페이지 요청 1.0초 하한과 robots 준수는 어떤 커밋에서도 낮추지 않는다.**
회수는 "안 보낸 요청의 쿨다운을 안 태운다" 로만 얻는다. 간격을 깎아서 얻지 않는다.
그래서 스텝 1은 `frontier.py` 와 `crawl.py` 를 **한 커밋**에 넣는다 — 쪼갠 중간 상태가
계약이 깨진 상태다.
