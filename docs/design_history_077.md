# 설계 102 — 「검색 서버 상주 메모리」를 무엇으로 재나

계획: `docs/plan_history_077.md` · 트리거 둘에 걸렸다 — **새 파일 생성** · **대안 2개 이상 갈림**.

## 0. 재는 대상을 먼저 못박는다

컨셉 **경량 2** 는 「검색 서버 **상주** 메모리 2GB 이하(판정: 100만 문서 색인 로드 후 RSS 측정)」다.
낱말 둘이 설계를 가른다:

- **「서버」** — 측정 프로세스가 아니라 `serve` 프로세스. 색인을 **만드는** 일은 서버의 일이 아니다.
- **「상주」** — 봉우리(peak)가 아니라 지금 붙들고 있는 것.

## 1. 갈래 셋

| | 어떻게 | 판정 |
|---|---|---|
| **A** | `resource.getrusage(RUSAGE_SELF).ru_maxrss` | **버림** |
| **B** | `perf_search.py` 에 세 줄 더한다 (재사용) | **버림** |
| **C** | 진짜 진입점을 자식으로 띄우고 밖에서 `ps` | **채택** |

**A 를 버린 이유 — 틀린 숫자를 낸다.** stdlib 한 줄이라 사다리에서 가장 높지만 `ru_maxrss` 는
**peak 이지 상주가 아니다**. 게다가 같은 프로세스에서 색인을 만들면 그 빌드 할당이 봉우리에
통째로 섞인다. 진짜 `serve` 는 **있는 DB 를 열 뿐 빌드를 안 한다** — 재면 실물보다 크게 나오고,
그 과대평가는 「2GB 안전」을 「2GB 위험」으로 잘못 읽게 한다. **더 게으른 길이 더 틀린 답을
주는 자리다**(사다리는 이해 뒤에 탄다).

**B 를 버린 이유 — A 의 오염을 그대로 물려받는다.** 사다리 2번(이미 있는 것 재사용)이라 제일
먼저 봤다. 그러나 `perf_search.py:92` 는 서버를 **같은 프로세스의 스레드**로 띄운다
(`threading.Thread(target=server.serve_forever)`). 측정 프로세스 = 서버 프로세스라 「서버의
메모리」를 따로 뗄 수 없고, 바로 위에서 `build_index` 가 돈 자리다. **재사용해야 할 것은
파일이 아니라 함수였다** — C 가 `build_index`·`query_paths` 를 임포트해서 쓴다(아래 4절).

**C 를 채택한 이유 — 정의와 측정이 같아진다.** `python3 -m websearch.serve <db> --port 0` 은
README 31번 줄이 사람에게 시키는 그 명령이다. 그것을 자식으로 띄우고 밖에서
`ps -o rss= -p <pid>` 를 읽으면 그 수가 곧 「검색 서버 상주 메모리」다 — 빌드는 부모가 하므로
자식에 안 섞이고, `ps` 의 `rss` 는 peak 이 아니라 **현재** 값이다.

## 2. 네 기준으로 본 C

- **되돌릴 수 있나** — 가장 중요한 축이고 여기서 가장 싸다. 새 파일 하나이고 `src/` 를 0줄
  고친다. 틀렸으면 **파일을 지우면 끝**이다. 제품 경로에 흔적이 없다.
- **더 적게 쓰나** — 의존성 0 을 지킨다(`psutil` 안 쓴다 — 컨셉 「의존성 0 유지」). 새 개념도
  0개다: `perf_crawl`·`perf_search` 가 이미 「임시 DB 를 만들고 재고 숫자를 찍는 측정 스크립트」
  관용구이고 이건 그 다섯 번째다.
- **기존 것과 맞나** — 맞다. `--port 0` 으로 띄우고 **부모가 stdout 첫 줄에서 실제 포트를 읽는
  것**은 `serve.main` 이 이미 그 용도로 만들어 둔 자리다(`serve.py:473` 주석: 「실제 포트를
  찍는다 — `--port 0` 으로 띄우는 e2e·측정 스크립트가 이것을 읽는다」). 0/1/2 관용구도 그대로 쓴다.
- **다음이 편한가** — 자식 프로세스를 밖에서 재는 틀은 나중에 크롤러·색인기 RSS 에도 그대로
  쓰인다. 다만 **지금 그것을 만들지 않는다**(추측성 확장은 감점).

## 3. 가정을 깨 봤다 — 탐침 (커밋 안 함 · 2026-09-15 반복 595)

**가장 위험한 가정**: 「자식 `serve` 의 포트와 현재 RSS 를 밖에서 읽을 수 있다」. 못 읽으면
설계가 통째로 무너지므로 **개발 전에** 밟았다. `/tmp/probe_rss.py` 로 실제로 띄워 재고 지웠다.

| 색인 | 띄운 직후 RSS | 질의 5종 뒤 RSS |
|---|---|---|
| 500 문서 | 17,008 KB | 17,968 KB |
| 4,000 문서 | **17,008 KB** | 18,160 KB |

**읽혔다 — 설계는 선다.** 그리고 탐침이 덤으로 답을 하나 줬다: **색인이 8배가 돼도 띄운
직후 RSS 가 바이트 단위로 같다**(17,008 KB). 질의 뒤 증가분도 960KB → 1,152KB 로, 8배에
192KB 만 더 붙었다.

**왜 그런지가 코드에 이미 적혀 있다** — `serve.py:222` 가 요청마다 `indexer.search(db_path, …)`
를 부른다. **서버는 연결을 상주시키지 않고 요청마다 연다**(`serve.py:8` 주석: 「3% 라 아낄 것이
없다」). 즉 경량 2 의 답은 **구조적으로 이미 정해져 있었고, 오늘 처음 실측으로 확인됐다.**

## 4. 그래서 이 계획이 만드는 값은 「오늘의 숫자」가 아니라 「기울기를 지키는 자」다

숫자가 좋다는 것이 곧 「잴 필요가 없었다」는 뜻이 **아니다**. 값은 **회귀 감지**에 있다 —
누군가 연결을 상주시키거나(`sqlite3.connect` 를 핸들러 밖으로 올리거나) 캐시를 얹는 날,
이 측정이 **평평하지 않게 된다**. 그날이 오기 전에는 아무도 안 본다는 것이 지금 상태다.

**설계 확정**:
- **두 규모**에서 잰다 — 한 규모는 「오늘 얼마」밖에 못 주지만 두 규모는 **기울기**를 준다.
  100만 문서를 못 만드니(60GB) 외삽만 찍고 **합격 판정은 안 낸다**(`perf_search.py` 머리말과 같은 태도).
- **재사용은 함수 단위**: `sys.path` 에 `e2e` 를 넣고 `perf_search` 의 `build_index`·`query_paths`
  를 임포트한다. 색인 만드는 코드를 두 벌로 만들지 않는다.
- **질의 수를 60 미만으로 묶는다.** 자식은 **진짜 진입점**이라 리미터가 켜져 있다
  (`RATE_LIMIT = 60`/분/IP — `serve.main` 은 `rate_limit=None` 갈래가 없다). 넘기면 재는 것이
  메모리가 아니라 **429** 가 된다. `perf_search` 가 `rate_limit=None` 을 쓰는 이유가 그것이고,
  여기서는 끄는 대신 **적게 쏜다**(질의 5종 × 소수 반복). 이건 제약이 아니라 실물 그대로다.

## 5. 거짓 초록을 막는 단언 — RSS 를 읽기 **전에** 건다

계획 101 이 배운 자리다(`\bHTTPServer\(` 가 **0개를 세면서** 통과했다). 여기서 0 을 세는 길은 셋:

1. **자식이 죽어 있다** → `ps` 가 빈 문자열을 낸다. `int("")` 로 죽게 두지 않고 **rc=2(재지 못했다)**.
2. **자식이 200 을 안 냈다**(429·503·500) → 서버가 색인을 한 번도 안 만졌는데 RSS 만 읽는 꼴이다.
   질의마다 200 을 단언한다.
3. **색인이 비었다** → `build_index` 반환값이 0 이면 잰 것은 빈 DB 다. 문서 수를 단언한다.

셋 다 **RSS 를 읽기 전에** 건다. 나중에 걸면 이미 숫자를 손에 쥔 뒤라 「그래도 값은 나왔다」로 샌다.

## 6. 하지 않기로 한 것

- **`ru_maxrss` 를 같이 안 찍는다.** 두 숫자를 나란히 두면 읽는 사람이 큰 쪽을 고른다(=peak).
- **`/proc` 를 안 본다** — macOS 에 없다. `ps -o rss=` 는 darwin·linux 둘 다에서 KB 다.
- **`src/` 를 안 고친다.** 숫자가 나빠도 이 계획은 고치지 않는다(계획서 「하지 않을 것」).
