# 계획 35 — `deadline-stop` (예산 만료가 재시도를 접는다)

- 슬러그: `deadline-stop` · 브랜치: `loop/deadline-stop` (현재 `loop/graceful-interrupt` 에서 판다)
- 상태: **스텝 1·2 완료 — 리뷰 대기** (2026-08-30)
- 근거: `docs/digest.md` `## 다음 계획 후보` `[5]` — "`--deadline` 만료가 `stop` 을 안 쓴다"
  (2026-08-30 계획 34 `graceful-interrupt` 리뷰가 남긴 항목)
- 선행: 계획 34 `graceful-interrupt` DONE — `crawl()`·`_fetch_one()` 이 `stop=` 을 받고
  워커가 `stop.is_set()` 에서 재시도를 접는다. **이 계획은 그 기제를 예산 축에 잇는 것이다.**

## 1. 문제 · 목표 · 기대 결과

**문제.** `--deadline` 은 "예산을 다하면 **새 요청을 안 던지고** 지금까지 저장한 것을
정상 반환한다" 는 계약이다(`crawl.py:126-127` 독스트링 · `docs/design_history_018.md`).
그 계약이 **워커 안에서 깨진다.** 예산이 만료돼도 워커의 재시도는 그대로 나간다.

착수 탐침 실측 (2026-08-30, 아래 2절):

```
--deadline 2 · 안 답하는 서버 · Crawl-delay: 30
  종료까지 70.08초 (예산의 35배)
  서버가 받은 페이지 요청 3건, 수신 시각 t = 0.05 / 30.05 / 60.06
```

**t=2 에 예산이 만료된 뒤 t=30.05 와 t=60.06 에 요청이 두 건 더 나갔다.**
이것은 "늦게 끝난다" 가 아니라 **`--deadline` 의 계약을 직접 어긴 것**이다.
`digest.md` `[5]` 는 이 항목을 "예산에 꼬리가 붙는다(69.57초)" 로만 적었는데,
**꼬리가 아니라 예산 밖에서 나가는 요청이다.**

뿌리는 이 저장소가 이미 두 번 적어 둔 것과 같다 — **"재시도도 요청이다"**
(`crawl.py:56` 독스트링 · `docs/design_history_012.md` 2절, 계획 14 `crawl-politeness`).
계획 14 는 그 사실을 *간격* 축에 적용했고, 이 계획이 *예산* 축에 적용한다.

**목표.** 위 탐침이 **12초 이하**로 끝나고 **서버가 받는 페이지 요청이 1건**이다.
rc·stdout·stderr 는 오늘 그대로다 (rc `0` · `수집 N 페이지` · `예산 N초 소진 — …`).

**기대 결과.** 70.08초 → 10초대. 남는 10초는 **이미 나간 요청의 소켓 읽기**
(`fetcher.TIMEOUT` 10초)이고, 그것을 줍는 것은 계획 23 `deadline-patches` 가
일부러 정한 계약이라 **줄이지 않는다**(6절).

## 2. 실측 — 처방이 절반만 맞았다

`digest.md` `[5]` 가 적어 둔 처방은 **"`main()` 이 예산 만료 시 `stop.set()` 하는
몇 줄이 전부라 값이 싸졌다"** 였다. 착수 때 다시 쟀다(digest `[7]`: 보류 항목의
*진단*은 옳아도 *처방*은 그때의 추정이다). **스크래치패드 사본**(`.git` 없음,
digest `## 반복 실패` 의 제자리 변이 항목)에 세 갈래를 심고 같은 탐침을 돌렸다.

| 심은 것 | 종료 | 서버가 받은 요청 |
|---|---|---|
| (오늘, 무변경) | **70.08초** | 3건 `0.05 / 30.05 / 60.06` |
| 예산 만료 시 `stop.set()` **만** | **70.08초** | 3건 `0.05 / 30.05 / 60.06` |
| `futures.wait` 를 남은 예산으로 자르기 **만** | **70.07초** | 3건 `0.05 / 30.06 / 60.06` |
| **둘 다** | **10.05초** | **1건** `0.05` |

**한 줄씩은 0초를 회수한다. 둘이 한 변경이다.** 이유:

1. `stop.set()` 만으로는 **메인 루프가 그 자리에 도달하지 못한다.**
   `crawl.py:236-238` 의 `concurrent.futures.wait(inflight, timeout=wait_for or None, …)`
   에서 `wait_for` 가 0/`None` 이면 `timeout=None` 이 되어 **워커가 끝날 때까지 잔다**.
   예산 검사는 `while` 머리(`crawl.py:194-198`)에 있는데 거기까지 70초 뒤에야 온다.
   같은 루프의 *다른* 대기 자리(`crawl.py:231` `wait_fn(wait if left is None else min(wait, left))`)
   는 계획 20 이 이미 예산으로 자르고 있다 — **자르기가 한 자리에만 걸려 있었다.**
2. 자르기만으로는 메인 루프가 t=2 에 깨어 빠져나가지만, `with pool` 을 나갈 때
   executor 가 워커를 기다리고 **워커는 `stop` 이 안 서 있어 재시도 앞 30초 잠을
   그대로 잔다**(`crawl.py:93-100`).

**일반화 — "깨우기" 와 "접기" 는 계획 34 에서 나눌 수 없는 하나였고(계획 34 2절 3번),
예산 축에서도 같다.** 34 는 신호 축에서 그것을 배웠고 이 계획은 예산 축에서 되풀이한다.

### 회귀 없음(사본에서 확인)

세 줄을 심은 사본에서 **단위 447건 OK** · `deadline_e2e.py` rc=0 ·
`interrupt_e2e.py` rc=0 · `crawl_delay_e2e.py` rc=0.

**이것이 곧 커버 구멍이다** — 오늘의 447건과 e2e 18종은 이 변화를 **하나도 안 잰다**.
고치기 전과 후가 똑같이 초록이므로, 새 단언 없이 넣으면 **검증되지 않은 변경**이고
누가 되돌려도 조용하다. 스텝 1·2 가 그 단언을 만든다.

### 재현 방법

탐침은 `e2e/interrupt_e2e.py` 의 `hang` 서버와 같은 수법이다 — `Crawl-delay: 30` 을
선언하고 페이지 요청에 답하지 않는 로컬 서버 하나, `--max 5 --deadline 2`,
CLI 서브프로세스, 벽시계와 서버 수신 시각을 잰다. 스텝 2 가 이것을
`e2e/deadline_e2e.py` 의 시나리오로 커밋한다.

## 3. 설계는 생략한다 — 사유

`rules/design.md` 1절 트리거 4개 중 걸리는 것이 없다:

- **사용자 데이터 형태**: DB·스키마 무변경. 저장 경로는 안 건드린다.
- **공개 계약 파괴**: 없다 — rc `0`·stdout·stderr 를 **유지하는 것이 완료 기준**이다
  (스텝 1). 오히려 `stop.set()` 을 순진하게 넣으면 `crawl.py:366`
  `return 130 if stop.is_set() else 0` 때문에 예산 만료가 rc 130 이 된다.
  **그 한 줄을 신호 전용 판정으로 가르는 것이 이 계획의 유일한 계약 작업이다.**
- **의존성**: 0개 추가. stdlib 도 새로 안 쓴다.
- **보안 경계**: 무관.

**대안이 둘이었나** — `digest.md` 가 "예산은 '새 요청을 안 낸다'이고 중단은
'떠 있는 것도 접는다'라 뜻이 갈린다, 그 선택부터 정할 것" 이라고 적었다.
**실측이 갈림길을 지웠다**: `stop` 이 접는 것은 *아직 안 보낸 재시도*뿐이고
(`_fetch_one` 의 `before_send` 진입 검사, `crawl.py:93`), *이미 나간 요청의 응답*은
그대로 줍는다(2절 표의 10.05초가 그 소켓 읽기다). 그러므로 `stop.set()` 은
"떠 있는 것을 버리는" 쪽이 **아니고**, 저장소가 이미 적어 둔 두 문장

> "재시도도 요청이다" (`crawl.py:56`) + "예산이 다하면 새 요청을 안 던진다" (`crawl.py:126`)

에서 **연역된다.** 갈래가 하나라서 설계 phase 가 고를 것이 없다.

## 4. 스텝

의존은 1 → 2 (2 가 1 의 산출물을 실행한다). 두 스텝 다 임계경로다.

### 스텝 1 — 예산 만료가 워커까지 간다 (`src` + 단위) — **완료 (2026-08-30)**

> 제품 11줄(주석 제외 7줄) · 단위 **450건 OK**(447 → +3) · e2e **18종 rc=0** ·
> 변이 4종이 **각각 새 단언 하나씩만** 죽었다 · 탐침 재실측 **70.08 → 10.05초**,
> 서버 수신 **3건 → 1건**, rc **0**.
>
> **단언은 넷이 아니라 셋이다.** 4번(SIGINT rc 130)은 계획 34 가 이미 재고 있고
> M3 을 심어도 그 단언은 안 죽는다 — 새로 쓰면 같은 것을 두 번 재는 중복이다.
> 대신 M4 를 재는 단언(만료를 "예산 소진"으로 보고한다)이 1번과 같은 테스트에 붙어
> 변이 4종은 그대로 하나씩 갈린다.
>
> **한 줄씩은 안 듣는다(2절)는 사실이 단언 설계를 갈랐다.** 벽시계로 종료 시각을 재면
> M1·M2 가 **같이** 죽어 어느 쪽이 빠졌는지 못 가린다. 그래서 1번은 떠 있는 요청이
> **없는** 자리(쿨다운 대기·가짜 시계)에서 신호만 보고, 2번은
> `concurrent.futures.wait` 를 감싸 **잠 자체의 벽시계 길이**를 잰다(2.01초 → 0.2초).

**어디서 시작하나**: `src/websearch/crawl.py`
- `:236-238` `concurrent.futures.wait(inflight, timeout=wait_for or None, …)`
- `:194-198` `left` 계산과 소진 검사
- `:341-366` `main()` 의 핸들러·rc 판정

**무엇이 이미 참인가**: `crawl(…, stop=Event)` 을 받고 워커가 `stop.is_set()` 에서
재시도를 접는다(계획 34, DONE). `main()` 은 이미 `stop` 을 항상 넘긴다(`crawl.py:355`).
`crawl.py:231` 의 잠은 이미 `left` 로 잘린다(계획 20).

**할 일 (세 줄기, 제품 ≈8줄)**
1. `futures.wait` 의 timeout 을 남은 예산으로 자른다 — `crawl.py:231` 과 같은 관용구다.
   `left` 는 여기서 항상 `> 0` 이다(`<= 0` 이면 위에서 이미 빠져나갔다).
2. 예산이 소진된 그 자리에서 `stop.set()` — 소진 분기 안, `interrupted` 판정 **뒤**다.
3. `main()` 의 rc 판정을 `stop.is_set()` 이 아니라 **핸들러가 세우는 신호 전용 플래그**로
   가른다. 예산 만료는 rc `0`, SIGINT 는 rc `130` 이다.

**무엇으로 확인하나 (완료 기준)**
- 단위 447 → **+4건 이상** OK, 새 단언이 각각 아래를 재라:
  - `crawl(stop=Event, deadline=…)` 에서 예산이 만료되면 `stop` 이 **서 있다**
  - `futures.wait` 가 예산보다 오래 잠들지 않는다(주입한 시계·벽시계 둘 중
    **벽시계**로 잰다 — digest `[7]` 두 번째 사례: 기본값 인자는 mock 이 못 본다)
  - `main()` 이 `--deadline` 만료로 끝나면 **rc 0** (신호 없음)
  - `main()` 이 SIGINT 로 끝나면 **rc 130** (오늘의 계약, 회귀 방지)
- 기존 447건 **전부 OK** · e2e 18종 **전부 rc=0**
- 변이 3종이 **각각 새 단언 하나씩만** 죽인다:
  - M1 `stop.set()` 줄 삭제
  - M2 `futures.wait` 자르기 삭제 (`timeout=wait_for or None` 으로 되돌리기)
  - M3 rc 판정을 `stop.is_set()` 으로 되돌리기
  - **M4 `stop.set()` 을 `interrupted` 판정 앞으로 옮기기** — 옮겨도 결과가 같으면
    그 순서를 아무도 안 재고 있다는 뜻이다(계획 34 의 C7d 와 같은 부류)
  - 심기 전 `count(원문) == 1` 을 먼저 단언한다 (digest `[8]`, BSD `sed` 거짓 초록)
  - 변이는 **스크래치패드 사본**(`.git` 없음)에서만 심는다 (digest `## 반복 실패`)

### 스텝 2 — e2e 가 그 값을 잰다 — **완료 (2026-08-30)**

> `e2e/deadline_e2e.py` 시나리오 3 추가(안 답하는 서버 + `Crawl-delay: 30` +
> `--max 5 --deadline 2`, CLI 서브프로세스). 실측: 서버 수신 페이지 요청 **1건** ·

> 파일 전체 rc=0 · 9.7 → **20.3초**(늘어난 10초가 곧 소켓 타임아웃이다).
> `--control` 은 **rc 2**(시나리오 3 만 따로 돌려도 `안 답하는 서버가 받은 페이지 요청
> 표본이 0개다` 로 2).
> 변이 M1(`stop.set()` 삭제)·M2(`futures.wait` 자르기 삭제) 각각에서 **3건 · 80초** 로
> 죽었다(`.git` 없는 사본). 단위 **450건 OK** · e2e **18종 rc=0**(합계 164초).
>
> **건수가 계약이고 시간은 파생값이다.** 두 발째는 `Crawl-delay` 만큼 뒤에 나가므로
> 건수가 늘면 시간도 죽지만 반대는 아니다(느린 기계에서 시간만 흔들린다). 그래서
> 단언 순서를 rc → **건수** → 시간으로 두고 실패 메시지도 건수가 먼저 나오게 했다.
> **`--control` 가드는 파일 전체로는 안 걸린다** — 시나리오 0 이 먼저 2 로 죽는다.
> 그래서 새 가드는 시나리오 3 만 따로 돌려서 확인했다.
> M1·M2 가 **같은 단언으로 죽는다** — 스텝 1 의 단위 단언이 둘을 가르므로(계획서 위)
> 여기서 또 가르는 것은 같은 것을 두 번 재는 중복이다. e2e 는 **밖에서 본 계약**만 본다.

**어디서 시작하나**: `e2e/deadline_e2e.py` (오늘 4시나리오 · 9.7초 · rc=0)

**무엇이 이미 참인가**: 스텝 1 이 커밋돼 있다. `interrupt_e2e.py` 에 그대로 쓸 수 있는
`hang` 서버(`Crawl-delay: 30` + 무응답)와 "서버가 요청을 받은 것을 보고 움직인다" 는
수법이 있다. `deadline_e2e.py` 는 **포트가 도메인**이라는 같은 수법을 쓴다.

**할 일**: 시나리오 하나를 더한다 — *예산 만료 뒤에 요청이 더 나가지 않는다*.
안 답하는 서버(`Crawl-delay: 30`) 하나에 `--max 5 --deadline 2`.

**무엇으로 확인하나 (완료 기준)**
- 종료 **12.0초 이하**(오늘 70.08초) · **rc 0** · stdout `수집 0 페이지` ·
  stderr 에 `예산 2초 소진`
- **서버가 받은 페이지 요청 1건**(오늘 3건) — 이것이 계약 단언이다. 시간은 파생값이고
  **요청 수가 "예산 밖에서 요청이 안 나간다" 를 직접 잰다**
- `--control` 로 세계를 깨면 **rc 2**(측정 불능) — 이 파일의 기존 관례
- e2e 18종 전부 rc=0 유지 · 단위 무회귀
- 되돌리기 변이 2종(M1·M2)에서 이 시나리오가 **죽는다**

## 5. 하지 않을 것

- **`fetcher.TIMEOUT`(소켓 읽기 10초)을 안 줄인다.** 목표 뒤 남는 10초가 전부 그것이고,
  이미 나간 요청의 응답을 줍는 것은 계획 23 `deadline-patches` 가 일부러 정한 계약이다.
  줄이려면 그것은 **다른 계획**이고 `digest.md` `[4]`(Ctrl-C) 와 같은 수술이다.
- **간격·robots·`Crawl-delay`·1초 하한을 낮추지 않는다.** 이 계획이 하는 것은
  *재시도를 접는 것*이지 *빨리 보내는 것*이 아니다. 접었는데 남은 요청이 더 빨리
  나가면 RED 다(7절).
- **`deadline=None` 경로를 안 건드린다.** 예산을 안 주면 오늘과 한 줄도 다르지 않아야
  한다 — 계획 20 이 정한 "기본값이 꺼진 플래그" 계약이다.
- **`stop=None` 경로를 안 건드린다.** `crawl()` 을 직접 부르는 호출자는 오늘 그대로다.
- **`--deadline` 만료의 rc·메시지를 안 바꾼다.** 130 으로 바뀌면 `crawl && indexer`
  파이프라인이 끊긴다.
- **DB·스키마 무변경**, `data/crawl.db` 실물 무접촉.
- `digest.md` `[6]`("다른 스킴의 큰 선언이 워커를 더 오래 붙든다")를 **닫았다고 적지
  않는다.** 그 항목은 `--deadline` 을 준 경우에만 완화되고, 안 준 경우는 그대로다.

## 6. 한도 (넘으면 RED)

- 도메인당 요청 간격 1초 이상 · robots.txt `Crawl-delay` 준수. **예산 만료 중에도 그렇다.**
  스텝 2 의 실측 단언(요청 1건)이 이것을 함께 지킨다 — 요청이 2건 이상 나오면
  간격을 확인하기 전에 이미 계약 위반이다.
- 기존 단언을 **낮추지 않는다.** 시간 상한을 올려 초록을 만드는 것은 실패다.
- 외부 네트워크 금지 — 로컬 테스트 서버만.
- `docs/specs/` 쓰기 금지 · `--no-verify` 금지 · `main` 직접 커밋 금지.
