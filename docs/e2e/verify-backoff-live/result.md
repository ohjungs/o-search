# 결과 — 계획 87 `verify-backoff-live` — 실물 서버로 84·86 을 확인한다

**코드 0줄.** 오늘 고친 것이 **실제 서버에서** 듣는지만 본다. 로컬 목이 아니라
어제 429 를 쏟아낸 바로 그 도메인들이다.

## 1. 첫 시도는 요청이 한 건도 안 나갔다 — 그것이 발견이다

429 를 받았던 위키미디어 6도메인을 시드로 주고 `--max 300`:

```
수집 0 페이지 · 14 도메인 · 0.0초 = 0.00 문서/초
```

**시드 부모가 신선해서(200 · 30일 이내) 팝 지점에서 스킵됐고, 링크 추출이 없으니
429 자식이 큐에 못 들어온다.** `store.py` 의 ponytail 주석이 이미 적어 둔 한계다:

> *"`RETRY_DAYS` 는 오늘 시드에서만 닿는다. 프런티어가 메모리라 매 실행 시드에서 다시
> 자라는데, 부모가 신선하면 팝 지점에서 스킵돼 링크 추출조차 안 일어나 자식이 큐에
> 못 들어온다. 여는 조건은 프런티어 영속화다."*

**계획 86 의 수정은 필요했지만 충분하지 않다** — 429 행을 「안 신선」으로 읽게 만들어도
그 URL 이 **큐에 들어올 길이 없으면** 아무 일도 안 일어난다. 86 을 닫을 때 이 축을
안 봤다. 실물 한 번이 그것을 잡았다.

## 2. URL 을 직접 시드로 주니 듣는다

429 행 6개를 DB 에서 뽑아 그대로 시드로:

```
수집 6 페이지 · 2.8초
429 행 3,811 → 3,807
```

| 결과 | 건수 | 뜻 |
|---|---|---|
| **200 으로 회복** | **4** | 계획 86 의 수정이 실제로 듣는다 |
| 다시 429 | 2 | **덮어쓰지 않고 그대로 남았다** — 계획 84 가 의도한 동작 |

**두 계획이 함께 옳게 동작한다**: 86 이 재시도를 열고, 84 가 또 거절당하면 안 박는다.

## 3. 그래서 남은 것 — 도달 가능성은 별개 축이다

3,807개 중 대부분은 **부모가 신선한 동안 큐에 못 들어온다.** 오늘 회복된 것은
직접 시드로 준 6개뿐이다. 처방은 셋 중 하나다:

1. **프런티어 영속화** — `store.py` 가 적어 둔 정답. 큐를 DB 에 두면 실행이 끊겨도
   남고 부모 신선도와 무관해진다. 가장 크고 가장 옳다.
2. **미완 URL 을 시드로 자동 편입** — `pages` 에서 「안 신선한」 행을 뽑아 시드에 더한다.
   작지만 시드의 뜻이 흐려진다(시드는 사람이 고른 출발점이다).
3. **아무것도 안 한다** — 부모가 30일 뒤 낡으면 자연히 다시 걷힌다.

**오늘은 3번이다.** 1번은 새 저장 구조라 별도 계획이고, 2번은 개념을 흐린다.
30일 안에 프런티어 영속화를 하면 1번이 2·3번을 다 대체한다.

## 4. 이 계획이 남긴 것

**로컬 목으로만 확인한 수정은 절반만 확인한 것이다.** 계획 84 는 로컬 429 서버로
백오프 곡선(2→4→8→16초)까지 봤고 그건 옳았다. 그런데 **그 수정이 실제 코퍼스에서
발동할 수 있는지**는 다른 질문이었고, 답은 「대부분 아니다」였다.
