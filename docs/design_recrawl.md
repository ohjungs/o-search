# 설계: 재크롤 — 신선도 술어 하나와 워터마크 루프 한 번의 확장

## 결정

**새 구조를 안 만든다.** 재방문은 `store` 에 술어 **하나**를 더해 `crawl.py:250` 이
`has` 대신 그것을 묻고, 갱신·삭제는 계획 78 이 이미 만든 **워터마크 루프 안**에서
`p.status` 열 하나를 더 들고 판정한다. 스키마·마이그레이션 0줄, 새 파일 0개.

## 대안 비교 — 출발점 셋

| | A. 최소 (안 만든다) | **B. 술어 + 루프 확장** | C. 되돌리기 우선 (플래그) |
|---|---|---|---|
| 재방문 | 사람이 DB 를 지우고 다시 돌린다 | `store.is_fresh(url)` | 같음 + `--recrawl` 옵트인 |
| 갱신·삭제 | 통째로 재구축 | 워터마크 루프 안 | 같음 + 플래그 뒤 |
| 코드 | 0줄 | `src/` 세 파일 소폭 | B + 플래그 배선 |
| 되돌리기 | 해당 없음 | 상수 둘을 크게 | 플래그 끄기 |

**A 를 버린 이유** — 사양 기능 5 는 「30일 **이내에**」라는 자동 주기를 요구하고 기능 3 은
「사람 개입 없이」다. DB 를 지우면 크롤 예산·간격을 처음부터 다시 치른다(실측 400장 109초
→ 10만 환산 **7.6시간**). 그리고 **삭제 반영은 흉내조차 못 낸다** — 지운 DB 에는 404 를
받았다는 사실이 없다.

**C 를 버린 이유는 「되돌릴 것이 이미 없다」다.** TTL 이 30일이라 실물 코퍼스(2026-09-07
수집, 30일 초과 **0건**)는 **10월 7일까지 요청을 한 건도 더 안 보낸다** — 이 기능은 켜는
순간 잠들어 있다. 플래그는 그 30일 동안 아무것도 안 지키면서 죽은 갈래 하나를 남긴다
(`project.md` 「죽은 플래그가 쌓인다」). 되돌리기는 플래그가 아니라 **상수 둘**이 준다 —
`FRESH_DAYS` 를 크게 잡는 것이 곧 끄는 것이고, 그건 한 줄이다.

## 계약

### 1. 신선도는 SQLite 가 잰다 — 시계는 하나다

```sql
SELECT 1 FROM pages WHERE url = ? AND fetched_at >= datetime(
    'now', CASE WHEN status BETWEEN 200 AND 299 THEN ? ELSE ? END)
```

`store.upsert` 가 `datetime('now')`(UTC)로 박으므로 **읽는 쪽도 같은 시계여야 한다.**
파이썬 시계를 쓰면 타임존·해상도가 어긋나 비교가 조용히 틀린다 — 계획 78 이 그 자리에서
실제로 한 번 빨개졌다(`indexer.py:201`). 질의 하나·왕복 하나·시계 하나다.

**바인딩까지 실제로 돌려 확인했다** (`datetime()` 수식어와 `CASE` 에 파라미터가 붙는가):

| 행 | 판정 |
|---|---|
| 31일 된 `200` | 낡음 → 다시 받는다 |
| 29일 된 `200` | 신선 → 안 받는다 |
| 16일 된 `404` | 낡음 → 다시 받는다 |
| 14일 된 `404` | 신선 → 안 받는다 |
| DB 에 없는 URL | 낡음 → 받는다 (`has` 가 False 이던 자리와 같다) |

### 2. `store.has` 는 안 건드린다 — 호출자 둘의 뜻이 다르다

`crawl.py:250` 은 「이 URL 을 **지금 받을까**」고 `crawl.py:337` 은 「리다이렉트 도착지가
**이미 저장됐나**」다. 한 함수로 합치면 뒤쪽 의미가 조용히 바뀐다. 술어를 **더한다**.

낡은 리다이렉트 도착지가 여기서 안 갱신되는 것은 손실이 아니다 — 그 URL 자체가
프런티어에 있으면 제 차례에 낡음으로 판정돼 다시 받는다.

> **반복 474 리뷰가 이 절의 뒷문단을 뒤집었다.** 「그 URL 자체가 프런티어에 있으면」이
> 조건문인 것이 문제였다 — 프런티어는 메모리라 매 실행 시드에서 다시 자라므로,
> **리다이렉트로만 닿는 URL 은 프런티어에 영영 안 들어온다.** 그러면 낡은 도착지의 새
> 본문을 **받아 놓고 버리고**, 출발지는 `pages` 에 안 남아 다음 실행이 같은 요청을 또
> 보낸다(탐침으로 재현). 그래서 `crawl.py` 의 그 자리도 `is_fresh` 를 묻는다 —
> **함수를 합친 것이 아니라 물음을 고친 것이다.** 「방금 저장한 것」은 여전히 신선해서
> 막히므로 한 실행 안의 중복 방지는 그대로다. `store.has` 는 이제 호출자가 0곳이지만
> 지우지 않는다(야간 금지: 파일·데이터 삭제 아님, 다만 공개 표면 축소라 사람 몫).

### 3. 갱신·삭제는 워터마크 루프 안에서, 이 순서로

루프의 집합(`p.fetched_at >= mark` 인 `docs`⋈`pages`)이 **정확히 「다시 받아 온 색인 문서」**
라 두 기능이 같은 자리에 산다. `SELECT` 에 `p.status` 한 열을 더한다.

| 순서 | 조건 | 처분 | 왜 |
|---|---|---|---|
| 1 | `status` 가 404·410 | `DELETE FROM docs` | 「없어졌다」의 표준 표현. `pages` 는 **안 지운다**(묘비) |
| 2 | `html IS NULL` | 그대로 둔다 | 5xx·`status 0`·비 HTML — **일시 장애를 영구 삭제로 만들지 않는다** |
| 3 | `is_noindex(html)` | `DELETE FROM docs` | 오늘 동작 그대로 (크롤 윤리) |
| 4 | 그 밖 | `DELETE` 후 재추출·`INSERT` | 갱신. `docs` 는 FTS5 라 지우고 넣는 것이 이 저장소의 관용구다 |

**2번은 오늘 잠복한 크래시를 막는 줄이다.** `is_noindex()` 첫 줄이 `html_text.lower()` 라
**`None` 이면 `AttributeError`** 인데, 이 루프의 `SELECT` 에는 `html IS NOT NULL` 이 없다.
오늘 안 터지는 이유는 `html` 이 NULL 이 되는 유일한 길이 **재크롤**이고 그게 아직 없어서다
— 이 계획이 그 길을 여는 순간 터진다. 순서상 2번이 3번보다 **앞**이어야 하는 이유다.

### 4. 갱신·삭제는 워터마크가 **있을 때만** 돈다

`mark` 가 없으면(옛 DB 의 첫 실행) 오늘처럼 전수 noindex 스윕만 하고 지나간다.

**근거가 되는 불변식**: `store.upsert` 는 언제나 `fetched_at=datetime('now')` 를 박는다.
따라서 **내용이 바뀌었으면 `fetched_at` 이 올라간다** — 워터마크 이전 문서는 안 바뀐 것이
보장된다. 재추출할 이유가 없다.

**값으로 재면 이 문이 계획 78 을 지킨다** (실물 코퍼스 60문서 실측):

| | 문서당 | 10만 환산 |
|---|---|---|
| `is_noindex` 만 (오늘 전수 스윕) | 10.70ms | 17.8분 |
| 재추출 + bigram (갱신) | **23.81ms** | **39.7분** |

전수에서 무조건 재추출하면 계획 78 이 35배로 줄인 고정비가 **두 배로** 돌아온다.

### 5. 반환 계약은 안 바꾼다 — 천장을 적어 둔다

`index_pages()` 는 계속 **신규 색인 수**만 센다. CLI 의 `removed = before + indexed - after`
(`indexer.py:467`)는 그대로 맞는다 — 갱신은 `DELETE`+`INSERT` 라 문서 수가 안 움직이고,
삭제는 줄어든 만큼 정확히 `removed` 로 나온다.

**고칠 것은 그 옆 문구 하나**다: `"%d 문서 색인 제외 — noindex 선언"` 이 404 삭제에는
거짓말이 된다.

**천장 — 갱신 건수는 아무도 안 센다.** 세려면 반환 계약을 바꿔야 하고 호출자가 **10파일
65곳**이다. 밤에 그 리팩터링을 열지 않는다. 올리는 법: 재크롤이 실제로 도는 날(빨라야
30일 뒤)에 `IndexResult(indexed, updated, removed)` 로 올린다.

### 6. TTL 상수는 `store` 에 산다

`pages` 를 아는 모듈이 하나고 판정이 그 표 위의 SQL 이라 자리가 거기다.

```python
FRESH_DAYS = 30   # concept.md 기능 5
RETRY_DAYS = 15   # 실패는 절반 — 죽은 URL 을 성공과 같은 빈도로 두드리지 않는다
```

`project.md` 에 값을 인용해 `ProjectConstTest` 가 코드와 대조하게 한다.

## 이 설계가 못 하는 것

- **연속 실패 백오프** — `pages` 에 실패 횟수를 둘 열이 없고, 더하면 스키마 변경이다.
- **내용이 안 바뀐 재크롤의 재추출 회피** — 해시 열이 필요하다(스키마). 지금은 다시 받은
  문서를 무조건 재추출하고, 그 집합은 크롤 예산이 이미 묶어 둔다.
- **`docs` 에 없는데 `pages` 만 낡은 문서의 재방문 우선순위** — 프런티어 순서는 안 건드린다.
  재크롤은 기존 큐 정책·예산·간격을 그대로 쓴다(크롤 윤리가 갈림길 1순위).
