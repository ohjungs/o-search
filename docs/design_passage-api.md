`has_next`·`page` 는 **응답에 없다**(페이지네이션을 안 연다 — 계획 5절).
문단당 `MAX_PASSAGE = 2000`자에서 자른다 — `MAX_QUERY`·`MAX_PAGE` 와 같은 자리의
자원 상한이다. 자르면서 질의어가 잘려 나가면 **정확도가 떨어지는 것이 정직하다**(안 보정한다).

**상한이 하나 더 있다 — `indexer.MAX_PASSAGE_HTML = 100,000`자**(개발 4, 리뷰 반려분).
`MAX_PASSAGE` 는 **응답 바이트**를 자르지 재파싱 **CPU** 를 안 자른다. 문서당 앞
10만자만 다시 파싱한다: 실측 최악(태그가 촘촘한 한글) 1,000자당 **0.118ms** 이고
`PASSAGE_LIMIT` 10건이면 **118ms — 예산 500ms 의 24%**(20만자는 47%라 안 썼다).
단위는 문자다(`pages.html` 은 sqlite 에서 `str` 로 나온다). 자리는 `indexer` 다 —
`serve` → `indexer` 가 import 방향이라 반대는 순환이고, CLI 질의는 `serve` 를 안 지난다.
**천장: 잘린 뒤의 문단은 근거로 안 나온다**(그 문서는 검색에는 그대로 나온다).

## 갈림길 1 — 문단을 어디서 얻나 → **A 원본 재파싱**

| 안 | 출발점 | 판정 |
|---|---|---|
| **A `pages.html` 재파싱** | 정공법 | **고른다.** 블록 경계가 원문에만 있고, 원문은 이미 DB 에 있다 |
| B 표식 색인 | 되돌리기 우선 | **접는다.** `body` 를 바꾸면 **전체 재색인**이다 — 계획 5절이 사람에게 올리라고 못박은 수술 |
| C 문자 창 | 최소 | **접는다.** 사양의 «문단» 을 «창» 으로 바꿔 읽는 것이다(계획 7절 위험 1번) |

**A 는 새 코드가 아니라 이미 있는 파서의 부산물이다.** `_TextParser._separate()` 가
블록 경계마다 이미 불리고 있고, 그 경계를 버리는 것은 `_normalize` 의 `split()` 뿐이다.
그래서 **`_TextParser` 를 한 줄도 안 고치고 하위 클래스로 끊는다** — `_separate()` 에서
지금까지 모은 것을 `_normalize` 해 블록으로 밀어내고 버퍼를 비운다.
색인 경로는 "같은 결과" 가 아니라 **안 지나간다**(회귀 위험 0).

**실측(2026-09-02 탐침, 스크래치패드)**

| 잰 것 | 값 |
|---|---|
| 불변식 `" ".join(blocks) == body` | 합성 13종 중 **12 참** · 코퍼스 64문서 **64/64 참** |
| 유일한 위반 | **블록 전체가 제어문자**일 때. 통짜 정규화가 겹공백을 남긴다(`'가  나'`) |
| 파싱 비용 (17.6KB) | `extract_text` 1.63ms → `extract_blocks` **1.83ms** (+12%) |
| 코퍼스 문서당 블록 | min 3 · avg 4.0 · max 4 |
| 검색+선택 (질의 40개, 인프로세스) | p50 **0.6ms** · p95 **0.7ms** — 예산 500ms 의 0.14% |
| 문단 채택률 | ko **199/200** · en **199/200** (각 99.5%) |
| 버린 둘 | `맛집`(한글 2-gram 이 블록을 가로질러 매치) · `tuples`(porter 가 `tuple` 로 매치) |

위반 한 줄은 `ponytail:` 주석으로 천장을 적고 **현 동작 그대로 테스트에 고정**한다 —
고치려면 `_normalize` 를 바꿔야 하고 그것이 색인을 바꾼다.

**`passages()` 는 `search()` 를 부른다 — 자체 질의를 짜지 않는다.** 그러면 503·500 판정과
옛 색인 검사를 **한 벌 더** 갖게 되고 계획 47 이 한곳에 모은 것이 다시 흩어진다.
대신 `pages.html` 을 읽으려 `_connect` 를 한 번 더 연다 — open+close **0.04ms**(설계 46 실측).

## 갈림길 2 — 파라미터 → **`_parse` 를 재사용하고 넓히지 않는다**

문단 수는 **서버 상수**(`PASSAGE_LIMIT = 10`)다. 사양 성능 5가 *"못 지키면 문단 수를
줄이지, 예산을 늘리지 않는다"* 라고 **서버 손잡이**로 못박았다 — 클라이언트가 돌리는
손잡이면 예산이 클라이언트 손에 있는 것이 된다.
`page` 는 `_parse` 가 이미 검증하므로 **받되 `1` 이 아니면 400** 이다. 조용히 무시하면
페이지를 넘기는 소비자가 같은 문단을 영원히 받는다.

## 갈림길 3 — 위치의 표기 → **블록 인덱스 하나**

문자 오프셋은 **거짓 정밀도**다. `docs.body` 는 응답에 없으므로 소비자가 오프셋을
맞춰 볼 원문이 없다. 순번은 *"이 문서의 N번째 문단"* 이라 문단 텍스트와 함께 뜻이 산다.
둘 다 내는 것은 쓰지도 않을 필드를 계약에 박는 것이다(계약은 지우기가 제일 비싸다).

## 갈림길 4 — 측정기 → **새 파일 `e2e/passage_eval.py`**

`quality_eval.py` 는 **한 글자도 안 고친다**(recall 숫자가 매달린 도구다).
코퍼스·질의 JSON 도 **동결 그대로 읽는다**. 새로 하는 것은 **HTML 포장**뿐이다 —
`quality_eval` 은 본문 전체를 `<p>` 하나로 감싸서 **문서당 블록이 1개**라 문단을 잴 수 없다.
`passage_eval` 은 같은 본문을 문장 단위 `<p>` 로 감싼다. **색인 본문은 64/64 바이트 동일**
(실측) — 마침표를 남기고 끊으면 정규화 뒤 같은 문자열이다. 같은 색인이라 채택률을
recall 옆에 놓고 읽을 수 있다.

**정확도 100% 는 기본값이다** — 고르는 규칙과 판정 규칙이 같은 술어라 그렇다.
그래서 숫자를 **둘** 찍는다: 사양 기능 8이 요구하는 **정확도**(≥90%, 미달 rc 1)와
실제로 움직이는 **채택률**(실측 99.5%, 기록만). 가드가 이 도구의 이빨이다 — 종료 **2**:
문단 총 0건 · 문서당 블록 < 2 · 반환 문단이 문서 본문과 통째로 같음 · 코퍼스/질의 수 미달.

**p95 는 HTTP 로 잰다**(사양 성능 5는 API 예산이다). `--port 0` 서버를 띄워 `perf_search`
와 같은 형태로 돈다. **주의 두 줄을 `project.md` 에 함께 적는다**: 코퍼스가 64문서라
FTS 축은 `perf_search`(3000문서 p95 8.90ms)가 재고 있고, 코퍼스 문서가 작아
**문서 크기 축은 이 숫자에 안 들어 있다**(18KB×10건 재파싱 = 탐침 실측 20.8ms).

## 안 고치는 것 (범위 밖)

`_TextParser`·`_normalize`·`search()`·`_send`·`_send_html`·화면 경로 · `/search` 스키마 ·
`quality_eval.py` · 코퍼스·질의 JSON · 스키마·`data/crawl.db` · 속도 제한 · 문서당 2문단 이상.

## 스텝 경계 — 계획의 3스텝 그대로

스텝 1이 `extract.py`+`indexer.py` 두 파일이지만 **산출물은 하나**(문단을 돌려주는 함수)라
노드 하나다. `extract_blocks` 만 있고 `passages` 가 없으면 검증할 것이 불변식뿐이고,
그 불변식은 «문단이 나온다» 를 안 보인다.

## 변이 표 — 여덟을 심는다

| # | 심는 변이 | 죽어야 하는 단언 |
|---|---|---|
| M1 | `_separate` 의 버퍼 비우기 삭제 | 불변식 `" ".join(blocks) == body`(블록이 누적된다) |
| M2 | `extract_blocks` 의 마지막 flush 삭제 | **깨진 HTML**(`<p>가<p>나<div>다`)의 마지막 블록 |
| M3 | 블록 마커를 `_normalize` 경로에 넣는 안으로 되돌림 | 기존 `test_extract.py` 본문 단언 — **대조군** |
| M4 | 매치 없는 문서에 첫 블록을 대신 낸다 | «매치 없는 문서는 안 낸다» 단위 **둘** (`passage_eval` 은 **안 죽인다** — 아래) |
| M5 | `position` 을 빈 블록 포함으로 센다 | 빈 `<p>` 가 낀 fixture 의 위치 값 |
| M6 | `page != 1` 거절 삭제 | `?page=2` 가 400 |
| M7 | `_send` 를 안 쓰고 직접 JSON 을 쓴다 | 모든 응답에 `version` — **대조군**(계약 물려받기) |
| M8 | `MAX_PASSAGE` 자르기 삭제 | 2,000자 넘는 블록의 응답 길이 |
| W1 | `MAX_PASSAGE_HTML` 자르기 삭제 | 캡 뒤에만 있는 문단이 안 나온다는 단언 |
| N1 | 캡을 한 글자 좁힘(`- 1`) | 캡 끝에 걸친 문단의 마지막 글자 |
| W2 | 캡 값 10만 → 100만 | **값 가드**(캡 × `PASSAGE_LIMIT` × 실측 계수 ≤ 예산 25%) |

**W2 는 처음에 살아남았다 (2026-09-02 개발 4 실측).** fixture 를 상수에서 만들면
(`"봄" * MAX_PASSAGE_HTML`) **상수와 함께 늘어나 값 변경이 안 보인다** — 기존 형제 상한
테스트도 같은 모양이라 같은 눈먼 자리를 갖는다. 값 가드를 세운 뒤에야 RED(1180ms >
125ms)가 났다. **메커니즘을 붙드는 단언은 값을 안 붙든다** — 손잡이는 따로 재야 한다.

M2 는 정상 HTML 에서는 닫는 태그가 flush 를 대신해 **살아남는다** — 그래서 깨진 HTML
케이스를 테스트에 반드시 넣는다(탐침에서 `<p>가<p>나<div>다` 가 `['가','나','다']` 였다).

**전수 재확인 (2026-09-02 테스트 phase, `.mutation-lock` 아래 제자리 · 전부 원복 ·
`git diff -- src/` 0줄).** 여덟 전부 RED. M2 는 위 예고대로 **깨진 HTML 케이스 단 1건**만
죽였고, M3·M7 은 **대조군이 제 일을 했다**(M3 은 기존 `TestExtractText` 8건 — 색인 경로를
지킨다 · M7 은 `TestPassagesSchemaVersion` — 계약 물려받기).

**M4 의 «passage_eval 정확도 하락» 은 근거가 아니라 관측 기록이다.** M4 를 심고 러너를
돌린 실측: 정확도 100.0% → **99.5%**, 채택률 99.5% → **100.0%**, **종료 코드는 그대로 0**
(합격선 90% 를 못 건드린다). 즉 러너는 M4 를 **안 죽인다** — 죽이는 것은 `TestPassages`
둘(`test_document_with_no_matching_block_is_not_returned` ·
`test_bigram_match_that_only_crosses_a_block_boundary_is_not_a_passage`)이고 표를 그렇게
고쳤다. 갈림길 4 가 *"정확도 100% 는 기본값이라 이빨은 가드에 있다"* 고 적은 것이 여기서
실물이 됐다 — **사양 숫자는 회귀를 못 잡는다. 잡는 것은 단위와 종료 2 다.**

**갈림길 4 의 «`wrap` 의 단언이 매 실행 확인한다» 는 틀렸다** (같은 phase 실측).
`" ".join(wrap(b)) == b` 는 `split(". ")`/`join` 의 **대수적 항등식**이라 어떤 본문에도
참이고, 그래서 **G7 은 닿을 수 없다**(합성 12종 · 코퍼스 64/64 · 무작위 2만종 위반 0건).
두 도구가 같은 것을 색인한다는 근거는 이 가드가 아니라 **«색인 본문 64/64 바이트 동일»
실측** 쪽이다. 가드는 값이 0이라 남겼고 근거는 `tests/test_passage_eval.py` 가 든다.
