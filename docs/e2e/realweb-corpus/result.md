# e2e: realweb-corpus — 실물 코퍼스로 후보 셋을 판정했다

2026-09-07. 코퍼스는 `data/crawl.db`(gitignore) — **남는 것은 코퍼스가 아니라 여기 적힌 숫자다.**

## 0. 어떻게 받아 왔나

```
python3 -m websearch.crawl \
  https://docs.python.org/3/library/index.html \
  https://developer.mozilla.org/en-US/docs/Web/HTML \
  https://en.wikipedia.org/wiki/Search_engine \
  https://ko.wikipedia.org/wiki/%EA%B2%80%EC%83%89_%EC%97%94%EC%A7%84 \
  --max 400 --same-site --workers 4 --deadline 900
→ 수집 400 페이지 · rc 0 · 109초
```

**초당 3.67장은 4 도메인 × 1초 간격의 이론 상한(4/s)에 붙은 값이다** — 예절을 지키면서
낼 수 있는 최대다. `perf_crawl` 의 기준선(10.25/s)이 「아무것도 안 막는 사이트」에서 잰
숫자라는 digest `[8]` 의 지적이 여기서 실물로 확인됐다: **실제 세계의 천장은 도메인 수다.**

| | 값 |
|---|---|
| 수집 | 400 / 400 · 전부 200 · 시드 도메인 밖 **0건** |
| 도메인 | docs.python.org 107 · developer.mozilla.org 105 · ko.wikipedia 97 · en.wikipedia 91 |
| HTML 크기 | 중앙값 **159,008 B** · 최소 11,006 · 최대 1,134,205 |
| 색인 | **361 문서** (13.4초) · DB 78MB → 100MB |
| 본문 글자수 | 중앙값 **13,560** · 평균 21,404 · 최대 180,299 |

**색인에서 39건이 빠진 것은 결함이 아니다** — 전부 ko.wikipedia 의
`?action=edit&redlink=1` 편집 폼이고 위키백과가 `noindex` 를 보낸다.
**`noindex` 처리가 실물에서 처음 발동해 옳게 걸렀다**(그전엔 합성 e2e 에서만 돌았다).

## 1. 블록 분포 — 합성이 못 보여 준 것

```
페이지당 블록 수 — 중앙값 335 · 최소 34 · 최대 2522
태그 상위 li 119708 · p 25087 · div 9698 · dt 7446 · td 4996 · summary 3276 · th 2939 · h2 2269
```

**`li` 가 `p` 의 4.8배다.** 합성 코퍼스 64건은 `p` 중심이라 이 축이 아예 없었다.
후보 `[8]` 이 「내비가 본문을 이긴다」고 말한 그 재료가 실물에는 5배로 깔려 있다.

## 2. 후보 [8] — 열렸다. **기록보다 문제가 크다**

질의 10개(ko·en 섞음) · 근거 문단 73건에서 뽑힌 블록의 태그:

| p | h1 | div | li | td |
|---|---|---|---|---|
| 30 | 15 | 14 | 12 | 2 |

**본문 문단은 41.1% 뿐이고 58.9% 가 비-본문이다.** 실제로 뽑힌 것들:

- `<li>` 「검색 엔진 범주 하위 문단 토글하기」 ← **UI 컨트롤 라벨**
- `<div>` 「3.3 어린이 안전 검색 엔진」 ← **목차 줄**
- `<h1>` 「검색 엔진 마케팅」 ← 다른 문서의 제목

digest 는 이것을 `<template>`·`aria-hidden` 같은 **숨은 텍스트** 문제로 적어 뒀는데,
실물의 주범은 숨은 것이 아니라 **보이지만 본문이 아닌 것**(목차·내비·제목)이다.
**진단이 좁았다** — 처방을 짤 때 `_SKIP_TAGS` 확장으로는 목차·내비가 안 잡힌다.

## 3. 후보 [9] — 열렸다. **결론이 뒤집혔다**

질의 10개 × 5회 = 표본 50.

| | p95 | 중앙값 |
|---|---|---|
| `search` | **15.56 ms** | 6.62 ms |
| `passages` | **43.37 ms** | 37.41 ms |

**`/passages` 총 p95 중 `/search` 몫은 35.9% 다 — 「대부분」이 아니다.**
고유 비용 27.81ms 가 검색 15.56ms보다 크다. 기록된 결론은 질의어가 문서마다 수천 번
반복되는 **합성 코퍼스가 만든 것**이었다. 「거래를 재려면 양쪽을 같은 자로 재라」가
성능 축에서도 그대로 걸렸다.

**그리고 지금은 문제가 아니다** — concept 예산 대비 `search` **5.2%** · `passages` **8.7%**.
이 축은 코퍼스가 훨씬 커진 뒤에 다시 연다.

## 4. 후보 [6] — 열렸다. **「지울 후보」가 「아직 안 쓴 축」으로 뒤집혔다**

비-p 로 뽑힌 43건 중, **같은 문서 안에 질의어를 담은 `<p>` 가 실제로 있던 것이 38건(88.4%)**.

```
[검색 엔진] 뽑힌 것 <h1> '검색 엔진 마케팅'
      같은 문서의 <p> '검색 엔진 마케팅(Search engine marketing, SEM)은 주로 유료 광고를 통해…'
```

`extract_blocks` 의 이름표는 합성에서 **동점 깨기 3순위로도 한 번도 안 걸려** 값이 0으로
측정됐고, 그래서 「지울 후보」로 등재돼 있었다. 실물에서는 **좋은 블록과 나쁜 블록을
가르는 바로 그 축**이고 실패의 88.4% 가 그것으로 회수 가능하다. **지우지 않는다.**

## 4-1. ⚠ 정정 — 위 88.4% 는 틀린 자로 잰 값이다 (2026-09-07 계획 74 스텝 1)

4절의 스크립트는 **캡 없이 전체 HTML** 을 파싱하고 `<p>` 가 질의어를 **담기만** 하면 셌다.
실제 선택기는 `MAX_PASSAGE_HTML` **35,000자 앞부분만** 파싱하고 **점수로** 고른다.
**같은 자로 다시 재면 숫자가 이렇게 바뀐다:**

| 비-`p` 픽 43건 중 | 건수 |
|---|---|
| 캡 **안**에 점수>0 인 `<p>` 가 있다 | **3** |
| └ 그 `<p>` 가 현행 픽을 **점수로도 이긴다** | **0** |
| 캡 **밖**에만 있다 | **35** |
| 아예 없다 | 5 |

**그래서 4절의 결론(「이름표는 아직 안 쓴 축」)은 성립하지 않는다.** 선택기가 보는
범위 안에서 규칙을 바꿔 봐야 문서 3~8건만 달라진다(`p` 2순위 1건 · `p` 하드 게이트 3건 ·
헤딩 배제 8건). **이름표는 여전히 할 일이 거의 없는 축이다.**

**진짜 축은 캡이었다** — 아래 4-2절.

**교훈은 내가 4절에 인용해 둔 그것이다** — 「거래를 재려면 양쪽을 같은 자로 재라」.
인용해 놓고 **이득만 느슨한 자로 쟀다.** 자를 맞추는 것은 인용이 아니라 배선이다.
2절의 문장도 같은 결함을 지난다: 「목차·`<h1>` 이 이긴다」가 아니라 **그것밖에 없었다.**

## 4-2. 진짜 축 — `MAX_PASSAGE_HTML` 35,000 대 실물 중앙값 159,008

**실물 페이지의 92%(370/400)가 캡에 잘린다.** 위키백과·MDN 은 앞 35KB 가 `<head>`·
내비·목차라 **선택기가 본문에 닿지도 못한다.**

| 캡 | 근거 건수 | 본문 `p` | 문서당 파싱 |
|---|---|---|---|
| **35,000 (현행)** | 73 | **41.1%** | 4.8ms |
| 100,000 | 95 | 67.4% | 8.0ms |
| 300,000 | **98** | **80.6%** | 14.6ms |
| 무제한 | 98 | 80.6% | 16.1ms |

**300K 와 무제한이 같은 결과**라 실질 천장은 300K다. 값은 두 갈래로 온다:
① 목차 대신 본문 문단 ② **근거를 아예 못 내던 문서 25건이 산다(73 → 98).**
후자가 더 크다 — 「틀린 근거」가 아니라 **「근거 없음」이 결과의 25.5%** 였다.
