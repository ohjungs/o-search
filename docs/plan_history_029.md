# 계획 43 — `focus-contrast`

**키보드 사용자에게만 보이는 색이 하나 있는데, 검사기가 그 색을 구조적으로 못 본다.
라이트 테마의 포커스 링은 흰 배경에서 2.80:1 이다 — 재기 시작하면 바로 빨간불이다.**

- **슬러그**: `focus-contrast`
- **브랜치**: `loop/focus-contrast`
- **기점**: `96eea95` (현재 HEAD, `loop/docs-citation-guard`)
- **phase**: 설계 (트리거 걸림 — 4절)
- **스텝**: 1개

**기점 주의**: PR #4(계획 38~41) 병합 후 `origin/main` 기점으로 체리픽이 필요하다.
`origin/main` 기점으로 열면 계획 42 가 만든 `DocCitationTest` 가 없어 이 계획서
자신이 인용 검사를 못 받는다.

## 1. 문제 · 목표 · 기대 결과

**문제.** `src/websearch/serve.py` 의 CSS 는 키보드 포커스 링을 이렇게 그린다:

```css
.sb input:focus-visible,.sb button:focus-visible,a:focus-visible{
  outline:3px solid var(--focus);outline-offset:2px}
```

`outline-offset:2px` 라 링의 바깥쪽 이웃 색은 언제나 `--bg-page` 다.
그 대비를 **저장소 자신의 측정 함수**(`e2e/design_check.contrast`)로 재면:

| 테마 | `--focus` | 이웃 | 실측 | WCAG 2.1 SC 1.4.11 (3:1) |
|---|---|---|---|---|
| 라이트 | `#f97316` | `--bg-page` `#ffffff` | **2.80:1** | **미달** |
| 다크 | `#fdba74` | `--bg-page` `#141110` | 11.14:1 | 통과 |
| 다크 | `#fdba74` | `--bg-input` `#1e1917` | 10.32:1 | 통과 |

**라이트 테마에서만 깨져 있다.** 그리고 이 값은 마우스 사용자에게 아예 안 보이는 색이라
눈으로 발견될 수 있는 자리가 아니다 — 재는 기계 말고는 볼 사람이 없다.

**그 기계가 이 토큰을 구조적으로 못 본다.** `e2e/design_check.check_contrast` 의
커버리지 강제는 접두어로 걸러 낸다:

```python
declared = {k for k in set(light) | set(dark) if k.startswith("--fg-")}
missing = declared - {fg for fg, _ in PAIRS}
```

`--focus` 는 `--fg-` 로 시작하지 않으므로 `declared` 에 안 들어가고, `PAIRS` 에도 없다.
**검사기는 이 토큰이 존재한다는 것조차 모른 채 "4축 전부 통과" 를 낸다**(실측 rc 0).
`serve.py` 의 CSS 위 주석이 규약을 *"`--fg-` 토큰을 새로 만들면 `PAIRS` 에도 짝을 적어라"*
로 적어 뒀는데, 규약이 접두어에 걸려 있어 접두어 밖의 토큰은 규약 자체가 안 덮는다.

계획 13 `search-ui` 리뷰가 이 검사기의 눈먼 자리 **4곳**을 찾아 닫았고, 그중 세 번째가
*"`PAIRS` 커버리지 강제가 라이트 맵만 봐서 다크에만 있는 `--fg-` 토큰이 그냥 빠져나갔다"*
였다(`docs/project.md ## 명령` 의 디자인 검사 절에 실측이 남아 있다). **이번 것은 그
구멍의 형제다** — 그때는 *어느 맵을 보나* 가 틀렸고, 이번은 *어느 이름을 보나* 가 틀렸다.
`digest ## 다음 계획 후보` 의 `[7] 살아남은 변이가 등가 변이가 아니라 형제 구멍일 때가
있다` 가 말하는 그 형태다.

**목표.** ① 라이트 포커스 링을 기준 위로 올린다. ② 색을 다시 재지 않고 지나갈 수 있는
길을 막는다 — **접두어 허용 목록을 명시적 제외 목록으로 뒤집어**, 앞으로 선언되는 어떤
색 토큰도 짝이 없으면 검사기가 종료 2(측정 불능)를 내게 한다.

**기대 결과.** `PYTHONPATH=src python3 e2e/design_check.py` 가 `[3]` 절에 비텍스트 대비
행을 새로 찍고 **rc 0**. 고치기 전에는 같은 명령이 **rc 1** 로 라이트 2.80:1 을 지목한다.
단위 **469건 OK** 무변(제품 변경은 CSS 색값 한 개다).

## 2. 근거

- **출처**: `docs/specs/concept.md` 의 `## 프로젝트에서 "잘 됐다"는 것` 디자인 3축 —
  *"텍스트 대비 4.5:1 이상, 키보드만으로 검색·결과 이동 가능"*. 사양은 루프가 고치지
  않는 읽기 전용 문서이고, **사양과 어긋나면 사양이 맞다**(`rules/discover.md`).
- **착수 실측**: 위 1절의 표. 저장소 자신의 `design_check.contrast` 로 쟀고,
  `design_check.token_maps` 가 `--focus` 를 라이트·다크 양쪽에서 실제로 파싱한다는 것
  (`#f97316` / `#fdba74`)까지 확인했다 — 새 축은 기존 파서 위에 얹힌다.
- **왜 지금까지 안 걸렸나**: 커버리지 강제가 `--fg-` 접두어에만 걸려 있다. 즉 이것은
  "아직 안 한 일" 이 아니라 **초록불이 근거 없이 켜져 있던 자리**다.

## 3. 스텝

**1개다.** 검사를 넣으면 그 자리에서 rc 1 이 되므로 검사와 색 교정을 가르면 첫 커밋이
RED 로 남는다(`rules/develop.md` 가 금지한다). 계획 42 스텝 1 과 같은 형태다.

### 스텝 1 — 비텍스트 대비 축과 뒤집은 커버리지 강제 (의존: 없음)

**시작 자리**: `e2e/design_check.py` 의 `MIN_CONTRAST` · `PAIRS` · `check_contrast` ·
`main` 의 `[3]` 출력 절. `contrast`·`luminance`·`token_maps`·`self_check` 는 **그대로
재사용한다** — 새로 만드는 것은 짝 목록과 임계값뿐이다(ponytail 2번).

**할 일**

1. 비텍스트 짝 목록과 임계값을 더한다. 짝은 실제로 인접하는 것만 적는다 —
   `--focus` 는 `outline-offset` 때문에 링 바깥이 언제나 `--bg-page` 다.
2. **커버리지 강제를 접두어 허용에서 명시적 제외로 뒤집는다.** 선언된 토큰 중
   어느 짝에도 안 나오는 것이 있으면 종료 2. 예외는 코드 안 상수에 이름과 **이유**를
   적은 것만(`--line` — 순수 장식 테두리). 그러면 앞으로 만드는 토큰은 이름이 무엇이든
   짝을 적거나 제외 사유를 적어야 통과한다.
3. 그 상태로 검사를 돌려 **rc 1 과 라이트 2.80:1** 을 눈으로 확인한다.
4. 라이트 `--focus` 값을 교정한다(설계가 고른 값). 다크는 **안 건드린다** — 11.14:1 로
   이미 통과이고, 손대면 통과하던 축을 이유 없이 흔드는 직교 편집이다(카파시 3번).
5. 검사를 다시 돌려 rc 0. 단위 스위트와 나머지 e2e 로 회귀를 확인한다.

**완료 기준 (실행해서 확인)**

- `PYTHONPATH=src python3 e2e/design_check.py` → **rc 0**, `[3]` 절에 비텍스트 행
  (라이트·다크 각 1)이 실제 값과 함께 찍힌다. 라이트 값이 임계값 이상이다.
- 고치기 **전에** 같은 명령이 **rc 1** 이고 라이트 `--focus` on `--bg-page` **2.80:1**
  을 지목하는 것을 봤다.
- `PYTHONPATH=src python3 -m unittest discover tests` → **469건 OK**(무변).
- `PYTHONPATH=src python3 e2e/quality_eval.py` rc 0 · `e2e/perf_search.py` p95 예산 안.
- `sha256 data/crawl.db` 무변경.
- `git diff --stat` 의 파일이 `e2e/design_check.py` · `src/websearch/serve.py` ·
  (필요 시) `README.md` 뿐이다.

**변이 (검사가 진짜 잡는지)** — `PYTHONDONTWRITEBYTECODE=1` 을 붙여 돌린다. 심기 전에
원문이 실제로 바뀌었는지 먼저 단언하고, revert 는 `&&` 로 잇지 않는다
(`digest ## 다음 계획 후보` 의 `[8] 변이가 실제로 심어졌는지를 먼저 단언한다`, 2회).

## 4. 설계 트리거 — 걸린다 (건너뛰지 않는다)

`rules/design.md` 1절의 **"대안이 2개 이상 갈림 — 어느 쪽이든 동작하지만 결과가 다름"**
에 걸린다. 갈림길이 둘이고, 둘이 서로를 가른다.

**갈림길 A — 임계값.** WCAG 2.1 SC 1.4.11 의 **3:1**(비텍스트 UI 지시자) 대 저장소가
이미 쓰는 `MIN_CONTRAST` **4.5**(SC 1.4.3, 텍스트). 사양이 "**텍스트** 대비 4.5:1" 이라
적었으므로 비텍스트에 4.5 를 요구하는 것은 사양보다 센 요구다.

**갈림길 B — 교정할 색.** 실측(저장소 함수, `--bg-page` `#ffffff` 기준):

| 후보 | 흰 배경 대비 | 버튼(`--bg-button` `#c2410c`) 위 | 비고 |
|---|---|---|---|
| `#f97316` (현재) | 2.80 | 1.85 | 3:1 미달 |
| `#ea580c` | 3.56 | 1.45 | 3:1 통과 · 4.5 미달 |
| `#c2410c` | 5.18 | **1.00** | 버튼색과 동일 — 링이 버튼에 묻는다 |
| `#9a3412` | 7.31 | 1.41 | 양쪽 다 통과 |

A 를 3 으로 고르면 B 는 `#ea580c` 로 족하고, 4.5 로 고르면 `#9a3412` 여야 한다.
**한쪽을 고르면 다른 쪽이 정해진다** — 그래서 개발 중 즉흥으로 내릴 결정이 아니다.
설계는 `docs/specs/concept.md` 의 우선순위(디자인은 갈림길에서 가장 낮다 — 즉 디자인
취향으로 접근성 기준을 깎지 않는다)를 근거로 스스로 고른다. 사용자에게 묻지 않는다.

## 5. 하지 않을 것

- **다크 테마의 어떤 값도** — 세 짝 전부 10:1 이상으로 통과다. 통과하는 축을 이유
  없이 건드리는 것은 직교 편집이다.
- **`--line` (1.34:1)** — 순수 장식 테두리(구분선·입력창 테두리)다. 입력창을 UI
  컴포넌트 경계로 보면 3:1 요구가 붙는다는 해석이 있지만, 그 판단은 이번 근거
  (사양 3축 · 포커스 링 실측)에 들어 있지 않다. **뒤집은 커버리지 강제의 제외
  상수에 이름과 사유를 적어 두는 것**으로 끝내고, 판단은 `digest` 후보로 넘긴다.
- **"키보드만으로 이동 가능" 의 나머지 절반** — 폼은 GET 이고 결과는 순수 앵커라
  플랫폼이 그냥 해 준다(ponytail 4번). `tests/test_serve.py` 의
  `test_form_is_get_so_keyboard_alone_works` 와 autofocus 단언이 이미 그 계약을 잡고
  있다. 재는 것이 없는 자리에 검사를 새로 만들지 않는다.
- **`design_check` 의 나머지 3축** — 전부 통과 중이고 이번 근거와 무관하다.
- **단위 테스트 추가** — 대비는 검사기가 **실제 응답 바이트**에서 CSS 를 읽어 매번
  다시 계산하는 것이 이 저장소의 계약이다(계획 13 설계의 갈림길 2). 단위에 색값을
  적으면 검사기가 값을 따로 드는 것과 같아져, 색을 고쳐도 옛 값으로 통과가 난다.
- **`serve.py` 의 CSS 규약 주석을 넘어서는 리팩터링** — 접두어를 말하던 문장 한 줄은
  강제가 뒤집히므로 그 줄만 맞춘다.

## 6. 건드릴 파일 (예상)

| 파일 | 무엇 |
|---|---|
| `e2e/design_check.py` | 비텍스트 짝 목록·임계값·출력 행 추가, 커버리지 강제 뒤집기 (~20줄) |
| `src/websearch/serve.py` | 라이트 `--focus` 값 1개 + CSS 위 규약 주석 한 줄 |
| `README.md` | `## 품질 기준` 표의 명암비 행에 비텍스트 축을 적을지는 개발 시 판단 (`tests/test_readme.py` 가 강제하는 범위 안에서만) |

여기 없는 파일을 고쳐야 하면 **YELLOW** — 계획이나 설계가 틀렸다는 뜻이다.

## 7. 이 계획이 틀렸다면 어디서 드러나나

- **설계가 4.5 를 고르는데 브랜드 오렌지 계열에 4.5 를 넘기면서 버튼과 구별되는 색이
  없다면** — 그때는 색이 아니라 `outline-offset`·두께 쪽 대안이 필요하고, 그것은
  이 계획의 범위(색값 하나)를 넘는다. 설계 phase 에서 YELLOW 로 멈춘다.
- **M3(맵 하나만 보기)이 M1 과 겹쳤는데도 초록이 나오면** — 새 축이 계획 13 이 닫은
  구멍을 다시 팠다는 뜻이다. 그 자리에서 축을 다시 짠다.
