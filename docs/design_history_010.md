# 설계: tokenizer — 한글 bigram 열 + porter

## 결정

`docs` FTS5 테이블에 **한글 문자 2-gram 전용 열 둘(`title_ng` · `body_ng`)** 을 더하고
토크나이저를 `porter unicode61` 로 바꾼다. 질의는 **전부 한글일 때만** bigram 구절
분기를 `OR` 로 덧붙인다. 기존 `title`/`body` 열과 어절 접두 매치는 그대로 둔다.

## 대안 비교

출발점을 셋으로 갈라 냈다 — ① 최소(있는 것으로) ② 정공법 ③ 되돌리기 우선.

| | A. `porter` 만 (최소) | B. `trigram` (정공법) | **E. bigram 열 + porter** | F. 형태소 분석기 |
|---|---|---|---|---|
| recall@10 **실측** | 36/40 | **27/40** | **39/40** | 미측정 |
| 코드량 | 1줄 | 2줄 | 약 25줄 | 라이브러리 + 사전 |
| 되돌리기 | 쉬움 | 쉬움 | 쉬움 (스키마 되돌리면 재구축) | 어려움 |
| 색인 크기 (3000문서 실측) | 1.3 MB | 미측정 | **3.1 MB (2.4배)** | — |
| p95 (OFFSET 990, 실측) | 5.5ms | — | **6.6ms** | — |
| 의존성 | 없음 | 없음 | 없음 | **추가** |

**선택: E** — 유일하게 한국어 3건을 전부 매치시킨다. SQLite 내장 기능(FTS5 열·구절
질의·bm25)만 쓰고 새 의존성이 없다.

**버린 이유**
- **A** — 한국어 3건을 하나도 못 고친다. E 안에 포함돼 있다(E 도 `porter` 를 쓴다)
- **B** — `trigram` 은 3자 미만 질의에서 토큰을 0개 만든다. fixture 한국어 질의
  20개 중 **10개가 2자**라 매치가 통째로 사라져 35/40 → **27/40 으로 후퇴**한다.
  실측으로 버렸다
- **F** — `concept.md` 경량 3(신규 의존성) 위반이고 야간 보류 항목이다.
  E 로 20/20 이 나온 이상 열 이유가 없다

## SQLite 요구 버전

**추가 요구 없음.** FTS5 열 추가·구절 질의·`porter` 는 FTS5 최초 버전(3.9.0)부터 있다.
`trigram` 은 3.34.0+ 를 요구했지만 **버렸으므로 그 요구가 따라오지 않는다.**
(측정 환경 `sqlite3.sqlite_version` = **3.51.0**, Python 3.9.6)

## 가정 — 깨본 결과

**"bigram 열을 더해도 기존 계약이 그대로다."** → **거짓이었다. 설계를 고쳤다.**

`snippet(docs, -1, …)` 은 **매치된 열 중 가장 왼쪽**을 고른다. 한글 bigram 으로만
매치된 문서는 `title`/`body` 가 매치되지 않으므로 `title_ng` 가 선택되어
사용자 화면에 이런 것이 나온다 (탐침 실측):

```
보관법 → 김치 치찌 찌개 개보 [보관 관법] 법을 을검 검색 색하 하면 …
```

`tests/test_indexer.py:194 test_snippet_comes_from_matching_column` 이 지키는 계약
("제목만 매치되면 제목에서 스니펫")도 `-1` 에 기대고 있어 열을 고정할 수도 없다.
→ **아래 계약의 스니펫 절이 이 발견의 결과다.**

두 번째 가정 **"색인이 감당할 만큼만 커진다"** → 참. 3000문서에서 1.3→3.1 MB(2.4배),
`OFFSET 990` p50 5.39→6.50ms. 컨셉 성능 1(300ms)에서 멀다.

## 계약 — 개발이 지킬 것

```python
SCHEMA = ("CREATE VIRTUAL TABLE IF NOT EXISTS docs "
          "USING fts5(title, body, title_ng, body_ng, url UNINDEXED, "
          "tokenize='porter unicode61', prefix='2 3')")
```

1. **bigram 생성** — 한글 사이 공백만 지우고(`올레 길` → `올레길`) 한글 런의
   문자 2-gram 을 공백으로 이어 붙인다. 한글이 없으면 빈 문자열.
   `title_ng` 는 제목에서, `body_ng` 는 본문에서 **따로** 만든다.
   *열을 나누는 것이 핵심이다* — 하나로 합치면 정답이 12건 뒤 꼴찌로 밀린다(탐침 실측:
   순위 13/13). 나누면 제목·본문 양쪽에서 매치돼 **가중치 조정 없이 1위**가 된다.
2. **질의 재작성** — `_fts_query(query)` 는 (2026-08-27 리뷰로 고쳤다, 아래 사유)
   - 제어문자 제거 → 어절 분리 → **어절마다** 한 덩이를 만들고 ` AND ` 로 잇는다
   - 어절에 bigram 이 나오면
     `("어절"* OR {title_ng} : "가나" + "나다" OR {body_ng} : "가나" + "나다")`
   - bigram 이 안 나오면(1자 한글·비한글 어절) `"어절"*` 그대로
   - **어절 단위여야 한다.** 처음에는 어절을 모두 붙인 뒤 "전부 한글일 때만" 한 번에
     bigram 분기를 걸었다. 그러면 그 분기가 어절이 문서에 **그 순서로 붙어 있을 때만**
     살아서 `냉장 보관법`·`올레길 안내`·`7코스 올레길` 이 **0건**이 됐다(리뷰 실측).
     어절마다 갈라 두면 AND 가 구조적으로 유지되므로 "전부 한글" 조건 자체가 사라진다
   - **두 열을 `{title_ng body_ng}` 하나로 묶지 않는다** — 1번과 같은 이유가 질의
     쪽에도 걸린다. 묶으면 한국어 포함률이 20/20 → **17/20**(정답이 13위로 밀린다)
3. **스니펫** — `snippet(docs, -1, …)` 을 버리고 **0번(title)·1번(body) 두 번** 부른다.
   구분자로 `"\x02"` 를 넘기고, 제목 스니펫에 그 문자가 있으면 제목을, 없으면 본문을
   쓴 뒤 문자를 지운다. `extract._normalize` 가 색인 텍스트에서 제어문자를 지우므로
   `\x02` 는 본문에 **절대** 들어 있지 않다(`src/websearch/extract.py:16,60`).
   → `search()` 반환 형태 `(url, title, snippet)` 은 **그대로**다
4. **랭킹** — `bm25(docs)` 를 가중치 없이 그대로 쓴다. 마법 상수를 넣지 않는다
5. **스키마 드리프트** — `index_pages()` 는 `sqlite_master.sql` 이 `SCHEMA` 와 다르면
   `docs` 를 DROP 하고 재생성한다. `pages` 는 건드리지 않는다.
   `search()` 는 드리프트를 만나면 조용히 빈 목록을 내지 말고 **명시적으로 실패**한다

## 되돌리기

스텝 2 커밋만 revert 하면 된다. `docs` 는 `pages` 에서 파생된 색인이고,
스텝 1 의 드리프트 재구축이 옛 스키마로도 **자동으로 되돌려 준다** —
revert 후 `index_pages()` 한 번이면 원래 색인이다.

## 범위 밖 (digest 후보)

- **`loaf` ↔ `loaves`** — 영어 불규칙 복수. `porter` 가 `loav`/`loaf` 로 가른다
- **색인 2.4배** — 천장. `prefix='2 3'` 이 bigram 열에도 걸려 낭비가 있는데
  FTS5 는 prefix 인덱스를 열별로 끌 수 없다. 실물에서 디스크가 문제되면
  bigram 을 별도 테이블로 빼는 것이 다음 칸이다
- **띄어쓰기 없는 영어·일본어·중국어** — 한글(`가-힣`)만 본다
