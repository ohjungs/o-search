# 결과 — 계획 84 `backoff-429`

## 1. 실물 확인 — 백오프가 실제로 벌어진다

429 만 내는 로컬 서버에 URL 8개를 준다:

```
페이지 요청 5건 · 간격: 2.0s → 4.0s → 8.0s → 16.0s
127.0.0.1: 32초 간격을 요구해 상한 30초를 넘는다 — 이 도메인은 더 가지 않는다
수집 0 · pages 행 0   ← 429 는 안 박혔다
```

**8개 중 5번만 보내고 손을 뗐다.** 고치기 전이었다면 8번 다 보내고 8행을 박았다.
전수 **719 OK rc 0**.

## 2. 근거 — 오늘 남의 서버에 실제로 피해가 갔다

1만 문서 크롤 실측. 위키미디어 6도메인이 응답의 **50~68%(총 3,686건)** 를 429 로
거절하는데도 같은 간격으로 계속 보냈다. 첫 429 는 크롤 시작 **44초** 만이었다.

원인은 예의를 **호스트명** 단위로 지킨 것이다. 여섯이 같은 IP(`103.102.166.224`)라
호스트마다 1초를 지킨 것이 **한 서버에 초당 6건**이 됐다 — 컨셉의 *"도메인당 요청
간격 1초 이상은 기능이 아니라 전제 조건"* 을 **글자로는 지키고 뜻으로는 어겼다.**

## 3. IP 로 묶지 않았다

CDN 뒤에서는 무관한 사이트 수천 개가 한 IP 를 쓴다. IP 로 묶으면 남남인 사이트들이
한 예산을 나눠 쓰게 되어 **더 나쁘다.** DNS 는 바뀌고 라운드로빈이면 실행마다 답이 다르다.

**429 백오프는 왜 429 인지 몰라도 옳다** — 원인이 공유 인프라든, 우리 IP 가 미운털이든,
그 시각의 부하든 처방이 같다. 서버가 유일하게 신뢰할 수 있는 정보원이다.

## 4. 새 기계를 안 만들었다

`frontier.set_delay` 는 이미 **단조 증가**이고 `MAX_DELAY`(30초)를 넘으면 도메인을
통째로 버린다. 429 백오프가 필요로 하는 것이 정확히 그 동작이다 —
**물러나다가 도저히 안 되면 손을 뗀다.** 2·4·8·16·32 로 다섯 번이면 상한을 넘는다.

## 5. 되돌리기를 안 한다 — 두 번 확인한 판단

처음에는 429 받은 URL 을 `frontier.add` 로 되돌리려 했다. **실측으로 그것이 조용히
무효임을 알았다** — `add` 가 `_seen` 으로 중복을 막는다.

**우회해서 되돌리는 편이 낫지도 않았다.** 서버가 방금 「너무 잦다」고 한 URL 을 같은
실행에서 다시 치는 것은 물러나는 것이 아니다. 저장을 안 했으므로 `is_fresh` 가 거짓이라
**다음 실행이 자연히 다시 받는다.** 안 하는 것이 곧 처방인 자리였다.

## 6. 테스트가 시계에서 두 번 미끄러졌다

① **멈춘 시계**로 짜니 도메인 쿨다운이 영영 안 풀려 요청이 한 번 나가고 끝났다 —
백오프가 쌓이는 것을 못 쟀다. ② 고치려고 `now()` 를 **부를 때마다** 흐르게 하니
프런티어 내부 조회까지 시간을 밀어 테스트가 **무한히 돌았다**(300초 타임아웃).

셋째 판이 맞았다 — **읽기는 공짜, 발신만 60초.** 재는 대상이 시계가 되지 않게 하는 것이
요령이고, 계획 78·82 가 각각 시계 해상도와 모의 크롤에서 배운 것의 세 번째 칸이다.

## 7. 남은 것 — 등재만 한다

`pages` 에 이미 박힌 **429 행 3,686개**는 지우지 않는다. 데이터 삭제이고 계획 80 이
정한 「`pages` 는 묘비로 남긴다」와 충돌한다. 재크롤이 다시 받게 두면 자연히 갈리지만
지금 정책으로는 **15일**이 걸린다 — 그 기간을 429 에 한해 줄일지는 별건이다.
