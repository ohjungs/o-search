# e2e 결과 — search-ui (009)

2026-08-27 · 브랜치 `loop/search-ui` · 자동(야간)

## 무엇을 사용자 관점으로 봤나

`concept.md:5-6` 이 제품으로 정의한 것은 "브라우저로 접속해 검색"이다.
이 계획 전까지 있던 것은 `GET /search` 의 JSON 뿐이었다 — **사람이 쓸 수 있는
화면이 없었다.** 그래서 e2e 는 사람이 실제로 밟는 경로를 그대로 걷는다:
홈을 열고 → 검색어를 치고 → 결과를 보고 → 없는 걸 검색해 보고 → 주소를 잘못 만진다.

수단은 둘이다.
- `e2e/design_check.py` — **로컬 서버(포트 0)의 실제 응답 바이트**로 컨셉 디자인
  4축을 판정한다. 네트워크를 타지 않는다.
- 라이브 서버 위 사용자 경로 답사(아래 표) — 적대적 문서 2개를 색인에 섞어 둔 채로 걷는다.

| 축 | 기준 | 실측 |

LCP 와 레이아웃은 브라우저 없이 못 재고, 헤드리스 추가는 야간 정지 조건이다.

## 적대적 문서를 섞은 채로 걸었다

색인에 두 개를 심어 두고 시나리오 2를 돌렸다: URL 이 `http://evil.test/"><script>…`
인 문서와, URL 자체가 `javascript:alert(1)` 인 문서.

- `<script` 출현 **0** · `href="javascript:` 출현 **0**
- `javascript:` URL 은 **링크가 되지 않고 글자로만** 나온다 — 결과를 숨기지는 않는다
- `evil.test` 의 URL 은 `&quot;&gt;&lt;script&gt;` 로 속성 안에 갇힌다
- `onerror=` 라는 글자는 화면에 **한 번 나온다.** 이것은 통과다 —
  `&lt;img src=x onerror=alert(1)&gt;` 안이라 태그가 아니라 텍스트다.
  (문자열만 세면 오탐이 나는 자리라 적어 둔다)

## 리뷰가 뒤집은 것 — 초록불이 근거 없이 켜져 있었다

백지 리뷰가 **이스케이프 자체는 안 뚫렸다**고 확인했다(적대적 URL 8종 실사격).
대신 **검증 장치가 비어 있는 자리 넷**을 찾았고, 전부 같은 실패 유형이었다 —
*없어진 것을 못 보는 검사*. 자세한 것은 `docs/project.md` 품질 기준.

가장 뼈아픈 것: 고정폭 검사가 `px` 만 봤는데 **이 제품 CSS 는 전부 `rem`** 이다.
검사기의 눈이 먼 자리가 정확히 제품이 사는 곳이었다.
그리고 이 파일의 XSS 단언이 전부 `assertNotIn` 이라, `_safe_href` 가 무조건
`None` 을 돌려줘도 **전부 통과**했다 — 링크가 통째로 사라지는 변이를 아무도 못 잡았다.
**부정 단언에는 긍정 짝이 있어야 한다.**

## 남은 것 (사람이 볼 자리)

- **페이지네이션 UI 가 없다.** JSON 은 `has_next` 를 내는데 화면에는 다음 페이지
  링크가 없다. 11번째 결과부터는 주소창을 직접 고쳐야 닿는다 (계획 범위 밖으로 명시)
- **모르는 경로는 아직 JSON 404 다.** 이제 사이트가 됐으니 사람이 오타로 닿을 수 있다
- **LCP·레이아웃은 여전히 대리 지표다.** 브라우저 레이아웃·페인트 시간은 못 잡는다.
  올리는 법은 사람이 헤드리스를 붙여 1번을 Lighthouse LCP 로 교체하는 것
- `rem→px` 환산은 루트 16px 가정이다. 사용자가 기본 글꼴을 키우면 실제로는 더 크다
