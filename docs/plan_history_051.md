## 1. 문제 · 목표 · 기대 결과

**문제.** README 의 「잘하고 있나 재는 자」 표 일곱 행은 이 프로그램이 **무엇을 얼마나 잘해야
하는지**를 사람에게 알려 주는 유일한 자리다. 그 안의 아홉 수치(상위 10 · 80% · 90% ·
0.3초 · 0.5초 · 초당 5장 · JS 50KB · 대비 4.5 · 비텍스트 3)는 전부 `e2e/*.py` 의 상수를
**손으로 옮겨 적은 것**이고, 옮겨 적은 것을 다시 맞춰 보는 단언이 하나도 없다. 표의 세
번째 칸이 「무엇으로 재나」로 측정기 파일을 가리키고 있어서, **문서가 가리키는 그 파일과
문서에 적힌 그 수치가 갈라져도 아무도 안 운다.**

**목표.** README 의 아홉 수치를 `e2e/*.py` 의 실제 상수와 묶어, **어느 쪽을 혼자 고쳐도
빨개지게** 한다. 저장소가 `test_readme.test_verification_counts_match_reality`
(단위 건수·e2e 종수)에서 이미 한 번 쓴 관용구 — 「문서의 숫자를 실제와 대조한다」 — 그대로다.

**기대 결과.** `tests/test_readme.py` 에 리터럴 표 한 벌과 클래스 하나가 늘고, 제품 `src/`
와 `e2e/` 는 **0줄**이며, README 의 수치는 한 글자도 안 움직인다(오늘 아홉이 다 맞다).

## 7. 위험

- **리터럴이 문서를 베끼면 두 층이 다 무너진다.** 계획 62 e2e 가 잡은 자리가 정확히
  그것이다(`CAUGHT` 주석의 「실물 첫 줄 그대로」가 거짓이었다). 여기서 재는 것은 **문구가
  아니라 수치**여야 한다 — 표에 `51200` 을 적으면 README 의 「50KB」가 바뀌어도 안 울고,
  README 문구 전체를 적으면 문구를 고치는 날 표도 같이 고쳐진다. 그래서 정규식은 수치만
  뽑고 환산은 코드가 하며, 실패 메시지에 **어느 행·어느 상수인지**를 적는다.
- **환산이 판정을 삼킬 수 있다.** `0.3`×1000 은 부동소수라 `300.0 != 300` 이 되지 않게
  비교 방식을 개발 스텝이 정한다(정수 비교 또는 허용오차 0 의 명시적 반올림).
- **문서 테스트가 제품을 끌고 온다.** `passage_eval` 은 임포트 시점에 `perf_search` 와
  `websearch.serve` 를 끌어온다 — 오늘 부작용 0 이지만, e2e 모듈이 임포트 시점에 서버를
  띄우게 되는 날 이 테스트가 먼저 아프다. 그때는 아픈 것이 맞다(그 자체가 결함이다).
- **README 「단위 N건」 줄.** 클래스가 하나 늘면 622 가 움직인다 — 같은 커밋에서 안 고치면
  `test_readme` 가 즉시 빨개진다(그것이 설계대로다).
