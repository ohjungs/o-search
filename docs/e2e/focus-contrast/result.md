## 3. 새 e2e 를 왜 0개로 두는가

`rules/e2e.md` 3절이 e2e 를 요구하는 이유는 **단위가 구조적으로 못 보는 자리** —
프로세스 경계 · 진짜 시계와 신호 · 실제 응답 바이트 · 모듈 배선 — 넷이다.
이 계획의 산출물이 그중 하나(**실제 응답 바이트**)에 걸리는데, **그 자리를 재는 e2e 가
이미 있다**: `e2e/design_check.py` 가 로컬 서버(포트 0)를 세워 `/` 와 `/?q=…` 를 실제로
받아 그 바이트에서 CSS 를 파싱한다. 계획이 고친 색값도 뒤집은 커버리지 강제도 전부
그 경로 위에서 판정된다. 하나 더 만들면 19종이 20종이 될 뿐이다(ponytail 1번).

**8단계 웹 UI 체크리스트**(`rules/e2e.md` 4절)는 이 계획에 대해 **1(시각 스캔)·2(상호작용)
쪽만 해당**하고 나머지는 화면 구조를 안 건드려 해당 없음이다. 1·2 는 브라우저 없이
직접 못 재므로 `design_check.py` 의 대리 지표([1] LCP · [4] 360px)와 `pagination_ui_e2e.py`
(링크를 실제로 따라간다)가 대신한다 — 이 저장소가 헤드리스를 안 붙인 이유는
`docs/project.md ## 품질 기준` 에 적혀 있다(의존성 추가라 루프가 야간에 못 붙인다).

## 4. 탐침 — 계획의 전제를 진짜 응답 바이트에서 확인했다

계획 1절은 *"`outline-offset:2px` 라 링의 바깥쪽 이웃 색은 언제나 `--bg-page` 다"* 를
전제로 짝을 하나만 적었다. 그 전제와 색값이 **응답에 실제로 들어 있는지**를 서버를 세워
확인했다(탐침 스크립트는 커밋하지 않는다 — 산출물이 아니라 측정이다):

```
[A] 응답 CSS 의 포커스 링 규칙:
    .sb input:focus-visible,.sb button:focus-visible,a:focus-visible
      {outline:3px solid var(--focus);outline-offset:2px}
    라이트 --focus:#ea580c 있음 · 홈/결과 동일 · outline-offset 2px
```

전제 세 가지(규칙이 살아 있다 · `var(--focus)` 를 쓴다 · offset 이 2px 이다)가 전부 참이다.

## 5. 여기서 새로 드러난 것 — 형제 구멍 하나 (계획 범위 밖 · `digest` 로 인계)

같은 탐침의 둘째 질문이 **눈먼 자리 하나**를 실측했다.

```
[B] 포커스 링 규칙을 통째로 지운 CSS 로 check_contrast:
    기준 위반 0건 · 측정 불능 0건
    → **조용히 통과한다 — 눈먼 자리**
```

`--focus` 토큰은 여전히 선언돼 있으므로 검사기는 3.56:1 을 찍고 rc 0 을 낸다.
**아무에게도 안 보이는 링을 초록으로 재는 것**이다. 계획 13 리뷰가 닫은 4곳(*어느 맵을
보나*)과 계획 43 이 닫은 것(*어느 이름을 보나*)에 이어, 이번 것은 *그 토큰을 쓰는 규칙이
살아 있나* 다 — **같은 계보의 다음 칸**이고, 계획서 2절이 인용한
`digest ## 다음 계획 후보` 의 `[7] 살아남은 변이가 등가 변이가 아니라 형제 구멍일 때가
있다` 가 말하는 그 형태다.

**이번에 고치지 않는다.** 계획 5절이 범위를 색값 하나와 커버리지 강제로 못박았고,
e2e phase 는 소스를 계획 범위 안에서만 고친다(`rules/e2e.md` 3절). 검사기에 한 줄을
더하는 것은 개발 스텝을 새로 여는 일이라 승인이 필요하다. `digest ## 다음 계획 후보`
에 실측과 함께 적었다.

**이것은 계획의 실패가 아니다** — 계획 7절이 적은 두 반증 신호(설계가 4.5 를 고르는데
맞는 색이 없다 / M3 이 M1 과 겹쳐도 초록)는 **둘 다 발동하지 않았다**. 위 [B] 는
계획이 예고한 자리가 아니라 계획이 닫은 구멍의 이웃이다.
