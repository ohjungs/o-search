# 결과 — 계획 88 `frontier-prime` — 받다 만 URL 을 되찾는다

## 1. 실물 결과

시드를 **하나만** 주고 `--max 60`:

```
전 429 행: 3,807
수집 60 페이지 · 69.9초
후 429 행: 3,747      ← 정확히 60 줄었다
```

**받은 60장이 전부 되찾은 URL 이다.** 시드(`en.wikipedia.org/wiki/Search_engine`)는
신선해서 스킵됐고, 큐를 채운 것은 `unfinished()` 다. 전수 **731 OK rc 0**.

## 2. 계획 87 이 남긴 문제였다

87 이 실물에서 잡았다 — 프런티어가 메모리라 매 실행 시드에서 다시 자라는데, **부모가
신선하면 팝 지점에서 스킵돼 링크 추출조차 없어 자식이 영영 큐에 못 들어온다.**
계획 86 이 429 행을 「안 신선」으로 읽게 만든 것만으로는 **아무 일도 안 일어났다**
(실물 3,807개가 그 상태였다).

## 3. 새 표를 안 만들었다

87 은 정답을 **프런티어 영속화**(새 저장 구조)로 적었다. 그런데 관측된 문제에 한해서는
그것이 필요 없다 — **그 URL 들은 이미 `pages` 에 있고**, 「다시 받아야 하나」의 판정자도
이미 있다(`is_fresh`). 없던 것은 그 판정을 **거꾸로 물어보는 길**뿐이었다.

`unfinished()` 는 `is_fresh` 와 **같은 조건을 부정해서** 쓴다 — 술어를 두 벌 두면
언젠가 갈린다.

**아직 못 푸는 것**: 발견됐지만 `pages` 에 한 번도 안 들어간 URL(큐에만 있다가 종료된
것)은 여전히 잃는다. 그건 진짜 프런티어 영속화의 몫이고 이 계획 밖이다.

## 4. 범위를 안 넓히는 것이 계약이다

`--same-site` 는 사용자가 「여기서 나가지 마라」고 한 것이다. 되찾기가 그 밖의 URL 을
큐에 넣으면 **사용자가 막은 곳으로 요청이 나간다** — 크롤 윤리 축이다.
`frontier.add` 가 `_scope` 를 보므로 자동으로 걸리지만, **자동으로 걸린다는 것이
계약이라는 뜻은 아니다.** `test_priming_does_not_widen_the_same_site_scope` 가 못박는다.

## 5. 상한과 순서

**상한 1,000.** 미완이 10만이면 프런티어를 그것으로 채우는 것은 크롤이 아니라 재시도
배치다. **오래된 순** — 가장 오래 못 받은 것이 가장 오래 기다린 것이다.

**시드보다 뒤에 넣는다.** 사람이 고른 출발점이 먼저다. `add` 가 `_seen` 으로 중복을
막으므로 겹치면 시드 쪽이 남는다.
