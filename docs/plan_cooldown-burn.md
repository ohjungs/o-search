# 계획: cooldown-burn — 요청도 안 보내고 태우는 도메인 쿨다운을 회수한다

슬러그 `cooldown-burn` · 브랜치 `loop/cooldown-burn` (기점 `9bd3771`, `loop/tokenizer`)
출처: `docs/digest.md` `## 판단 필요` `[high]` (crawl-throughput 008 리뷰 보류 → 재검토로 열었다)

## 문제

`Frontier.next()` 는 URL 을 팝하면서 `_last_fetch[domain]` 에 **팝 시각**을 쓴다
(`src/websearch/frontier.py:70`). 그런데 팝이 곧 요청은 아니다. 두 자리에서 갈라진다:

| 팝 이후 경로 | 페이지 요청이 나가나 | 지금 쿨다운을 태우나 |
|---|---|---|
| `store.has(url)` 이 참 → `continue` (`crawl.py:69-70`) | **안 나간다** | **탄다** |
| robots 가 막음 → `_store_result` 가 `mark_sent` 없이 반환 (`crawl.py:98-99`) | **안 나간다** | **탄다** |
| 정상 → `mark_sent(domain, sent_at)` (`crawl.py:100`) | 나간다 | 탄다 (정상) |

앞의 둘은 **아무 데도 요청하지 않고 그 도메인을 1초 재운다.** 동시화 뒤로는 이것이
공회전이 아니라 **처리량 손실**이다 — 쿨다운에 걸린 도메인은 `next()` 가 건너뛰므로
워커 풀이 덜 찬다.

**robots.txt 요청은 이 간격 계약 밖이라는 것을 이 저장소가 이미 정했다** —
`e2e/perf_crawl.py:87` `page_gaps()` 가 `/robots.txt` 를 간격 측정에서 뺀다(digest `[4]`).
그러므로 robots 가 막은 URL 이 페이지 간격 1초를 소비할 근거가 없다.

## 근거 — 실측 (2026-08-27 반복 82, scratchpad 탐침 · 네트워크 안 침)

`e2e/perf_crawl.py` 의 서버 하네스(12도메인 · 응답지연 0.4s · 48문서)를 그대로 쓰되
**robots.txt 가 페이지 11개 중 6개를 막는 사이트**로 바꿔 쟀다. 현실의 사이트는 대개
무언가를 막는다. 신규 크롤이고 이어받기가 아니다 — **지금 당장 도는 경로다.**

| | 처리량 | 요청 없이 태운 쿨다운 | 페이지 최소 간격 |
|---|---|---|---|
| **현재** | **4.48/s** | 120회 팝 중 **72회** | 1.003s |
| 팝 쓰기 제거 + **제출 시점** `mark_sent` | 4.49/s | 0회 | 1.005s |
| 팝 쓰기 제거 + **실제 발신 시각만** | **10.25/s** | 0회 (72회는 정당하게 안 태움) | 1.007s |

**두 가지가 나왔다.**

1. **현재 값이 컨셉 성능 2(초당 5문서, `concept.md:44`)를 밑돈다.** robots 가 뭔가를
   막는 사이트에서 4.48/s 다. `perf_crawl.py` 는 아무것도 막지 않는 사이트만 재서
   이 사실을 못 봤다 — 10.25/s 라는 기준선은 **막는 것이 없는 세계의 숫자**였다.
2. **digest 가 적어 둔 답("제출 시점 `mark_sent` + 팝 쓰기 제거")은 아무것도 회수하지
   못한다.** 4.48 → 4.49/s. 제출 시점에는 robots 판정이 아직 안 났기 때문이다
   (`_fetch_one` 이 워커 **안에서** `robots.allowed()` 를 부른다, `crawl.py:31`).
   회수는 **실제로 나간 요청에만** 시계를 걸어야 나온다 — 2.29배.

## 목표

**요청이 나간 도메인만 쿨다운을 소비한다.** 회복 목표는 위 시나리오에서 **9.0/s 이상**
(현재 4.48/s · 탐침 10.25/s). 그러면서 **페이지 최소 간격 1.0초와 robots 준수는 그대로다.**

## 넘지 않는 선 — 어기면 RED

- **도메인당 페이지 요청 간격 1.0초 하한을 어떤 커밋에서도 낮추지 않는다** (`concept.md:31-33`,
  크롤 윤리는 기능이 아니라 전제 조건).
- **robots.txt 준수를 늦추거나 건너뛰지 않는다.**
- 회수는 "안 보낸 요청의 쿨다운을 안 태운다" 로만 얻는다. **간격을 깎아서 얻지 않는다.**

## 설계가 먼저 닫을 구멍 (008 리뷰가 남긴 경고)

팝 쓰기를 그냥 지우면 **간격 위반 구멍이 열린다**: 워커가 예외로 끝나면
`_store_result` 의 `except` 가지(`crawl.py:95-97`)가 `mark_sent` 없이 반환하는데
**요청은 이미 나갔을 수 있다.** 그러면 `_last_fetch` 가 비어 다음 팝이 즉시 나간다.

**이 구멍을 닫는 것이 설계의 첫 항목이다.** 순진한 수정은 RED 다.
보수적 방향(실제 발신보다 **늦게** 잡는 것)은 안전하고 이르게 당기는 것만 위반이다 —
`mark_sent` 가 이미 `max` 로 늦은 쪽으로만 움직인다(`frontier.py:82`).

## 설계 트리거 — 걸린다. 설계 phase 를 돈다

`rules/design.md` 1절: **공개 인터페이스 변경**(`Frontier.next()` 가 간격 시계를 건다는
계약이 사라진다) · **파일 3개 이상**(`frontier.py`·`crawl.py`·`tests/test_frontier.py`) ·
**대안이 갈린다**(위 표의 세 갈래 + add 시점 robots 필터).

**사용자 승인은 필요 없다.** `design.md` 4절의 넷 중 어디에도 안 걸린다 — 프런티어는
**내부** 계약이고(`Frontier` 를 부르는 곳은 `crawl.py:66` 하나뿐, grep 실측),
저장 데이터 형태·의존성·보안 경계와 무관하다. 설계가 스스로 정하고 근거를 남긴다.

## 스텝

**2개다.** 쪼갤 수 있는데 안 쪼갠 자리가 하나 있고, 그 이유가 아래 스텝 1에 있다.

### 스텝 1 — 간격 시계를 팝에서 떼어 실제 발신에 건다
- 의존: 없음
- 할 일: `Frontier.next()` 의 `_last_fetch` 쓰기를 없애고, `crawl` 이 **요청이 실제로
  나간 경로에서만** `mark_sent` 하도록 한다. 예외 경로의 구멍은 설계가 정한 방식으로
  같은 커밋에서 닫는다(보수적으로 늦게 잡는 쪽).
- 건드릴 파일: `src/websearch/frontier.py` · `src/websearch/crawl.py` ·
  `tests/test_frontier.py` · `tests/test_crawl.py`
- **`frontier.py` 와 `crawl.py` 를 한 커밋에 넣는다 — 쪼개면 안 된다.** 팝 쓰기만 먼저
  지운 중간 커밋은 예외 경로에서 **1초 계약이 깨진 상태**다. 위 "넘지 않는 선" 은
  계획이 끝났을 때가 아니라 **매 커밋에서** 지켜야 한다.
- 완료 기준:
  ① `store.has` 가 참이라 건너뛴 URL 이 그 도메인의 쿨다운을 **안 태운다**
     (주입 시계로 결정적으로 단언 — 긍정 짝: 실제로 나간 요청은 **태운다**)
  ② robots 가 막은 URL 도 안 태운다 (같은 긍정 짝)
  ③ **워커가 예외를 던져도 다음 요청이 1.0초 안에 안 나간다** (구멍 회귀 테스트)
  ④ `tests/test_frontier.py` 에서 **팝 쓰기에 기대던 9건**을 새 계약으로 다시 쓴다.
     지우지 않는다 — 재는 것은 그대로 두고 시계를 거는 방법만 바꾼다.
     (실측: 팝 쓰기를 지우면 `test_mark_sent_only_moves_later`·
     `test_seconds_until_ready_skips_excluded_domain`·`test_same_domain_respects_interval`·
     `test_wait_time_reported`·`test_declared_delay_slows_only_that_domain`·
     `test_delay_never_goes_below_the_floor`·`test_exactly_max_delay_is_kept_not_dropped`·
     `test_interval_never_shrinks`·`test_wait_time_uses_declared_delay` 9건이 깨진다)
  ⑤ 기존 260 테스트 전부 통과 · `e2e/crawl_delay_e2e.py` 종료 0(간격 계약 무손상)

### 스텝 2 — 회수분을 숫자로 고정한다 — 막는 사이트를 재는 눈을 만든다
- 의존: 1
- 문제: `e2e/perf_crawl.py` 는 **아무것도 막지 않는 사이트**만 잰다. 이 버그가 8일 동안
  안 보인 이유가 그것이다. 고쳐 놓고 같은 눈으로 재면 **다음에 또 못 본다.**
- 할 일: `perf_crawl.py` 에 robots 가 일부를 막는 시나리오를 더하고, 회수된 처리량을
  기준선 상수로 박는다. **합격선(`TARGET_RATE=5.0`)과 기준선 상수는 다른 질문이다** —
  전자는 "제품 목표를 넘나", 후자는 "어제보다 나빠졌나" (digest 후보 4번).
- 건드릴 파일: `e2e/perf_crawl.py` · `docs/project.md`(품질 기준 절의 숫자)
- 완료 기준: 차단 시나리오에서 **9.0/s 이상**이고, 팝 쓰기를 되돌리는 변이가
  **실제로 이 검사를 빨갛게 만든다**(변이로 확인하고 적는다 — 돌아가는 것과
  잡는 것은 다르다, `project.md` 변이 검사 절). 페이지 최소 간격 0.95s 이상 유지.

## 하지 않을 것

- **`store.has` 가 상태 불문 스킵하는 것** — 같은 DB 로 재실행하면 시드부터 스킵돼
  크롤이 **0으로 끝난다**(반복 82 탐침으로 재확인). digest `[high]` 의 별도 항목이고
  **recrawl 계획 소관**이다. 이 계획은 쿨다운만 본다.
  → 이것 때문에 digest 가 적은 "영향은 이어받기 크롤 한정" 은 **틀렸다**. 이어받기는
    아예 안 돌아서 잴 수가 없고, 실제로 값이 나오는 곳은 **robots 가 막는 신규 크롤**이다
- **`recrawl`**(`fetched_at` 스키마 변경) · **`X-Robots-Tag`** — 승인 대기, 야간 금지
- **add 시점 robots 필터** — `robots.allowed()` 가 네트워크를 탈 수 있어 메인 스레드에
  I/O 를 들인다. 동시화 설계 계약 4(메인 스레드는 네트워크를 안 한다)를 깬다.
  설계에서 대안으로 세우되 이 이유로 버릴 것으로 본다
- **`Ctrl-C` 지연 · `--deadline`** — digest `[4]`, 별도 계획
- **워커 수·간격 조정** — 처리량을 손잡이로 얻지 않는다. 회수로만 얻는다

## e2e 시나리오 (계획 시점 확정)

1. **막는 사이트에서 처리량이 회복된다** — robots 가 절반을 막는 12도메인에서 9.0/s 이상
2. **간격은 그대로다** — 페이지 최소 간격 0.95s 이상, robots.txt 는 측정에서 제외
3. **robots 준수가 그대로다** — 막힌 경로 요청 수 **0건** (긍정 짝: 허용 경로는 수집됨)
4. **워커 예외에도 간격이 유지된다** — 일부러 예외를 던지는 워커를 섞어도 최소 간격 유지
5. **되돌리기 경로** — `--workers 1` 이 같은 문서 집합을 낸다 (기존 시나리오 유지)
