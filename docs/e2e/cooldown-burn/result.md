## 무엇을 사용자 관점으로 봤나

**"robots.txt 가 뭔가를 막는 평범한 사이트를 크롤하면 얼마나 나오나."**

008 이 만든 기준선 10.25/s 는 **아무것도 막지 않는 사이트**의 숫자였다. 현실의
사이트는 대개 무언가를 막는다. 그 세계에서 실제로 도는 값은 **4.48/s** 로 컨셉
성능 2(초당 5문서)를 **밑돌고 있었고 8일 동안 아무도 몰랐다** — 재는 눈이 없었다.

원인은 `Frontier.next()` 가 **팝하면서** 도메인 쿨다운을 걸던 것이다. 팝은 요청이
아니다. robots 가 막았거나 이미 수집한 URL 은 **아무 데도 요청하지 않고** 그 도메인을
1초 재웠다. 동시화 뒤로는 이것이 공회전이 아니라 **워커 풀이 덜 차는 처리량 손실**이다.

수단은 `e2e/perf_crawl.py` — **실제 네트워크를 치지 않는다.** 로컬 서버 12개를 서로
다른 포트로 띄우고(포트가 곧 netloc), 응답 지연 0.4초로 실제 웹의 대기를 흉내낸다.
이번에 더한 것은 **`robots.txt` 본문을 갈아끼워 같은 하네스로 다른 세계를 재는 것**이다.

## 이 e2e 가 실제로 잡는가 (변이로 확인)

돌아가는 것과 잡는 것은 다르다. **이 phase 에서 두 변이를 다시 넣어 재확인했다** —
리뷰(반복 87)와 이 phase 가 `perf_crawl.py` 를 건드렸으니 **하네스가 여전히 잡는지는
다시 재야 아는 것**이다. `src/` 와 `e2e/` 를 통째로 scratchpad 로 복사해 거기서 돌렸다
(**작업 트리는 안 건드렸다** · `git status` 로 확인). 트리 전체를 복사하는 이유는
`perf_crawl.py` 가 import 시점에 **자기 위치 기준으로** `src` 를 `sys.path[0]` 에
밀기 때문이다 — 사본만 만들고 저장소에서 돌리면 **같은 코드를 두 번 재게 된다**(반복 84).

| 변이 | 잡은 곳 (이번 실측) | **그때 통과해 버리는 곳** |
|---|---|---|
| 팝 시점 시계 복원(원래 버그) | **[차단] 4.48/s 로 실패** · 단위 3건 | [열림] 10.2/s **통과** |

**오른쪽 열이 이 계획의 교훈이다.** 검사 하나가 초록이라고 구멍이 없는 것이 아니다.

## 남은 것 (사람이 볼 자리 — `digest.md ## 판단 필요`)

이 e2e 로는 안 잡히고, 야간 자동 적용 대상도 아니다. **둘 다 이 계획이 연 것이 아니다.**

1. **`Crawl-delay` 도메인의 첫 요청이 예외로 끝나면 그 뒤가 1.0초로 나간다** — robots
   위반. `except` 가지가 `set_delay()` 를 못 부른다. 착수 전 `9bd3771` 에서 같은 값이
   나오는 것을 대조로 확인했다. 고치려면 캐시 peek 같은 새 공개 API 가 필요해
   **동시화 계약 4**와 부딪힌다
2. **`fetcher` 재시도가 도메인 간격을 안 지킨다** — 연결 실패 시 **3회가 0.4ms 안에**
   나간다(탐침 실측). 재시도는 `fetcher` 안에서 일어나 `mark_sent` 를 안 지나므로
   프런티어는 요청 1회로 안다. 타임아웃 실패는 10초씩 벌어져 문제가 안 되고,
   **빠르게 실패하는 경로만** 뭉친다. `fetcher.py` 는 이 계획의 diff 에 없다
