# e2e 결과 — 계획 78 `index-watermark`

실물 코퍼스 400문서(361색인), 계획 77 의 압축 표현 위에서 잰다.

## 1. 무엇이 막고 있었나

색인기의 「뒤늦게 noindex 를 선언한 문서를 뺀다」 루프가 **매 실행 전 문서**를 훑었다.

```
문서당 10.21ms · 실물 400문서 4.08초
→ 10만 문서면 신규 0건이어도 매 실행 17.0분
```

**증분 색인의 의미를 이 루프가 지우고 있었다** — 신규 문서 텍스트 추출은 이미 증분인데
(`url NOT IN (SELECT url FROM docs)`), 이 루프가 그 옆에서 전수를 돌아 고정비가 됐다.

## 2. 얻은 것

| | 옛 | **새** |
|---|---|---|
| 첫 색인 (361문서) | 13.45초 | 13.45초 (안 건드렸다) |
| **재실행 · 신규 0건** | **4.08초** | **0.11초** |
| 10만 환산 매 실행 고정비 | **17.0분** | **29.5초** (35배) |

전수 **675 OK rc 0** · e2e 3종(noindex·indexer·hidden_passage) 통과.

## 3. 왜 워터마크인가 — 그리고 왜 `docs` 에 안 넣었나

이 루프의 선언은 **재크롤로 `pages.html` 이 갈렸을 때만** 생긴다. `pages` 에 이미
`fetched_at` 이 있으므로 「지난 색인 이후 받아 온 것」만 보면 된다.

`docs` 에 색인 시각 열을 더하는 쪽이 더 곧지만 **FTS5 가상 테이블**이라 열을 늘리면
기존 색인을 통째로 다시 만들어야 한다(`_docs_sql` 재구축 경로가 그 값을 이미 보여 준다).
그래서 `index_meta(key, value)` 한 줄짜리 표를 따로 뒀다 — 재색인 0회.

**워터마크가 없으면 전수다.** 옛 DB 의 첫 실행이 그렇고, 그래야 이 기능이 생기기 전에
들어온 뒤늦은 선언도 한 번은 걷힌다.

## 4. 두 번 걸린 시계 문제 — 실측이 고쳤다

**① 새 워터마크는 «끝난 시각»이 아니라 «시작 시각»이다.** 도는 중에 크롤러가 넣은 행은
이번에 봤을 수도 못 봤을 수도 있다. 끝난 시각을 적으면 그 창의 문서가 **영영** 재검사에서
빠진다. 시작 시각이면 다음 실행이 한 번 더 본다.

**② 비교가 `>` 가 아니라 `>=` 다.** `datetime('now')` 는 초 단위라, 색인 시작과 재크롤이
**같은 초**에 걸리면 `>` 는 그 문서를 놓친다 — **테스트 셋이 실제로 빨갛게 났다**
(`test_already_indexed_page_that_declares_noindex_is_removed` 외 2건). 짐작이 아니라
실측이 잡았다.

둘 다 같은 방향의 선택이다: **재검사는 멱등이므로 덜 보는 쪽이 아니라 더 보는 쪽으로
기운다.** `>=` 가 매번 다시 보는 것은 경계의 1초에 받아 온 문서뿐이다.

## 5. 테스트가 시계에 기대지 않게 고친 자리

처음 쓴 증분 테스트는 「`fetched_at` 을 안 건드린다」를 **같은 초**로 표현했다. ② 를
고치자 그 테스트가 깨졌는데, **깨진 쪽이 테스트였다** — `>=` 아래에서 같은 초는 정당하게
재검사된다. `fetched_at` 을 `2020-01-01` 로 명시해 **계약**(「이번 실행보다 먼저 받아 온
문서는 다시 안 본다」)을 재도록 바꿨다. 시계 해상도에 기댄 단언은 언젠가 반드시 흔들린다.

## 6. 남은 고정비

재실행 0.11초의 대부분은 신규 문서를 고르는 첫 SELECT(`url NOT IN (SELECT url FROM docs)`)
가 `pages` 를 훑는 몫이다. 10만 환산 29.5초라 지금은 문제가 아니고, 문제가 되면 처방은
같다 — `pages` 에 색인 상태 열(코드의 `ponytail:` 주석)이다. **이 계획에서는 안 한다**:
그 열은 스키마 변경이고, 지금 값이 29.5초라 근거가 아직 없다.
