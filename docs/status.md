## 변이 검증 — 1건, 제자리(`.mutation-lock`)

「실패 시 출력」은 **진짜 스위트에서 진짜 실패를 내야** 의미가 있어 메모리 탐침이
아니라 제자리로 갔다. `crawl.py` 한 줄 `crawl(args, max_pages, …)` → `max_pages + 1`
(오프바이원)이고, 그 자리를 고른 이유는 **한 테스트가 두 스트림을 다 쓰기 때문**이다 —
`test_max_zero_is_rejected_like_workers_and_deadline` 은 `--max 0` 거절을 stderr 로,
대조군 `--max 1` 의 `수집 0 페이지` 를 stdout 으로 낸 뒤 마지막 줄에서 넘어간 값을 잰다.

```
FAIL: test_max_zero_is_rejected_like_workers_and_deadline (test_crawl.TestCrawl)
AssertionError: 2 != 1
Stdout:  수집 0 페이지
Stderr:  --max 는 1 이상의 숫자 하나를 받는다
```

파급은 **3건**(나머지 둘은 `=`/공백 형태의 인자 전달 테스트라 stdout 만 낸다).
`-b` 의 천장도 같은 화면에서 봤다: **빨간 실행은 `FAILED` 뒤로 늦은 `Stdout:` 세
덩이가 더 붙는다** — unittest 가 실패한 테스트의 버퍼를 보고서에 넣고 **진짜
스트림에도 되비추기** 때문이고, 되비친 stdout 이 블록 버퍼라 판정 뒤에 늦게 나온다.
초록 실행에서 0줄이면 목표는 달성이고 이건 봐야 할 것이라 무해하다(계획 phase 판단).

**원복은 초록이 아니라 `git diff` 로 확인했다** — 변경 0줄 · 미추적 0개(`.mutation-lock`
삭제 확인). **커밋된 변이 0.**
