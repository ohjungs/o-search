# 설계: crawl-throughput — 크롤 루프 동시화

계획: `docs/plan_crawl-throughput.md`

## 결정

**메인 스레드가 상태를 독점하고 네트워크만 스레드풀에 던진다.**
`Store`·`Frontier`·크롤 카운터는 지금처럼 한 스레드만 만지고,
워커 스레드는 **`robots` 확인 + `fetch` 만** 하고 결과 튜플을 돌려준다.
동시에 띄우는 요청 수는 `--workers`(기본 8), **도메인당 in-flight 는 1개**.

## 대안 비교

출발점 셋에서 하나씩 냈다 (`rules/design.md` 3-1절).

| | A. 최소 — 네트워크만 던진다 | B. 정공법 — 워커가 파이프라인 전부 | C. 되돌리기 우선 — 프로세스 샤딩 |
|---|---|---|---|
| 구조 | 메인이 팝·저장·링크, 풀은 `robots`+`fetch` | 워커가 팝→robots→fetch→저장→링크 | 코드 무변경. 도메인을 나눠 크롤 프로세스 N개 |
| 동시 접근 | **없음** — 공유 상태를 한 스레드가 독점 | `Frontier`·`Store` 에 락 필요, 스레드별 SQLite 커넥션 | 프로세스 간 DB 공유 — **`database is locked` 가 N배** |
| 되돌리기 | `--workers 1` = 오늘과 같은 경로 | 락·커넥션이 얽혀 커밋 revert 뿐 | 프로세스 1개로 (가장 쉬움) |
| 코드량 | 적음 (`crawl.py` 루프 + `next(exclude=)`) | 많음 | 0 — 대신 **운영·시드 분할이 사람 일**이 된다 |
| 기존과 일치 | ○ 단일 스레드 상태라는 현 관용구 유지 | △ 이 저장소에 락이 하나도 없다 | △ `crawl.main` 은 프로세스 1개 전제 |
| 다음이 편한가 | 보통 — 저장이 병목이 되면 그때 연다 | 좋음(이론상) — 지금 필요 없는 확장 | **나쁨** — 도메인 간 링크를 넘길 방법이 없다 |

**선택: A.**

- 동시성이 필요한 이유가 **네트워크 대기 하나뿐**이다. 대기가 있는 곳만 던지면
  락도 스레드별 커넥션도 필요 없다 — 안 쓴 코드가 가장 좋은 코드다
- `concept.md:59` 에서 크롤 윤리가 성능보다 위다. **팝 결정이 한 곳에 남아 있어야**
  간격 계약을 지금 테스트 그대로 지킬 수 있다
- **버린 이유: B** — 락을 도입하는 대가로 얻는 것이 없다. 저장·링크추출은 로컬 연산이라
  대기가 없고, 지금 병목이 아니다(실측 근거는 네트워크뿐). 추측성 확장이다
- **버린 이유: C** — 링크를 따라 프런티어를 넓히는 것이 이 크롤러의 정의인데
  (`concept.md:24`), 샤드 A 가 발견한 B 도메인 링크를 넘길 방법이 없다.
  게다가 실측에서 크롤을 죽인 `database is locked` 를 **정면으로 늘린다**.
  `concept.md:74` 의 "분산 크롤러 — 2단계까지 금지" 에도 걸린다

## 가정 — 깨봤다

**"응답이 도메인 간격보다 오래 걸리면 같은 도메인이 in-flight 인 채로 다시 팝된다."**
→ **참이다.** 코드로 확인했다(탐침 불필요 — `plan.md` 3-1절 "읽어서 보이면 탐침하지 않는다").
`frontier.py:53-54` 의 자격 조건은 **팝 이후 경과 시간뿐**이고, 그 요청이 끝났는지는
보지 않는다. 응답 3초 · 간격 1초면 t+1 에 같은 도메인이 다시 나온다.

순차 루프에서는 이것이 문제가 될 수 없었다 — 다음 팝 자체가 응답 뒤에야 일어난다.
**동시화가 이 구멍을 처음 연다.** 그래서 아래 계약 3이 설계에 들어간다.

이것이 이 설계에서 가장 위험한 가정이었다: 거짓이었다면 `crawl.py` 만 고치면 됐고,
참이므로 **`Frontier` 도 함께 고쳐야 한다**(계획서의 "건드릴 파일" 과 일치).

## 계약 — 개발이 지킬 것

1. **`crawl.crawl(..., workers=8)`** — 키워드 인자 추가. 기존 호출부·테스트는 그대로 돈다.
   `crawl.main` 에 `--workers N` 플래그(`--max` 와 같은 방식, 숫자 아니면 종료 코드 2)
2. **`Frontier.next(exclude=())`** — `exclude` 에 든 도메인은 건너뛴다. 기본값이 오늘과 동일.
   `_last_fetch` 를 찍는 시점·라운드로빈은 **바꾸지 않는다**
3. **도메인당 in-flight 1개.** 메인 루프가 in-flight 도메인 집합을 들고
   `frontier.next(exclude=busy)` 로만 팝한다. **동시성이 politeness 를 먹는 것을 막는
   유일한 장치다** — 테스트로 박는다
4. **워커는 공유 상태를 만지지 않는다.** 워커 함수는 `(url, robots_cache, now)` 를 받아
   `(allowed: bool, delay: float|None, sent_at: float|None, FetchResult|None)` 를 돌려준다.
   (`sent_at` 은 **계약 9가 뒤에 넣은 것** — 아래 "설계를 고친 곳" 참조)
   `Store`·`Frontier` 접근 금지 — SQLite 커넥션은 계속 메인 스레드 전용이다
   (`RobotsCache` 는 예외: base 당 캐시 dict 쓰기뿐이고, 계약 3 때문에
   같은 base 를 두 워커가 동시에 받을 수 없다)
5. **URL 처리 순서는 오늘과 같다** — `robots.allowed()` → `robots.delay()` → `fetch()`.
   워커 안에서 이 순서가 유지되므로 사이트가 보는 요청 순서는 변하지 않는다
6. **실패 격리** — 워커가 던진 예외는 `Future` 가 잡는다. 메인은 그것을
   **fetch 실패(status 0)와 같게 취급**하고 stderr 에 한 줄 남긴 뒤 계속 간다.
   워커 하나가 죽어도 크롤은 안 죽는다
7. **`max_pages` 상한** — `saved + len(inflight) < max_pages` 일 때만 새로 던진다.
   반환값이 `max_pages` 를 넘지 않는다(오늘의 계약 유지)
8. **놀지 않는다** — 던질 URL 이 없으면 `futures.wait(..., FIRST_COMPLETED,
   timeout=frontier.seconds_until_ready(exclude=busy))` 로 기다린다.
   in-flight 가 0일 때만 `sleep`.
   **`exclude=` 는 구현 중에 필요해졌다** — 떠 있는 도메인은 대기시간이 0으로 읽혀,
   그 0에 가리면 정작 쿨다운이 풀리는 도메인을 놓치고 완료만 기다린다
9. **간격 시계는 팝이 아니라 발신에서 시작한다** — `Frontier.mark_sent(domain, at)` 신설.
   워커가 `fetcher.fetch()` **직전** 시각을 재서 결과 튜플에 실어 보내고, 메인이
   그것으로 `_last_fetch[domain]` 을 덮는다. 워커는 여전히 프런티어를 안 만진다(계약 4).
   **아래 "설계를 고친 곳" 참조 — 이건 최적화가 아니라 윤리 위반 수정이다**

## 설계를 고친 곳 (2026-08-27 · 개발 스텝 1 이후) — 계약 9 신설

스텝 1의 `e2e/perf_crawl.py` 가 **변이를 하나도 안 넣은 원본 코드에서** 도메인 간격
위반을 잡았다: 도메인 2개·응답 0.4초로 돌리면 **0.819초** 간격이 나온다.
`concept.md:25` 는 도메인당 1초 이상을 "기능이 아니라 전제 조건" 으로,
어기는 코드는 **리뷰에서 RED** 라고 못박았다.

뿌리는 `digest.md [4]` 로 이미 적혀 있던 것이다 — **간격 시계가 요청 발신이 아니라
팝 시각에서 시작한다.** `frontier.py:62` 가 팝 순간 `_last_fetch` 를 찍는데,
그 도메인을 처음 만졌으면 `crawl.py:31` 의 `robots.allowed()` 가 robots.txt 를
받느라 0.4초를 쓰고 **그 뒤에** 페이지 요청이 나간다. 다음 번은 robots 가 캐시라
곧바로 나가므로, 실제 간격 = `interval - robots왕복` 이 된다.

계획서는 이것을 `## 하지 않을 것` 에 두고 "동시화가 악화시키지 않는지만 확인한다"
고 했다. **확인해보니 이미 위반 중이었고, 동시화는 이것을 반드시 악화시킨다** —
지금은 도메인 간격이 5초씩 벌어져 숨어 있지만(그래서 기존 e2e 가 못 봤다),
동시화의 목적이 바로 그 간격을 1초까지 좁히는 것이라 **모든 도메인의 첫 간격이
0.6초가 된다.** 스텝 2는 이걸 고치지 않으면 판정 ②를 통과할 수 없다.

범위를 좁게 유지한다: **페이지 요청 사이의 간격**만 계약이다. robots.txt 요청
자체가 간격 시계에 실리지 않는 것(도메인당 딱 한 번)은 그대로 두고
`e2e/perf_crawl.py` 의 판정 ②도 robots.txt 를 뺀다 — 그건 별개 건이다.

## 되돌리기

**`--workers 1`.** 그때 in-flight 는 최대 1개라 팝→fetch→저장이 오늘과 같은
순서로 직렬화된다 — 배포도 revert 도 아닌 **설정 한 글자**다.
개발 스텝 2가 이것을 테스트로 확인한다(계획서 "워커 1개면 오늘과 같다").
그래도 안 되면 커밋 하나 revert (`crawl.py`·`frontier.py` 두 파일).

기본값 8은 **보정 손잡이지 상수가 아니다** — 실제 웹의 응답시간 분포는 로컬 서버와
다르다. 아침에 사용자가 실측으로 조정할 수 있게 CLI 에 노출한다.
