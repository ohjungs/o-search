# 계획 54 — `passage-html-column`

**계획 53 이 닫은 것은 「`pages` 테이블이 통째로 없다」 한 축뿐이다.**
`pages` 는 있는데 **`html` 열이 없는** DB 에서는 「DB 상태 판정이 질의 내용에
달렸다」가 그대로 살아 있다 — 같은 고장난 DB 에 `q=김치찌개` 는
`sqlite3.OperationalError: no such column: html` 로 **500**, `q=zzzznope`·`q=%01` 은
`hits` 가 비어 `SELECT html` 에 닿지도 못해 **200 `{"passages": []}`** 다.
소비자가 같은 순간의 같은 DB 를 «우리가 터졌다» 와 «근거가 없다» 로 갈라 읽는다.

## 1. 문제 · 목표 · 기대 결과

### 문제

`indexer.passages()`(`src/websearch/indexer.py`)는 계획 53 에서 `search()` 뒤·`hits`
루프 **앞**에 가드를 하나 얻었다. 그 가드는 `sqlite_master` 를 보고 **`pages` 테이블의
유무만** 판정한다. 같은 자리의 주석이 그 좁음을 스스로 적어 뒀다:

> 테이블의 **유무만** 본다. `pages` 는 있는데 `html` 열이 없거나 권한이
> 막힌 DB 는 기다린다고 안 낫는 상태라 500 이 맞는 이름이다.

**그 주석은 답의 절반에만 참이다.** 이름(500)은 맞을 수 있지만 «세 질의가 500 으로
모인다» 는 오늘 참이 아니다. 열이 빠진 DB 에서 `SELECT html FROM pages WHERE url = ?`
는 **루프 안**에 있으므로 `hits` 가 비면 한 번도 실행되지 않고, 그 질의는 200 `[]` 로
끝난다. 즉 계획 53 이 테이블 축에서 닫은 고장이 **열 축에서 글자 그대로 살아 있다.**

계보가 셋이다. 셋 다 같은 원칙의 재발이다.

1. **계획 47 `db-open-atomic`** — `search()` **안**의 무토큰 조기 반환을 DB 상태 판정
   뒤로 밀었다. `indexer.search()` 의 주석이 원칙을 못박았다: *"무토큰 질의의 조기
   반환은 **DB 상태 판정 뒤**다. 앞에 두면 판정이 질의 내용에 달린다."*
2. **계획 53 `passage-db-state`** — 같은 고장이 `passages()` 에서 **테이블 축**으로
   재발한 것을 닫았다(500/200/200 → 503/503/503).
3. **이 계획** — 같은 고장이 같은 함수에서 **열 축**으로 남아 있다(500/200/200).

### 목표

`passages()` 가 `pages` 를 **읽기 전에**, 그 창고가 **읽을 수 있는지까지** 판정하게
한다. 판정은 `hits` 가 비었든 찼든 **같은 자리에서 같은 답**을 낸다.
어떤 코드로 답할지(500 인가 503 인가)는 설계가 고른다 — 6절 갈림길 1.

### 기대 결과

- `html` 열이 없는 DB: `/passages` 가 질의 3종(매치 있음 · 매치 없는 낱말 · 무토큰)에
  **같은 상태 코드 하나**. 오늘은 500 / 200 `[]` / 200 `[]` 다.
- 정상 DB 대조군 3종은 **200 · 오늘과 같은 본문** (오탐 0).
- 같은 고장난 DB 의 `/search` 는 **200 무변** — 색인만으로 되는 검색을 안 깬다.
  계획 53 이 갈림길 2 에서 고른 「가드는 `passages()` 안, `search()` 뒤」가 그대로
  유지된다는 뜻이다.
- 제품 diff 는 `src/websearch/indexer.py` 한 파일(설계가 503 을 고르면 그대로 한 파일,
  500 을 고르면 `serve.py` 는 이미 `except Exception` → 500 이라 역시 0줄).
  스키마·재색인·마이그레이션 **0**.

### 무엇이 이미 참인가 (이 저장소를 처음 여는 사람을 위한 전제)

- **가드는 이미 옳은 자리에 있다.** 계획 53 이 `passages()` 안, `search()` **뒤**,
  `hits` 루프 **앞**에 놓았다. 이 계획이 옮길 것은 자리가 아니라 **판정의 넓이**다.
- **오늘의 답을 못박는 테스트가 이미 있다.** `tests/test_serve.py` 의
  `TestPassagesWithoutHtmlColumn` 이 «매치되는 질의는 500 · 나머지 둘은 200 `[]`» 를
  단언하고, docstring 이 그 의도를 적어 뒀다: *"아래가 바라는 것이 아니라 오늘의
  답이다. 천장을 옮기는 날 이 테스트가 빨개져 「그 갈림을 알고 바꾼다」가 되게 하려고
  잰다."* **TDD 의 RED 는 새로 짓는 것이 아니라 그 두 단언을 뒤집는 것이다.**
- **같은 고장을 만드는 방법도 그 테스트가 갖고 있다.** `setUp` 이 `pages` 를 DROP 하고
  `html` 없는 스키마로 다시 만든다(`ALTER TABLE … DROP COLUMN` 은 sqlite 버전을 타서
  안 쓴다). 이 계획의 탐침도 같은 방법을 썼다.
- **503 세 이름의 우선순위는 `search()` 가 이미 정한다.** `passages()` 의 가드가
  `search()` **뒤**라 「없는 DB(`FileNotFoundError`) → 옛 색인(`StaleIndexError`) →
  창고 없음(`NoCrawlDataError`)」 순이다. 열 축을 더해도 이 순서 뒤에 붙는다(3절 실측).
- **`serve.do_GET` 의 JSON 사다리는 이미 두 갈래를 갖고 있다.**
  `(FileNotFoundError, StaleIndexError, NoCrawlDataError)` → 503,
  `except Exception` → 500 «검색 중 오류가 났다». 어느 쪽을 골라도 **`serve.py` 는
  0줄**이다 — 이 계획은 `serve` 를 안 건드린다.

### 이 계획이 스스로 인정하는 약점 — 도달 조건이 낮다

후보 `[6]` 이 **8점이 아닌 이유**로 적은 그대로다: `store`·`indexer` 의 어떤 경로도
`html` 없는 `pages` 를 만들지 않는다. 이 상태에 닿으려면 사람이 스키마를 손으로
고쳐야 한다 — 계획 53 이 연 「테이블이 통째로 없다」가 크롤 DB 를 지우거나 옛 DB 를
물려받으면 **실제로** 생기는 것과 다르다.

**그래서 이 계획의 값은 «고장을 만난다» 가 아니라 다음 둘이다.**

1. **제품 주석이 오늘 거짓을 말하고 있다.** 위에 인용한 «500 이 맞는 이름이다» 는
   다음 사람이 그대로 믿을 문장인데, 실제로 나가는 것은 500 하나가 아니라 500/200
   갈림이다. 코드가 아니라 **주석이 틀린 것**이므로, 설계가 「제품 0줄 · 주석과 테스트
   docstring 만 고친다」를 고를 수도 있다(6절 갈림길 1 의 안 C).
2. **같은 원칙이 세 번째로 재발했다.** 계획 47 이 `search()` 안에서, 계획 53 이
   `passages()` 의 테이블 축에서 닫았고 이번이 열 축이다. **한 함수 안에서 두 번
   되풀이된 것은 자리의 문제가 아니라 판정의 넓이 문제**라는 신호다.

### 후보의 처방을 실행 전에 다시 쟀다 — **이번엔 서술과 처방이 둘 다 맞았다**

`digest [7]` 「기록된 답을 실행 전에 다시 재라」의 여섯 번째 적용이다.
스크래치패드 탐침이 임시 DB 를 만들어(`store.upsert` 2건 → `indexer.index_pages` →
`pages` 를 DROP 하고 `html` 없는 스키마로 재생성) `indexer` 를 직접 불렀다.
**저장소의 `data/crawl.db` 는 읽지도 않았다.**

| DB 상태 | `q=김치찌개` | `q=zzzznope` | `q=%01` |
|---|---|---|---|
| 정상 (대조군) | 문단 1건 | `[]` | `[]` |
| **`html` 열 없음** | **`OperationalError: no such column: html`**(→ HTTP 500) | **`[]`**(→ 200) | **`[]`**(→ 200) |
| `html` 열 없음 + 옛 색인 | `StaleIndexError` | `StaleIndexError` | `StaleIndexError` |
| `html` 열 없음 + `docs` 없음(색인 전) | `[]` | `[]` | `[]` |
| `pages` 테이블 없음 (계획 53 이 닫은 축) | `NoCrawlDataError` | `NoCrawlDataError` | `NoCrawlDataError` |

같은 고장난 DB 의 `indexer.search()` 는 **세 질의 전부 오늘과 무변**이다
(`q=김치찌개` → 결과 1건 · 나머지 둘 → `[]`). 후보가 적은 500/200/200 이 글자
그대로 재현됐고, 서술도 처방도 오늘 다시 재서 참이다.

### 처방 후보가 실제로 도는 것까지 쟀다

가드 자리에서 **`SELECT html FROM pages LIMIT 1` 한 줄**이 질의와 무관하게 판정을
낸다는 것을 같은 탐침으로 확인했다.

| DB 상태 | `SELECT 1 FROM sqlite_master …`(오늘의 가드) | `SELECT html FROM pages LIMIT 1`(후보) |
|---|---|---|
| 정상 | `pages` 존재 → 통과 | **OK** → 통과 (오탐 0) |
| `html` 열 없음 | `pages` 존재 → **통과해 버린다** | **`OperationalError: no such column: html`** |
| `pages` 없음 | 없음 → `NoCrawlDataError` | `OperationalError: no such table: pages` |

**마지막 행이 설계가 풀 문제다** — 한 문장으로 두 축을 다 보면 두 고장이 같은
`OperationalError` 로 합쳐져, 계획 53 이 고른 「테이블 없음 = 503」과 구별하려면
예외 **메시지 문자열**을 읽어야 한다. 그 값은 sqlite 판이 바뀌면 흔들린다.

- **무엇으로 확인하나**: `PYTHONPATH=src python3 -m unittest discover -b tests`
  (오늘 599건 OK). 건수가 늘면 `README.md` 의 `단위 599건` 과
  `tests/test_readme.py` 의 건수 단언을 **같은 커밋에서** 고친다 — 계획 53 개발이
  잊을 수 없었던 것과 같은 이유로 그 단언이 함께 RED 로 뜬다.

## 5. 완료 기준 (검증 가능 · 대칭으로 잰다)

1. `html` 열 없는 DB 의 `indexer.passages()` 가 질의 3종(`김치찌개` · `zzzznope` ·
   `%01`)에 **같은 결말**을 낸다 — `subTest` 셋으로 잰다(계획 53 리뷰 `[R53-1]` 이
   가르쳐 준 자리다: 단언을 `with` 밖에 두면 첫 질의에서 멈춘다).
2. 같은 DB 의 `/passages` HTTP 응답이 질의 3종에 **같은 상태 코드**다. 오늘은
   500 / 200 / 200.
3. 응답 본문에 **DB 경로가 안 샌다**(`assertNotIn(self.db, …)` — 오늘의 테스트가
   이미 재는 축이라 뒤집은 뒤에도 남긴다).
4. **정상 DB 대조군 3종 무변** — `/passages` 가 200 이고 문단 본문이 오늘과 같다
   (가드 오탐 0. 8절의 최대 위험).
5. 같은 고장난 DB 의 **`/search` 200 무변** — 색인만으로 되는 검색을 안 깬다.
   이 단언은 구현 **전에도** 초록이어야 한다(가드를 `_connect()` 로 올리는 실수를
   붙드는 유일한 자리다 — 계획 53 개발이 «대조군이 RED 때부터 초록인 것이 값» 이라
   적은 그 자리).
6. `html` 열 없음 + **옛 색인**은 여전히 `StaleIndexError` 다 — 새 판정이 `search()`
   앞으로 새지 않았다는 뜻이고, 갭 후보 「판정 셋의 순서」를 붙드는 첫 단언이다.
7. `html` 열 없음 + **`docs` 없음(색인 전)** 은 여전히 `[]` 다 — 「색인 전은 `/search`
   와 같은 답」이라는 오늘의 계약을 새 가드가 안 깬다.
8. **변이 둘이 죽는다**(스크래치패드 사본에서 심는다 · `git checkout` 0회):
   ① 새 판정 줄 삭제 → 오늘의 500/200/200 이 돌아와 RED ·
   ② 새 판정을 `hits` 루프 **안**으로 옮김 → 매치 없는 두 질의가 다시 200 으로 갈려 RED.
   ②가 이 계획의 축(«판정이 질의 내용에 안 달린다»)을 직접 잰다.
9. 전수: 단위 **599건 이상 OK**(맨몸·단독) · e2e **21종 rc 0** ·
   `passage_eval` 정확도 **≥ 90%** · `/passages` p95 **≤ 500ms**.
10. `data/crawl.db` sha256 **무변** · `docs/specs/` **무변** · 스키마·재색인·
    마이그레이션 **0** · 새 의존성 **0** · **PR #7 무접촉**.

## 6. 설계가 필요하다 — 트리거 둘이 걸린다

| 트리거 | 이 계획에서 |
|---|---|
| **대안이 2개 이상 갈림** | 갈림길 1 이 500·503·「제품 0줄」 셋으로 갈린다 |
| 공개 인터페이스 변경 | `/passages` 의 상태 코드는 남의 시스템이 읽는 계약이다(`README.md` 의 상태 코드 표 · 사양 「계약 안정성」) |

### 갈림길 1 — 세 질의를 **무엇으로** 모으나

- **안 A — 500 «검색 중 오류가 났다»**. `digest` 후보 `[6]` 이 적어 둔 답이고
  제품 주석도 그 이름을 적었다. 근거: 열이 빠진 창고는 **재시도로 안 낫는다** —
  503 «기다렸다 다시 걸어라» 는 인프라에게 틀린 말이다. `serve` 는 이미
  `except Exception` → 500 이라 **`serve.py` 0줄**이고, `indexer` 는 새 예외를 안
  만들고 `OperationalError` 를 **루프 앞에서 한 번 나게** 하면 된다.
- **안 B — 503 «색인이 아직 준비되지 않았다»**(`NoCrawlDataError`). 근거: 계획 53 이
  테이블 축에서 고른 답과 **같은 표면**이라 소비자가 배울 것이 늘지 않고,
  `README.md` 의 계약 표에 줄을 안 더한다. 반대 근거: `NoCrawlDataError` 의
  docstring 이 뜻하는 상태(«크롤한 적 없는 DB») 와 다르고, 크롤·색인을 다시 돌려도
  **열은 안 생긴다**.
- **안 C — 제품 0줄. 주석과 테스트 docstring 의 틀린 진술만 고친다.** 근거: 이 상태는
  사람이 스키마를 손으로 고쳐야 닿고, 오늘 살아 있는 손실은 **거짓 주석 한 줄**이다
  (ponytail 1칸 — 없어도 되는 코드는 안 쓴다). 반대 근거: 같은 원칙이 한 함수에서
  두 번 재발했고, 판정을 안 넓히면 다음 축(권한·손상 페이지)에서 또 열린다.

**설계는 `docs/specs/concept.md` 의 우선순위를 먼저 본다** — 「계약 안정성 > 기능 추가」
이고 디자인 5 가 *"HTTP 상태 코드가 뜻을 갖는다"* 라 **한 DB 두 답**이 가장 무거운
손실이다. A 와 B 는 둘 다 그것을 닫고 C 는 안 닫는다. 셋을 표로 갈라 고른다.

### 갈림길 2 — 판정을 **어떻게** 넓히나

- **안 ㄱ — `SELECT html FROM pages LIMIT 1` 한 줄을 오늘의 가드 뒤에 잇는다.**
  3절이 실측했다: 정상 DB 는 OK(오탐 0), 열 없는 DB 는 질의와 무관하게
  `OperationalError`. 오늘의 `sqlite_master` 가드가 테이블 축을 먼저 걸러 주므로
  두 고장이 안 섞인다. ponytail 6칸(한 줄).
- **안 ㄴ — `PRAGMA table_info(pages)` 로 열 이름 목록을 읽어 `html` 을 찾는다.**
  예외가 아니라 값으로 판정하므로 **어느 축인지 이름으로 갈린다**. 대신 줄이 늘고,
  판정이 «읽을 수 있나» 가 아니라 «이름이 있나» 로 좁아진다(권한·손상은 여전히 루프
  안에서 터진다).
- **안 ㄷ — `sqlite_master` 가드를 지우고 `SELECT html FROM pages LIMIT 1` 하나로
  합친 뒤 예외 메시지로 두 축을 가른다.** 줄이 가장 적지만 **메시지 문자열에 계약을
  건다** — sqlite 판이 바뀌면 조용히 갈린다. 3절 마지막 표가 이 위험을 쟀다.

되돌리기 수단은 셋 다 같다: 브랜치째 버린다(제품 diff 가 한 파일 몇 줄이다).

## 7. 하지 않을 것 (범위 고정)

- **스키마·마이그레이션·재색인 0.** `pages`·`docs` 어느 쪽도 안 건드린다.
  `html` 열을 **되살리는** 복구 기능은 이 계획이 아니다 — 우리는 «없는 것을 올바른
  이름으로 말한다» 까지만 한다.
- **`serve.py` 를 안 건드린다.** 두 갈래(503 튜플 · `except Exception`)가 이미 있다.
  화면(HTML) 사다리도 안 넓힌다 — 계획 53 설계 갈림길 3 이 실서버로 확인한 결정이고,
  넓히면 **어떤 테스트로도 RED 로 못 만드는 줄**이 생긴다.
- **`_connect()` 를 안 건드린다.** 판정을 거기로 올리면 `pages` 가 성한지와 무관하게
  `/search` 까지 죽는다(완료 기준 5 파손).
- **`sqlite_master` 질의 두 벌을 헬퍼로 안 뽑는다.** `index_pages()` 와의 중복은
  계획 53 이 `ponytail:` 주석으로 천장을 적어 둔 자리다. 뽑는 것은 직교 편집이고,
  «셋째 호출자가 생기면» 이 그 주석이 적은 여는 조건이다.
- **새 e2e 를 미리 약속하지 않는다.** 제품 diff 가 몇 줄이면 `e2e/` 에 더할 것이
  없을 수 있다 — e2e phase 가 판정한다(계획 41·53 과 같은 판정 방식).
- **`docs/specs/` 는 읽기 전용.** `data/crawl.db` 무변경. **PR #7 무접촉.**
- **후보 `[6]` 의 나머지 축(권한이 막힌 DB)은 안 연다.** 오늘 탐침이 안 쟀고 근거가
  없다 — 열려면 근거부터 만든다.

## 8. 위험

1. **가드 오탐 — 가장 큰 위험.** 정상 DB 에서 새 판정이 걸리면 `/passages` 가 통째로
   죽는다. 3절이 정상 DB 에서 후보 질의가 **OK** 를 내는 것을 이미 쟀고, 완료 기준 4
   가 대조군 3종으로 붙든다. 계획 53 e2e 가 정상 DB 다섯 줄 무변으로 확인한 것과
   같은 축이다.
2. **값이 낮다는 판정이 뒤집히지 않을 위험.** 이 계획은 도달 조건이 낮은 고장을 연다.
   설계가 안 C(제품 0줄)를 고르는 것이 정답일 수 있고, **그것도 이 계획의 정상 종료**다
   — 그때 남는 산출물은 거짓 주석의 교정과 그 판단의 기록이다.
3. **비용이 질의마다 한 번 늘어난다.** 안 ㄱ·ㄴ은 `/passages` 요청마다 SELECT 를
   하나 더 친다. 계획 53 이 잰 오늘의 `/passages` p95 는 **1.55ms**(예산 500ms 의
   0.3%)라 여유는 크지만, 완료 기준 9 가 p95 를 다시 잰다.
4. **`sqlite3` 판 의존.** 안 ㄷ은 예외 메시지에 계약을 건다. 설계가 고르면 그 메시지를
   붙드는 단언이 함께 있어야 하고, 없으면 조용히 갈린다.
5. **러너 규율.** 이 계획의 모든 검증 명령은 **맨몸**으로 돈다 — 파이프·리다이렉션을
   붙이지 않는다. 계획 53 이 «재확인 실행» 에서 두 번 어겼고, 방아쇠는 언제나
   «이미 초록일 것 같은 실행» 이다.
