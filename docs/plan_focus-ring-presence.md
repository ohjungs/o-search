## 1. 문제 · 목표 · 기대 결과

**문제.** `src/websearch/serve.py` 의 CSS 는 키보드 포커스 링을 이렇게 그린다:

```css
.sb input:focus-visible,.sb button:focus-visible,a:focus-visible{
  outline:3px solid var(--focus);outline-offset:2px}
```

계획 43 이 `--focus` 의 **색**을 `#ea580c` 로 올려 라이트 3.56:1 · 다크 11.14:1 을
못박았고, `e2e/design_check.py` 의 `NONTEXT_PAIRS` 가 매 실행 그 두 행을 찍는다.
그런데 검사기가 보는 것은 **토큰 선언**(`--focus:#ea580c`)뿐이고 **그 토큰을 쓰는
규칙**은 안 본다. 규칙이 사라져도 선언은 남으므로 검사기는 계속 3.56:1 을 찍는다.

**착수 탐침 실측** (2026-09-01, 메모리에서 · 저장소 무수정). 링을 죽이는 변이 6종을
심고 — 심긴 것을 먼저 단언한 뒤(`digest ## 반복 실패` 의 "변이가 실제로 심어졌는지
먼저 단언한다") — `check_contrast` 를 돌렸다:

| 변이 | CSS 길이 | 기준 위반 | 측정 불능 | 판정 |
|---|---|---|---|---|
| V0 무변경 | 2310 | 0 | 0 | rc 0 |
| V1 규칙 통째 삭제 | 2194 | 0 | 0 | **rc 0** |
| V2 `outline:none` | 2292 | 0 | 0 | **rc 0** |
| V3 `var(--focus)` → `var(--line)` | 2309 | 0 | 0 | **rc 0** |
| V4 `:focus-visible` → `:focus` | 2286 | 0 | 0 | **rc 0** |
| V5 `outline-offset:2px` 제거 | 2292 | 0 | 0 | **rc 0** |
| V6 `outline-offset:0` | 2308 | 0 | 0 | **rc 0** |

**여섯 전부 살아남는다.** `digest ## 다음 계획 후보` 의 항목은 V1 하나만 쟀고,
탐침이 그 구멍을 다섯 배로 넓혔다.

**V3 와 V5·V6 는 후보가 몰랐던 갈래다.**
- **V3**: 규칙은 살아 있는데 **다른 토큰**을 쓴다. `--line` 은 라이트에서
  `--bg-page` 대비 **1.08:1** 이라(그 값은 `NO_PAIR` 의 사유 문자열이 이미
  적어 뒀다) 링이 사실상 안 보이는데, 검사기는 여전히 `--focus` 를 잰다 —
  **재는 색과 그려지는 색이 갈린다.**
- **V5·V6**: `NONTEXT_PAIRS` 바로 위 주석이 *"포커스 링은 `outline-offset:2px` 라
  링의 이웃은 언제나 페이지 배경이다"* 라고 **짝 선택의 근거를 CSS 한 선언에
  걸어 뒀다.** 그 선언을 지우면 링은 `--bg-input`·`--bg-button` 에 붙고,
  `status.md ## 사람이 정할 것` 의 2번이 적은 **`--focus` on `--bg-button` 1.45:1**
  이 가정이 아니라 실제 이웃이 된다. **검사기의 짝 자체가 무효가 되는데
  아무도 안 붙든다.**

**목표.** 응답 CSS 에 **포커스 링을 실제로 그리는 규칙이 살아 있는지**를 검사기가
재게 한다. 위 6종 중 몇을 잡을지, 못 잡는 것을 왜 안 잡는지는 설계가 정한다(6절).

**기대 결과.** `e2e/design_check.py` 가 맨몸 rc 0 을 유지하고(제품 CSS 는 멀쩡하다),
링을 죽이는 변이에서 **빨개진다.** 짝짓는 단위 단언이
`tests/test_design_check.py` 에 붙어 **검사기 자신이 좁아지는 변이도 죽는다.**

**걸리는 트리거는 "대안이 2개 이상 갈림"이고, 갈림길이 둘이다.**

**갈림길 A — 종료 코드.** `digest` 항목의 처방은 *"없으면 **종료 2**"*(측정 불능)다.
그런데 **같은 파일의 형제 관용구는 종료 1 이다** — `check_mobile` 은
`overflow-wrap:anywhere` 가 없을 때 `fail` 에 넣는다(탐침 실측: 그 선언을 지우면
`fail=1 unm=0`). "링이 없다"는 **못 잰 것(2)이 아니라 기준 위반(1)** 이라는 읽기가
가능하고, 형제와 갈리는 쪽을 고르려면 사유가 필요하다. **`digest` 의
`[7] 기록된 답을 실행 전에 다시 재라`** 가 정확히 이 자리다 — 계획 41 도 물려받은
처방이 *"한 칸 틀렸었다"*(자리도 타입도).

**갈림길 B — 무엇을 자국으로 삼나.** 응답 CSS 안의 실측 출현 수:
`var(--focus)` **1회** · `:focus-visible` **3회** · `outline` **2회** ·
`outline-offset` **1회**. 어디에 거느냐로 잡는 변이 집합이 갈린다 —
`var(--focus)` 만 보면 V1·V2·V3 를 잡고 V4·V5·V6 를 놓치며, `outline-offset` 까지
보면 V5·V6 도 잡지만 검사가 CSS 작성 방식을 못박아 앞으로 오탐을 낳는다.
**어느 쪽이든 동작하지만 결과가 다르다** — `rules/design.md` 1절의 그 칸이다.

→ **`phase: 설계`**. 산출물 `docs/design_focus-ring-presence.md`.
설계는 대안을 **세 출발점**(최소 / 정공법 / 되돌리기 우선)에서 하나씩 내고,
고른 뒤 **가장 위험한 가정 하나를 깨본다**(`rules/design.md` 3-1·3-2절).
깰 가정의 후보: *"응답 바이트 안의 자국으로 '링이 보인다'를 대리할 수 있다"* —
거짓이면(예: 자국은 있는데 다른 규칙이 덮어쓴다) 이 계획은 브라우저 없이는
못 재는 것을 재는 척하게 된다.

## 8. 이 계획이 틀렸다면 어디서 드러나나

- **설계가 "응답 바이트로는 못 잰다"로 결론 내면** — 그때 이 계획은 검사를 다는
  대신 **왜 못 재는지를 검사기 주석과 `digest` 에 적고 닫는 일**이 된다.
  `rules/design.md` 3-2절이 그 갈래를 열어 뒀다(가정이 거짓이면 개발로 가지 않는다).
- **새 검사가 제품 CSS 에서 rc 0 을 못 내면** — 자국 선택이 틀린 것이다.
  스텝 1 완료 기준 1번이 첫 실행에서 잡는다.
- **변이 6종 중 잡기로 한 것이 안 잡히면** — 완료 기준 3번이 잡는다.
- **잡는데 단위가 안 붙들면** — 완료 기준 4번이 잡는다. 이것이 안 되면 계획 42 가
  진단한 *"린트형 검사는 데이터가 초록일 때 자기 자신을 못 잰다"* 를 세 번째로
  재발시키는 것이다.
