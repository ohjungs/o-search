# 설계 54 `passage-html-column`

**결정: 제품 한 줄 + 주석.** `indexer.passages()` 안, 계획 53 이 심은 `sqlite_master`
가드 **직후**·`hits` 루프 **앞**에 `db.execute("SELECT html FROM pages LIMIT 0")` 한 줄을
둔다. 열이 없으면 sqlite 가 내는 `OperationalError` 가 **질의와 무관하게** 한 번 나고,
`serve.do_GET` 의 `except Exception` 이 이미 그것을 500 으로 옮긴다.
**`serve.py` 0줄 · `README.md` 0줄 · 새 예외 0개 · 스키마·마이그레이션·재색인 0 ·
시그니처 무변.** 제품 diff 는 `src/websearch/indexer.py` **한 파일**이다.

## 1. 갈림길 1 — 어떤 답이 맞는 이름인가 (A 500 · B 503 · C 제품 0줄)

계획서 6절이 연 셋을 출발점을 갈라서 다시 세웠다: **최소**(C 제품 0줄) ·
**정공법**(A 500) · **되돌리기 우선**(B 503, 계획 53 과 같은 표면이라 이름 하나 빼면 무름).

| | A 500 «우리가 터졌다» | B 503 `NoCrawlDataError` | C 제품 0줄 (주석만) |
|---|---|---|---|
| 세 질의가 한 답으로 모이나 | **모인다** 500/500/500 | 모인다 503/503/503 | **안 모인다** 500/200/200 그대로 |
| 다시 돌리면 낫는 상태인가 | 아니다 → 500 이 참 | 아니다 → **503 이 거짓말** | — |
| `serve.py` | 0줄 | 0줄(튜플에 이미 있다) | 0줄 |
| `README.md` | **0줄** — 이미 «그 밖의 오류에는 500» | 0줄 | 0줄 |
| 제품 diff | 1줄 | 4~5줄(새 판정+예외 재사용) | 0줄 |

**결정을 낸 실측은 「기다리면·다시 돌리면 낫나」 한 줄이다** (2026-09-04 · 반복 316,
임시 DB, 저장소 `data/crawl.db` 는 사본으로만 읽었다).

- `store.Store(db)` 재생성 → **열이 안 살아난다**(`SCHEMA` 가 `IF NOT EXISTS` 라 옛
  정의로 조용히 남는다). 남은 열은 `['url', 'status']`.
- 이어지는 `store.upsert()` → `OperationalError: table pages has no column named html`.
- `indexer.index_pages()` → `OperationalError: no such column: html`.

**크롤도 색인도 그 DB 에서 죽는다.** 503 은 사양 5(`docs/specs/concept.md` — 상태 코드가
뜻을 갖는다)와 `README.md` 의 «색인을 다시 돌리면 낫는 상태» 정의에 정면으로 어긋나고,
503 을 보고 재시도 루프에 들어간 인프라는 **영원히 안 낫는 것을 계속 두드린다.**
그래서 B 를 버렸다 — 계획 53 과 «같은 표면» 이라는 값보다 «틀린 말» 이라는 손실이 크다.

**C 를 버린 이유.** 계획서가 C 를 진지하게 세운 근거(이 상태는 사람이 손으로 스키마를
고쳐야 닿는다)는 참이다. 그러나 C 는 **거짓 주석을 참으로 바꿀 뿐 고장을 안 고친다** —
「판정이 질의 내용에 달렸다」가 계획 47·53 에 이어 **세 번째로** 같은 함수에 남는다.
A 의 값은 «고장을 만난다» 가 아니라 **그 원칙이 코드에 못박히는 것**이고, 값이 1줄이다.
ponytail 사다리로 봐도 C(0줄)와 A(1줄)의 차이는 한 줄인데, 그 한 줄이 사양 5 를 지킨다.

## 2. 갈림길 2 — 무엇으로 판정하나 (탐침 넷)

계획서는 `SELECT html FROM pages LIMIT 1` 을 후보로 적었다. **네 개를 다 재 보니 그것이
가장 비쌌다.** 1000행·행당 10,426바이트 html 의 정상 DB, 200회 평균:

| 탐침 | 정상 DB | 고장 DB | 비용 |
|---|---|---|---|
| `SELECT html FROM pages LIMIT 1` (계획서 후보) | OK · 오탐 0 | `OperationalError` | 0.0128 ms |
| **`SELECT html FROM pages LIMIT 0`** | **OK · 오탐 0** | **`OperationalError`** | **0.0016 ms** |
| `SELECT html FROM pages WHERE 0` | OK · 오탐 0 | `OperationalError` | 0.0015 ms |
| `PRAGMA table_info(pages)` | 행을 훑어 `html` 찾음 | 행에 없음 → **판정을 직접 써야** | — |
| (대조) 오늘의 `sqlite_master` 가드 | 통과 | **통과해 버린다** | 0.0024 ms |

**`LIMIT 1` 이 8배 비싼 이유가 결론이다** — 열이 있는지만 물으면 되는데 **html 본문 한
행을 통째로 읽는다.** `LIMIT 0` 은 sqlite 가 준비(prepare) 단계에서 열 이름을 풀므로
행을 한 개도 안 읽고 같은 판정을 낸다. 그래서 계획서 후보 대신 **`LIMIT 0`** 을 고른다.

`WHERE 0` 은 비용이 같지만 «열이 있나만 묻는다» 를 `LIMIT 0` 이 더 곧게 읽는다.
`PRAGMA table_info` 는 **버린다** — 행을 훑고, «없다» 를 우리가 예외로 번역해야 하니
새 판정 한 벌이 늘고(계획 47 이 한곳에 모은 것이 흩어진다), 얻는 것이 없다.

**계획서 3절이 걱정한 「예외 메시지 문자열을 읽어야 한다」는 안 일어난다.** 테이블이 통째로
없는 DB 는 **위쪽 `sqlite_master` 가드가 먼저** `NoCrawlDataError` 를 내고 끝나므로, 새 줄은
`pages` 가 있는 것이 확정된 뒤에만 준비된다. **순서가 문자열 비교를 대신한다**(3절 표).

## 3. 가장 위험한 가정을 깼다 — 오탐 0 과 순서 (반복 316 실측)

**가정: 정상 경로의 어떤 DB 상태에서도 새 줄이 오탐을 안 내고, 판정 셋의 우선순위가 안
흔들린다.** 계획서 8절이 최대 위험으로 적은 것이다. 추측하지 않고 제안 계약을
`src/` 밖에 그대로 복제해(추가되는 줄 하나만 다르다) 일곱 상태 × 세 질의를 다 쟀다.

| DB 상태 | 오늘 (매치·무매치·무토큰) | 제안 |
|---|---|---|
| 정상 | 200 · 200 · 200 | **200 · 200 · 200** (오탐 0) |
| `html` 열 없음 | **500 · 200 · 200** | **500 · 500 · 500** ← 갈림 닫힘 |
| `pages` 테이블 없음 | 503 · 503 · 503 | 503 · 503 · 503 (계획 53 무변) |
| 옛 색인 | 503 · 503 · 503 | 503 · 503 · 503 |
| 색인 전 | 200 · 200 · 200 | 200 · 200 · 200 |
| `html` 열 없음 + 옛 색인 | 503 · 503 · 503 | 503 · 503 · 503 |
| `html` 열 없음 + 색인 전 | 200 · 200 · 200 | **500 · 500 · 500** ← 아래 |

**두 가지가 확인됐다.**

1. **우선순위는 오늘 그대로다.** 없는 DB(`FileNotFoundError`) → 옛 색인
   (`StaleIndexError`) → 창고 없음(`NoCrawlDataError`) → **열 없음(500)** 이 맨 뒤에
   붙는다. 새 판정이 `search()` 앞으로 새지 않는다.
2. **마지막 행은 알고 바꾸는 값이다.** 「`html` 열 없음 + 색인 전」은 오늘 조용한
   200 `[]` 인데 제안은 500 이다. **그 DB 는 색인을 돌리면 낫는 것이 아니라 색인이
   죽는다**(1절 실측) — 200 은 «근거가 없다», 500 은 «우리가 터졌다» 이고 참인 쪽은
   후자다. 개발이 이 행을 단언으로 못박는다.

**고장난 DB 의 `/search` 는 세 질의 모두 오늘과 같다**(매치 2건 · 0건 · 0건). 새 줄이
`passages()` 안에만 있고 `_connect()` 로 안 올라가서다 — 계획서 완료 기준 5 를 지킨다.

**대조군의 한계를 그대로 적는다.** `data/crawl.db` 사본은 `pages` 행이 **2건**뿐이라 다섯
질의 전부 오늘·제안 모두 0건으로 같았다(동일=True) — **오탐 0 을 이 코퍼스가 증명하지는
못한다.** 오탐을 실제로 붙드는 것은 **599건 전체 통과**(맨몸·단독 `13.544s` `OK`,
반복 316 재측)와 개발이 더할 정상 DB 단언이다. 실코퍼스 지연 증분은 `-0.001 ms`
(`-0.32%`, 잡음 안)라 사양 5(p95 500ms)에 닿지 않는다.

## 4. 계약 (개발이 지킬 것)

**`src/websearch/indexer.py` 의 `passages()`.** 계획 53 이 심은 `sqlite_master` 가드가
`NoCrawlDataError` 를 내는 `if` 블록 **바로 다음 줄**, `for url, title, _snippet in hits:`
루프 **앞**. 시그니처·docstring 의 계약 문장은 무변이되, docstring 의 «500(손상)» 진술이
이제 참이 되므로 그대로 둔다.

```python
        # 창고가 있는지 다음에 **읽을 수 있는지**. 열이 없으면 sqlite 가 준비 단계에서
        # OperationalError 를 내고, serve 의 except Exception 이 500 으로 옮긴다.
        # `LIMIT 0` 이다 — `LIMIT 1` 은 열 이름만 물으면서 html 본문을 한 행 통째로
        # 읽어 8배 비싸다(0.0128 대 0.0016 ms, 1000행·10KB 실측).
        # 이 줄도 **루프 앞**이다. 안이나 뒤면 `hits` 가 빈 질의가 판정에 못 닿아
        # 같은 고장난 DB 가 `q=김치` 면 500, `q=%01` 이면 200 으로 다시 갈린다.
        db.execute("SELECT html FROM pages LIMIT 0")
```

**`serve.py`·`README.md`·`store.py`·스키마 전부 0줄.** `except Exception` 이 이미 500 을
내고, `README.md` 의 «색인을 다시 돌리면 낫는 상태 … 에는 503, 그 밖의 오류에는 500» 이
이 상태를 이미 덮는다 — 그래서 `tests/test_readme.py` 도 무변이다.

**테스트(TDD).** `tests/test_serve.py` 의 `TestPassagesWithoutHtmlColumn` 을 뒤집는 것이
RED 다. 새 클래스를 만들지 않는다 — `setUp` 의 고장 만드는 방법(`DROP TABLE pages` 후
`html` 없는 스키마로 재생성)을 그대로 쓴다.

- `test_matching_query_is_500` — 유지(500 · `error` 문구 · **DB 경로 안 샘** ·
  로그에 `OperationalError`). 뒤집히는 것은 아래다.
- `test_query_without_match_is_200_the_split_that_is_left` — **500 을 기대하도록 뒤집고
  이름에서 «남은 갈림» 을 뺀다.** 세 질의(`매치 있음`·`zzzznope`·`%01`)가 한 테스트 안
  `subTest` 셋이어야 「판정이 질의 내용에 안 달린다」가 한 축으로 잡힌다.
- 클래스 docstring 의 «천장은 500 하나가 아니라 500/200 갈림이다» 는 **이제 거짓**이라
  고친다. 계획서가 «오늘 살아 있는 손실은 거짓 주석» 이라 적은 자리다.
- **같은 고장난 DB 의 `/search` 가 200 인 단언을 그 옆에 둔다** — 구현 **전에도** 초록이라야
  한다. 가드가 `_connect()` 로 올라가는 것을 붙드는 유일한 자리다(계획 53 과 같은 규율).
- **「`html` 열 없음 + 색인 전」 500** 한 건(3절 표 마지막 행). 알고 바꾼 값의 못이다.
- `tests/test_indexer.py` 에 `passages()` 가 세 질의 모두 `OperationalError` 를 내는
  단언 하나 — HTTP 밖에서도 갈림이 닫혔음을 잰다.

## 5. 천장 (`ponytail:` 주석으로 코드에 남긴다)

- **열 하나만 본다.** `url`·`status` 가 없거나 `docs` 가 깨진 DB, 권한이 막힌 DB 는 여전히
  루프 안에서 터져 500 이다 — 답이 같은 500 이라 갈림이 없고, 전수 검증은 값보다 비싸다.
  > **리뷰 54 정정 — 「답이 같은 500 이라 갈림이 없다」는 거짓이었다.** 리뷰가 임시 DB 로
  > 직접 쟀다: `url` 열이 없는 DB 는 `q=김치찌개` **500** · `q=zzzznope`·`q=%01`
  > **200 `[]`** 로, 이 설계가 `html` 축에서 닫은 그 갈림이 `url` 축에 글자 그대로 살아
  > 있다. `status` 는 반대 방향으로 틀렸다 — `passages()` 가 그 열을 아예 안 읽어 없어도
  > 세 질의 모두 정상 200 이고 아무 일도 안 난다. **판정(열 하나만 본다)은 유지한다** —
  > 다만 근거는 「갈림이 없다」가 아니라 도달 조건뿐이고, 남은 축은 `digest` 후보로
  > 등재했다. 2절의 「8배(0.0128 대 0.0016 ms)」도 재현이 안 됐다 — 같은 기계·같은
  > 모양에서 `execute()` 만 1.4배(0.0051 대 0.0036), 호출마다 새 연결이면 1.1배
  > (0.0199 대 0.0179)다. `LIMIT 0` 이 늘 같거나 싸다는 결론은 그대로다.
  세 번째 열이 근거 경로에 생기면 그때 `PRAGMA table_info` 한 번으로 올린다.
- **복구는 안 한다.** 없는 열을 `ALTER TABLE ... ADD COLUMN` 으로 되살리는 것은 이 계획이
  아니다(계획서 7절). 우리는 «없는 것을 올바른 이름으로 말한다» 까지만 한다.
- `sqlite_master` 질의가 `index_pages()` 와 두 곳인 것은 계획 53 이 이미 `ponytail:` 로
  천장을 적어 둔 자리다. **셋째 호출자가 생기면 뽑는다** — 이번에도 안 뽑는다.

## 6. 역할 검토

- **스태프** — 1줄·1파일·직교 편집 0. `serve` 사다리를 안 넓혀 「어떤 테스트로도 RED 를
  못 만드는 줄」이 안 생긴다(계획 53 갈림길 3 의 결론을 그대로 승계).
- **QA** — 599건 전부 통과가 오탐의 방벽이고, 뒤집는 단언 하나가 이 변경의 RED 다.
  변이: 새 줄을 지우면 `%01`·`zzzznope` 행이 200 으로 돌아가 RED. `LIMIT 0` 을
  `LIMIT 1` 로 바꾸면 초록이다 — **비용 축은 테스트가 아니라 주석이 지킨다**(명시).
- **보안** — 응답 본문에 DB 경로·트레이스백이 안 실린다(기존 단언 유지). 새 줄은 상수
  SQL 이라 질의 문자열이 안 닿는다. 500 으로 바뀌는 두 행 모두 본문은 고정 문구다.
- **SRE** — 재시도해도 안 낫는 상태에 **503 을 안 준다**는 것이 이 변경의 값이다.
  500 은 `serve` 가 이미 로그에 원인을 남기는 경로라 관측성 손실 0. 서버는 안 죽는다.
- **제품** — 소비자가 «우리가 터졌다» 와 «근거가 없다» 를 다시 갈라 읽는다. 사양 5(상태
  코드가 뜻을 갖는다)를 세 번째 재발 지점에서 지킨다.
