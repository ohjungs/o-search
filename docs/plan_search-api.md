# 계획: search-api — 질의를 받아 랭킹 결과를 돌려주는 HTTP API

- **슬러그**: `search-api`
- **브랜치**: `loop/search-api`
- **근거**: `docs/index.md` 사양 분할 4번. 의존(2 indexer)이 완료돼 열린다.
  `docs/specs/concept.md` 기능 1(제목·URL·스니펫 결과 목록, 페이지네이션 10건 단위)과
  성능 1(p95 300ms)의 **측정이 여기서 처음 가능해진다** — 지금 `docs/project.md`
  품질 기준의 "성능 측정: 없음" 을 채우는 것이 이 계획의 절반이다.
- **시작**: 2026-08-25 (야간 반복 29)

## 문제 재진술 <!-- 카파시 1번 -->

- **문제**: 검색이 `python3 -m websearch.indexer <db> --query Q` 로만 된다.
  `src/websearch/indexer.py` 의 `search(db_path, query, limit=10)` 은 이미
  `(url, title, snippet)` 을 bm25 순으로 돌려주지만, 브라우저에서 쓸 수 있는
  경로가 없고 응답 시간을 측정할 지점도 없다.
- **목표**: `GET /search?q=...&page=N` 이 JSON 결과를 돌려주는 HTTP 서버와,
  p95 응답 시간을 실제로 재는 명령. 둘 다 stdlib 로 한다.
- **기대 결과**: 서버를 띄우고 `curl 'localhost:PORT/search?q=김치'` 로
  10건 이하의 결과 JSON 을 받는다. 측정 명령이 p95 숫자를 출력하고 그 숫자가
  `docs/project.md` 의 기준선이 된다.
- **명시하는 가정**: p95 300ms 는 **100만 문서 기준**이다. 지금 색인은 그보다
  훨씬 작으므로 이 계획이 내는 숫자는 합격/불합격 판정이 아니라 **기준선**이다.
  색인이 커질 때 이 숫자와 비교해 회귀를 잡는 것이 목적이다.

## 하지 않을 것 <!-- 범위 고정, 카파시 3번 -->

- **HTML 화면·검색창** — `search-ui` 계획(사양 분할 5번). 이 계획은 JSON 만 낸다.
- **랭킹 개선** — bm25 그대로 쓴다. 정답 포함률은 `quality-eval` 계획 소관.
- **인증·레이트리밋·CORS·배포** — 컨셉이 "로그인 없음"이고 배포는 루프 밖이다.
  단 **입력 검증은 생략하지 않는다** (아래 스텝 3, 신뢰 경계).
- **새 의존성** — 컨셉 경량 3. `http.server` 로 안 되는 것이 실측으로 나오면
  그때 설계에서 다시 연다.
- **재크롤·색인 갱신** — `digest.md` "판단 필요" [8] 은 `recrawl` 계획 소관.
  이 계획은 색인된 것을 그대로 서빙한다.

## 설계 <!-- 6-1 판단 -->

- **필요** → `docs/design_search-api.md`
  - 트리거 ①: **새 모듈 생성** — HTTP 서버 파일이 하나 생긴다.
  - 트리거 ②: **공개 인터페이스 변경** — 페이지네이션에 offset 이 필요한데
    `indexer.search()` 는 `limit` 만 받는다. 시그니처가 바뀐다.
  - 트리거 ③: **대안이 갈린다** — 응답을 매 요청 새 sqlite 연결로 낼지
    (`http.server` 는 요청마다 스레드), 연결을 재사용할지. p95 에 직접 영향이 있고
    sqlite 연결은 스레드를 넘나들 수 없다.
  - 설계에서 결정할 것: 서버 모듈의 위치와 진입점, 응답 JSON 형태(키 이름),
    연결 전략, 측정 스크립트가 무엇을 몇 번 재는지.

## 스텝

### 1. 검색 결과 JSON 을 내는 GET /search
- **완료 기준**: 테스트 먼저 실패 확인 후 통과 — ① `q` 가 있으면 결과 배열
  ② 각 항목이 url·title·snippet 키를 가진다 ③ 매치 없으면 빈 배열과 200
  ④ 결과 순서가 `indexer.search()` 와 같다(bm25)
- **건드릴 파일**: `src/websearch/serve.py`(신설), `tests/test_serve.py`(신설)
- **의존**: 설계
- **상태**: 완료 (2026-08-25, 반복 31 — 테스트 7개, 전체 97/97)

### 2. 페이지네이션 10건 단위
- **완료 기준**: `page=2` 가 11~20번째 결과를 준다. `page` 없으면 1.
  `indexer.search()` 에 offset 이 붙고 기존 호출부(CLI)가 그대로 동작한다
  (전체 스위트 통과로 확인)
- **건드릴 파일**: `src/websearch/indexer.py`, `src/websearch/serve.py`, 각 테스트
- **의존**: 1
- **상태**: 완료 (2026-08-25, 반복 32 — 테스트 8개, 전체 105/105)

### 3. 신뢰 경계 — 잘못된 입력과 잘못된 경로
- **완료 기준**: 테스트로 고정 — ① `q` 없음/빈 문자열 → 400, 트레이스백 없음
  ② 매우 긴 질의·NUL·제어문자·FTS5 문법 문자 → 500 없이 200 또는 400
  ③ `page` 가 숫자가 아니거나 1 미만이거나 상한(100) 초과 → 400 ④ `/` 등 없는 경로 → 404
  ⑤ POST → 501 (설계에서 405→501 변경, 사유는 design 계약 절) ⑥ 색인 없는 DB → 트레이스백 대신 빈 결과
- **근거**: `docs/digest.md` "반복 실패" 에 **CLI 진입점마다 방어를 따로 쓴다**가
  2회 기록돼 있다. HTTP 핸들러는 **세 번째 진입점**이라 같은 부류가 또 난다.
  방어를 한 자리에 모으는 것을 설계에서 정한다
- **건드릴 파일**: `src/websearch/serve.py`, `tests/test_serve.py`
- **의존**: 1
- **상태**: 완료 (2026-08-25, 반복 33 — 테스트 10개, 전체 115/115)

### 4. p95 측정 명령과 기준선
- **완료 기준**: 스크립트가 질의 셋을 N회 돌려 p50·p95 를 출력한다.
  숫자와 그때의 색인 문서 수를 `docs/project.md` 품질 기준 "성능 측정"·
  "기준선 파일" 에 적는다. 측정은 **로컬 서버 대상**이고 네트워크를 타지 않는다
- **건드릴 파일**: `e2e/perf_search.py`(신설), `docs/project.md`
- **의존**: 2
- **상태**: 완료 (2026-08-25, 반복 34 — p50 1.26ms · p95 6.60ms / 3000문서)

## e2e 시나리오 <!-- 사용자가 하는 그대로 -->

1. 로컬 서버 페이지 몇 개를 crawl 로 수집하고 색인한다(기존 e2e 와 같은 방식).
2. `python3 -m websearch.serve <db> --port 0` 로 API 서버를 띄운다.
3. `GET /search?q=김치` — 200, JSON, 정답 URL 이 결과에 있다.
4. `GET /search?q=김치&page=2` — 1페이지와 겹치지 않는다.
5. `GET /search` (q 없음) → 400, `GET /없는경로` → 404, `POST /search` → 501.
   **어느 것도 트레이스백을 내지 않는다.**
6. `e2e/perf_search.py` 가 p50·p95 숫자를 출력한다.
