**문서당 81,954B 는 계획 77 압축이 실물에서 처음 확인된 값**이다(옛 250,184B).
10만 문서 환산 **8.2GB** 로 계획 77 의 예측 8.6GB 와 맞는다.

## 2. robots 실측 — 12/12 허용

도메인당 요청 1건 · 1초 간격으로 확인했다. 확인 자체가 예의를 지킨다.

| 도메인 | allowed | Crawl-delay | 라이선스 |
|---|---|---|---|
| docs.python.org · peps.python.org | True | 없음 | PSF |
| developer.mozilla.org | True | 없음 | CC BY-SA 2.5 |
| en·ko·simple.wikipedia.org | True | 없음 | CC BY-SA |
| en.wikibooks / wikiversity / wikiquote .org | True | 없음 | CC BY-SA |
| docs.djangoproject.com | True | 없음 | BSD |
| doc.rust-lang.org | True | 없음 | MIT / Apache-2.0 |

**`www.gnu.org` 의 4초는 지킨다** — `_fetch_one` 이 `max(DOMAIN_INTERVAL, floor,
requested)` 로 잡으므로 깎이지 않는다. 그 도메인만 초당 0.25문서로 기여하고 그것이 맞다.

## 3. 고른 기준 셋 — 셋 다 만족해야 넣는다

1. robots 가 **허용**한다 (실측)
2. 본문이 **열린 라이선스**다 — 색인은 원문 HTML 을 저장한다
3. 문서가 **깊다** — 링크를 따라 수천 장이 나와야 규모에 기여한다

## 4. 코드를 안 만든 이유

CLI 가 시드를 인자로 받으므로 `grep` 한 번이면 된다:

```bash
PYTHONPATH=src python3 -m websearch.crawl $(grep -v '^#' seeds/tier1.txt) --max 100000
```

`--seeds-file` 플래그를 새로 만들 이유가 없다. **파일로 남기는 이유는 다른 데 있다** —
시드를 매번 손으로 치면 「어느 도메인을 왜 골랐나」와 「robots 를 확인했나」가 셸
히스토리에만 남는다. 크롤 윤리가 갈림길 1순위인데 그 판단을 검증할 수 없게 된다.

## 5. 요약의 천장 표기가 부정확한 자리 — 적어 뒀다

요약은 천장을 **도메인 수로만** 센다. 12도메인 중 `www.gnu.org` 가 4초를 요구하므로
참값은 **11.25** 인데 `12.00` 으로 나온다. 정확히 재려면 `Frontier` 의 도메인별 간격
표가 필요한데 CLI 는 그것을 안 들고 있고, 이 줄의 목적은 **자릿수 안내**지 계량이 아니다.

**틀리는 방향이 안전한 쪽이다** — 천장을 높게 부르면 「아직 여유가 있다」로 읽혀
**간격을 깎을 이유가 안 생긴다.** 낮게 부르면 반대가 되고, 그 압력이 계획 81 이 못을
박은 자리다. 코드 주석에 이 근사와 방향을 적었다.
