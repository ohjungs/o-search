# 결과 — 계획 90 `rejection-visible`

## 1. 근거 — 계획 84 가 문제를 고치면서 **자를 같이 없앴다**

2026-09-10 회수 크롤(3,000장) 뒤 「백오프가 얼마나 일했나」를 재려니 **DB 에 증거가
0건**이었다. 계획 84 가 「429 는 페이지가 아니라 거절」이라 `pages` 에 안 박게 했고
**그 판단은 옳다** — 그런데 그 순간 이 축의 **관측이 통째로 사라졌다.**

어제 1만 크롤은 `429 3,686건` 이라는 숫자가 있어서 문제를 **잴 수** 있었다.
오늘은 크롤 로그의 폐기 3줄이 유일한 증거였다.

**안 박는 것과 안 세는 것은 다르다.** 저장은 「이 URL 은 이렇다」는 **주장**이라 거짓이
되고, 세는 것은 「이번 실행에서 이런 일이 있었다」는 **사실**이다.

## 2. 결과

```
수집 N 페이지 · 거절 M건(429) · … 도메인 · …초 = … 문서/초 (지속 상한 …)
```

**0 은 안 찍는다** — 매 실행 「거절 0건」이 붙으면 요약이 길어지고, 길어진 요약은
안 읽힌다. 그러면 정작 0 이 아닌 날을 놓친다. 전수 **749 OK rc 0**.

## 3. 이 계획이 훨씬 큰 것을 하나 잡았다 — 테스트가 실물 코퍼스를 쓰고 있었다

`crawl.main` 은 DB 경로를 안 받는다. 기본값이 곧 **사용자의 실물 코퍼스**다.

```
전수 20초 → 267초   ← 계획 88(되찾기)이 들어간 뒤
원인: main 호출 테스트마다 data/crawl.db(0.94GB · 14,160행)를 열고
      미완 URL 1,000개를 읽어 왔다. -b 로 가려져 아무도 못 봤다.
```

**느린 것보다 나쁜 것은 테스트가 사용자 데이터에 행을 넣는다는 사실이다.**
이 파일은 크롤러를 재는데, 그 크롤러가 실제로 크롤 결과를 그 DB 에 썼다.

처방은 `setUpModule` 에서 `DEFAULT_DB` 를 임시 경로로 씌우는 것 —
**모듈 하나로 막는다.** 개별 테스트에 맡기면 새 테스트가 생기는 날 빠진다
(`Frontier._scope` 를 `add` 한 자리에만 둔 것과 같은 이유다).

결과: **267초 → 20.25초**, 실물 코퍼스는 다시 안 건드린다.

## 4. 왜 못 봤나

- `-b`(버퍼)가 출력을 삼켰다.
- 계획 88 전에는 실물 DB 를 **열기만** 해서 느리지 않았다 — 되찾기가 들어가며
  **읽는 양이 1,000행**이 되자 비로소 시간으로 드러났다.
- **성능 회귀가 결함을 드러낸 것**이지, 성능이 문제였던 게 아니다.

## 5. 남은 것

`crawl.rejected` 는 **함수 속성**이다. 반환 형태를 안 바꾼 이유는 호출부가 여섯이고
전부 정수를 기대하기 때문이다 — CLI 하나가 읽는 값 때문에 공개 계약을 넓히지 않는다.
대가는 `crawl` 을 목으로 바꾼 테스트에서 `Mock` 이 참으로 읽히는 것이고,
`isinstance(rejected, int)` 한 줄로 치렀다(실측 `TypeError` 가 잡아 줬다).
