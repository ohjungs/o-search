- 한 일: 리뷰가 올린 **승인 필요 1건**을 닫았다. `indexer.passages` 가
  `extract.extract_blocks(row[0][:MAX_PASSAGE_HTML])` 로 읽는다. 사용자가 저장소에
  승인을 위임했으므로 `rules/severity.md` 3·4절의 사람 게이트는 열린 것으로 보고
  진행했고, **값·단위·자리는 이 반복이 다시 정했다**.
- **셋을 리뷰 제안과 다르게 정했다.** ① **값 100,000** — 직접 재니 리뷰 표보다 2배
  비쌌다(한글·태그 촘촘: 10만자 **11.7ms** · 20만자 23.6ms · 250만자 301.9ms.
  영문·성긴 마크업은 그 절반). 최악값 **1,000자당 0.118ms** 로 잡으면 10만자 × 문서
  10건 = **118ms, 예산 500ms 의 24%**(20만자는 47%라 안 썼다). 리뷰의 «257KB→6.0ms»
  는 성긴 쪽 숫자였고 **비용은 바이트가 아니라 문자와 태그 밀도에 붙는다.**
  ② **단위는 문자** — sqlite 에서 `str` 로 나오고, 바이트로 자르려면 `encode` 가 한 벌
  더 드는 데다(막으려던 그 비용) 코드포인트 중간에서 잘린다. 형제 `MAX_PASSAGE` 도
  문자다. ③ **자리는 `indexer.py`** — `serve` 가 `indexer` 를 import 하므로 반대는
  **순환**이고, `-m websearch.indexer --query` 는 `serve` 를 안 지나 상한이 안 걸린다.
  «자르는 쪽이 상수를 갖는다» 가 형제들과도 맞는다(`MAX_PASSAGE` 는 `serve` 가 자른다).
- **변이 W2 가 테스트 설계의 구멍을 드러냈다**(`.mutation-lock` 아래 셋 · 전부 원복 ·

  글자 좁힘) **RED**(`김치찌` ≠ `김치찌개`) · **W2(값 10만→100만)는 살았다.** fixture 를
  상수에서 만들면(`"봄" * MAX_PASSAGE_HTML`) **상수와 함께 늘어나 값 변경이 안 보인다** —
  기존 형제 상한 테스트도 같은 모양이다. 그래서 **값 가드**를 하나 더 세워
