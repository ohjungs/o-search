## 명령

**아래 명령은 전부 맨몸으로 돈다** — 파이프·`grep`·`head`·`tail`·리다이렉션을 붙이지
않는다. 붙이면 러너의 종료 코드와 판정 줄이 잘려 **실패가 통과로 보인다**
(`digest ## 반복 실패` 의 최다 재발 항목이다 — 방아쇠는 언제나 "이미 초록일 것 같은
실행"이다). 규율이 아니라 배치 문제라 `status.md ## 한도` 에만 있던 이 문장을
**명령을 읽는 자리**로 옮겼다.

  **1번과 4번이 대리 지표인 이유**: LCP 와 레이아웃은 브라우저 없이 못 잰다.
  헤드리스 브라우저는 의존성 추가라 루프가 야간에 붙일 수 없다. 그래서 LCP 를
  *나쁘게 만드는 원인*과 360px 을 *넘치게 만드는 원인*을 대신 잰다.
  **못 잡는 것**: 브라우저 레이아웃·페인트 시간, 웹폰트(지금 0개), 실제 RTT.
  **올리는 법**: 사람이 헤드리스를 붙이기로 하면 1번을 Lighthouse LCP 로 교체한다.

  **대비는 검사기가 색값을 들지 않는다** — `--fg-*`/`--bg-*` 토큰을 응답 CSS 에서
  매번 읽어 계산한다. 색을 고치면 검사기가 새 값으로 다시 잰다(드리프트 불가).
  `--fg-` 토큰을 새로 만들고 `design_check.PAIRS` 에 짝을 안 적으면 **종료 2** 다.
  (변이 확인 7종 전부 잡힘: JS 70KB→1 · 대비 2.78:1→1 · `width:800px`→1 ·
  `overflow-wrap` 제거→1 · viewport 제거→1 · 짝 없는 `--fg-` 토큰→2 · 토큰 전무→2)

  **검사기가 눈이 멀어 있던 네 자리를 리뷰가 찾아 닫았다**(2026-08-27, 반복 75).
  전부 "없어진 것을 못 보는" 같은 실패 유형이다 — 초록불이 근거 없이 켜져 있었다.
  1. 다크 블록이 없으면 라이트 맵이 다크 행세를 하며 **7쌍 OK 를 찍고 종료 0**
     이었다. 다크 CSS 를 통째로 지워도 통과했다 → 이제 **종료 2**
  2. 다크 미디어쿼리가 2개면 `"".join()` 결과가 원문에 없어 `replace` 가 무동작이
     되고 **라이트 맵이 다크 값으로 오염**됐다(`--bg-page` 가 `#000000` 으로 측정됨)
     → 인덱스 슬라이싱 + 중괄호 세기. `and (min-width:…)` 가 붙은 형태도 이제 찾는다
  3. `PAIRS` 커버리지 강제가 라이트 맵만 봐서 **다크에만 있는 `--fg-` 토큰이
     그냥 빠져나갔다** → 두 맵의 합집합
  4. 고정폭 검사가 `px` 만 봤는데 **이 제품 CSS 는 전부 `rem`** 이다. 눈이 먼 자리가
     정확히 제품이 사는 곳이었다 → rem/em/vw/% 환산, 모르는 단위는 **종료 2**

  → `concept.md:22-23` 기능 2 합격**(합격선 80%). 순위 분포 1위 39 · 미검출 1.
  `tokenizer` 계획(010)이 옛 기준선 ko 17 · en 18 을 여기까지 올렸다.
  - **미포함 1건은 `loaf`←`loaves`** 다. 영어 **불규칙** 복수(f→ves)라 `porter` 가
    `loaf`/`loav` 로 가른다. 사전을 들이지 않는 한 못 고친다 (`docs/design_tokenizer.md` 범위 밖)
  - **오탐 기준선 — 매치 수 평균 14.0 · 최소 11 · 최대 28.** 옛 토크나이저는 평균 13.8 ·
    최소 11 · 최대 28 이었다. **매치를 넓히면 이 줄이 먼저 움직인다** — 포함률은 정답이
    들어왔는지만 세고 함께 딸려 온 것은 못 센다. `quality_eval.py` 가 매 실행 찍는다.
    최소 11 은 가드 G2(≤10 이면 측정 불능)의 여유가 **1건**뿐이라는 뜻이다
  - 2~10위가 여전히 0건이라 `recall@1` 과 `recall@10` 이 같다 — **상위 10 이라는 창은 이
    fixture 에서 아무 일도 하지 않는다**(후한 창 덕에 나온 숫자가 아니다). 랭킹 축은
    여전히 못 재고 있고, 재려면 코퍼스를 고쳐야 하는데 코퍼스는 동결이다
  코퍼스·질의 셋은 **동결**이다 — 바꾸면 이 숫자와 비교가 끊긴다
- **근거 문단 품질·지연**: `PYTHONPATH=src python3 e2e/passage_eval.py` — 같은 동결
  코퍼스·질의를 **문장 단위 `<p>` 로만 다시 포장해** 색인하고(`quality_eval.py` 와 코퍼스는
  한 글자도 안 고친다) `--port 0` 서버의 `GET /passages` 를 HTTP 로 두드린다. 종료 **0**
  통과 · **1** 미달(정확도 <90%(사양 기능 8) 또는 p95 >500ms(성능 5)) · **2** 측정 불능.
  (2026-09-02 실행 확인, 약 1.5s. **다섯 갈림길을 전부 변이로 확인했다** — 점수 무시하고
  첫 블록 선택→정확도 10.2% 로 1 · 통짜 포장으로 되돌림→2(G4 블록<2 + G6 문단==본문) ·
  마침표를 버려 색인 본문이 바뀜→2(G7) · fixture 경로 오타→2 · 예산 1ms→1).
  `--repeat 0` 은 표본이 0이라 **2**(전엔 트레이스백을 내며 rc 1 로 샜다 — 1 은 «미달» 이다)
- **근거 문단 기준선**: **2026-09-02 / 64문서(블록 253개) / 40질의 × 5회 = 200요청:
  정확도 100.0% · 채택률 99.5%(문단 398 / 매치 문서 400) · p95 1.38ms**(예산 500ms 의 0.3%).
  - **정확도 100% 는 기본값이다** — 문단을 **고르는** 규칙(`indexer.passages`)과 여기서
    **재는** 규칙이 `_bigrams` 를 같이 쓰는 **같은 술어**다. 숨기지 않고 도구 첫 화면에
    적어 두었고, 그래서 이 도구의 이빨은 정확도가 아니라 **종료 2 가드 넷**이다.
    실제로 움직이는 숫자는 **채택률**이고(사양에 선이 없어 기록만 한다) 매치 없는 문서에
    첫 블록을 대신 내는 변이에서 99.5 → 100% 로 움직였다 — 그 변이의 정확도는 99.5% 라
    합격선 90% 를 못 건드린다. **그 변이를 죽이는 것은 단위 `TestPassages` 둘이다**(실측)
  - **p95 에 안 들어 있는 축이 둘이다.** 코퍼스가 64문서라 **FTS 축**은 아래
    `perf_search` 기준선(3000문서)이 재고 있고, 코퍼스 문서가 작아 **문서 크기 축**은
    아무도 안 재고 있다(설계 탐침 실측: 18KB 문서 10건 재파싱 20.8ms). 사양의 500ms 는
    100만 문서 기준이라 **이 숫자도 합격 판정이 아니라 회귀용 기준선**이다
  - **문서 크기 축은 이제 재는 대신 막는다** (2026-09-02 개발 4). `indexer.MAX_PASSAGE_HTML`
    **= 100,000자**가 재파싱 입력을 자른다 — 실측 최악(태그가 촘촘한 한글) 1,000자당
    **0.118ms** 이고 `PASSAGE_LIMIT` 10건이면 **118ms, 예산의 24%**. 상한이 없으면
    크롤러 자신의 `fetcher.MAX_BYTES`(2MB)까지 채운 문서 10건이 예산을 넘는다.
    **천장은 «잘린 뒤의 문단은 근거로 안 나온다»** 이고 그 문서도 검색에는 그대로 나온다.
    값을 바꾸면 **단위 `TestPassages` 의 값 가드**가 예산 25% 선에서 막는다
- **기준선 파일**: 없음 — 숫자를 여기 적는다. **2026-08-27 / 3000문서 색인 /
  질의 5종 × 200회 = 1000 요청: p50 1.39ms · p95 9.11ms · 최대 9.50ms** (예산 300ms 의 3.0%).
  옛 기준선은 2026-08-25 의 p50 1.27ms · p95 6.71ms 였고, `tokenizer` 계획(010)의
  한글 2-gram 열이 **p95 를 1.36배로** 올렸다 — 색인도 3000문서에서 1.3→3.1MB(2.4배)다.
  매치 품질(ko 85%→100%)과 맞바꾼 값이고 컨셉 우선순위상 품질이 성능보다 위다.
  p95 를 끌어올리는 것은 `page=100`(OFFSET 990, p50 9.06ms) 하나다 — 나머지 질의는
  모두 1.9ms 이하다.
  **이 숫자는 합격 판정이 아니다** — 컨셉의 300ms 는 100만 문서 기준이고 여기는 3000문서다.
  색인이 커지거나 질의 경로가 바뀌었을 때 이것과 비교해 회귀를 잡으라고 적어 둔다
