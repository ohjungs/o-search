# 결과 — 계획 91 `frontier-persist` — 크롤이 실행을 넘어 이어진다

## 1. 실물 결과

```
1회차: 수집 3 · discovered 20 · pages 3
2회차: 수집 5 · pages 8      ← 시드가 신선한데도 이어받았다
```

**고치기 전 2회차는 0장이다.** 시드가 신선해 팝 지점에서 스킵되고, 링크 추출이 없으니
큐가 비어 크롤이 그대로 끝났다. 전수 **753 OK rc 0**.

## 2. 계획 87 이 「정답」으로 적어 둔 것

87 이 실물에서 잡았고 88 이 **절반**을 닫았다 — 88 은 `pages` 에 **이미 있는** 미완
URL 을 되찾았지만, **큐에만 있다가 종료된 URL** 은 `pages` 에 한 번도 안 들어가므로
여전히 잃었다(88 e2e 3절이 「진짜 영속화의 몫」으로 적어 뒀다).

**이것이 규모를 막는다.** 컨셉 1단계(10만 문서)는 한 번에 도는 크기가 아닌데,
`--max` 로 끊긴 크롤이 다음 실행에 그 지점을 못 이어받았다.

## 3. `pages` 에 안 박고 별도 표를 둔 이유

`pages` 는 **「받아 본 것」**이다. 발견은 수집이 아니다. 안 받은 URL 을 거기 넣으면
계획 84·86 이 429 에서 닫은 거짓(**「안 받은 것을 받았다고 적는다」**)을 다시 여는
것이다. 그래서 `discovered(url, seen)` 한 표를 따로 뒀다.

**지우는 자리는 안 만들었다.** 받고 나면 `pages` 에 행이 생겨 `unfinished()` 가 알아서
뺀다 — 지우는 곳이 둘이면 한쪽만 고쳐진다. 판정은 `unfinished` 한 곳이다.

## 4. `Frontier.add` 가 받아들인 것을 돌려준다

발견 URL 을 디스크에 남기려면 **무엇이 큐에 들어갔나**를 알아야 한다. 처음에는
`u in frontier` 로 물으려 했는데 그런 연산자가 없었고, **만들지 않았다** —
부르는 쪽이 범위·중복을 **다시** 판정하면 거르는 자리가 둘이 되고, 그러면 새 호출부가
생기는 날 조용히 샌다. `Frontier` 가 `_scope` 를 `add` 한 곳에만 둔 것과 같은 이유다.

그래서 `add()` 가 받아들인 목록을 돌려주고, 크롤은 `store.remember(frontier.add(found))`
한 줄이다. **`--same-site` 범위를 넘은 URL 은 애초에 안 돌아오므로 기억되지도 않는다** —
계획 88 이 계약으로 못박은 「되찾기가 범위를 안 넓힌다」가 여기서도 공짜로 지켜진다.

## 5. 남은 것

- **`discovered` 는 안 지운다.** 10만 문서 크롤이면 이 표도 수십만 행이 된다. 지금은
  `unfinished(limit=1000)` 이 읽는 양을 막고 있고, 표 자체의 크기는 아직 근거가 없다.
- **우선순위가 없다.** 오래된 순으로만 준다 — 어느 URL 이 더 값진가는 랭킹 문제이고
  크롤 예산이 진짜로 모자랄 때 열 자리다.
