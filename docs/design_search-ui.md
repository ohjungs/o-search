## 갈림길 1 — HTML 을 어디로 내나

### 대안

| | 형태 | 되돌릴 수 있나 | 더 적게 쓰나 | 기존 것과 맞나 | 다음이 편한가 |
|---|---|---|---|---|---|
| 가 | `/search` 에서 `Accept` 협상 | 나쁨 — 이미 나간 URL 의 의미가 바뀐다 | 헤더 파싱 + 한 핸들러에 두 렌더 | 아니오 | 캐시·디버깅이 헤더에 묶인다 |
| **나** | **`/` 는 HTML, `/search` 는 JSON 유지** | **좋음 — 분기 하나 지우면 원상** | **분기 하나 + 템플릿** | **예 — `do_GET` 이 이미 경로로 분기** | **둘이 서로 안 막는다** |
| 다 | 정적 HTML + `fetch()` | 보통 | JS + 정적 파일 서빙 = 가장 많다 | 아니오 — 서빙할 정적 경로가 없다 | LCP 를 스스로 나쁘게 만든다 |

### 고른 것: (나)

**(가)를 버린 이유.** `Accept` 협상은 **같은 URL 이 클라이언트에 따라 다른 것을 내게**
한다. 브라우저는 `text/html,application/xhtml+xml,*/*;q=0.8` 을 보내고 curl 은 `*/*` 를
보낸다 — 그러면 `e2e/perf_search.py` 가 재는 p95 가 **어느 코드의 p95 인지 헤더에 달리게**
된다. 성능 축(`concept.md` 우선순위에서 디자인보다 위다)의 측정 대상이 흐려지는 것을
디자인 편의로 사는 거래라 우선순위가 거꾸로다. 되돌리기도 나쁘다: 이미 `/search` 를
JSON 으로 쓰는 e2e 둘이 있는데, 협상을 넣으면 그 계약이 "헤더에 따라 참"이 된다.

**(다)를 버린 이유.** JS 를 0KB 에서 올린다. `concept.md:50` 을 형식상으로는 지키지만
(50KB 여유가 크다) **첫 화면에 왕복을 하나 더 얹는다** — HTML 받고, JS 받고, 그제야
`/search` 를 친다. LCP 1.5s 는 이 계획이 스스로 재겠다고 세운 기준인데 첫 결정으로
그 기준을 나쁘게 만드는 것은 자기 발등이다. `concept.md:71` 이 크롤 쪽에서 "정적 HTML만,
SPA 는 못 읽는 것을 받아들인다"고 정해둔 것과도 결이 맞는다 — **우리가 남에게 요구하는
형태를 우리 화면이 어기지 않는다.**

**(나)의 화면 수는 둘이다** (`concept.md:49` "화면은 둘뿐"):

```
GET /            → 검색 홈   (검색창 하나)
GET /?q=김치     → 결과 페이지 (검색창 + 결과 리스트)
GET /search?q=…  → JSON  (기존 그대로, 한 바이트도 안 바뀐다)
그 외            → 404    (기존 그대로)
```

같은 경로가 `q` 유무로 홈/결과를 가르는 것은 **분기 하나**다. 경로를 하나 더 파면
(`/results`) 코드가 늘고 화면 수 계약이 애매해진다.

**되돌리는 수단**: `do_GET` 의 `/` 분기와 템플릿 상수를 지운다. `/search` 쪽 코드는
손대지 않으므로 되돌림이 JSON 경로에 닿지 않는다. 브랜치째 버리는 것은 그다음 수단.

### 파라미터 검증은 재사용한다 — 새로 만들지 않는다

`serve.py:24` 의 `_parse()` 가 이미 `q`(1~200자)·`page`(1~100)를 검증한다.
HTML 경로도 **같은 함수를 쓴다.** `rules/security.md` 의 이유가 아니라 `serve.py:27`
주석이 직접 말하는 이유다 — *"진입점 방어를 여기 한 곳에 모은다. 핸들러 메서드마다
흩으면 하나가 빠진다."* 화면용 검증을 따로 쓰면 그 주석이 예언한 그대로 된다.

**차이는 하나**: 홈은 `q` 가 없는 것이 정상이다. `_parse()` 는 빈 `q` 에
`ValueError` 를 낸다. 그래서 HTML 경로는 **`q` 가 비었으면 `_parse()` 를 부르기 전에
홈을 낸다.** `_parse()` 를 고치지 않는다 — 고치면 JSON 경로의 400 계약이 바뀐다.

`ValueError` 는 HTML 경로에서 **400 + 사람이 읽는 오류 화면**이 된다. JSON 과 같은
사유 문자열을 쓰되 `html.escape()` 를 통과시킨다 (사유에 사용자 입력이 섞이지
않지만 — `_parse()` 의 문구는 전부 상수다 — 그 성질에 기대지 않는다).

## 갈림길 2 — 대비 4.5:1 을 무엇에 대고 재나

### 문제의 진짜 모양

브라우저 없이 "이 텍스트가 저 배경 위에 있다"를 알려면 CSS 캐스케이드가 필요하다.
캐스케이드를 재현하는 것은 파서 한 벌이고, 야간에 의존성을 못 붙이니 직접 짜야 한다 —
**검사기가 검사 대상보다 커진다.** 그렇다고 검사기에 색을 하드코딩하면
**드리프트**한다: CSS 의 색을 고쳐도 검사기는 옛 값으로 통과를 내준다. 그건 검사가
아니라 검사처럼 생긴 상수다.

### 대안

| | 방법 | 드리프트 | 커버리지 구멍 | 크기 |
|---|---|---|---|---|
| 가 | 검사기에 기대 색값 하드코딩 | **있다** | 있다 | 작다 |
| 나 | CSS 캐스케이드 구현 | 없다 | 없다 | **검사 대상보다 크다** |
| **다** | **토큰 이름 쌍만 검사기가 들고, 값은 매번 CSS 에서 읽는다** | **없다** | **규약으로 막는다** | **작다** |

### 고른 것: (다) — 이름은 검사기, 값은 CSS

CSS 의 모든 텍스트·배경 색을 **커스텀 프로퍼티로만** 선언하고 이름에 규약을 준다:

```css
:root{ --bg-page:#fff; --fg-body:#1a1a1a; --fg-muted:#5c5c5c; --fg-link:#a83208; … }
```

검사기가 들고 있는 것은 **쌍의 이름**뿐이다:

```python
PAIRS = [("--fg-body", "--bg-page"), ("--fg-muted", "--bg-page"), …]
```

값은 **응답 HTML 의 `<style>` 에서 매번 읽는다.** 색을 고치면 검사기가 새 값으로
다시 계산한다 → 드리프트가 구조적으로 불가능하다.

**커버리지 구멍은 규약이 막는다.** 검사기는 스타일에 있는 `--fg-` 로 시작하는 토큰을
전부 모아 **`PAIRS` 에 빠진 것이 하나라도 있으면 종료 2**(측정 불능)를 낸다. 새 텍스트
색을 추가하면 쌍을 적기 전까지 검사가 통과하지 않는다. "검사기에 안 적었으니 안 재고
넘어간다"가 불가능해진다.

**다크 모드는 두 번째 맵이다.** `@media (prefers-color-scheme: dark)` 블록의
`--…:…` 선언을 기본 맵 위에 덮어 두 번째 맵을 만들고, **같은 `PAIRS` 를 두 맵 모두에**
돌린다. 다크만 대비가 깨지는 것이 가장 흔한 회귀인데 그 자리를 정확히 덮는다.

**계산은 WCAG 2.x 상대휘도 그대로다** (stdlib 만으로 12줄):
채널 `c/255` → `c/12.92 if c<=0.03928 else ((c+0.055)/1.055)**2.4`,
`L = .2126R+.7152G+.0722B`, 비율 `(L밝+.05)/(L어두+.05)`.
색 표기는 **`#rgb`·`#rrggbb` 만 허용**한다. 그 외(`rgb()`·`color-mix()`·명명색)를
만나면 **종료 2** — 조용히 건너뛰면 그게 커버리지 구멍이다.

### 4.5:1 — 시안 팔레트를 실측했다. 색을 바꿀 필요가 없다

**이 절은 한 번 틀렸다가 고쳤다. 그 사실을 남긴다.**
처음에 나는 `demo_ui.py` 의 `#c2410c` 링크가 흰 배경 위에서 4.06:1 이라 미달이고
`#6b6b6b` 는 4.83:1 로 아슬아슬하다고 **눈으로 짐작해 적었다.** 그리고 두 색을
바꾸는 계획까지 세웠다. 실제로 WCAG 식을 돌려보니 전부 틀렸다:

| 색 | 배경 | 실측 |
|---|---|---|
| `#1a1a1a` 본문 | `#fff` | 17.40 |
| `#4d4d4d` 스니펫 | `#fff` | 8.45 |
| `#6b6b6b` 메타 | `#fff` | **5.33** (짐작 4.83) |
| `#c2410c` 링크·브랜드 | `#fff` | **5.18** (짐작 4.06) |
| `#7c6f64` URL | `#fff` | **4.87** ← 가장 낮다 |
| `#fff` 버튼 글자 | `#c2410c` | 5.18 |
| `#eee`/`#fdba74`/`#c9c1bc`/`#a1897a`/`#a89a92` (다크) | `#141110` | 16.20 / 11.14 / 10.59 / **5.70** / 6.89 |
| `#1a1008` 버튼 글자 (다크) | `#f97316` | 6.68 |

**전부 4.5 를 넘는다. 가장 낮은 것이 `#7c6f64` 의 4.87.**
그래서 **색을 하나도 바꾸지 않는다** — 바꿀 이유가 실측에 없다 (ponytail 1번).

이것이 갈림길 2 를 (다)로 고른 이유를 그대로 증명한다. **사람의 색 감각은 대비비를
못 맞춘다.** 내가 방금 두 색 다 1할 넘게 틀렸다. 검사기가 값을 CSS 에서 읽어
매번 계산하지 않으면, 다음에 색을 만지는 사람도 정확히 같은 방식으로 틀린다.

여유가 가장 적은 `#7c6f64`(4.87) 가 이 팔레트의 **회귀 최전선**이다. 검사기가
이 쌍을 반드시 덮어야 하고, 실패했을 때 "어느 쌍이 몇 대 1인지" 출력해야 한다.
(측정 명령: `e2e/design_check.py`. 위 숫자는 그 식으로 2026-08-27 실측.)

## 나머지 두 축 — 천장을 명시한다

### LCP 1.5s → 대리 지표 (`ponytail:` 천장)

**직접 못 잰다.** 실측하려면 헤드리스 브라우저가 필요하고, 야간 의존성 추가는
정지 조건이다. 대신 **LCP 를 나쁘게 만드는 원인 쪽**을 잰다:

| 재는 것 | 왜 |
|---|---|
| 외부 서브리소스 0건 (`<script src>`·`<link rel=stylesheet>`·`<img>`·`@import`) | 왕복이 늘면 LCP 가 늘어난다. HTML 한 왕복이면 상한이 RTT+생성시간이다 |
| 문서 gzip 바이트 | 전송 시간의 유일한 변수 (왕복이 1이므로) |
| 서버 생성 시간 p95 (로컬 왕복) | 이미 `perf_search.py` 가 JSON 에 대해 재는 것의 HTML 판 |

**못 잡는 것**: 브라우저 레이아웃·페인트 시간, 웹폰트(지금 0개), 실제 네트워크 RTT.
**업그레이드 경로**: 사람이 헤드리스 브라우저를 붙이기로 하면 Lighthouse LCP 로
교체한다. 그때까지 이 셋이 대리한다. 검사기 상단에 이 문단을 `ponytail:` 주석으로 박는다.

### 360px 가로 스크롤 → 원인 셋

레이아웃 없이 판정할 수 없으니 **넘치게 만드는 원인**을 잰다:

1. `<meta name="viewport" content="width=device-width…">` 가 있다
2. CSS 에 **360px 을 넘는 고정폭이 없다** (`width:`/`min-width:` 의 px 값)
3. **끊기지 않는 긴 문자열을 접는 선언이 URL 자리에 있다** (`overflow-wrap:anywhere`)

3번이 이 제품의 진짜 원인이다. 검색 결과에 나가는 것은 **크롤한 남의 URL** 이고,
공백 없는 긴 URL 하나가 360px 뷰포트를 그대로 밀어낸다. 1·2 만 재면 이 축은
"통과하는데 실제로는 넘치는" 검사가 된다.

## 스텝별 산출물 (계획 5절을 구체화한다)

### 스텝 1 — `src/websearch/serve.py`, `tests/test_serve.py`

- `do_GET` 에 `parts.path == "/"` 분기. `/search` 분기는 **손대지 않는다.**
- 모듈 상수로 `PAGE`(문서 뼈대 + `<style>`)·`SEARCHBOX`. `str.format` 을 쓰되
  **치환값은 전부 `html.escape()` 를 통과한 뒤에** 들어간다.
- **이스케이프 4자리**: 질의어(입력 `value`·`<title>`), 결과 제목, URL, 스니펫.
  `html.escape(s, quote=True)` — 속성 자리(`value=`·`href=`)에 들어가는 것은
  기본값 `quote=True` 가 필요하다.
- **`href` 는 이스케이프만으로 부족하다.** `javascript:` 스킴은 `&`·`<`·`"` 를 하나도
  안 쓰고 `html.escape()` 를 그대로 통과한다. 크롤러가 `http`/`https` 만 담는다는
  성질에 기대지 않고 **렌더 시점에 스킴을 확인**한다(아니면 링크 없이 텍스트로).
  신뢰 경계라 ponytail 사다리로 줄이지 않는다.
- 접근성: `<form role="search">`, 입력에 `aria-label` 또는 연결된 `<label>`,
  `<html lang="ko">`, 결과 제목은 `<h2><a>`. **키보드는 폼 GET 이라 기본으로 된다** —
  탭으로 입력→버튼, 엔터로 제출. JS 가 없으니 포커스 트랩도 없다.
- 테스트는 `tests/test_serve.py` 의 `ServeTestCase`(임시 DB·포트 0)를 상속한다.

### 스텝 2 — `e2e/design_check.py`(신규), `docs/project.md`

- `serve.make_server(db, 0)` 를 스레드로 띄우고 `/` 와 `/?q=…` 를 받아 잰다.
  **실제 네트워크 없음.** 코퍼스는 `e2e/quality/` 를 재사용한다.
- 종료 코드: **0** 통과 · **1** 기준 위반 · **2** 측정 불능
  (색 토큰 없음 / `PAIRS` 에 빠진 `--fg-` 토큰 / 해석 못 하는 색 표기 / `<style>` 없음).
  `e2e/quality_eval.py` 가 이미 쓰는 관용구다.
- 축마다 실측 숫자를 출력한다 — 통과/실패만 찍으면 `project.md` 에 적을 것이 없다.
