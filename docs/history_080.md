- **근거는 오늘 남의 서버에 실제로 간 피해다.** 1만 크롤에서 위키미디어 6도메인이
  응답의 **50~68%(3,686건)** 를 429 로 거절하는데 같은 간격으로 계속 보냈다. 여섯이
  **같은 IP** 라 호스트마다 1초를 지킨 것이 **한 서버에 초당 6건**이 됐다 — 컨셉의
  「도메인당 1초는 전제 조건」을 **글자로는 지키고 뜻으로는 어겼다.**
- **IP 로 안 묶었다** — CDN 뒤 무관한 사이트 수천 개가 한 IP 를 쓰므로 더 나쁘다.
  **429 백오프는 왜 429 인지 몰라도 옳다**: 원인이 무엇이든 처방이 같고, 서버가 유일하게
  신뢰할 수 있는 정보원이다.
- **새 기계를 안 만들었다** — `set_delay` 가 이미 단조 증가 + `MAX_DELAY` 초과 시 도메인
  폐기라 429 백오프가 필요로 하는 동작 그대로다. 실물: **2.0→4.0→8.0→16.0초** 뒤 폐기,
  8개 URL 중 **5번만** 보내고 손을 뗐다. `pages` 행 **0** (429 는 안 박힌다).
- **되돌리기는 두 번 확인하고 안 했다.** `add` 가 `_seen` 으로 막아 조용히 무효였고,
  우회해서 되돌리는 편이 낫지도 않다 — 방금 「너무 잦다」고 한 URL 을 같은 실행에서 다시
  치는 것은 물러나는 게 아니다. 저장을 안 했으므로 다음 실행이 자연히 받는다.
- **테스트가 시계에서 두 번 미끄러졌다** — 멈춘 시계로는 쿨다운이 안 풀려 한 번만 나갔고,
  `now()` 마다 흐르게 하니 내부 조회까지 시간을 밀어 **무한히 돌았다**(300초 타임아웃).
  셋째 판이 맞았다: **읽기는 공짜, 발신만 60초.** 계획 78·82 의 시계 교훈의 세 번째 칸.
