- 슬러그: `graceful-interrupt` · 브랜치: `loop/graceful-interrupt`
- 상태: **DONE** (2026-08-30. 개발 스텝 1 `f316320` · 2 `3437ff1` · 3 `99de009` · 4 `6349a37` · 테스트 `0c0bc91` · 리뷰 `d5c3496` · e2e `b94bfb8`. 설계서 `design_history_021.md` 의 계약 절이 명세)
- **결과: 목표 12초에 실측 10.0초** — 단위 **447건 OK** · e2e **18종 rc=0**(`--control` 2) · 변이 **17/17 사망** · 결과 기록 `docs/e2e/graceful-interrupt/result.md`
- 선행: 계획 33 `clock-injection` DONE (`crawl()`·`_fetch_one()` 이 `sleep=` 을 받는다)

## 1. 문제 · 목표 · 기대 결과

**문제.** `python3 -m websearch.crawl <seed>` 를 돌리다 Ctrl-C 를 눌러도 프로세스가
바로 안 죽는다. `digest.md` 의 `[4] Ctrl-C 가 최대 30초 안 먹는다` 항목이고, 그 항목이
적어 둔 숫자("최악 90초", "`Event.wait` 로 바꾸면 닫힌다")는 **이번 계획 착수 전 탐침에서
셋 다 틀린 것으로 나왔다.** 아래 2절이 실측이다.

**목표.** SIGINT 를 받은 뒤 **12초 안에** 프로세스가 끝난다. 끝나는 방식은 오늘과 같아야
한다 — 이미 받은 응답은 줍고(DB 커밋 유실 0), 새 요청은 안 나가고, `Crawl-delay` 를
어기는 발신이 하나도 없다.

**기대 결과.** 아래 2절 탐침 A(`Crawl-delay: 30`, 응답 없는 서버)를 다시 돌려
**69.57초 → 12초 이하**. 탐침 B(느린 응답 8초)는 **7.56초 → 8초 이하로 유지**
(여기는 이미 소켓 읽기 하나뿐이라 줄 것이 없다 — 나빠지지 않는 것이 판정이다).

## 2. 실측 — 최악 지연은 무엇으로 이루어져 있나

탐침: `Crawl-delay: 30` 을 선언하고 페이지 요청에 **응답을 영원히 안 주는** 로컬 서버에
`--workers 1` 로 크롤을 걸고, 0.5초 뒤 SIGINT. 서버가 요청 수신 시각을 찍는다.
(스크립트는 스크래치패드 `gi_probe.py`·`gi_probe2.py` — 저장소에 안 넣는다)

```
신호 뒤 종료까지: 69.57초  rc=-2 (SIGINT)
서버 수신:  t= 0.05 /robots.txt
           t= 0.05 /            ← 신호는 t=0.51
           t=30.07 /   (+30.01)
           t=60.07 /   (+30.01)
```

**분해 (한 URL, 재시도 2회):**

| 구간 | 어디 | 실측 | `Event.wait` 로 지워지나 |
|---|---|---|---|
| 소켓 읽기 × 3 | `fetcher.py:39` `urlopen(timeout=10)` | **30초** | **아니오 — 1초도 안 준다** |
| 재시도 앞 잠 × 2 | `crawl.py:74` `sleep(remaining)` | **40초** (각 20초) | 예 |
| 합 | | **70초** | |

세 가지가 `digest.md:160` 과 다르다:

1. **최악은 90초가 아니라 70초다.** 90 은 `10×3 + 30×2` 로 더한 값인데, `before_send` 의
   `remaining = interval - (now() - sends[-1])` 이 **이미 흘러간 타임아웃 10초를 뺀다.**
   그래서 발신–발신 간격은 `interval` 자체(30초)이지 `interval + 10` 이 아니다.
   실측 발신 간격이 정확히 **30.01초**다.
2. **`Event.wait` 는 70초 중 40초만 지운다.** 남는 30초는 전부 소켓 읽기다. 그리고 실제로
   손이 가장 많이 가는 상황(느린 서버, 재시도 없음)은 **7.56초가 전부 소켓 읽기**라
   `Event.wait` 가 **0초** 줄인다. "대기를 `Event.wait` 로 바꾸면 끝" 은 참이 아니다.
3. **잠만 깨우면 예절이 깨진다.** 재시도 앞 잠을 깨우고 그대로 두면 `Crawl-delay: 30` 을
   선언한 서버에 **10초 간격으로 3발**이 나간다. 지금 40초를 붙들고 있는 것이 바로 그
   예절이다. 그러므로 **"잠을 깨우는 것"과 "재시도를 취소하는 것"은 두 변경이 아니라
   하나의 변경이다.** 하나만 하면 RED(`project.md` 한도: robots.txt 준수).

**추가로, 아무도 안 세던 네 번째 자리가 있다.** 탐침 2(`gi_probe2.py`)는 플래그만
세우는 SIGINT 핸들러가 각 대기를 깨우는지 직접 쟀다:

| 대기 | 자리 | 플래그 핸들러가 깨우나 |
|---|---|---|
| `concurrent.futures.wait(timeout=20)` | `crawl.py:184` | **아니오 — 20.01초 다 잔다** |
| `Event.wait(20)` | (`crawl.py:179` 의 후보) | 예 — 0.51초 |
| `time.sleep(5)` | `crawl.py:179` 현재 | **아니오 — 5.01초 다 잔다** |

PEP 475 이후 락 획득은 신호 핸들러가 돌고 나면 **남은 시간으로 재시도**한다. 그래서
`sleep` 자리를 `Event.wait` 로 갈아도 **`futures.wait` 자리는 그대로 최대 30초 잔다**
(`frontier.seconds_until_ready(exclude=busy)` 가 `MAX_DELAY` 까지 나온다).
오늘 Ctrl-C 가 그나마 먹는 이유는 기본 핸들러가 **예외를 던지기** 때문이다 — 탐침 A 의
스택 끝이 `threading.py:312 waiter.acquire() / KeyboardInterrupt` 로, 메인 스레드는
`futures.wait` 안에서 죽는다. 플래그로 갈아타는 순간 이 성질을 잃는다.

## 3. 설계가 필요한 이유 (건너뛰지 않는다)

`design.md` 1절 트리거 중 셋에 걸린다.

- **대안이 2개 이상 갈림** — 워커가 재시도를 포기하는 방법이 최소 셋이다.
  ① `before_send` 가 예외를 던진다(→ `_store_result` 의 예외 가지가 도메인마다
  `요청이 예외로 끝났다` 를 찍는다) ② `_fetch_one` 이 그 예외를 잡아 기존 반환
  튜플의 어떤 모양으로 바꾼다(어떤 모양인지가 곧 계약 변경이다) ③ `fetcher.fetch` 가
  `before_send` 의 반환값을 보고 재시도를 멈춘다(`fetcher` 는 오늘 간격이라는 개념을
  모른다 — `fetcher.py:23-25` 가 명시한 계약이다). 셋의 결과가 서로 다르다.
- **공개 인터페이스 변경** — `crawl(...)` 시그니처에 중단 손잡이가 붙는다.
  `sleep=` 처럼 주입 지점으로 둘지, `stop=Event` 로 둘지, 아예 `sleep` 자리를
  `Event.wait` 로 흡수할지가 안 정해졌다(2절 네 번째 자리 때문에 흡수만으로는 부족하다).
- **3개 이상 파일** — `src/websearch/crawl.py` · `tests/test_crawl.py` ·
  `e2e/` 신규 1개. `fetcher.py` 는 위 ③ 을 고르면 추가된다.

설계가 답해야 하는 것은 **네 자리(소켓·재시도 잠·메인 루프 잠·`futures.wait`)를 몇 개의
기제로 덮는가**이고, 특히 `futures.wait` 를 어떻게 깨울지다.

### 스텝 3 — CLI 가 SIGINT 를 잡는다 — **DONE**

**결과: 단위 445건 OK(+4) · e2e 17종 rc=0 · 변이 4/4 사망.** 제품은 `main()` 25줄.
실물 탐침(서브프로세스에 진짜 SIGINT): **rc 130 · 신호 뒤 0.01초 · 받은 1페이지 유지**.
핸들러 복원은 설계서의 `getsignal` 대신 **`signal.signal` 의 반환값**을 썼다 —
같은 객체인데 등록과 저장이 한 줄이라 순서를 틀릴 자리가 없다.
**계약 9(독스트링의 "최악 90초" → 실측 69.57초)도 여기서 같이 닫았다.**
**교훈: 신호 테스트에 진짜 신호를 쓰지 않는다** — `os.kill(getpid(), SIGINT)` 는
핸들러가 `SIG_DFL` 로 내려간 뒤라 테스트 프로세스를 죽인다. 설치된 핸들러를 직접
부르고, 센티널 핸들러를 깔았다 되돌리는 컨텍스트 매니저 안에서 돈다.

- 자리: `src/websearch/crawl.py:249~292` 의 `main()`.
- 할 일: `signal.signal(signal.SIGINT, ...)` 로 신호를 세우고 `crawl()` 에 넘긴다.
  **두 번째 Ctrl-C 는 기본 동작으로 돌려놓는다** — 첫 번째로도 안 끝나는 상황에서
  사용자가 프로세스를 못 죽이게 되면 지금보다 나쁘다.
  종료 코드와 출력: 중단으로 끝나도 `수집 N 페이지` 를 찍고 rc 를 정한다(값은 설계가 정한다.
  오늘 SIGINT 는 rc=-2 로 죽는다 — 셸에서 130).
- 완료 기준: `tests/test_crawl.py` 신규 — `main()` 이 핸들러를 걸고 **끝날 때
  원래 핸들러로 되돌린다**(`signal.getsignal(SIGINT)` 이 호출 전후로 같다).
  단위 전건 OK.
- 예상 파일: `src/websearch/crawl.py` · `tests/test_crawl.py`
- 의존: 스텝 1·2 (넘길 신호 객체가 있어야 한다)

### 스텝 4 — e2e — **DONE** (`6349a37`, 2026-08-30 13:0x)

`e2e/interrupt_e2e.py` 신규 하나(제품 코드 0줄). rc=0 · 18.3초 · `--control` rc=2 ·
단위 445건 OK · **변이 3종 전부 사망**(메인 루프 검사 제거 → 시나리오 2 가 30.0초 ·
재시도 취소 제거 → 시나리오 1 이 30.0초 · 핸들러 등록 제거 → 40초 안에 안 끝난다).
실측: 안 답하는 서버 + `Crawl-delay: 30` 에서 **SIGINT 뒤 10.0초 · rc 130 · 페이지 요청
1건 · DB 0행**(신호 없이는 69.57초).

**계획이 안 본 것 둘.**
① **스텝 1 변이를 잡은 것은 시나리오 1 이 아니라 2 다.** 안 답하는 서버에서는 워커가
접히고 프런티어가 비어 **메인 검사 없이도** 루프가 끝난다 — 링크가 있어 프런티어가 안
비는 느린 서버라야 그 검사가 유일한 종료 근거다.
② **신호 시점을 고정 sleep 으로 잡으면 안 된다.** "0.5초 뒤 SIGINT" 는 부팅에도 못 미치는
날이 있고, 그러면 아무것도 안 재고 초록이 켜진다 — 서버가 그 요청을 **받은 것을 보고** 보낸다.
계획서의 "응답 8초" 는 **5초**로 낮췄다(`fetcher.TIMEOUT` 10초와의 여유 2초는 부하 걸린
기계에서 타임아웃으로 샌다. 재는 것은 값과 무관하고 상한 단언 8초는 그대로다).

- 자리: `e2e/interrupt_e2e.py` 신규. `e2e/deadline_e2e.py` 가 서버·임시 DB·`--control`
  관용구의 본이다(종료 0 통과 / 1 위반 / 2 측정 불능).
- 할 일: 5절 시나리오를 **CLI 를 서브프로세스로 띄워** 잰다. `crawl()` 직접 호출이
  아니다 — 신호는 프로세스 경계의 물건이고, 계획 020 의 M6(CLI 가 안 넘기는 변이)이
  단위에 안 잡힌 전례가 있다.
- 완료 기준: `PYTHONPATH=src python3 e2e/interrupt_e2e.py` rc=0, 그리고 **변이 3종에서
  전부 실패**: ① 스텝 1 의 루프 검사 제거 ② 스텝 2 의 재시도 취소 제거
  ③ 스텝 3 의 핸들러 등록 제거. e2e 전체 18종 rc=0.

## 5. e2e 시나리오 (지금 확정한다 — 나중에 쓰면 구현에 맞춰 낮아진다)

1. **응답 없는 서버 + `Crawl-delay: 30`.** 크롤 시작 0.5초 뒤 SIGINT →
   **12초 안에 종료**(오늘 69.57초). 서버가 받은 페이지 요청은 **1건**(오늘도 3건이지만
   오늘은 예절을 지키느라 70초를 쓴다 — 이제 안 쓰고도 1건이어야 한다).
2. **느린 서버(응답 8초), 재시도 없음.** 0.5초 뒤 SIGINT → **8초 안에 종료**,
   그 페이지는 **DB 에 들어와 있다**(이미 받은 응답을 버리지 않는다). 회귀 방지용이다.
3. **예절.** 시나리오 1 에서 서버가 찍은 페이지 요청 수신 시각의 최소 간격이
   **`Crawl-delay` 미만이 아니다**(발신이 1건이면 자동 통과 — 2건 이상 나가면 여기서 죽는다).
4. **두 번째 Ctrl-C.** 첫 SIGINT 뒤 0.2초에 두 번째 SIGINT → 프로세스가 죽는다
   (사용자가 탈출구를 잃지 않는다).
5. **대조군** `--control`: 신호를 안 보내면 크롤이 정상 종료하고 페이지를 수집한다.
   측정 불능이면 종료 **2**.

## 6. 하지 않을 것

- **`fetcher.TIMEOUT = 10` 을 낮추기.** 목표 12초의 바닥이 이 10초다. 낮추면 느린
  서버를 통째로 버리는 것이라 별도 판단이다 — `digest.md` 후보로 남긴다.
- **SIGTERM 경로.** 기본 동작(즉시 종료)이 이미 하드 상한이고, 핸들러를 붙이면
  **오히려 느려진다**. 건드리지 않는다.
- **`--deadline` 과의 통합**, 그리고 "재시도를 크롤 루프로 승격"(`digest.md` `[high]`
  닫힘 항목이 "옳지만 크다" 로 남긴 후보). 이 계획은 신호만 넣는다.
- **`serve.py:338` 의 `KeyboardInterrupt`** 와 `indexer.py` 의 중단 — 범위 밖.
- **`digest.md` `[5]` 91만 회 공회전**(`sleep=lambda s: None`). 스텝 1 이 `:179` 를
  바꾸면 저절로 사라질 수 있으나 **표적으로 삼지 않는다** — 리뷰 phase 에서 확인만 하고
  결과를 `digest.md` 에 적는다.
- **`main` 병합.** 사람 판단 항목이다.

## 7. 한도 (넘으면 RED)

- 도메인당 요청 간격 1초 이상 · robots.txt `Crawl-delay` 준수. **중단 중에도 그렇다** —
  중단이 예절의 예외가 되는 순간 이 계획은 실패다.
- `data/crawl.db` 실물·스키마를 건드리지 않는다. 탐침은 임시 디렉터리에서만.
- 외부 네트워크 금지 — 로컬 테스트 서버만.

## 8. 닫으며 — 이 계획이 남긴 것 (2026-08-30)
