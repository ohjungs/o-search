# 컨셉: websearch — 열린 웹 검색엔진

## 무엇을 만드나

누구나 브라우저로 접속해 검색어를 입력하면, 크롤러가 수집·색인한 웹 문서에서
랭킹된 결과(제목·URL·스니펫)를 받는 **공개 웹 검색엔진**.

구글의 "전 웹"은 규모의 문제이지 구조의 문제가 아니다. 이 프로젝트는
**구조를 완성하고 규모는 단계로 키운다**: 시드 URL에서 출발해 링크를 따라
프런티어를 넓히는 크롤러가 색인을 계속 키우고, 검색은 그 시점의 색인 안에서
동작한다. "모든 것을 검색"은 최종 방향이고, 각 단계의 완성 기준은 아래
숫자로 판정한다.

로그인 없음. 누구나 검색할 수 있고, 검색 외의 기능은 없다.

## 이 프로젝트에서 "잘 됐다"는 것

### 기능

1. 검색창에 질의 입력 → 관련도순 결과 목록(제목, URL, 스니펫 3줄 이내,
   검색어 하이라이트). 페이지네이션 10건 단위.
2. 한국어·영어 질의 모두 동작한다. (판정: 한국어 질의 20개·영어 질의 20개
   테스트 셋에서 상위 10건 안에 정답 문서 포함 — 각 80% 이상)
3. 크롤러는 시드에서 출발해 **사람 개입 없이** 프런티어를 확장한다.
   robots.txt 준수, 도메인당 요청 간격 1초 이상은 기능이 아니라 **전제 조건**
   — 어기는 코드는 리뷰에서 RED다.
4. 색인 규모 단계 (단계 완료 = 아래 숫자 + 성능 축 동시 충족):
   - 1단계: 10만 문서
   - 2단계: 100만 문서
   - 3단계: 1,000만 문서 (여기부터 분산 검토 허용 — "하지 않을 것" 참조)
5. 재크롤: 색인된 문서는 30일 이내에 재방문해 갱신·삭제를 반영한다.

### 경량

1. 2단계(100만 문서)까지 **단일 머신**에서 크롤·색인·검색이 전부 돈다.
2. 검색 서버 상주 메모리 2GB 이하 (판정: 100만 문서 색인 로드 후 RSS 측정).
3. 신규 의존성은 계획서에 사유 한 줄 없이 추가하지 않는다.
   저장소·역색인은 SQLite(FTS5)로 시작한다 — 교체는 성능 축 숫자가
   실측으로 깨졌을 때만.

### 성능

1. 검색 응답 p95 300ms 이하 (100만 문서 색인, 로컬 측정 기준).
2. 크롤 처리량 초당 5문서 이상 지속 (politeness 지키면서 — 도메인 다양성으로
   해결하는 문제이지 간격을 줄여 해결하는 문제가 아니다).
3. 문서 1건 색인 반영 지연(수집→검색 가능) 10분 이내.

### 디자인

1. 화면은 둘뿐: 검색 홈(검색창 하나), 결과 페이지(검색창 + 결과 리스트).
2. 결과 페이지 LCP 1.5s 이하, JS 번들 50KB(gzip) 이하 — 검색엔진 프런트는
   가벼운 게 곧 디자인이다.
3. 텍스트 대비 4.5:1 이상, 키보드만으로 검색·결과 이동 가능.
4. 모바일(360px)에서 가로 스크롤 없음.

## 갈림길에서의 우선순위

```
크롤 윤리(robots·간격) > 검색 품질(정답 포함률) > 검색 성능(p95) > 색인 규모 > 기능 추가 > 디자인 다듬기
```

- "색인을 더 키우는 것"과 "지금 색인에서 더 잘 찾는 것"이 부딪히면 **후자**.
  규모는 단계가 정해져 있으니 조급할 이유가 없다.
- "랭킹을 똑똑하게"와 "응답을 빠르게"가 부딪히면 p95 300ms 안에서만 똑똑해진다.
- 저장소·라이브러리 교체 논쟁은 실측 숫자가 깨졌을 때만 연다. 예감은 근거가 아니다.

## 하지 않을 것

- **로그인·개인화·검색 기록** — 누구나 익명으로 쓰는 것이 컨셉이다.
- **광고·수익화** — 없음.
- **이미지·동영상·뉴스 등 버티컬 검색** — 텍스트 웹 문서만. (3단계 이후 재논의)
- **JS 렌더링 크롤링**(헤드리스 브라우저) — 정적 HTML만. SPA 페이지는 못 읽는
  것을 받아들인다. (재논의 조건: 정답 포함률 80%가 이것 때문에 막혔다는 실측)
- **분산 크롤러·분산 색인** — 2단계까지 금지. 단일 머신 한계를 실측으로 확인한
  뒤에만 3단계에서 검토한다.
- **자체 형태소 분석기 개발** — 기존 것을 쓰거나 trigram으로 버틴다.
- **검색어 자동완성·오타 교정** — 핵심 검색이 1단계 기준을 넘긴 뒤에.

# 확장: 다른 시스템이 쓰는 검색 (2026-09-01 사용자 지시)

## 무엇이 달라지나

지금까지 이 엔진의 소비자는 **사람의 브라우저** 하나였다. 여기에 **다른 시스템**을
소비자로 추가한다. 그쪽이 원하는 것은 결과 화면이 아니라 **근거 문단**이다 —
자기 쪽 모델에게 먹일, 출처가 붙은 텍스트 조각.

그래서 만드는 것은 둘이다.

1. **JSON API** — 화면 없이 검색 결과를 받는 자리.
2. **근거 문단 API** — 질의에 답할 근거가 될 문단을 출처와 함께 돌려주는 자리.

## RAG 를 어디까지 하나 — 검색이 R 을 맡고 G 는 안 한다

RAG 는 검색(Retrieval) + 생성(Generation)이다. **이 저장소는 R 만 한다.**

- **생성을 안 하는 이유**: 모델 호출은 외부 네트워크·API 키·과금을 끌고 들어온다.
  셋 다 이 저장소가 지금까지 한 번도 안 건드린 것이고, 크롤 윤리·단일 머신·의존성
  최소라는 축과 정면으로 부딪힌다. **무엇보다 그건 이 프로젝트가 잘하는 일이 아니다.**
- **대신 R 을 제대로 한다**: 문서가 아니라 **문단**을 돌려주고, 문단마다 출처 URL·제목·
  문서 내 위치를 붙인다. 부르는 쪽이 그것을 자기 모델에 먹인다.
- 이 경계는 되돌릴 수 있다. G 를 하기로 한다면 그때 별도 계획으로 연다.

## "잘 됐다"는 것 — 네 축에 더한다

### 기능

6. **JSON 검색**: 질의를 주면 랭킹된 결과를 JSON 으로 돌려준다. 화면이 주는 것과
   같은 결과여야 한다 — 판정: 같은 질의에 대해 화면의 결과 순서와 JSON 의 순서가
   **완전히 일치**한다.
7. **근거 문단**: 질의를 주면 문단 N개를 돌려준다. 각 문단은 **출처 URL · 문서 제목 ·
   문서 내 위치**를 반드시 갖는다. 위치가 없는 문단은 돌려주지 않는다.
8. **근거 정확도**: 돌려준 문단이 질의어를 실제로 담고 있다 — 판정: 평가 집합에서
   **문단의 90% 이상이 질의어(또는 그 2-gram)를 포함**한다. 못 채우면 RED.
9. **계약 안정성**: 응답 스키마는 버전을 갖는다. 필드를 지우거나 뜻을 바꾸는 변경은
   새 버전에서만 한다 — 부르는 쪽이 남의 시스템이라 조용한 변경이 곧 장애다.

### 경량

4. **API 는 새 프로세스를 만들지 않는다.** 지금 도는 검색 서버가 같이 낸다.
   판정: 실행할 명령이 늘지 않는다(`serve` 하나 그대로).
5. **의존성 0 을 유지한다.** 근거 문단을 만드는 데 임베딩 모델·벡터 DB 를 쓰지
   않는다 — FTS5 와 2-gram 이 이미 있는 것으로 문단을 고른다.

### 성능

4. **JSON 검색 p95 300ms 이하** — 화면과 같은 예산이다(같은 일을 하므로).
5. **근거 문단 p95 500ms 이하** — 문단을 자르고 고르는 일이 더 붙는 만큼만 더 준다.
   이 숫자를 못 지키면 **문단 수를 줄이지, 예산을 늘리지 않는다.**

### 디자인

5. **오류가 사람이 아니라 기계에게 읽힌다.** API 응답은 실패해도 JSON 이고,
   HTTP 상태 코드가 뜻을 갖는다(400 질의가 틀렸다 · 503 색인이 없다).
   HTML 오류 화면을 JSON 자리에 내지 않는다.

## 갈림길 우선순위 — 기존 줄에 끼워 넣는다

```
크롤 윤리 > 검색 품질 > 검색 성능 > 계약 안정성 > 색인 규모 > 기능 추가 > 디자인 다듬기
```

- **계약 안정성이 색인 규모보다 위**인 이유: 색인이 작은 것은 부르는 쪽이 견디지만,
  스키마가 조용히 바뀌는 것은 못 견딘다.
- "문단을 더 똑똑하게 고르기"와 "p95 500ms"가 부딪히면 **예산이 이긴다.**
- 임베딩·리랭커 논쟁은 **근거 정확도 90% 가 FTS5 로 안 되는 것이 실측될 때만** 연다.
  예감은 근거가 아니다(기존 규칙 그대로).

## 하지 않을 것 — 여기에도 더한다

- **생성(LLM 호출)** — 위 이유. 재논의 조건: 별도 계획으로만.
- **API 키·계정·요금제** — 로그인 없음이라는 컨셉 그대로다. 남용 대응은 인증이 아니라
  **속도 제한**으로 한다.
- **벡터 DB·임베딩 모델** — 위 재논의 조건 전까지.
- **스트리밍 응답·웹소켓** — 한 번에 주고 끝낸다.

## 사람이 정할 것 (루프가 혼자 못 여는 셋)

1. **속도 제한을 지금 넣나, 나중에 넣나.** 로그인이 없으므로 IP 기준이 유일한 손잡이다.
   공개 API 를 제한 없이 여는 것은 남용에 그대로 열어 두는 것이다.
   **가정(적을 때까지 유효)**: 1단계에서는 **IP 당 분당 60회**로 시작한다.
2. **JSON 검색과 근거 문단을 한 계획으로 묶나, 둘로 쪼개나.**
   **가정**: 쪼갠다 — JSON 검색이 먼저고, 근거 문단이 그 위에 선다.
3. **`docs/specs/` 는 원래 사람만 쓰는 자리다.** 이 절은 사용자의 지시를 옮겨 적은
   것이고, 숫자(90% · 500ms · 60회/분)는 **초안이다.** 고칠 것이 있으면 여기서 고친다.
