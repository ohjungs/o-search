## 이 계획의 e2e 질문은 하나다

**"가짜 시계가 초록인데 진짜 대기가 사라지지 않았는가."**

단위 433건은 전부 가짜 시계 위에서 돈다. 이 계획은 **그 가짜 시계를 꽂는 방식**을
바꾼 것이므로, 단위가 초록인 것은 계획이 안전하다는 증거가 못 된다.
진짜 벽시계·진짜 로컬 HTTP 서버로 재야 답이 나온다.

그래서 통과 여부만 적지 않고 **`main`(`f888518`)과 같은 세션·같은 기계에서 A/B** 로 쟀다.
날짜가 다른 기록과 비교하면 부하 차이가 섞여 "안 바뀌었다" 를 증명하지 못한다.

**A/B 가 공정한 근거**: `git diff f888518 HEAD -- e2e/` 가 **빈 출력**이다 —
양쪽이 문자 그대로 같은 시나리오 파일을 돌렸다. 다른 것은 `src`·`tests` 뿐이다.
`main` 트리는 `git archive f888518 | tar -x` 로 스크래치패드에 풀어서 썼다
(워크트리·브랜치를 안 건드린다 — 자동 스냅샷 훅이 개입할 자리를 없앤다).

## 왜 이 셋이 직접 표적인가 (계획 e2e 절 1~3)

1. **`crawl_delay_e2e`** — robots 의 `Crawl-delay` 와 1초 하한을 **서버가 기록한
   실제 도착 시각**으로 잰다. 이 계획이 워커 쪽 대기(`crawl.py:74`)를 없앴다면
   `2.01s` 가 즉시 무너진다. 컨셉 갈림길 1순위(크롤 윤리)를 지키는 자리다.
2. **`perf_crawl`** — 이음매를 끼우며 대기가 **늘어나는** 반대쪽 실수를 잡는다.
3. **`deadline_e2e`** — 메인 쪽 대기(`crawl.py:179`, 스텝 3)가 예산을 자르는 자리다.
   `[1] CLI 배선`(변이 M6 을 죽이는 단언)과 `[2] 실시계 만료`가 둘 다 그 대기를 지난다.

여기에 계획서가 안 적은 둘을 더 넣어 A/B 했다 — **`crawl_politeness_e2e` 와
`retry_interval_e2e`** 는 리뷰가 확인한 대로 `crawl.crawl()` 을 `sleep=` **없이**
부르는 e2e 다(= 기본값 `time.sleep` 경로). 이번 변경이 연 "기본값으로 새는" 갈래
(리뷰의 변이 M4)를 실제 벽시계로 밟는 유일한 두 자리라 벽시계 조에 포함했다.
