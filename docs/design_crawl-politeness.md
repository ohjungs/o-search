# 설계: crawl-politeness — 예의 계약을 워커 경계 밖으로 새지 않게 한다

계획: `docs/plan_crawl-politeness.md` · 브랜치 `loop/crawl-politeness`

## 0. 이 설계가 지키는 상위 계약

`docs/specs/concept.md` 갈림길 우선순위: **크롤 윤리 > 검색 품질 > 성능 > 규모 > 기능 > 디자인.**
그래서 아래 셋은 어떤 대안에서도 흔들리지 않는다.

1. 선언된 `Crawl-delay` 보다 빠르게 때리지 않는다
2. **모르면 느린 쪽으로 틀린다** — 단, "모른다" 와 "요청을 안 보냈다" 는 구별한다(1-4절)
3. 성능과 부딪히면 **성능을 깎는다**

이미 있는 동시화 계약(`docs/design_history_008.md`)도 그대로 둔다. 특히
**계약 4: 메인 스레드는 네트워크를 타지 않는다.** 이 설계는 계약 4 를 건드리지 않는다.
그리고 `cooldown-burn` 계약 9(**간격 시계는 팝이 아니라 실제 발신에서 시작한다**)를
깨지 않는다 — 깨면 차단 사이트 처리량이 10.29 → 4.48/s 로 되돌아간다(실측 있음).

## 1. 문제 A — 예외 경로에서 Crawl-delay 가 증발한다

### 1-1. 결정

**`RobotsCache` 에 네트워크를 타지 않는 조회 `known_delay(url)` 을 추가한다.**
`crawl._store_result` 의 예외 가지가 그것으로 이미 아는 간격을 프런티어에 건다.
성공 가지와 예외 가지가 **같은 헬퍼 `_apply_delay()`** 를 지나게 해서 상한 초과 처리
(`MAX_DELAY` → 도메인 포기 + 안내 출력)가 한 곳에만 있게 한다.

### 1-2. 대안 비교 — 출발점 셋에서 하나씩

| | **A. 최소** — 캐시 peek | **B. 정공법** — 워커가 안 죽는다 | **C. 되돌리기 우선** — 발신 전 선반영 |
|---|---|---|---|
| 무엇 | `RobotsCache.known_delay()` 는 `self._delays.get(base)` 만 읽는다. 예외 가지가 부른다 | `_fetch_one` 이 스스로 `try/except` 해서 5-튜플 `(allowed, requested, sent_at, result, error)` 를 돌려준다. `_store_result` 는 언제나 `requested` 를 받는다 | 메인 스레드가 제출 **전에** `robots.delay()` 를 불러 `set_delay` 를 먼저 건다 |
| 코드 | robots.py +4줄, crawl.py +6줄 | crawl.py +15줄, 워커 계약 문장 재작성 | crawl.py +2줄 |
| 계약 4 | **지킨다** — peek 은 I/O 가 없다 | 지킨다 | **깬다** — `robots.delay()` 는 robots.txt 를 받을 수 있다 |
| 위험 | `_delays` 를 워커가 쓰는 동안 메인이 읽는다(1-3절) | `future.result()` 의 재발생이 사라져 **워커 버그가 조용해진다**. 지금은 예외가 그대로 올라와 URL 과 함께 찍힌다 | 메인 스레드가 robots.txt 왕복(최대 10초)에 걸리면 **크롤 전체가 멈춘다** |
| 되돌리기 | 메서드 삭제 + 호출 1줄 | 튜플 모양이 바뀌어 호출부·테스트 동반 | 2줄 삭제 |

**A 를 고른다.** C 는 계약 4 를 깨서 즉시 탈락(성능이 아니라 구조가 무너진다 — 메인
스레드가 막히면 떠 있는 8개 워커의 결과 수거도 같이 막힌다). B 는 A 가 하는 일을
전부 하면서 **디버깅 가능성을 잃는다** — 워커가 죽는 것은 지금도 드물고, 드문 일일수록
찍힌 스택이 유일한 단서다. A 는 세 줄이고 잃는 것이 없다.

### 1-3. `_delays` 를 두 스레드가 만지는 것에 대해

워커가 `_load()` 안에서 `self._delays[base] = float(delay)` 를 쓰고, 메인이
`known_delay()` 에서 `.get()` 으로 읽는다. **dict 의 단일 키 get/set 은 GIL 아래에서
원자적**이라 찢어진 값을 읽지 않는다. 읽는 값은 "그 시점에 알려진 것" 이고, 아직
안 들어왔으면 `None` 이다 — 없는 값을 지어내지 않는다.

새 락을 두지 않는다. 락은 계약 3(도메인당 in-flight 1개)이 이미 하는 일을 두 번 하는 것이다.

### 1-4. "모른다" 와 "안 보냈다" 를 구별한다

`known_delay()` 가 `None` 을 주는 경우는 둘이다.

| 경우 | 그때 실제로 나간 요청 | 이 설계의 처리 |
|---|---|---|
| robots.txt 를 **아직 못 읽었다**(예외가 `robots.allowed()` 안에서 났다) | 페이지 요청 **없음** | 기본 1.0초 그대로. 위반이 아니다 — 다음 시도가 robots 를 먼저 읽고 그때 간격이 잡힌다 |
| robots.txt 는 읽었고 **Crawl-delay 지시가 없다** | 페이지 요청 있었을 수 있음 | 기본 1.0초. 사이트가 요구한 값이 없으므로 하한이 곧 답이다 |

즉 `None` 을 "1.0초로 때려도 된다" 로 읽는 것이 **두 경우 모두에서 옳다.**
이 문단이 없으면 다음 사람이 `None` 을 보고 "느린 쪽으로 틀려야 하니 30초" 를 넣는다.

### 1-5. 계약 문장 (코드 주석에도 같은 말이 들어간다)

> **간격 시계를 거는 자리는 `_store_result` 하나다**(cooldown-burn 계약 2·3).
> **간격 값을 거는 자리도 `_store_result` 하나다** — 성공이든 예외든 `_apply_delay()` 를 지난다.

## 2. 문제 B — 재시도가 간격 없이 몰아친다

### 2-1. 결정

**`fetcher.fetch(url, before_send=None, retries=RETRIES)`.**
`fetch` 는 시도 **하나하나 앞에서** `before_send()` 를 부른다. 간격을 아는 것도, 재우는
것도, 발신 시각을 재는 것도 전부 `crawl._fetch_one` 이 넘긴 클로저가 한다.
`fetcher` 는 간격이라는 개념을 모른 채로 남는다.

`_fetch_one` 이 넘기는 클로저:

```
첫 발신      → 시각만 기록
재시도 발신  → (마지막 발신 + interval) 까지 time.sleep 후 시각 기록
```

`interval = max(frontier.DOMAIN_INTERVAL, robots 가 요청한 값 or 0)`.
그 값이 `MAX_DELAY` 를 넘으면 **재시도를 아예 안 한다**(`retries=0`) — 2-4절.

`_fetch_one` 이 돌려주는 `sent_at` 은 **마지막 발신 시각**이다(첫 발신이 아니다).
계약 9 는 그대로다: 시계는 실제 발신에서 시작한다. 발신이 여럿이면 **마지막** 것이다.

### 2-2. 대안 비교

| | **A. 최소** — `fetcher` 안에서 sleep | **B. 정공법** — 재시도를 크롤 루프로 승격 | **C. 되돌리기 우선** — 발신 훅 |
|---|---|---|---|
| 무엇 | `fetch(url, interval, sleep=time.sleep)`, `continue` 앞에서 잔다 | 실패한 URL 을 프런티어에 되돌려 넣고 **프런티어가 재게** 한다 | 위 2-1 |
| 마지막 발신 시각 | **모른다.** `sent_at + interval*(시도수-1)` 로 **추정**하거나 `FetchResult` 에 필드를 늘려야 한다 | 프런티어가 매 발신마다 안다 | **잰다** — 클로저가 `now()` 를 기록한다 |
| `fetcher` 가 아는 것 | 도메인 간격(모듈 경계 침범) | 없음 | 없음 |
| 코드 | fetcher +5, crawl +3, `FetchResult` 필드 추가(**공개 데이터 구조 변경**) | frontier +requeue·시도수, crawl 대폭, `_seen` 재진입 처리, 저장 카운트 재검토 | fetcher +4, crawl +10 |
| 되돌리기 | 필드가 남아 부분 되돌리기가 지저분 | 어렵다 | 인자 2개 삭제 — 기본값이라 호출부 무변경 |
| 부작용 | 워커 스레드를 붙든다 | **재시도가 그 도메인의 다른 URL 과 경쟁**해 순서가 뒤집힌다 | 워커 스레드를 붙든다 |

**C 를 고른다.** A 와 C 는 둘 다 워커를 붙드는 값을 치르지만(2-3절), A 는 마지막 발신
시각을 **추정**한다. 추정은 `fetcher` 가 정확히 `interval` 만큼 잤다는 가정에 기대는데,
그 가정이 틀어지는 날 **아무 테스트도 실패하지 않고 간격만 짧아진다** — 예의 축에서
가장 나쁜 실패 모양이다. C 는 같은 값에 실측을 준다.

B 는 구조적으로 가장 옳다(재시도도 프런티어의 시민이 된다). 열지 않는 이유는 크기다 —
`frontier._seen`·저장 카운트·`max_pages` 회계가 전부 딸려 온다. **`digest.md` 에
후보로 남긴다**: 재시도가 잦은 사이트에서 워커가 놀게 되면 그때가 B 의 값이 서는 때다.

### 2-3. 무엇을 잃는지 숫자로 적는다

재시도가 붙은 요청은 워커 하나를 최대 `2 × interval`(기본 2초) 더 붙든다.
전부 실패하는 도메인이 8개 이상 동시에 걸리면 그 시간 동안 풀이 찬다.

**받아들인다.** 컨셉 우선순위에서 크롤 윤리가 성능 위다. 그리고 이 대가는
**빠르게 실패하는 경로에서만** 발생한다 — 타임아웃 실패는 이미 10초씩 벌어져 있어
`interval - 경과` 가 음수가 되고 잠들지 않는다(클로저가 남은 시간만 잔다).

회귀는 `e2e/perf_crawl.py` 의 `BASELINE_BLOCKED = 9.0` 이 잡는다. 그 세계에는
재시도가 없으므로 **숫자가 안 움직이는 것이 정상**이고, 움직이면 happy path 에
잠을 흘린 것이다.

### 2-4. `MAX_DELAY` 초과 도메인은 재시도하지 않는다

사이트가 `Crawl-delay: 86400` 을 선언하면 `frontier.set_delay()` 가 그 도메인을 버린다.
버릴 도메인이라도 **이미 나간 요청 뒤에 몰아치면 안 된다.** 그렇다고 86400초를 잘 수도
없다(워커가 하루를 붙든다).

**답은 재시도를 안 하는 것이다.** 간격을 지킬 수 없으면 다시 보내지 않는다 —
"깎아서 계속 때리는 것은 윤리 위반" 이라는 `frontier.py` 의 기존 문장과 같은 판단이다.
`_fetch_one` 이 `retries=0` 을 넘긴다. 첫 요청 1회는 이미 나갔고 그 응답은 정상 처리한다.

### 2-5. 시간을 어떻게 재나 — 새 주입 지점을 만들지 않는다

`_fetch_one` 은 `time.sleep` 을 **모듈 전역으로** 부른다. 기존 테스트가 이미
`mock.patch("websearch.crawl.time.sleep")` 로 가짜 시계를 흘려보내는 패턴을 쓴다
(`tests/test_crawl.py:41`·`343`·`391`). **그 패턴을 그대로 쓴다** — `sleep` 인자를
새로 뚫으면 주입 지점이 둘이 되고, 다음 사람은 어느 것이 진짜인지 모른다.

`crawl()` 의 시그니처는 **안 바뀐다.** `_fetch_one()` 의 시그니처도 안 바뀐다.
바뀌는 공개 표면은 `fetcher.fetch` 의 기본값 인자 2개뿐이다.

**실제 sleep 으로 테스트를 느리게 만들지 않는다** — 단위 테스트는 전부 가짜 시계다.
실제로 자는 것을 보는 곳은 e2e 하나뿐이고, 거기서만 초 단위 시간을 쓴다.

## 3. 되돌리는 법

| 무엇 | 어떻게 |
|---|---|
| 문제 A 만 | `robots.known_delay()` 삭제, `_apply_delay()` 를 성공 가지에 인라인 |
| 문제 B 만 | `fetcher.fetch` 의 인자 2개 삭제(기본값이라 호출부 무변경), `_fetch_one` 의 클로저 삭제 |
| 전부 | `git revert` — 두 스텝이 커밋 2개로 갈려 있다 |

## 4. 사람에게 물어야 하는가

`rules/design.md` 4절의 넷 중 어디에도 안 걸린다.
사용자 데이터 형태 ✗ · **공개** 계약 파괴 ✗(기본값 인자라 기존 호출이 그대로 돈다) ·
의존성 추가 ✗(stdlib 만) · 보안 경계 ✗.
→ **스스로 정하고 근거를 남긴다.** 야간 자동 적용 대상이다(40줄 이내면).

## 5. 테스트가 무엇을 고정하나 (개발 스텝이 이대로 쓴다)

**부정 단언에는 긍정 짝을 붙인다.** 아래 표의 각 줄은 짝이 맞아야 한다.

| # | 잰다 | 짝 |
|---|---|---|
| 1 | `Crawl-delay: 5` + 첫 요청 예외 → 다음 간격 ≥ 5.0 | 예외 없는 대조군도 5.0 (잴 대상이 살아 있다) |
| 2 | robots 를 못 읽은 도메인 → 1.0 그대로 | robots 를 읽은 도메인 → 그 값 (`None` 을 지어내지 않는다) |
| 3 | 연결 실패 3회 → `sleep` 이 2회, 각각 ≥ interval | 성공 → `sleep` 0회 (항상 자는 것이 아니다) |
| 4 | `sent_at` = 마지막 발신 | 재시도가 없으면 `sent_at` = 첫 발신 (계약 9 불변) |
| 5 | `HTTPError`·`UnicodeError` → 재시도 0, sleep 0 | 기존 계약 유지 |
| 6 | interval > `MAX_DELAY` → 시도 1회 | interval ≤ `MAX_DELAY` → 시도 3회 |

**변이 검사는 "이 줄을 안 썼다면 무엇이 되는가" 로 고른다**(`digest.md [7]` 의 교훈).
기본값이 있는 인자는 지웠을 때 기본값으로 돌아가지 0 이 되지 않는다.
**무변이 기준선을 먼저 잡고** 센다.
