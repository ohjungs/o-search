# e2e 결과 — crawl-throughput (008)

2026-08-27 · 브랜치 `loop/crawl-throughput` · 자동(야간)

## 무엇을 사용자 관점으로 봤나

사용자가 실제 웹을 크롤할 때 겪은 두 가지다: **너무 느리다**(초당 0.5문서),
그리고 **1,700문서에서 죽는다**(`database is locked`).

수단은 `e2e/perf_crawl.py` — **실제 네트워크를 치지 않는다.** 로컬 서버 12개를
서로 다른 포트로 띄우고, 프런티어가 `netloc` 으로 도메인을 가르는 성질을 이용해
12개 도메인인 척 만든다. 응답 지연 0.4초가 실제 웹의 대기를 흉내낸다.

## 시나리오와 결과 (4/4 통과)

| # | 시나리오 | 결과 |
|---|---|---|
| 1 | 12도메인·도메인당 12페이지·지연 0.4초 웹에서 48문서를 10초 안에 | **4.68초 · 초당 10.25문서** (기준 5.0) |
| 2 | 어떤 도메인도 1초 안에 두 번 맞지 않는다 | 12도메인 전부 **0.95초 이상** · 위반 0 |
| 3 | 같은 URL 을 두 번 요청하지 않는다 | **중복 0** |
| 4 | 워커 1로 돌려도 결과 문서 집합이 같다 | **sha1 동일** `541d455a…` · 24.59초 · 1.95/s |

시나리오 4가 되돌리기 경로의 증거다 — `--workers 1` 은 **느릴 뿐 결과가 같다**.
48개 경로의 sha1 이 동시 실행과 한 글자도 다르지 않다.

## 목표 대비

`concept.md:44` 성능 축 2번은 **초당 5문서**. 사용자 실측 출발점이 **초당 0.5문서**였다.
같은 조건의 순차 크롤이 1.95/s, 동시 크롤이 10.25/s — **5.3배**이고 기준의 **2배**다.

## 잠긴 DB (스텝 3)

e2e 시나리오에는 없다. 유닛에서 사용자 크래시와 **같은 예외**를 재현해 닫았다
(`tests/test_store.py` `TestConcurrentAccess`). DB 를 읽는 e2e 3종
(`indexer`·`noindex`·`search_api`)을 돌려 WAL 이 읽는 쪽 전제를 안 깼는지 확인했다.

## 남은 것 (사람이 볼 자리)

- **`store.has()` 로 건너뛴 URL 이 도메인 쿨다운을 태운다.** 이어받기 크롤에서만
  드러나고 신규 크롤인 이 e2e 로는 안 잡힌다. 고치는 방법에 간격 위반 구멍이 있어
  야간에 손대지 않았다 — `docs/status.md` 패스 A 2번 참조
- **Ctrl-C 가 최대 30초 늦는다** (동시화가 만든 회귀, 유실은 없다)
- `perf_crawl` 기준선은 순차 대 동시까지만 가른다. workers 8→4 정도의 부분 회귀는
  시간이 아니라 `TestConcurrency`(배리어)가 잡는다
