## 1. 문제 · 목표 · 기대 결과

**문제 1 — 크롤에 시간 상한이 없다.** 착수 전 실측(`aeb2eeb`, 2026-08-27, 로컬 실서버):

| 탐침 | 결과 |
|---|---|
| 한 도메인 `Crawl-delay: 2` · 5페이지 크롤 | 총 **8.05초**, 페이지 요청 간격 2.01 · 2.01 · 2.01 · 2.00 |
| `crawl()` 시그니처 | `(seeds, max_pages, db_path, robots_cache, now, workers)` — **시간 인자 0개** |
| `crawl.main()` 이 아는 플래그 | `--max` · `--workers` — **시간 인자 0개** |
| `grep -rn 'deadline\|budget' src/websearch/` | **0건** |

`MAX_DELAY = 30` 이 막는 것은 **요청 하나당** 대기뿐이다. 페이지 수만큼 곱해지므로
`--max 100` 인 사이트가 `Crawl-delay: 30` 을 선언하면 99 × 30 = **2970초(약 50분)** 이고,
그 위에 재시도 대기와 타임아웃이 더 얹힌다. 위 8.05초가 그 축소판이다 —
페이지를 늘리면 총 시간은 선형으로 늘고 **끊을 수단이 없다**.

**문제 2 — 같은 뿌리. 크롤 루프에 "그만" 을 전할 방법이 없다.**
실측(SIGINT, `Crawl-delay: 3`, 페이지 요청은 서버가 연결을 즉시 끊어 빠르게 실패):

```
SIGINT 0.51s 에 보냄 → 종료 6.07s (대기 5.56s) · rc=-2
```

`_fetch_one.before_send` 가 재시도 앞에서 3초씩 두 번 자고,
`with ThreadPoolExecutor` 가 나가면서 그것을 기다린다(`crawl.py:79-84` 독스트링이
이미 이 사실을 적어 뒀다). `Crawl-delay` 가 상한 30 이면 **같은 자리가 60초**다.

**목표.** `crawl()` 과 CLI 에 **총 크롤 시간 예산**을 준다. 예산이 다하면 새 요청을
던지지 않고 지금까지 저장한 것을 돌려준다. 무인 크롤이 밤을 통째로 쓰는 일이 끝난다.

**기대 결과.**
- `crawl(seeds, max_pages, deadline=D)` — 예산 `D` 초가 지나면 새 요청을 안 던지고
  **지금까지 저장한 페이지 수**를 돌려준다(예외가 아니라 정상 반환)
- CLI: `python3 -m websearch.crawl <seed> --deadline 60`
- **대조군 — 예산을 안 주면 오늘과 한 글자도 안 다르다.** 기본값은 무제한이고
  기존 e2e 14종이 전부 그대로 rc=0 이어야 한다
- **예산이 예의를 깎지 않는다.** 끊기는 순간까지 도메인 간격과 robots 는 그대로다.
  깎는 설계는 RED (`concept.md` 갈림길 1순위 · `project.md ## 한도`)

## 2. 설계가 필요하다 — 트리거 둘

`design.md` 1절에 **두 줄이 걸린다.** 019 와 달리 이 계획은 설계를 건너뛰지 않는다.

1. **공개 인터페이스 변경** — `crawl()` 시그니처에 인자 하나, CLI 에 플래그 하나.
2. **대안이 2개 이상 갈린다** — 둘 다 동작하는데 닫는 구멍이 다르다.

| | A. 메인 스레드만 예산을 본다 | B. 워커까지 보는 중단 신호 |
|---|---|---|
| 수단 | 주입된 `now()` 로 남은 예산 계산 → 제출 중단 | `threading.Event` 를 `_fetch_one` 까지 넘긴다 |
| 문제 1 | 닫는다 (초과분 = 워커 최악 대기만큼) | 닫는다 (초과분 ≈ 0) |
| 문제 2 (Ctrl-C 5.56초) | **못 닫는다** | 닫는다 |
| 값 | `time.sleep` 이음매를 안 건드린다 | `time.sleep` → `Event.wait` 로 바꿔야 한다 |
| 위험 | 예산이 "대략" 이다 | `tests/test_crawl.py` 가 **9곳**에서 `mock.patch("websearch.crawl.time.sleep")` 으로 가짜 시계를 흘려보낸다 — 그 이음매가 사라지면 간격을 재는 테스트가 통째로 죽는다 |

**설계에서 정할 것은 이것 하나다: B 를 고른다면 가짜 시계 9곳의 축을 어디로 옮기나.**
digest 의 규칙대로 깨진 테스트를 지우는 답은 없다(018 이 017 e2e 를 깼을 때 축을
userinfo 로 옮겨 살린 그 방식). 옮길 자리가 없으면 A 로 간다 — 그때는 문제 2 가
이 계획 밖으로 남고, 그 사실을 `digest.md` 에 **닫지 않은 채로** 남긴다.

→ `docs/design_deadline.md`

## 4. e2e 시나리오 (계획 시점에 확정 — `rules/plan.md` 7절)

로컬 실서버가 **받은 것**으로 잰다. 나중에 구현에 맞춰 낮추지 않는다.
한 도메인이 `Crawl-delay: 2` 를 선언하고 페이지가 5개다(위 탐침과 같은 세계, 8.05초).

1. `--deadline 3` → 크롤이 **6초 안에** 끝나고 서버가 받은 페이지 요청이 **5개 미만**이다
2. **대조군** — 같은 사이트, 예산 없이 → **5페이지 전부**, 8초대.
   예산을 안 주면 오늘 그대로다
3. **대조군(예의)** — 예산으로 끊겨도 페이지 요청 간격이 **전부 2초 이상**이다.
   예산이 간격을 깎는 순간 여기가 먼저 빨개진다
4. **측정 불능은 조용한 통과가 아니다** — 서버가 페이지 요청을 **0건** 받았거나
   대조군이 5페이지를 못 채웠으면 **종료 코드 2**. `--deadline` 이 아무것도 안 한
   경우와 서버가 안 뜬 경우를 구별 못 하는 채로 초록을 켜지 않는다
   (017 이 심고 018·019 가 덕을 본 가드와 같은 관용구)

설계가 B 로 가면 **시나리오 5** 를 더한다: SIGINT 를 보낸 뒤 종료까지 **1초 미만**
(착수 전 기준선 5.56초). A 로 가면 이 시나리오는 안 만들고 그 사실을 결과에 적는다.

## 5. 하지 않을 것

- **`MAX_DELAY`·`DOMAIN_INTERVAL` 값 변경** — 컨셉 절대 조건이다. 예산을 지키려고
  간격을 깎는 것은 RED (`project.md ## 한도`)
- **`fetcher.RETRIES`·재시도 구조 변경** — "재시도를 크롤 루프로 승격" 은
  digest `[high]` 가 "옳지만 크다" 로 남긴 **별도 후보**다. 이 계획은 재시도가
  지금 자리에 있는 채로 예산을 건다
- **Ctrl-C 즉시 종료** — 설계가 B 를 고르면 딸려 오고, A 를 고르면 계획 밖이다.
  **어느 쪽이든 digest 항목은 이 계획이 실제로 닫은 만큼만 지운다**
- **recrawl(`store.has` 상태 불문 스킵) · indexer 증분 · 스키마** — 야간 금지
- **`serve`·색인·검색 경로** — 무관 (직교 편집 금지)
- **기존 `data/crawl.db` 옛 열쇠 행 통합 · URL userinfo** — 승인 대기 `[high]` 둘
- **`loop/*` 브랜치 병합** — 사람 몫
- 무관한 리팩터링·이름 변경·포맷팅

## 6. 열린 질문 (야간에는 안 묻는다 — 아침 판단용으로만 적는다)

1. **예산으로 끊겼을 때 종료 코드.** 이 계획은 **0**(정상 종료 — 예산대로 끝난 것이다)
   으로 간다. 스크립트가 "다 돌았다" 와 "예산에 걸렸다" 를 구별해야 하면 사람이 정한다.
