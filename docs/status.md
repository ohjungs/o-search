### [승인 필요 · medium] 본문 크기 축에 상한이 없다 — 초록불이 예산을 보증하지 않는다

`/passages` 는 요청당 최대 10개 문서의 `pages.html` 을 **통째로 다시 파싱한다**. 그런데
`serve.py` 가 자원 상한을 넷 두는 자리(`MAX_QUERY` · `MAX_PAGE` · `REQUEST_TIMEOUT` ·
`MAX_PASSAGE`)에 **재파싱하는 입력 크기만 빠져 있다.** `MAX_PASSAGE` 는 응답 바이트를
자르지 CPU 를 안 자른다. 실측(이 반복):

| `pages.html` 1건 | `extract_blocks` 1회 | 10건이면 |
|---|---|---|
| 23 KB | 0.6 ms | 5.7 ms |
| 257 KB | 6.0 ms | 59.7 ms |
| **2.5 MB** (`fetcher.MAX_BYTES` = 2MB 근처) | 60.1 ms | **600.7 ms** |

**크롤러 자신의 상한까지 채운 문서 10건이면 파싱만으로 예산 500ms 를 넘는다.**
e2e 코퍼스는 문서당 본문 208자·블록 4개라 **이 축을 구조적으로 못 잰다** — 러너
docstring 이 *"문서 크기 축도 안 들어 있다"* 고 정직하게 적어 뒀지만, **정직한 미측정도
여전히 미측정이다.** `p95 1.76ms (예산의 0.4%)` 를 보고 여유가 넘친다고 읽으면 안 된다.

**고치지 않고 올린 이유**: 문턱이 제품 손잡이다(`MAX_QUERY` 를 200 으로 정한 것과 같은
종류의 결정). 신뢰 경계의 자원 상한이라 `rules/severity.md` 3·4절이 자동 적용을 막는다.
**제안(스텝 4)**: `indexer.passages` 가 `extract.extract_blocks(row[0][:MAX_PASSAGE_HTML])`
로 읽고 상수를 `serve` 의 세 형제 옆에 둔다 — 200KB 면 10건 60ms(예산의 12%)다.
**천장은 «그 뒤의 문단은 못 찾는다»** 이고 `ponytail:` 주석에 적을 것. 대안은 상한 대신
`perf_search.py` 에 큰 문서 축을 얹어 회귀로만 잡는 것 — 둘 중 하나는 정해야 한다.
`data/crawl.db` 는 오늘 **2행 · 66바이트**라 실물이 이 축을 밟은 적은 아직 없다.

### [자동 수정 · medium] 종료 코드 1/2 의 네 번째 구멍 — HTTP 경로가 그대로 샜다

직전 커밋 제목이 *"러너 rc 1 누출 결함 봉함"* 인데 **같은 문이 옆에 하나 더 열려 있었다.**
`measure()` 의 `urlopen` 은 비2xx 에 `HTTPError` 를 던지고 `main()` 어디서도 안 잡힌다 →
**트레이스백 + 파이썬 기본 rc 1**. 1 은 «미달» 예약값이라 *"문단 품질이 떨어졌다"* 로
읽힌다. 재현(`indexer.passages` 를 던지게 바꿔 서버가 500 을 내게 함): rc **1** ·
트레이스백에 파일 경로. `except OSError` 세 줄로 **rc 2**(`HTTPError ⊂ URLError ⊂ OSError`
이고 3.9 의 `socket.timeout` 도 OSError 하위라 나눠 적어도 하는 일이 같다).
**단위 1건을 TDD 로 세웠다** — 고치기 전 RED(`1 != 2`)를 눈으로 보고 갔다.
**`--repeat`·G7·PAGE_SIZE 에 이어 네 번째다** — 문장이 아니라 자리가 반복된다.
