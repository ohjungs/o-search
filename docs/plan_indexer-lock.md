# 계획 39 — `indexer-lock`: 크롤이 도는 중에 색인하면 5초 만에 트레이스백이 난다

상태: **계획** (2026-08-31) — 설계 생략(아래 6절). 2스텝 예정.
브랜치: `loop/indexer-lock` (기점 `bf78d02`, `loop/digest-rotate` 에서 팠다)
슬러그: `indexer-lock`

## 1. 문제 · 목표 · 기대 결과

**문제는 하나인데 뿌리가 둘이다.**

① **`indexer` 만 쓰기 락을 5초밖에 안 기다린다.** `store.py:22` 는
`sqlite3.connect(path, timeout=30)` 이고 그 줄의 주석이 이유를 적어 뒀다 —
"쓰기끼리 부딪히면 죽는 대신 기다린다. **실측에서 1,700문서째에 크롤을 죽인 게 이거다**"
(계획 8 `crawl-throughput` 이 닫았다). 그런데 `indexer.py:78`·`136`·`181` 은
`sqlite3.connect(db_path)` 로 **timeout 을 안 준다** — sqlite3 기본은 5.0초다.
같은 DB 에 붙는 두 모듈이 락을 **6배 다르게** 기다린다. 계획 8 이 닫은 것의 **형제 구멍**이다.

② **`indexer.main` 에 `sqlite3` 예외 갈래가 없다.** `FileNotFoundError`·`NoCrawlDataError`·
`StaleIndexError`·`KeyboardInterrupt` 넷은 잡아서 복구법 한 줄 + rc 2(중단은 130)를 내는데,
`sqlite3.DatabaseError` 계열은 그대로 흘러 **트레이스백 + rc 1** 이 된다.
이 저장소가 21·24·26·27·29 에서 다섯 번 닫은 계약("CLI 는 트레이스백을 안 낸다")의
같은 파일·다른 입력이다 — 앞의 다섯은 **인자**를 탐침했고 **환경**(락)은 아무도 안 쟀다.

**목표.** 크롤이 도는 중에 색인을 돌려도 (ㄱ) 흔한 충돌은 **기다렸다 성공**하고
(ㄴ) 그래도 안 되면 **트레이스백 대신 복구법**을 낸다.

**기대 결과.**
- 다른 프로세스가 쓰기 락을 20초 쥐고 있어도 색인이 **성공**한다(오늘은 5.02초에 rc 1).
- 락이 30초를 넘으면 **rc 2 + 한 줄 안내**(트레이스백 없음).
- 검색(`--query`)은 오늘처럼 안 막힌다 — WAL 이라 읽기는 쓰기를 안 기다린다(3절 C).
- `docs` 는 어느 갈래에서도 안 줄어든다(계획 37 의 `BEGIN` 이 이미 참으로 만들어 뒀다).

## 2. 근거

- **7순위 — `digest.md ## 반복 실패` 의 "CLI 가 예상 못 한 입력에 트레이스백을 낸다".**
  항목은 `indexer-cli-guard`(2026-08-29)로 닫힘 표시돼 있지만, 그 항목이 직접 적어 둔
  근본 원인 문장이 남아 있다 — "적어 둔 근본 원인('CLI 진입점마다 방어를 따로 쓴다')은
  **과했다** — 착수 때 셋을 다 탐침하니 실제로 남은 구멍은 한 곳이었다." 그 탐침은
  **인자**만 봤다. 락은 인자가 아니라 환경이라 세 CLI 어디서도 안 쟀다.
- **`digest.md ## 판단 필요` `[7]`("변이 검사는 값을 지웠을 때로 잡아야 한다").**
  이 항목이 `store.py` 의 `timeout=30` 을 검증한다던 변이가 **아무것도 고정하지 못했다**고
  이미 적었다("0.3초만 락을 붙드는 테스트는 인자를 지워도 통과한다 — sqlite3 기본은
  0이 아니라 **5000ms**"). 실측으로 확인했다: 오늘 단위 457건에 `database is locked`·
  `OperationalError` 단언이 **0건**이고, `store.py` 의 30초를 고정하는 단언도 **0건**이다.
- **계획 38 이 `status.md` 에 남긴 다음 후보 ①** — "`sqlite3.connect` timeout 불일치
  (`indexer.py:78·136·181` 5초 대 `store.py:22` 30초)".
- 축: 34~38 이 이어 온 **종료 계약** 축의 다음 칸이다. 34~36 은 신호·예산, 37 은 중단 중
  데이터, 38 은 기록이었다. 이번은 **동시 실행**이고 남은 마지막 갈래다.

1~6순위에는 열 것이 없다(3절 A).

둘 다 덮는다** — 락이면 락 안내를, 아니면 원문을 낸다. 형제를 따로 열지 않는 이유다.

## 4. 스텝 분할과 완료 기준

**스텝 1 — `indexer` 의 세 연결을 `store` 와 같은 30초로 맞춘다.**
`indexer.py:78`·`136`·`181` 의 `sqlite3.connect(db_path)` → `sqlite3.connect(db_path, timeout=30)`.
값은 새로 정하지 않는다 — `store.py:22` 가 이미 고른 값을 따른다(ponytail 2번).

- 완료 기준: 락 8초를 쥔 채 색인이 **rc 0**(오늘 rc 1) · 락 20초도 **rc 0**.
- 변이 M1: 세 곳의 `timeout=30` 을 **지운다**(0 으로 바꾸지 않는다 — `digest.md [7]`).
  락을 **8초 이상** 쥐는 테스트라야 죽는다(5초 기본이 받아주므로 0.3초 락은 통과한다).

**스텝 2 — `main` 에 `sqlite3.DatabaseError` 갈래를 넣는다.**
`StaleIndexError` 갈래와 같은 관용구로 rc **2** + 복구법 한 줄.
락이면 "DB 가 잠겨 있다 — 크롤이 끝난 뒤 다시 돌린다", 아니면 원문을 그대로 보인다
(다른 `DatabaseError` 를 락으로 오인하지 않기 위해서다).

- 완료 기준: 락 35초에서 **rc 2 · 트레이스백 0줄** · stderr 첫 줄에 복구법.
  진짜 DB 가 아닌 파일도 **rc 2 · 트레이스백 0줄**.
- 변이 M2: `except` 절 삭제 → rc 1 로 죽는다. M3: rc 2 → 0. M4: 락 분기 문구 제거.

**두 스텝 공통 검증(매 스텝):**
- `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 -m unittest discover -s tests` — **457건 이상 OK**
- `PYTHONPATH=src python3 e2e/indexer_e2e.py` · `e2e/indexer_interrupt_e2e.py` — rc 0
- `shasum -a 256 data/crawl.db` = `85c96744…5bda18` 무변경

## 5. 하지 않을 것

- **`store.py` 는 안 건드린다.** 30초는 계획 8 이 실측으로 고른 값이고 이번 근거는
  "다르다" 이지 "30이 틀렸다" 가 아니다.
- **`serve.py` 는 안 건드린다.** 탐침 C 가 읽기는 안 막히는 것을 쟀다. 서버가 부르는
  `search()` 는 읽기 전용이다 — 스텝 1 이 그 연결에도 `timeout` 을 붙이지만 동작은 안 바뀐다.
- **재시도·백오프·큐를 안 만든다.** 기다림은 sqlite3 이 이미 한다(rung 3).
- **`crawl` 이 색인을 자동으로 돌리게 만들지 않는다.** README 가 셋을 나눠 놓은 것은
  설계이고 이 근거로 뒤집을 것이 아니다.
- **`sqlite3.DatabaseError` 를 `store`·`crawl` 에도 다는 것**은 안 한다 — 근거가 없다.
  세 번째 자리가 실측으로 나오면 그때 공통화한다(`## 반복 실패` 항목이 적어 둔 기준).
- `docs/specs/` 는 읽기만.

## 6. 설계 생략

`design.md` 1절 트리거를 하나도 안 건드린다: 새 파일 0 · 공개 인터페이스 변경 0 ·
데이터 구조·스키마 변경 0 · 파일 2개(`src/websearch/indexer.py` · `tests/test_indexer.py`) ·
되돌리기는 3줄 되돌리기다. **"대안이 2개 이상 갈림" 도 아니다** — timeout 값은
`store.py:22` 가 이미 골랐고, 예외 갈래의 모양은 같은 파일의 `StaleIndexError` 가 관용구다.

**짧은 경로도 아니다.** 다섯 중 둘이 거짓이다 — 스텝이 둘이고(3절 G4 가 하나로는 못
닫는 것을 쟀다), 동시 쓰기라 "데이터와 무관" 이 애매하다. **애매하면 평소 경로다**(`SKILL.md` 4-1).

## 7. e2e 판단

**새 e2e 파일은 안 만든다.** 재는 것이 "진짜 프로세스 둘이 같은 DB 에 붙는다" 인데
그것은 단위에서 `subprocess` + 락 홀더로 그대로 재현된다(3절 탐침이 이미 그 모양이다) —
서버도 네트워크도 사용자 화면도 없다. e2e 19종은 그대로 두고 회귀로만 돌린다.
이 판단이 틀렸다는 신호는 "단위로는 못 재는 자리가 나온다" 이고, 그러면 그때 연다.
