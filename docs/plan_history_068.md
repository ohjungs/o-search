# 계획 84 `backoff-429` — 서버가 「너무 잦다」고 하면 물러난다

## 1. 왜 지금인가 — 오늘 남의 서버에 실제로 피해가 갔다

2026-09-09 1만 문서 크롤 실측. 위키미디어 6도메인이 **응답의 50~68% 를 429** 로 거절했다.

```
en.wikiversity.org  200: 328 · 429: 684 (68%)
en.wikiquote.org    200: 354 · 429: 662 (65%)
en.wikibooks.org    200: 362 · 429: 659 (65%)
ko.wikipedia.org    200: 369 · 429: 627 (63%)
simple.wikipedia.org 200: 380 · 429: 603 (61%)
en.wikipedia.org    200: 502 · 429: 507 (50%)
                    나머지 6도메인은 429 가 **0건**이다
총 3,686건 · 크롤 시작 44초 만에 첫 429
```

**원인은 예의를 «호스트명» 단위로 지키기 때문이다.** 여섯이 같은 IP 다:

```
en·ko·simple.wikipedia.org · en.wikibooks·wikiversity·wikiquote.org
  → 전부 103.102.166.224
```

호스트마다 1초를 지켜서 **한 서버에 초당 6건**이 갔다. 컨셉이 *"도메인당 요청 간격
1초 이상은 기능이 아니라 **전제 조건**"* 이라 한 것을 글자로는 지키고 뜻으로는 어겼다.

**크롤을 중단한 것이 이 계획의 출발점이다** — 7,287장에서 멈췄다.

## 2. 결함이 둘이다

**① 429 를 받고도 안 물러난다.** 서버가 명시적으로 「너무 잦다」고 말하는데 다음 요청이
같은 간격으로 나간다. 3,686번을 그렇게 했다.

**② 429 를 「받았다」고 기록한다.** `pages` 에 `status=429` 행이 박히고, 계획 80 의
재크롤 정책상 실패는 `RETRY_DAYS`(15일) 뒤에나 다시 본다 — **못 받은 것을 받았다고
적은 것**이다. 코드가 바로 옆 `_Interrupted` 자리에 *"안 받은 것을 받았다고 적는
거짓"* 이라고 이미 적어 뒀는데, 429 갈래에는 그 판단이 적용되지 않았다.

## 3. 처방 — IP 로 묶지 않는다, 서버가 말한 대로 따른다

**IP 로 도메인을 묶는 안을 버렸다.** CDN 뒤에서는 수천 개의 무관한 사이트가 한 IP 를
공유하므로, IP 로 묶으면 서로 남남인 사이트들이 한 예산을 나눠 쓰게 되어 **더 나쁘다.**
DNS 는 바뀌고 라운드로빈이면 실행마다 답이 다르다.

**429 백오프는 왜 429 인지 몰라도 옳다.** 원인이 공유 인프라든, 우리 IP 가 미운털이든,
그 시각에 그 서버가 바쁜 것이든 — 처방은 같다. 서버가 유일하게 신뢰할 수 있는 정보원이다.

**기존 기계를 그대로 쓴다:**

- `frontier.set_delay(domain, seconds)` 는 이미 **단조 증가**이고 `MAX_DELAY`(30초)를
  넘으면 **그 도메인을 통째로 버린다.** 429 백오프가 필요로 하는 것이 정확히 그것이다 —
  물러나다가 도저히 안 되면 손을 뗀다.
- `Retry-After` 헤더가 있으면 그 값을 쓴다. 없으면 **직전 간격의 2배**(최소 2초).

**429 는 저장하지 않고 URL 을 프런티어에 되돌린다.** 백오프가 걸린 뒤 다시 시도된다.

## 4. 스텝

| # | 산출물 | 완료 기준 |
|---|---|---|
| 1 | 429 → 백오프 + 미저장 + 재큐 (TDD) | 실패 테스트 먼저 · 전수 초록 |
| 2 | 실물 확인 | 로컬 429 서버로 백오프가 실제로 늘어나는지 |

## 5. 하지 않을 것

- **IP·ASN 으로 도메인을 묶지 않는다.** 3절의 이유.
- **`DOMAIN_INTERVAL` 을 올리지 않는다.** 1초는 사양이 준 하한이고, 문제는 하한이 아니라
  「한 서버에 여러 호스트로 붙는 것」이었다. 하한을 올리면 429 를 안 내는 6도메인까지
  같이 느려진다 — 값을 안 내는 곳에서 값을 치른다.
- **이미 저장된 429 행 3,686개를 지우지 않는다.** 데이터 삭제고, 계획 80 이 정한
  「`pages` 는 묘비로 남긴다」와 충돌한다. 대신 **재크롤이 그것을 다시 받게** 두면
  자연히 갈린다 — 다만 지금 정책으로는 15일이 걸린다. 그 기간 단축은 별건이라 등재만 한다.
