# 설계: quality-eval — 정답 포함률 측정 하네스

- 슬러그 `quality-eval` · 계획 `docs/plan_quality-eval.md` · 2026-08-25

## 결정

**토픽 클러스터 코퍼스를 손으로 써서 `e2e/quality/` 에 JSON 2개로 고정하고,
러너가 질의마다 "매치 문서 수 ≥ 11" 을 먼저 검사한 뒤에만 recall@10 을 보고한다.**

`limit=10` 이라 **매치가 10건 이하인 질의는 정답이 구조적으로 상위 10 안에 있다.**
그 질의의 포함률은 1 로 고정이고 아무것도 재지 못한다. 방해 문서가 방해하고 있는지를
사람 눈이 아니라 **러너가 매 실행 판정**하게 만드는 것 — 이것이 이 설계의 핵심이다.

## 착수 전 탐침 (실측, 커밋 없음) — 설계를 바꾼 것

`SCHEMA` 그대로 메모리 DB 를 만들어 `_fts_query` 를 통과시켰다.

| 질의 → 문서 | 결과 | 뜻 |
|---|---|---|
| `김치찌개` → `김치찌개를` | **매치** | 접두 `*` 가 조사를 잡는다 — 계획이 시험하려던 대상 |
| `김치찌개` → `돼지김치찌개` | 실패 | 복합어 뒷부분은 못 잡는다 (`unicode61`) |
| `김치찌개` → `김치 찌개` | 실패 | 띄어쓰기 변형도 못 잡는다 |
| `김치찌개 맛집` → 둘 다 가진 문서 없음 | **0건** | **다어절은 AND 다** |

**AND 가 설계를 바꿨다.** 2어절 질의는 두 어절을 **한 문서가 다** 가져야 매치되므로
매치 수가 순식간에 10 밑으로 떨어지고, 그러면 위 가드에 걸려 측정 자체가 성립하지 않는다.
→ **질의는 1어절을 원칙**으로 하고, 2어절은 두 어절 모두 토픽 전역 어휘일 때만 쓴다.

## 대안 비교 — 코퍼스를 무엇으로 만드나 (이 계획의 성패)

| | A. 최소 (템플릿 생성) | **B. 손으로 쓴 토픽 클러스터** | C. 실제 웹 문서 고정 |
|---|---|---|---|
| 되돌리기 | 쉬움 | 보통 (파일 삭제) | 보통 |
| 코드량 | 적음 (`perf_search` 재사용) | 데이터 많음·코드 적음 | 적음 |
| 기존과 일치 | ○ | ○ (`perf_search.py:50` 패턴) | ✕ 저장소에 남의 문서 |
| **재려는 것이 들어 있나** | **✕ 조사·복합어·띄어쓰기가 조합에서 안 나온다** | ○ 자연히 들어간다 | ○ |
| 다음이 편한가 | 나쁨 | 좋음 | 나쁨 (재현·라이선스) |

**B.** A 는 `perf_search.py` 가 이미 하는 일이라 공짜지만, 생성 문서에는 위 탐침이 보여준
**실패 원인 자체가 없다** — 100% 가 나와도 토크나이저가 좋아서가 아니라 코퍼스가 쉬워서다.
C 는 `project.md` 재현성·저장소 위생에 걸린다.

### 구조 (B 의 구체값)

**언어당 2토픽 × 16문서 = 32문서, 토픽당 질의 10개. 총 64문서 / 40질의.**
한국어 토픽 `김치찌개`·`제주도 여행`, 영어 토픽 `sourdough baking`·`python for beginners`.

- 한 토픽의 16문서는 **토픽 어휘를 전부 공유한다** → 그 토픽 질의는 16건 안팎이 매치된다
  (가드 11 에 5건 여유. 복합어·띄어쓰기 때문에 몇 건 새는 것을 흡수한다)
- **정답 문서도 같은 토픽 다른 질의의 방해 문서다.** 그래서 64문서로 끝난다
- 질의당 정답은 **1건** — 나머지 15건은 같은 어휘를 쓰되 그 의도를 만족하지 않는다
  (레시피 ↔ 맛집 후기 ↔ 유래 ↔ 보관법 ↔ 실패담). 정답이 둘로 읽히면 **그 질의를 버린다**

## 세 갈림길의 답

1. **방해 문서** — 위 토픽 클러스터 + 가드 G2. 설계가 아니라 **매 실행 검사**로 보증한다
2. **정답은 1건** — `concept.md:22` 이 "정답 문서 포함"(단수)이다. 집합이면 부분 점수 정의가
   또 갈리고 이후 숫자 비교가 흐려진다. 분모 = 언어별 질의 20, 분자 = 상위 10에 그 URL 이 든 질의 수
3. **파일** — `e2e/quality/*.json` 2개. 러너 안 리터럴은 데이터가 로직을 파묻고,
   문서당 파일은 64개가 된다. `json` 은 stdlib 이고 diff 가 읽힌다

## 가정 — 틀리면 무너지는 것

- **깬 것**: "다어절 질의도 충분히 매치된다" → **거짓**(0건). 위에서 설계를 고쳤다
- **남은 것**: "16문서 토픽에서 정답이 상위 10 밖으로 밀릴 수 있다." bm25 가 정답을 늘 위로
  올리면 포함률은 또 100% 가 된다. 코퍼스를 써 봐야 안다 →
  **100% 가 나오면 합격이 아니라 의심 신호**로 다루고 e2e 시나리오 3(방해 문서 제거 시
  포함률이 오르는가)으로 가른다

## 계약 — 개발이 지킬 것

```
e2e/quality/corpus.json   [{"url", "lang": "ko"|"en", "title", "body"}]      HTML 아님
e2e/quality/queries.json  [{"q", "lang": "ko"|"en", "answer": <corpus 의 url>}]
e2e/quality_eval.py [--corpus PATH] [--queries PATH]
```

- 러너가 `<html><title>{title}</title><body><p>{body}</p></body></html>` 로 감싸 `pages` 에
  넣고 `indexer.index_pages()` 를 부른다 (`e2e/perf_search.py:50` 과 같은 경로, 네트워크 없음)
- 판정은 `indexer.search(db, q, limit=100)` **한 번**으로 낸다 — 앞 10건이 곧 `limit=10` 결과이고
  (`ORDER BY bm25, rowid`, 결정적), 같은 목록에서 매치 수와 정답 순위를 함께 얻는다
- **가드 — 전부 종료 코드 2. 품질 미달과 구분한다**
  - G1 `answer` 가 코퍼스에 없다 (오타 난 정답은 조용히 불합격으로 보인다)
  - G2 어떤 질의의 매치 수 ≤ 10 (**측정 불능** — 이 설계의 핵심)
  - G3 언어별 질의 수 ≠ 20 (`concept.md:22` 판정문)
- 종료 코드 `0` 두 언어 모두 ≥80% / `1` 미달 / `2` 코퍼스 결함·사용법
- 출력: `한국어 NN/20 (NN%)` · `영어 NN/20 (NN%)` · 미스마다 `[ko] 질의 → 기대 URL (매치 N건, 순위 M|밖)`

## 범위 밖 (→ digest 후보)

- 랭킹·토크나이저 수정 (계획 `## 하지 않을 것`) · MRR·nDCG 같은 다른 지표 (컨셉은 포함률 하나만 요구)
- 코퍼스는 **동결**이다. 바꾸면 과거 숫자와 비교가 끊기므로, 바꾼 반복에서 재측정해 `project.md` 를 갱신한다
- 나오는 숫자는 이 fixture 위의 값이지 웹 전체의 절대 품질이 아니다 — `perf_search` 의 기준선과 같은 성격
