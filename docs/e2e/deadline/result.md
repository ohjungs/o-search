## 왜 이것들만 보나

단위 393건이 이미 예산의 계약(덜 보낸다·간격 안 깎는다·소진 보고·CLI 오류값)을 덮는다.
**단위가 구조적으로 못 보는 자리만** e2e 로 옮겼다. 겹치는 것은 다시 재지 않았다.
거기에 **잣대(0)와 측정 불능 가드(4)** 를 붙인다 — 없으면 "덜 모았다" 가 아무것도 못
모으는 세계에서도 참이라 초록이 근거 없이 켜진다(017 이 심고 018·019 가 덕을 본 관용구).

## M6 을 정말 잡는지 확인했다

`rules/e2e.md` 7절(실행 없이 통과 기록 금지)과 짝으로, **일부러 배선을 끊고 돌렸다.**
사본(`scratchpad/mut2`)에서 `main()` 의 `crawl(..., deadline=deadline)` → `crawl(...)` 로 변이:

```
AssertionError: CLI 가 --deadline 을 crawl() 로 안 넘겼다 (M6) — stderr:
```

**단위 393건은 이 변이에 하나도 안 죽었다**(테스트 2/4 에서 M6 이 살아남은 이유이자
이 e2e 의 존재 이유다).
잡는 단언은 세 겹이다: 소진 메시지 유무 · `saved < max` · 경과 시간 상한.

**마감 시점에 깨끗하게 재실측했다.** 첫 판은 사본에 `data/` 의존 오류(`test_quality_*`
3건)가 섞여 "393건 중 3건은 사본 탓" 이라는 단서를 달아야 했다. 이번엔 변이 사본의
`src/` 만 쓰고 **저장소의 `tests/` 를 그대로** 돌려 섞인 것 없이 `Ran 393 / OK` 를 봤다:

```
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=<사본>/src python3 -m unittest discover tests
→ Ran 393 tests in 2.895s / OK      (M6 이 심어진 채로)
```

단위가 눈먼 이유는 `tests/test_crawl.py` 가 `crawl` 을 `mock.patch` 로 갈아끼우고
CLI 를 보기 때문이다 — 리뷰 3/4 가 지적한 자리 그대로다.

## 시나리오 2 가 남긴 수치 — 보류 패치의 근거

**서버가 200 HTML 로 응답한 페이지 8건, 저장된 것 7~8건. 차이가 버려진 것이다.**

실측은 **0건과 1건 사이를 오간다** — 만료 순간 요청이 떠 있었는지가 실시계 타이밍에
달렸다. 그래서 아래처럼 단언하지 않고 출력만 한다.

이미 보낸 요청의 응답을 버린 것이라 다음 실행에서 같은 URL 을 또 때린다.
`docs/patches/deadline-inflight-reap.patch`(리뷰 3/4, critical, 승인 대기)가 고치는 자리다.

**이 수치를 단언으로 못 박지 않았다.** 결과를 줍는지 버리는지는 아직 승인 대기인
설계 결정이고, 지금 방향을 단언에 박으면 패치를 적용하는 쪽이 깨진다.
**패치가 승인되면 그때 `discarded == 0` 단언으로 승격한다.**

**왜 단위로는 못 보나(구조적)**: 가짜 시계는 `time.sleep` 에서만 흐르고, `sleep` 은
`if not inflight:` 안에서만 한다 — 즉 **떠 있는 요청이 없을 때만 시간이 간다.**
"떠 있는 요청을 둔 채 예산 만료" 는 가짜 시계로 도달 불가다. 실시계에서는 fetch 가
도는 동안 시간이 가므로 바로 난다. 그래서 이 e2e 는 **도메인별 응답 지연을 어긋나게**
줘서(0.3 / 0.8 / 0.9 / 1.0초) 만료 순간에 요청이 떠 있도록 만든다.

`discarded == 0` 이 나와도 버그가 없다는 뜻이 아니라 그 라운드에 떠 있던 요청이
없었다는 뜻이다 — 스케줄링에 달렸다. 그래서 하한 단언을 안 걸었다.

## 크롤 윤리

**끝을 당기려고 아무것도 낮추지 않았다.** 도메인당 1초 하한·robots 준수 그대로고,
시나리오 0·1 모두에서 실제 간격을 재서 최소 1.00s 를 확인했다. 예산이 하는 일은
**"덜 보낸다"** 뿐이다. 빠르게 끝나는 이유는 요청을 **덜 보내서**지 빨리 보내서가 아니다.
