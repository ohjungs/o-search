# 측정 결과 — 계획 96 `docs-delete-rowid` 스텝 2

갱신 경로가 문서마다 한 번 치는 `DELETE FROM docs` 의 **문서당 값**을 코퍼스 크기별로,
**옛 열쇠(`url`)와 새 열쇠(`rowid`) 둘 다** 잰다. 한쪽만 재면 「원래 빠른 기계」와
구별되지 않는다 — 음성 대조가 판정의 절반이다.

## 1. 왜 `url` 이 비싼가

`docs` 는 FTS5 가상 테이블이고 `url` 은 `UNINDEXED` 열이다(`indexer.SCHEMA`).
그래서 URL 로 지우는 것은 **색인 전수 스캔**이고, 값이 「재크롤 집합 × 코퍼스 크기」로
곱해진다. 워터마크 조인은 그 행을 이미 손에 들고 있으므로 `d.rowid` 를 얹으면
전수 스캔이 rowid 조회가 된다.

## 2. 잰 값 (2026-09-11 · 2판, 둘째 판 괄호)

| N(`docs` 행) | 옛 `url` (ms/건) | **새 `rowid`** (ms/건) | 배수 |
|---|---|---|---|
| 1,000 | 0.164 (0.157) | **0.012** (0.012) | 14x |
| 10,000 | 2.693 (2.742) | **0.012** (0.013) | 220x (209x) |
| 40,000 | 11.950 (11.995) | **0.014** (0.014) | 881x (868x) |
| **1천 → 4만 증가율** | **72.9배** (76.3배) | **1.2배** (1.2배) | |

**판정 둘 다 통과.**
① 새 열쇠의 문서당 값이 코퍼스 크기를 따라 늘지 않는다 — 4만/1천 **1.2배** (기준 ≤ 2배).
② 옛 열쇠는 같은 실행에서 선형으로 는다 — **72.9배** (코퍼스는 40배). 후보 `[7]` 의
   「1천 0.09 → 4만 3.35ms(37배)」와 **모양이 같다.**

**절대값이 후보보다 3.5배 큰 이유는 입력의 모양이다** — 여기 합성 본문은 어절 200개
(`"pyeongsan gwangju 본문 문단 " × 40`)로 후보가 쟀을 때보다 길다. 전수 스캔의 값은
색인 크기를 따라가므로 본문이 길수록 비싸진다. **모양(선형 대 상수)이 판정이고 절대값은
이 입력에서의 눈금**이다 — `project.md` 의 「숫자 옆에 그 숫자를 낸 입력의 모양을 적는다」.

## 3. 재현하는 법

측정기는 상시로 둘 근거가 아직 없어 **커밋하지 않는다**(새 파일 추가는 설계 트리거다).
아래를 `/tmp/measure_delete.py` 로 저장해 `PYTHONDONTWRITEBYTECODE=1 python3
/tmp/measure_delete.py` 로 돌린다. 상시 필요해지면 그때 `e2e/perf_*.py` 관용구로 만든다.

```python
# 임시 DB 에 indexer.SCHEMA 로 docs 를 만들고 N 행을 넣은 뒤,
# 아직 안 지운 구간에서 40행씩을 각각 url·rowid 열쇠로 지워 문서당 벽시계를 잰다.
#   build(db, n): INSERT INTO docs(title, body, url) VALUES (?,?,?)  × N
#   measure(n):   url 은 앞 구간, rowid 는 뒤 구간(n//2 부터) — 같은 행을 두 번 안 지운다
#   본문: "pyeongsan gwangju 본문 문단 " * 40 · N = 1000, 10000, 40000
```

## 4. 이 표가 못 재는 것 (천장)

- **404·410 갈래와 noindex 갈래의 열쇠**는 여기서 안 갈린다. 그 둘은 지우고 끝이라
  두 열쇠의 **결과가 같고** 갈리는 것은 값뿐이다 — 단위 변이 M1·M2 가 살아남는 것과
  같은 이유다(`tests/test_indexer.py` 의 `test_update_touches_only_the_row_the_join_handed_it`
  docstring). 이 표의 `url` 열이 그 둘의 값이기도 하다.
- **실물 코퍼스에서의 갱신 총량**은 안 잰다 — 재크롤 집합의 크기는 크롤 일정이 정한다.
  이 표는 문서당 값이고, 총량은 「그 값 × 재크롤 건수」다.
- 합성 본문이라 **문서 크기 분포**가 실물과 다르다(3절 참조).

## 5. e2e — 실물 코퍼스 A/B (2026-09-12 · 반복 551)

계획서 e2e 시나리오 둘을 **실물 `data/crawl.db` 사본 두 벌**에서 돌렸다. 원본은 건드리지
않았다(읽기 전용 복사 → `/tmp/e2e-rowid/{new,old}.db` · 각 2.48GB).

- **새 팔** `PYTHONPATH=src` (HEAD · `rowid` 열쇠)
- **옛 팔** `PYTHONPATH=/tmp/oldsrc` (`main:src/websearch/` 통째 · `url` 열쇠)
- 양쪽 `python3 -m websearch.indexer <db>` 를 **순차로** 돌렸다 — 동시에 돌리면 재는 것이
  벽시계가 아니라 CPU 경합이다.

### 5-1. 워터마크를 되돌린 이유

실물의 `recheck_watermark` 가 `2026-09-11 14:57:11` 로 **`max(pages.fetched_at)` 과 같다**
— 크롤 직후 색인이 이미 돌아서다. 그대로면 갱신 루프가 볼 쌍이 **1건**이라 갱신 경로를
못 잰다. **양쪽 사본에 똑같이** `2026-09-11 14:53:00` 으로 되돌려 「재크롤이 들어온 코퍼스」를
만들었다 — **갱신쌍 1,225건** (양쪽 동일 확인). 코퍼스는 `docs` **40,347행** 그대로라
2절 표의 4만 행과 직접 대조된다.

**실물이 스스로는 이 경로를 안 보여 준다**는 것 자체가 기록할 값이다 — 되돌리지 않았으면
「e2e 통과」가 1건짜리 실행을 본 것이 된다.

### 5-2. 시나리오 1 — 결과가 같은가

| | 1판 (본문 안 갈림) | 2판 (200건 본문 교체 + 30건 404) |
|---|---|---|
| `docs` 행 (새/옛) | 40,347 / 40,347 | **40,317 / 40,317** |
| 중복 URL | 0 / 0 | 0 / 0 |
| 404 된 URL 의 `docs` 행 | — | **0 / 0** (사라졌다) |
| 새 본문(`zzmarkerpyeongsan`) 히트 | — | **200 / 200** |
| `GET /search` 16응답 | 색인 **전**과도 바이트 동일 | **새 팔 == 옛 팔** 바이트 동일 |

1판만으로는 부족했다 — 워터마크만 되돌린 실행은 **같은 HTML 을 다시 처리**하는 것이라
「갱신된 본문이 나온다 · 404 가 사라진다」를 건드리지 않는다. 그래서 2판에서 양쪽 사본에
**똑같이** 갱신집합 중 200건의 `pages.html` 을 교체하고 30건을 `status=404 · html=NULL`
로 뒤집었다. 양쪽 다 `30 문서 색인 제외` 를 찍었고 위 표대로 결과가 일치한다.

응답은 실제 `serve.make_server` 를 띄워 `GET /search?q=…&page=…` 로 받았다(질의 8종 × 2쪽,
`rate_limit=None`). **바꾼 것은 값이지 결과가 아니다 — 실물에서 확인됐다.**

### 5-3. 시나리오 2 — 값을 2절 표와 대조한다

| 판 | 새 `rowid` | 옛 `url` | 차 | 갱신쌍당 차 |
|---|---|---|---|---|
| 1판 | **23.09s** | 190.37s | 167.28s | **136.6ms** |
| 2판 | **16.79s** | 187.05s | 170.26s | **139.0ms** |

두 팔의 코드 차이는 삭제 열쇠(와 조인의 `d.rowid`)뿐이라 **차는 삭제에 귀속된다.**
실행 전체로 **8.2배 · 11.1배**다. (1판 새 팔이 2판보다 느린 것은 첫 실행이라 파일 캐시가
차가웠던 것이다 — 옛 팔은 두 판이 190/187 로 같다.)

**2절 표의 4만 행은 11.95ms/건이었는데 실물은 137ms/건 — 11.5배다.** 3절이 적어 둔 천장이
수치로 맞았다: 전수 스캔의 값은 **행 수가 아니라 색인 크기**를 따라간다.

| | 합성 4만 | 실물 4만 |
|---|---|---|
| 평균 본문 | 960자 | **16,210자** (16.9배) |
| 삭제 1건 | 11.95ms | **137ms** (11.5배) |

**모양은 2절이 맞았고 눈금은 실물이 더 나쁘다.** 판정 ①②는 실물에서도 그대로다 —
새 열쇠는 4만 코퍼스에서도 상수(전체 실행 17초에 갱신 1,225건이 묻힌다).

### 5-4. 이 실행이 못 잰 것

- **재크롤 총량은 여전히 크롤 일정이 정한다.** 1,225건은 워터마크를 되돌려 만든 수다.
  실물이 하루에 얼마를 재크롤하는지는 이 표가 모른다.
- **`0 문서 색인`** — 양쪽 다 신규 색인 0건이다(미색인 419건은 `html IS NULL` 이거나
  noindex). 이 실행이 잰 것은 **갱신 경로뿐**이고 신규 색인 전수 조인(계획서 「하지 않을
  것」)은 손대지 않았다.
- **중복 `docs` 행이 0인 코퍼스에서만 쟀다.** 중복이 있으면 두 열쇠의 **결과가 갈린다**
  — 리뷰 보류 건(`status.md ## 사람 결정 대기`)이 그것이고, 이 e2e 는 그 갈림을 재지 않는다.

### 5-5. 재현하는 법

```bash
mkdir -p /tmp/e2e-rowid && cp data/crawl.db /tmp/e2e-rowid/new.db && cp data/crawl.db /tmp/e2e-rowid/old.db
mkdir -p /tmp/oldsrc/websearch                       # 옛 팔 = main 의 src/websearch 통째
for f in $(git ls-tree --name-only main:src/websearch/); do
  git show main:src/websearch/$f > /tmp/oldsrc/websearch/$f; done
# 양쪽 사본에 똑같이: recheck_watermark 를 '2026-09-11 14:53:00' 으로 UPDATE
#   (2판은 갱신집합을 url 순으로 정렬해 앞 200건 html 교체 · 다음 30건 status=404/html=NULL)
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src      /usr/bin/time -p python3 -m websearch.indexer /tmp/e2e-rowid/new.db
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/tmp/oldsrc /usr/bin/time -p python3 -m websearch.indexer /tmp/e2e-rowid/old.db
# 응답 대조: serve.make_server(db, port=0, rate_limit=None) 을 띄워 GET /search 를 JSON 으로 덤프해 diff
```
