# 설계: cooldown-burn — 간격 시계를 팝에서 떼어 실제 발신에 건다

## 결정

`Frontier.next()` 는 `_last_fetch` 를 **읽기만** 하고, 간격 시계는 `mark_sent()` 만 건다.
`crawl` 은 **요청이 실제로 나간 경로에서만** 시계를 걸되, **워커 예외 경로에서는
`now()` 로 보수적으로 건다** — 요청이 나갔는지 알 수 없기 때문이다.
`frontier.py` 와 `crawl.py` 를 **한 커밋**에 넣는다.

## 대안 비교

출발점 셋에서 하나씩 냈다.

| | **A. 최소**<br>팝 쓰기 삭제 + 예외 경로 보수적 마킹 | **B. 정공법**<br>프런티어가 in-flight 를 1급으로<br>(`next()`→리스, `release(lease, sent_at\|None)`) | **C. 되돌리기 우선**<br>팝 쓰기는 두고 스킵 경로에서<br>`cancel(domain, prev)` 로 되돌린다 |
|---|---|---|---|
| 되돌리기 | 커밋 하나 revert | 커밋 하나 revert (호출부 개조가 커서 충돌 여지) | 커밋 하나 revert |
| 코드량 | **가장 적음** — 새 개념 0, `mark_sent` 재사용 | 많음 — 리스 객체·수명 관리 신설 | 보통 — `cancel()` 신설 |
| 기존과 일치 | **○** `mark_sent` 주석이 이미 이 계약을 적고 있다 | △ 프런티어가 크롤 수명주기를 알게 된다 | ○ 기존 계약 무손상 |
| 다음이 편한가 | **좋음** — 불변식이 "시계 = 실제 발신" 하나 | 보통 — 호출처가 하나뿐인데 범용 구조 (추측성 확장) | **나쁨** — 스킵 경로가 늘 때마다 취소를 빠뜨린다 |
| `test_frontier.py` | 9건 재작성 (계약이 바뀌므로 정당) | 9건 + 신규 API 테스트 | **0건** |

**선택: A** — 셋 중 코드가 가장 적고, **이 저장소가 이미 적어 둔 계약과 일치한다.**
`frontier.py:75-79` 의 `mark_sent` 주석이 "간격 시계를 팝이 아니라 여기서 다시 건다" 라고
쓰여 있다. 팝 쓰기는 그 문장과 모순된 잔재다 — A 는 코드를 **제 주석에 맞추는** 일이다.

**버린 이유: B** — `Frontier` 호출처는 `crawl.py:66` **하나뿐**이다(grep 실측).
구현 하나짜리 범용 리스 구조는 사다리 1번(추측성)에 걸린다. 지금 필요한 것은
"시계를 언제 거나" 뿐인데 B 는 "누가 무엇을 빌려갔나" 를 새로 만든다.

**버린 이유: C** — 테스트 9건을 안 깨는 것이 유일한 장점인데, **그게 곧 단점이다.**
"팝 = 요청" 이라는 **틀린 전제를 남긴 채** 증상 경로마다 취소를 붙인다. 지금은 스킵 경로가
둘(`store.has`·robots)이지만 셋째가 생기면 조용히 다시 태운다. ponytail: 증상이 아니라
원인을 고친다. (C 의 처리량은 A 와 같을 것으로 본다 — **재지 않았다.** 갈리는 것은
숫자가 아니라 구조라서, 재도 선택이 안 바뀐다)

**버린 이유: 제출 시점 마킹 / add 시점 robots 필터** — 계획 phase 가 이미 닫았다.
전자는 **실측으로 0을 회수**(4.48→4.49/s, robots 판정이 워커 안에서 난다),
후자는 메인 스레드에 네트워크 I/O 를 들여 동시화 계약 4를 깬다.

## 가정 — 3-2절에서 깬 결과

실제 코드 사본(`scratchpad/mut3`)에 A 를 적용해 확인했다. 네트워크는 치지 않았다.

1. **"팝과 실제 발신 사이 창은 `exclude=busy` 가 이미 덮는다"** → **참.**
   한 도메인 6URL·워커 8 로 굶겨도 발신 간격 최소 **1.010s**.
   `crawl.py:71` 이 제출 **전에** `busy.add(domain)` 하고, `busy` 는 매 바퀴 `inflight`
   에서 다시 만들어진다. 창이 열린 채로 같은 도메인이 두 번 팝되지 않는다.
2. **"예외 경로 구멍은 실재하고 보수적 마킹이 닫는다"** → **참, 양쪽 다.**
   예외를 주입하니 순진한 수정(팝 쓰기만 삭제)이 **0.310s** 로 1초 계약을 깼다.
   008 리뷰의 경고가 옳았다. 보수적 마킹을 넣으면 **1.010s** 로 돌아온다.
3. **회수는 실제로 난다** → 차단 사이트에서 **4.47 → 10.28/s**(목표 9.0 초과),
   페이지 최소 간격 1.005s, 차단 경로 요청 0건.

**개발이 반드시 가져갈 부수 발견:** 차단 시나리오**만** 재면 순진한 수정도 통과한다
(10.31/s · 1.001s). 구멍은 **예외를 주입해야만** 보인다 — 스텝 1 완료 기준 ③과
스텝 2 e2e 시나리오 4를 빼면 이 설계의 핵심이 검증되지 않는다.

## 계약 — 개발이 지킬 것

1. `Frontier.next()` 는 `_last_fetch` 를 **쓰지 않는다.** 읽어서 거르기만 한다.
   시계를 거는 유일한 자리는 `mark_sent()` 다. (`Frontier` 공개 시그니처는 그대로)
2. `crawl` 이 `mark_sent` 를 부르는 경우는 **둘뿐**이다:
   - 정상 — `mark_sent(domain, sent_at)` (워커가 찍은 실제 발신 시각)
   - **예외** — `mark_sent(domain, now())`. 요청이 나갔는지 모르므로 **늦게** 잡는다.
     `mark_sent` 가 `max` 로 늦은 쪽으로만 움직이니(`frontier.py:82`) 안전하다
3. `store.has` 스킵과 **robots 차단은 시계를 걸지 않는다** — 페이지 요청이 안 나갔다.
4. `_store_result` 에 `now` 를 넘긴다(내부 함수 시그니처 변경, 호출처 1곳).
5. **`frontier.py` 와 `crawl.py` 는 한 커밋.** 팝 쓰기만 지운 중간 커밋은 1초 계약이
   깨진 상태다 — 넘지 않는 선은 계획이 끝날 때가 아니라 **매 커밋**에서 지킨다.
6. 도메인당 페이지 요청 1.0초 하한과 robots 준수를 **낮추지 않는다.** 어기면 RED.

## 되돌리기

**커밋 하나 revert.** 새 파일도 새 의존성도 없고, 저장 데이터 형태를 만지지 않는다.
되돌리면 팝 쓰기가 그대로 돌아온다(느리지만 계약은 지켜지는 오늘의 상태).
피처 플래그를 두지 않는다 — 플래그로 갈리는 두 경로 중 하나가 **간격 계약이 깨진 쪽**이
될 수 있고, 그런 것은 끌 수 있게 두면 안 된다.

## 범위 밖

- **`store.has` 의 상태 불문 스킵** — 같은 DB 재실행이 시드부터 막혀 0으로 끝난다.
  별개의 `[high]`, **recrawl 계획 소관**. 이 계획은 쿨다운만 본다
- **`recrawl`(`fetched_at` 스키마) · `X-Robots-Tag`(스키마)** — 승인 대기, 야간 금지
- **`Ctrl-C` 지연 · `--deadline`** — digest `[4]`, 별도 계획
- digest 후보: **차단 사이트를 재는 눈이 8일 동안 없었다.** 기준선 10.25/s 는
  "막는 것이 없는 세계" 의 숫자였고, 그래서 4.48/s 가 안 보였다. 스텝 2가 이 눈을 만든다
