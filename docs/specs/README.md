# specs — 사용자가 쓰는 곳

이 폴더는 **사람이 작성하는 유일한 곳**이다. `docs/` 의 나머지는 루프가 쓰고 갱신한다.

여기에 사양을 넣고 루프에게 가리키면 된다.

```
/loop-harness @docs/specs/결제연동.md 대로 구현해줘
/loop-harness night @docs/specs/검색개선.md
```

## 파일 규칙

- **파일명**: `<슬러그>.md` — 한글도 된다. 계획 슬러그가 여기서 나온다
- **완료된 사양**: `_archive/` 로 옮긴다. 루프가 마지막 계획을 마칠 때 옮긴다
- **루프는 이 폴더의 파일을 고치지 않는다.** 읽기만 한다

사양과 계획이 어긋나면 **사양이 맞다.** 루프가 계획을 고친다.
사양 자체를 바꾸고 싶으면 여기 파일을 직접 고치고 루프에게 다시 알린다.

## 무엇을 적나

정해진 서식은 없다. 있는 그대로 쓰면 된다.
다만 아래가 있으면 루프가 계획을 훨씬 정확하게 세운다.

| 항목 | 없으면 |
|---|---|
| **무엇을 · 왜** | 목적을 모르면 엉뚱한 걸 만든다 |
| **완료 판정 기준** | "잘 되면" 은 검증할 수 없다. 무엇을 실행해 무엇을 확인할지 |
| **하지 않을 것** | 범위가 새어나간다. 이번에 안 할 것을 적으면 그대로 지킨다 |
| **기존 코드와의 관계** | 어느 파일·모듈에 닿는지. 모르면 "모름" 이라고 적어도 된다 |
| **제약** | 성능·호환성·마감. 설계 대안을 고를 때 쓴다 |

## 루프가 하는 일

1. 이 파일을 읽고 **원문 그대로** 참조한다 (요약하지 않는다)
2. 9스텝을 넘으면 **계획 여러 개로 쪼갠다** — 되돌릴 수 있는 단위로
3. 쪼갠 결과를 **시작 전에 보여준다**. 야간이면 아침 보고서에 남긴다
4. 각 계획서에 이 사양의 **어느 절**을 근거로 삼았는지 적는다
5. 모호한 곳이 있으면 **묻는다.** 야간이면 착수하지 않고 보류한다

## 예시

```markdown
# 결제 연동

## 무엇을 · 왜
카드 결제를 붙인다. 지금은 계좌이체만 돼서 이탈률이 높다.

## 완료 판정
- 테스트 카드로 결제 성공 → 주문 상태가 `paid` 로 바뀐다
- 결제 실패 시 주문은 `pending` 유지, 사용자에게 실패 사유 표시
- `npm test` 통과, e2e 시나리오 2건 추가

## 하지 않을 것
- 환불 — 별도 사양
- 정기결제
- 결제 수단 저장

## 기존 코드
`src/order/` 아래. `createOrder()` 뒤에 붙는다.
결제사 SDK 는 아직 안 정했다.

## 제약
- 카드 정보를 우리 서버에 저장하지 않는다
- 결제사 응답 지연 시 30초 타임아웃
```

`결제사 SDK 는 아직 안 정했다` 처럼 **안 정해진 것을 적어두면**
루프가 그 지점에서 설계 단계를 거치거나, 의존성 추가라 보류한다.
숨기지 말고 적는 편이 낫다.
