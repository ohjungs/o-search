# 계획: 검색 품질 측정 — 정답 포함률 80%

- **슬러그**: `quality-eval`
- **브랜치**: `loop/quality-eval` (`loop/crawl-delay` 6bb2785 에서 갈라졌다 — 이 저장소의 계획 브랜치는 직렬로 쌓인다)
- **근거**: `docs/index.md` 사양 분할 7번 — `docs/specs/concept.md:22-23` 기능 2
- **시작**: 2026-08-25

## 목표

`docs/specs/concept.md:22-23` 은 기능 2 의 합격을 **"한국어 질의 20개·영어 질의 20개
테스트 셋에서 상위 10건 안에 정답 문서 포함 — 각 80% 이상"** 이라고 못박았다.
이 숫자는 **한 번도 잰 적이 없다.** 검색 품질은 갈림길 우선순위 2번(`concept.md:59`,
크롤 윤리 바로 다음)인데 재는 수단이 없어서, 지금까지의 랭킹 관련 선택
(FTS5 `unicode61` 토크나이저, `prefix='2 3'`, `_fts_query` 의 접두 재작성, `bm25` 정렬)이
품질을 올렸는지 내렸는지 **아무도 모른다.**

완료되면 `PYTHONPATH=src python3 e2e/quality_eval.py` 한 줄로 한국어·영어 각각의
정답 포함률(recall@10)이 나오고, 80% 기준의 합격·불합격이 판정된다.
`e2e/perf_search.py` 가 성능 축에 해 준 것을 품질 축에 해 주는 것이다.

**이 계획은 재는 계획이지 고치는 계획이 아니다.** 80% 에 미달해도 랭킹을 손대지
않는다 — 숫자와 원인 분류를 남기고, 개선은 그 근거 위에서 별도 계획으로 연다.

## 이미 참인 것 (착수 전 사실 — 읽고 확인했다)

- **질의 경로**: `src/websearch/indexer.py:78` `search(db_path, query, limit=10, offset=0)`
  → `(url, title, snippet)` 목록을 `ORDER BY bm25(docs), rowid` 로 돌려준다.
  `limit` 기본값이 이미 10이라 "상위 10건" 을 그대로 잰다.
- **질의 재작성**: `indexer.py:71` `_fts_query()` 가 어절마다 `"단어"*` 로 접두 매치를 붙인다.
  한국어 조사(`김치찌개를` ← `김치찌개`)를 잡아 주는 유일한 장치이고,
  **이 계획이 실제로 시험하는 대상**이다.
- **토크나이저**: `indexer.py:12-15` `SCHEMA` — `fts5(title, body, url UNINDEXED, tokenize='unicode61', prefix='2 3')`
  (착수 시 열 이름을 `text` 로 잘못 적었다. 실제 열은 `body` 다).
  `unicode61` 은 한국어를 **공백 단위로만** 자른다. 즉 `매운 김치찌개` 문서에서
  질의 `김치찌개` 는 접두 매치로 걸리지만 복합어 **뒷부분**(`돼지김치찌개` ← `김치찌개`)은
  못 잡는다. 미달이 나온다면 1순위 용의자다.
- **색인 진입점**: `indexer.py:18` `index_pages(db_path)` — `pages` 테이블에서 미색인 행을
  읽어 `docs` 에 넣고 개수를 돌려준다. `extract.is_noindex` 인 문서는 뺀다.
- **코퍼스를 크롤 없이 만드는 기존 방법**: `e2e/perf_search.py:50` `build_index()` 가
  `pages` 테이블(`url, html, status`)을 직접 채운 뒤 `indexer.index_pages()` 를 부른다.
  **이 패턴을 재사용한다** — 네트워크도 크롤 루프도 타지 않는다.
- **한도**: `docs/project.md` — 외부 네트워크를 때리는 테스트 금지. 코퍼스는 저장소 안에 고정한다.
- 현재 `PYTHONPATH=src python3 -m unittest discover tests` 146/146 통과 (2026-08-25 착수 전 확인).

## 하지 않을 것

- **랭킹·토크나이저 변경** — 이 계획은 자를 만드는 것이다. 자를 만들면서 재는 대상을
  같이 고치면 숫자의 의미가 사라진다. 미달이면 원인만 분류해 `digest.md` 후보로 남긴다
- **형태소 분석기 도입** — `concept.md:76` "하지 않을 것"
- **`search-ui`** — `docs/index.md` 6번, 별도 계획
- **`recrawl` · `X-Robots-Tag`** — 스키마 변경이라 무인 모드 금지. 사람 승인 대기
- **실제 웹에서 코퍼스 수집** — `project.md` 한도 위반. 코퍼스는 저장소 안 고정 fixture
- **`serve.py` / HTTP 경로** — 재는 대상은 랭킹이지 전송이 아니다. `indexer.search` 직접 호출
  (이 판단이 옳은지는 설계에서 확정한다)

## 설계

**필요** → `docs/design_quality-eval.md`

트리거 세 가지에 걸린다:

1. **새 모듈** — 평가 하네스와 코퍼스 fixture 는 지금 없는 것이다
2. **대안이 갈린다** — 아래 셋이 계획서 안에서 저울질되기 시작했다:
   - 코퍼스를 **어떻게 만들어야 측정이 거짓말하지 않는가**. 정답 문서만 질의어를 가지면
     recall@10 은 자동으로 100% 가 되고 **아무것도 재지 못한다**. 방해 문서(같은 어휘를
     공유하지만 정답이 아닌 문서)의 설계가 이 계획의 성패다
   - **정답이 1건인가 집합인가** — 포함률의 분모·분자 정의가 여기서 갈린다
   - 코퍼스·질의 셋을 **파일로 둘 것인가 스크립트 안에 둘 것인가**
3. **되돌리기 어렵다** — 코퍼스와 질의 셋은 한 번 정하면 이후 모든 품질 숫자의 기준선이
   된다. 나중에 바꾸면 과거 숫자와 비교가 끊긴다

## 스텝 (설계가 갱신할 수 있다)

### 1. 코퍼스 fixture — 방해 문서를 포함해 고정한다
- **의존**: 없음
- **예상 파일**: `e2e/quality/corpus.*` (형식은 설계가 정한다)
- **완료 기준**: 한국어 문서·영어 문서·방해 문서를 담은 fixture 가 생기고,
  `indexer.index_pages()` 로 색인했을 때 반환 문서 수가 fixture 문서 수와 같다
  (`is_noindex` 로 조용히 빠지는 문서가 0건임을 확인)

### 2. 질의 셋 40개 + 정답 매핑
- **의존**: 1 (문서의 URL 을 정답으로 가리켜야 한다)
- **예상 파일**: `e2e/quality/queries.*`
- **완료 기준**: 한국어 20개·영어 20개, 각 질의의 정답 URL 이 **코퍼스에 실제로 존재**한다
  (러너가 시작할 때 대조해 없으면 즉시 실패 — 오타 난 정답은 조용히 불합격으로 보인다)

### 3. 러너 `e2e/quality_eval.py`
- **의존**: 2
- **예상 파일**: `e2e/quality_eval.py`
- **완료 기준**: 실행하면 `한국어 NN/20 (NN%)`, `영어 NN/20 (NN%)` 와 실패한 질의 목록이
  출력되고, 두 비율이 모두 80% 이상이면 종료 코드 0, 미달이면 1
- **완료 기준(설계가 추가)**: 가드 3종이 종료 코드 2 로 갈린다 —
  정답 URL 부재 / **어떤 질의의 매치 문서 수 ≤ 10**(측정 불능) / 언어별 질의 수 ≠ 20.
  근거는 `docs/design_quality-eval.md` `## 결정`

### 4. 실측 · 기록
- **의존**: 3
- **예상 파일**: `docs/project.md`(품질 기준 절), `docs/e2e/quality-eval/result.md`
- **완료 기준**: 실제 숫자가 `project.md` 에 적히고, 미달 질의는
  **원인이 분류**되어(조사/복합어 = 토크나이저 / 동의어 / bm25 순위) `digest.md` 후보로 남는다

## e2e 시나리오

1. `PYTHONPATH=src python3 e2e/quality_eval.py` → 한국어·영어 정답 포함률이 각각
   출력되고 둘 다 80% 이상이면 종료 코드 0
2. **자가 검증(측정이 진짜 재는지)**: 정답 문서 한 건을 코퍼스에서 뺀 채 돌리면
   그 질의가 **실패로 잡힌다.** 잡히지 않으면 러너가 거짓말하는 것이다
   (`project.md` 변이 검사 절 — `__pycache__` 때문에 `PYTHONDONTWRITEBYTECODE=1` 을 붙인다)
3. 방해 문서를 전부 뺀 채 돌리면 포함률이 **눈에 띄게 올라간다** — 안 오르면
   방해 문서가 방해하고 있지 않다는 뜻이고, 그 코퍼스로 잰 80% 는 의미가 없다
