# 계획 55 — `db-state-invariant`

**같은 원칙이 네 번째로 재발했다.** 계획 47 은 `search()` 안에서, 53 은 `pages`
테이블 축에서, 54 는 `pages.html` 열 축에서 「DB 상태 판정이 질의 내용에 달렸다」를
닫았다. 오늘 `pages.url` 축이 같은 모양으로 살아 있다 — 같은 고장난 DB 에
`q=김치찌개` 는 `sqlite3.OperationalError: no such column: url` 로 **500**,
`q=zzzznope`·`q=%01` 은 `hits` 가 비어 루프에 닿지 못해 **200 `{"passages": []}`** 다.

**그래서 이 계획은 자리를 넓히는 것이 아니라 자를 세우는 것이 본체다.**
직전 반복이 `status.md` 에 *"네 번째가 나오면 자리를 또 넓히는 대신 원칙을 기계로
만드는 것을 먼저 검토한다"* 를 남겼고, 이 계획이 그 지시를 실행한다.

- **슬러그**: `db-state-invariant`
- **브랜치**: `loop/db-state-invariant`
- **기점**: `09b642e` (`loop/passage-html-column` 의 HEAD · 계획 54 DONE 문서까지)

## 1. 문제 · 목표 · 기대 결과

### 문제

`indexer.passages()`(`src/websearch/indexer.py`)는 `hits = search(...)` 뒤,
`hits` 루프 앞에서 DB 상태를 두 번 판정한다 — `sqlite_master` 로 `pages` 테이블의
유무를 보고(계획 53), `SELECT html FROM pages LIMIT 0` 으로 `html` 열을 읽을 수
있는지 본다(계획 54). 둘 다 **루프 앞**이라 질의 내용과 무관하게 걸린다.

그런데 같은 함수가 루프 **안**에서 `SELECT html FROM pages WHERE url = ?` 로
`url` 열도 읽는다. `url` 은 판정에 없어서, 그 열이 빠진 DB 는 매치되는 질의에서만
루프에 들어가 터진다 — **판정이 다시 질의 내용에 달린다.**

**진짜 문제는 `url` 한 자리가 아니다.** 계획 53·54 는 각각 자리 하나를 닫으면서
테스트 클래스를 하나씩 늘렸다(`TestPassagesWithoutPagesTable` ·
`TestPassagesWithoutHtmlColumn` · `TestPassagesWithoutHtmlColumnBeforeIndexing`,
전부 `tests/test_serve.py`). 클래스마다 깨진 스키마를 **손으로** 적으므로,
다섯 번째 자리가 생기는 날 그것을 알아차리는 기계가 저장소에 **0개**다.

### 목표

1. `pages` 열 축에서 「한 상태 = 한 판정」이 참이 된다(`url` 축을 닫는다).
2. **그 사실을 스키마에서 자동으로 다시 재는 자를 세운다** — 열이 늘거나 줄면
   자의 눈금도 같이 늘거나 준다. 사람이 표를 다시 적을 필요가 없다.

### 기대 결과

`store.SCHEMA` 의 열 넷을 각각 뺀 DB 넷에 세 질의(`김치찌개`·`zzzznope`·`%01`)를
먹이면 **한 DB 안에서 세 답이 같다.** 오늘 실측과 대비하면:

| 빠진 열 | 오늘 (`q=김치찌개` / `zzzznope` / `%01`) | 이 계획 뒤 |
|---|---|---|
| `url` | **예외 / 정상 / 정상** — 갈린다 | 예외 셋 |
| `html` | 예외 셋 (계획 54 가 닫았다) | 무변 |
| `status` | 정상 셋 | **무변 — 안 건드린다** |
| `fetched_at` | 정상 셋 | **무변 — 안 건드린다** |
| (없음, 대조군) | 정상 셋 | 무변 |

### 무엇이 이미 참인가 (이 저장소를 처음 여는 사람을 위한 전제)

- `passages()` 는 `search()` 를 부른 뒤 자기 연결을 하나 더 연다. DB 상태 판정
  한 벌(없는 DB → 503 · 옛 색인 → 503)은 `search()` 것을 그대로 물려받는다.
- 계획 53 이 `sqlite_master` 가드를 심어 `pages` 테이블 축을 503 으로 모았다.
- 계획 54 가 `SELECT html FROM pages LIMIT 0` 을 그 아래 줄에 심어 `html` 열 축을
  500 으로 모았다. 그 줄의 `ponytail:` 주석이 **바로 이 계획의 처방을 적어 두었다**
  — *"넓히는 날은 `SELECT url, html FROM pages LIMIT 0` 한 낱말이거나 … `PRAGMA
  table_info` 한 번"*.
- `serve.py` 는 `passages()` 의 예외를 표로 옮긴다 — `FileNotFoundError`·
  `StaleIndexError`·`NoCrawlDataError` 는 503, 나머지는 500. `tests/test_serve.py`
  의 `TestPassagesSchemaVersion` 이 그 표를 붙든다. **HTTP 표면에 줄을 더할 일이
  없다는 뜻이다.**
- `store.SCHEMA` 는 `CREATE TABLE IF NOT EXISTS pages (url, html, status,
  fetched_at)` 이고 `IF NOT EXISTS` 라 **열이 빠진 `pages` 는 `Store()` 재생성으로
  안 낫는다**(계획 54 설계 실측).
- 단위 **603건 OK**(2026-09-05 이 반복이 맨몸·단독으로 다시 확인 · 13.301초 · rc 0).

## 2. 근거

**출처 5순위** — `docs/digest.md` 의 `## 다음 계획 후보` 에 있는 `[5]` 항목
(*"같은 갈림이 `pages.url` 축에 그대로 남아 있다 — 계획 54 가 닫은 것은 `html` 열
하나뿐이다"*, 2026-09-04 계획 54 **리뷰** 실측 · 신뢰도 95). 그 항목이 스스로 적은
**여는 조건**이 *"`passages()` 의 탐침을 손대는 다음 계획"* 이고 이 계획이 그것이다.

**두 번째 근거는 `status.md` 가 남긴 지시다** — *"원칙이 세 번(계획 47·53·54)
재발했다. 네 번째가 나오면 자리를 또 넓히는 대신 원칙을 기계로 만드는 것을 먼저
검토한다."* 이 계획의 2절 목표가 그 검토의 실행이다.

### 이 계획이 스스로 인정하는 약점 — 도달 조건이 낮다

`store`·`indexer` 의 어떤 경로도 `url` 없는 `pages` 를 만들지 않는다. 이 상태에
닿으려면 사람이 스키마를 손으로 고쳐야 한다 — 계획 54 의 `[6]` 과 똑같은 약점이고,
그래서 후보 점수가 5 다. **값은 자리에 있지 않고 자에 있다**: 네 번째 재발이
「손으로 적은 표는 늙는다」를 보여줬으므로, 이 계획이 사는 것은 `url` 한 열이 아니라
다섯 번째 열이 생기는 날 그것을 **말해 주는 기계**다.

`digest [7]` 의 「기록된 답을 실행 전에 다시 재라」를 여섯 번째로 적용했다. 임시

하나씩 빼고 다시 만들어 `indexer.passages()` 를 직접 불렀다(저장소 `data/crawl.db`
는 **열지도 않았다**). 세 질의는 `김치찌개`·`zzzznope`·`\x01` 이다.

| DB 상태 | `q=김치찌개` | `q=zzzznope` | `q=%01` |
|---|---|---|---|
| 정상 (대조군) | 3건 | 0건 | 0건 |

| `fetched_at` 열 없음 | 3건 | 0건 | 0건 |
| `url`·`html` 둘 다 없음 | `no such column: html` | `no such column: html` | `no such column: html` |

**후보 항목의 서술은 글자 그대로 참이다** — `url` 축의 갈림이 살아 있고, `status`
축은 `passages()` 가 그 열을 아예 안 읽어 없어도 정상이다.

**그런데 같은 표가 처방 후보 하나를 죽인다.** 계획 54 의 주석이 남긴 둘째 안
(`PRAGMA table_info` 로 필요한 열 집합을 대조)은 «필요한 집합» 을 `store.SCHEMA`
전체로 잡으면 위 표의 3·4행(오늘 **정상**인 두 상태)을 500 으로 만든다 — 오탐이다.
집합을 손으로 `url`·`html` 둘만 적으면 값은 첫째 안과 같고 줄만 는다. **`PRAGMA`
안은 오늘 실측에서 탈락했다**(설계가 다시 확인한다 — 6절 갈림길).

### 색인 경로는 이미 갈리지 않는다 — 확인만 하고 안 건드린다

`indexer.index_pages()` 는 같은 `sqlite_master` 가드 뒤에서
`SELECT url, html FROM pages …` 로 **두 열을 함께** 읽는다. 질의를 받지 않는
경로라 갈릴 축 자체가 없다. 이 계획은 그 함수를 손대지 않는다.

## 5. 완료 기준 (검증 가능 · 대칭으로 잰다)

1. `store.SCHEMA` 에서 뽑은 열 넷 × 세 질의 **12칸**에서 **한 DB = 한 판정**이다.
2. **오탐 0**: 정상 DB 대조군 세 질의가 무변(3건 / 0건 / 0건)이고, `status`·
   `fetched_at` 을 뺀 DB 도 무변이다 — 이 계획은 오늘 정상인 상태를 하나도 깨지
   않는다.
3. 자가 **스키마에서** 눈금을 얻는다: `store.SCHEMA` 에 열을 하나 더한 사본에서
   케이스 수가 4 → 5 로 **저절로** 는다.
4. 자가 자기 눈금이 비면 RED 다: 열 이름을 0개 뽑으면(파싱 실패) 조용한 초록이
   아니라 실패다 — 「린트형 검사는 데이터가 초록일 때 자기를 못 잰다」의 대비책.
5. 변이 ①: 새 탐침에서 `url,` 을 지우면 자가 RED.
6. 변이 ②: 탐침 줄을 `hits` 루프 **안**으로 옮기면 RED. 계획 54 e2e 가 「삭제」와
   「루프 안으로」가 HTTP 표면에서 **동치**임을 밝혔으므로 둘을 가르는 단언을
   요구하지 않는다 — **둘 다 RED** 로 잰다.
7. HTTP 표면 확인(줄은 안 더한다): `url` 열 없는 DB 의 `/passages` 세 질의가
   **500 셋**이고 `/search` 와 화면은 200 무변.
8. 단위 603 → 603+N OK(rc 0) · e2e **21종 전수 rc 0** · 새 e2e 파일 판정은 e2e
   phase 로 넘긴다.
9. `data/crawl.db` sha256 무변 · `docs/specs/` 무변 · 스키마·마이그레이션·재색인

## 6. 설계가 필요하다 — 트리거 「대안이 2개 이상 갈린다」

세 안이 **닫는 범위가 서로 다르다.** 말로 고르지 않고 설계 phase 가 넷을 만들어
같은 자로 잰다(계획 49 가 쓴 방식).

### 갈림길 1 — 자의 눈금을 어디서 얻나

| 안 | 무엇 | 닫는 범위 | 값 |
|---|---|---|---|
| ① | `store.SCHEMA` 에서 열 이름을 뽑아 한 열씩 빼며 돈다 | 오늘 넷 + **앞으로 생길 열 전부** | 스키마 파싱 몇 줄이 테스트에 생긴다. 파싱이 0건을 내면 조용히 초록이 될 위험(기준 4가 막는다) |
| ② | 열 표를 손으로 적는다 | 오늘 넷 | 읽기 쉽다. **다섯 번째 열이 생기는 날 늙는다** — 이 계획이 고치려는 실패 유형 그 자체 |
| ③ | 상태마다 테스트 클래스를 하나씩(계획 53·54 방식의 연장) | 오늘 한 자리 | 자리마다 클래스가 는다. 네 번 해 봤고 그 비용이 이 계획의 근거다 |

### 갈림길 2 — 제품 처방

| 안 | 무엇 | 오늘 실측이 말하는 것 |
|---|---|---|
| A | `SELECT url, html FROM pages LIMIT 0` (한 낱말) | 3절 표의 2행을 닫고 3·4행을 안 건드린다 |
| B | `PRAGMA table_info(pages)` + 필요한 열 집합 | 집합을 `SCHEMA` 전체로 잡으면 **3·4행이 오탐**. 둘만 적으면 A 와 같은 값에 줄만 는다 |
| C | 제품 0줄, 자만 세운다 | 자가 RED 를 하나 남긴 채 끝난다 — 그대로는 못 닫는다 |

**설계가 실제로 답할 것**: ① + A 가 유력해 보이지만, ①의 파싱이 `SCHEMA` 문자열
문법에 묶이는 값이 «자동으로 느는 눈금» 보다 싼지는 아직 안 쟀다. 설계가 ①·②를
둘 다 만들어 **열을 하나 더한 스키마 사본**에 먹여 갈라야 한다.
